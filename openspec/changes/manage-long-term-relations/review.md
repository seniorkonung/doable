Безопасные ошибки, диагностика, локализация и доступность распределены по задачам 3.8, 3.11, 3.14, 3.15, 3.18 и 3.23–3.29. Каскадное архивирование, восстановление без обратного каскада и блокировка удаления намерения покрыты задачами 3.9, 3.10 и 3.29.

Отложенные в Phases 4–5 обязательства (изменение, самостоятельные архивирование, восстановление и удаление связи, массовое удаление) согласуются с границами плана. Зависимости 3.1–3.31 проверены на исполнимость порядка; итоговая контрольная точка 3.31 ссылается на все задачи фазы.

При сверке с кодом установлено следующее. Порядок каскада в 3.9 совместим с trigger `intentions_archive_requires_no_active_relations` схемы 2. Текущая классификация удаления по нарушению внешнего ключа как общего конфликта (`drift_personal_graph_repository.dart:1121–1125`) обосновывает типизированную проверку `EXISTS` в 3.10. Канонический connection setup и adapter verifier подходят для регистрации query-функций в 3.7, а hooks `LocalDatabaseConnectionObserver` и существующий worker миграции — для проверок прерывания в 3.12. Совпадение ключей русского и английского ARB уже проверяется в `test/app/localization/locale_resolution_test.dart`, что достаточно для 3.18. Архивирование намерения сейчас выполняется без подтверждения, поэтому объяснение каскада в 3.29 — новое поведение, а не изменение существующего диалога. Активного Flutter-приложения для проверки через DTD не требовалось: код не изменялся.

Исправление F1 проверено по последствиям. Преамбула пакета охватывает фазы 1–3 и ограничивает временные фасады Phase 1. Раздел Phase 3 определяет общие контракты, проверку перехода (`flutter analyze` и `flutter test test/intention test/graph test/app`) и запрет временной совместимости между отмеченными задачами. На это правило ссылаются задачи, меняющие интерфейс, отказы, проекции, конструктор или coordinator: 3.5, 3.8–3.11, 3.14, 3.15 и 3.17. Задача 3.10 переводит исчерпывающие обработчики отказов с сохранением действующего сообщения `detailsDeleteConflict` до объяснения зависимостей в 3.29. Задача 3.11 переводит вызов конструктора в `AppRuntime`, а 3.17 больше не служит отложенным местом совместимости. Контрольная точка 3.13 включает наборы presentation и app, а 3.31 проверяет поиском единственную production-реализацию репозитория и выполнение команд только через `GraphCommandCoordinator`; сейчас `execute` в `lib` вызывается только в `graph_command_coordinator.dart:492`. Проверки 3.22 и 3.30 остаются согласованными с новым правилом.

Исправление F2 проверено по последствиям. Задача 3.8 закрепляет, что подтверждённое изменение перечитывает наблюдение каждого намерения с изменившейся сводкой — того же набора, чьи абсолютные количества входят в пакет по решению 6 design, — и не перечитывает наблюдения неизменённых намерений с прежней сводкой. Задача 3.9 определяет набор для каскада: архивируемое намерение и соседей по архивированным в каскаде связям, без соседей только по ранее архивированным связям. Задача 3.11 определяет набор для создания: оба участника. Проверки 3.8, 3.9 и 3.11 выполняются через настоящий репозиторий и охватывают повторную выдачу для затронутых намерений и её отсутствие для посторонних, при no-op, откате, отказе и восстановлении намерения. Требование согласуется с решениями 1 и 6 design и ADR-0009; для `watchRelation` аналогичное правило уже задаёт 3.15. Составное состояние 3.21 может опираться и на пакет завершения, и на наблюдение: оба источника теперь дают актуальную сводку, поэтому проверка 3.21 на управляемых входах остаётся достаточной для уровня ViewModel. Нынешнее уведомление только изменённого намерения (`drift_personal_graph_repository.dart:230–231`) остаётся исходным состоянием, которое меняют эти задачи.

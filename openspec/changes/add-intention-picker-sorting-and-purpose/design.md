## Context

Изменение добавляет экрану выбора закреплённый заголовок списка с листом «Показать и упорядочить», тип намерения, сортировку по названию и подзаголовок назначения с листом «Что вы выбираете». Мотивация — в [proposal](proposal.md), поведение — в дельтах [намерений](specs/intention-management/spec.md), [дневного выбора](specs/daily-choice-management/spec.md) и [связей](specs/long-term-relation-management/spec.md).

Текущее состояние:

- **Экран выбора.** `IntentionPickerView` строит шапку `TopBar`, ряд `SearchField` + `FilterButton` и `IntentionPickerResults`. Выдача — `CustomScrollView`, и `CatalogHeader` в ней прокручивается вместе со строками. `IntentionPickerKind` по назначению выбирает тексты «действие» или «намерение».
- **Назначения.** Sealed `IntentionPickerPurpose` с вариантами `SelectDailyChoiceAction`, `SelectDailyChoiceSource` и `SelectRelationParticipant` — ключ семейства провайдеров модели каталога и условий по тегам. Страницы `DailyChoiceActionPickerPage`, `DailyChoiceSourcePickerPage` и `RelationParticipantPickerPage` владеют маршрутом и закрытием.
- **Потоки.** Поиски дневного выбора получают `DailyChoicePickerContext`: `Initial…` открывает запуск создания, `Auxiliary…` — только `DailyChoicePathReplacementFlow`. Поиск участника получает `excludedIntentionId` и `RelationParticipantSelectionContext` от `RelationEditorPage`. Черновик формы держит участников как `RelationParticipantSummary` (идентификатор, название, архивное состояние) и вид, пока не выбранный как `null`.
- **Модель каталога.** `IntentionCatalogViewModel` строит `IntentionCatalogQuery` из назначения и параметров: охват, `IntentionReadinessFilter { all, readyOnly }`, название, теги, исключение, `IntentionCatalogOrder`. Правки графа модель согласует сама: принадлежность выдаче проверяет `entry.matches(query)`, место строки — `query.compare` (`combined.sort`, `items.sort` и граница курсора), `totalCount` поправляет на разницу «после − до».
- **Чтение порций.** Репозиторий Drift считает `COUNT(*)` и читает порцию с `ORDER BY <временная метка>, id ASC` и курсором `(временная метка, id)`. Двенадцать частичных индексов покрывают охваты × поля × направления. Колонка `title_search_key` — хранимый generated column функции `doable_title_search_key`. Её долговечность и допустимый межрелизный дрейф данных Unicode определяет [ADR-0008](../../../docs/adr/0008-treat-sqlite-schema-functions-as-durable-contract.md). Пересчёта при обновлении данных нет, поэтому `matches` уже сравнивает с *хранимым* ключом.
- **Сравнение строк.** SQLite сравнивает `TEXT` в `BINARY` побайтно в UTF-8, то есть по кодовым точкам. `String.compareTo` в Dart сравнивает единицы UTF-16: `'\u{E000}'.compareTo('\u{1F600}')` даёт 1, хотя по кодовым точкам `U+E000` идёт раньше.
- **Дизайн-система.** Есть `TopBar` без подзаголовка, `CatalogHeader` как неинтерактивный текст и `Sheet` по содержимому без действия в строке заголовка. Нет групп вариантов, ромбов, колец, пунктирных линий и формы связи.
- **Схема.** Версия 5 — базовая без путей обновления. Меньший маркер bootstrap считает повреждением. Так v5 стала базовой в коммите `7729b064`.

Ограничения:

- компоненты дизайн-системы — представления без предметных типов ([ADR-0029](../../../docs/adr/0029-represent-design-system-as-foundation-module.md), [ADR-0030](../../../docs/adr/0030-keep-design-system-components-presentational.md));
- каталог читается ограниченными порциями без загрузки всего результата ([ADR-0005](../../../docs/adr/0005-use-bounded-catalog-snapshots.md));
- модуль намерений не зависит от модулей дневного выбора и связей: тексты и тело напоминания строят их страницы;
- листы показываются в корневом навигаторе ([ADR-0032](../../../docs/adr/0032-present-design-system-sheets-over-root-navigator.md));
- параметры поиска принадлежат странице ([ADR-0028](../../../docs/adr/0028-scope-opening-parameter-state-to-page-instances.md));
- время измеряют только бенчмарки.

## Goals / Non-Goals

**Goals:**

- Один порядок по названию в SQL, курсоре и согласовании правок без расхождений на стыке порций.
- Тип намерения как ещё одно условие совместного поиска; числа обоих типов из того же подсчёта, что и общее количество.
- Закреплённый заголовок списка, лист «Показать и упорядочить», подзаголовок и лист «Что вы выбираете» на компонентах дизайн-системы.
- Основа общего графического языка путей и связей в объёме нынешних потребителей.
- Схема версии 6 с индексами порядка по названию.

**Non-Goals:**

- Каталог графа намерений, форма связи, страницы пути и подтверждения.
- Сортировка по правилам языка, сохранение параметров между открытиями.
- Круг действия, точечная линия места шага, тон приоритета, масштаб `ReasonChain`, интерактивная `RelationForm`, вариант `OptionGroup` в конце строки.
- Миграция данных схемы 5.

## Decisions

### 1. Порядок по названию — хранимый ключ поиска, сравнение по кодовым точкам

Порядок по названию задают `title_search_key` и идентификатор. Курсор — пара `(ключ, id)`, тем же шаблоном, что у временных меток:

```text
                  order = (title key, id)
                            |
     +----------------------+----------------------+
     v                      v                      v
 SQL ORDER BY          keyset cursor          Dart compare
 title_search_key,     key > b.key OR         stored key by code
 id ASC                (key = b.key AND       points, then id
                        id > b.id)
 (first page)          (continuation)         (merge graph changes)
     \                      |                      /
      +----------- one and the same order --------+
```

- **Ключ.** `IntentionCatalogSortField` получает `title`. SQL и курсор используют колонку `title_search_key` без функции в запросе, поэтому порядок покрывают индексы.
- **Порядок по названию допустим при любом назначении.** Запрос, адаптер и модель каталога не ограничивают его назначением: `changeOrder` принимает его и для каталога графа, и чтение, курсор и согласование правок обязаны держать его на любом охвате. Каталог графа получит этот порядок вместе со своим дизайном. Пока он его не предлагает, и это граница экрана, а не домена: страница каталога перечисляет предлагаемые ей четыре порядка по времени собственным закрытым набором и подписывает исчерпывающим `switch` по этому набору, а не по полю и направлению. Поэтому подписи порядка по названию на ней не появляются, а вид каталога не меняется.
- **Сводка несёт непрозрачный ключ порядка.** `IntentionSummary` получает ключ порядка названия по [ADR-0045](../../../docs/adr/0045-order-titles-by-opaque-key-of-stored-search-projection.md). Это значение-тип без доступа к содержимому, которое умеет только сравниваться с другим таким ключом по кодовым точкам (`runes`), а не через `String.compareTo`. Ключ строит адаптер, и только в `_rehydrateSummary`:
  - чтение порции добавляет к выборке колонку `title_search_key`;
  - снимок команды передаёт ключ, который `_StoredIntentionCommandSnapshot` уже читает.
  
  `query.compare` для поля `title` сравнивает эти ключи, а при равенстве — идентификаторы. Сырой поисковый ключ границу `PersonalGraphRepository` по-прежнему не пересекает ([ADR-0009](../../../docs/adr/0009-unify-personal-graph-module-and-revision.md)).
- **Почему из хранимой проекции, а не вычисленный.** После обновления данных Unicode `titleSearchKey(title)` в Dart может разойтись с ключом, сохранённым прежней версией. Тогда вставка правки в загруженный список и SQL-порядок разойдутся. `matches` снимка по той же причине уже сравнивает с хранимым ключом.

Отклонённые альтернативы:

- **Вычислять ключ в Dart из названия.** На одно поле меньше, но порядок держался бы на неявном обязательстве пересчитывать ключи в каждом будущем изменении данных Unicode.
- **Сырой хранимый ключ строкой в сводке.** Работает так же, но выводит поисковую проекцию за границу репозитория вопреки ADR-0009 и позволяет сравнить её через `String.compareTo`, то есть не по порядку SQLite.
- **Отдельный ключ сортировки** с собственной функцией схемы — свёртка диакритики, «ё» рядом с «е». Новая долговечная функция по ADR-0008, данные нормализации и миграция при каждой правке алгоритма. Компромиссы варианта A приняты и записаны в спецификации.
- **Пользовательская collation SQLite.** Индексы зависели бы от регистрации функции сравнения на каждом соединении, и любая её правка тихо портила бы индекс.
- **Сортировка всего результата в памяти.** Нарушает ADR-0005.

### 2. Тип — значение условия готовности; числа типов — из одного подсчёта

- **Запрос.** `IntentionReadinessFilter` получает третий вариант «только без готовности». Тип не становится новым полем: это то же условие готовности ([тип намерения](../../../CONTEXT.md) выводится из готовности к действию), и `includes`, `matches` и SQL-условие получают одну исчерпывающую ветку.
- **Модель.** Выбранный тип хранит модель каталога. Условие готовности запроса строится из назначения и типа:

  | Назначение | Тип | Условие готовности |
  |---|---|---|
  | поиск действия | закреплён | только с готовностью |
  | общий каталог | не предлагается | все |
  | исходное намерение, участник | выбирается | по выбранному типу |

  Доступность типа — sealed-значение выбора: открыт (с выбранным типом), закреплён (действия) или не предлагается. Экран рисует группу по нему, а `changeType` применяет выбор только к открытому типу, как `changeScope` — только к общему каталогу.
- **Подсчёт.** Адаптер считает `COUNT(*)` и `SUM(is_action_ready)` по условию *без* готовности, но со всеми остальными ограничениями. Из этой пары выводятся:
  - числа «Все», «Действия» и «Намерения» (как «Все» − «Действия»);
  - общее количество текущего результата по его условию готовности.
  
  Это один запрос вместо нынешнего `COUNT(*)`.
- **Числа типов — по запросу.** Запрос каталога может попросить числа типов. Тогда первая порция несёт их, иначе в ней только общее количество, как сейчас. Модель просит их только для назначения с открытым типом. Если адаптер не вернул запрошенные числа или они противоречат общему количеству, модель считает это нарушением контракта, как прочие несоответствия порции.
- **Правки графа.** Модель поправляет оба числа тем же правилом «после − до»:
  - принадлежность — по `matches` для запроса без условия готовности;
  - тип — по готовности снимков до и после.
  
  Смена готовности на странице намерения, открытой стрелкой из строки, переносит намерение между типами и поправляет оба числа.

Отклонённые альтернативы:

- **Отдельный перечень типа в запросе рядом с готовностью.** Два поля выражали бы одно условие и допускали противоречивые сочетания вроде «только с готовностью» и типа «Намерения».
- **Три отдельных подсчёта или подсчёт при открытии листа.** Лишние запросы и отдельная поддержка чисел под правками; лист показывал бы числа с задержкой.
- **Числа типов в каждой первой порции.** Контракт порции расширился бы для всех потребителей. Каталог графа и поиск действия, которым числа не нужны, и все их тестовые адаптеры получили бы обязательное поле без смысла для них.

### 3. Индексы и схема версии 6 без миграции

- **Шесть частичных индексов**: `(title_search_key ASC, id ASC)` и `(title_search_key DESC, id ASC)` для активного, архивного и полного охвата. Обратный проход по возрастающему индексу дал бы `id DESC` при равных ключах, а курсор ждёт `id ASC`.
  - Поиски этого изменения читают по названию только активный и полный охват. Индексы архивного охвата — решение владельца: каталог графа намерений, где есть архивный охват, получит порядок по названию следующим изменением, а базовая схема 6 без миграции — последний случай добавить индексы без пути обновления.
  - До сортировки каталога графа индексы архивного охвата не читает ни один запрос.
- **Базовая версия 6, как в `7729b064`:**
  - `currentSchemaVersion = 6`;
  - снимок `drift_schema_v5.json` заменяется на `drift_schema_v6.json`;
  - комментарий стратегии миграции называет базовой схему 6;
  - README описывает ручную очистку данных схемы 1–5;
  - путь обновления не добавляется.
  
  Это исключение только для этого изменения: последующие изменения схемы по умолчанию получают миграцию.
- **Диагностика.** Событие чтения порции каталога получает поле сортировки — время создания, время изменения или название. Новый индексный путь иначе неотличим в длительностях от прежних. Пользовательского текста событие по-прежнему не несёт.

### 4. Закреплённый заголовок и лист «Показать и упорядочить»

```text
IntentionPickerView
+---------------------------------------------+
| TopBar(title, subtitle, mark, onTitle)      |----> "What you choose" sheet
| SearchField | FilterButton                  |----> TagsPanel (unchanged)
| CatalogHeader(type, count?, summary, onOpen)|----> "Show and sort" sheet
+---------------------------------------------+         |
| IntentionPickerResults (rows only)          |         | OptionGroup x3
+---------------------------------------------+         v
                                          IntentionCatalogViewModel
                                          changeType / changeOrder
```

- **Заголовок списка выходит из прокрутки.** `CatalogHeader` стоит в `IntentionPickerView` под рядом поиска. `IntentionPickerResults` рисует только строки, пустые состояния и подгрузку. Тип и сводка берутся из текущего выбора модели (`notifier.selection`) и меняются сразу, до ответа первой порции новых параметров. `AsyncValue.value` в это время может сохранять прежнее подтверждённое состояние, поэтому его `selection` не служит источником текущего выбора. Число берётся только из подтверждённого состояния, чей запрос совпадает с текущими параметрами; иначе заголовок без числа.
- **`CatalogHeader` становится кнопкой** по README дизайн-системы:
  - `title`, `count?`, `summary`, `onOpen`, `expanded`, `label`;
  - `InkWell` над рядом с пилюлей сортировки справа.
- **Лист «Показать и упорядочить».** Композиция модуля экрана выбора из `Sheet` по содержимому и трёх `OptionGroup`.
  - Лист следит за той же моделью каталога через провайдер назначения. Выбранные варианты, подписи группы «Порядок» и наличие «Сбросить» определяются текущим `notifier.selection` и обновляются после каждого нажатия до ответа новой первой порции, в том числе при повторном выборе во время получения выдачи. Заголовок за листом показывает тот же выбор без числа; числа типов, как и число заголовка, берутся только из подтверждённой выдачи текущих параметров.
  - Правило порядка при смене поля применяет экран к последнему выбору модели: от времени к названию и обратно — первый порядок нового поля, между двумя временами — прежнее направление. Следующее нажатие до ответа порции опирается на уже изменённый `notifier.selection`, а не на параметры прежней выдачи. Модель получает готовый `IntentionCatalogOrder`.
  - Смена типа или порядка возвращает список к началу тем же путём, что сейчас неидентичный `query`.
- **`Sheet` по содержимому получает `action`** — «Сбросить» в строке заголовка, как у раскрываемого листа.
- **Новый компонент `OptionGroup`** в варианте `lg`: подпись группы, равные колонки пилюль, число после подписи варианта, недоступная группа с пояснением, семантика взаимоисключающих вариантов. Вариант `sm` не строится.

Отклонённая альтернатива — оставить заголовок в прокрутке и добавить в шапку отдельную кнопку сортировки. Это противоречит дизайну и спецификации и прячет за листом то, что заголовок обязан называть.

### 5. Назначение: экран получает готовые тексты и тело, страницы их строят

Экрану выбора передаётся описание назначения — значение модуля экрана выбора без предметных типов дневного выбора и связей:

- подзаголовок;
- отметка подзаголовка: нет, исходное поле или связанное поле;
- строка листа;
- построитель тела листа.

`IntentionPickerView` отдаёт подзаголовок и отметку в `TopBar`, а по нажатию открывает лист «Что вы выбираете». Это `Sheet` по содержимому: построенное тело и нижняя кнопка «Вернуться к списку».

Тексты «Новый дневной выбор: исходное намерение» и «Новый дневной выбор: конечное действие» сохраняются по дельте `daily-choice-management`. При стандартном масштабе текста со шрифтом Inter на ширинах 360 и 390 dp оба подзаголовка ожидаемо обрезаются многоточием, в том числе внутри названия роли. Полное размещение текста в шапке не требуется: строка остаётся одной, а завершающий шеврон 12 — видимым. Это применение правила «Назначение поиска для выбора», а не повод сокращать формулировки. Доступное название кнопки содержит полный подзаголовок независимо от обрезки; в листе роль целиком называет первый шаг.

```text
DailyChoiceLauncher ----Initial---->  SourcePickerPage / ActionPickerPage
PathReplacementFlow --Replacement-->        | purpose line:
                                            |  "New daily choice | Path change: role"
                                            |  body = FlowSteps(3 steps)
RelationEditorPage --participant pick-->  RelationParticipantPickerPage
   (role, flow, kind?, source?, related?,   | purpose line:
    archived relation?)                     |  "New relation | Relation change: role"
                                            |  mark = diamond | ring
                                            |  body = RelationForm.choosing
                                            v
                                     IntentionPickerView
```

Названия на схеме: `New daily choice` — «Новый дневной выбор», `Path change` — «Замена пути», `New relation` и `Relation change` — «Новая связь» и «Изменение связи».

- **Дневной выбор.**
  - `AuxiliaryDailyChoicePickerContext` переименовывается в контекст замены пути: сегодня его открывает только замена, а подзаголовок теперь зависит от этого смысла.
  - Страница поиска выводит поток из контекста, а направление — из своего вида: поиск исходного намерения — от намерения, поиск действия — от действия.
  - Тело — компонент `FlowSteps` дизайн-системы: пронумерованные шаги, отметка текущего, пояснение под шагом.
- **Связь.**
  - Маршрут поиска участника получает описание выбора: роль, поток (создание или изменение), вид или его отсутствие, снимки исходного и связанного участников и архивное состояние связи.
  - Исключаемый идентификатор и «Вместо: …» выводятся из него: участник другой роли и участник этой роли. Отдельный параметр `excludedIntentionId` и `RelationParticipantSelectionContext` из маршрута уходят, и противоречивое сочетание собрать нельзя.
  - Поток выводится из `RelationEditorContext`: обе формы создания — создание, редактирование — изменение.
- **Тексты** приходят из локализации страниц. Английские строки повторяют выбранный словарь ролей, а не фразы макета.

Отклонённые альтернативы:

- **Описание назначения внутри `IntentionPickerPurpose`.** Назначение — ключ провайдеров каталога. Тексты и снимки названий сделали бы ключ зависимым от отображения, а модуль намерений — от модулей потоков.
- **Sealed-набор всех восьми контекстов в модуле экрана выбора.** Тот же разворот зависимостей: экран знал бы шаги дневного выбора и форму связи.

### 6. Общий графический язык путей и связей

Слои в модуле основ, названия по общим правилам `context/doable-design-system/README.md`:

```text
tokens       strokeNeed 2, strokeCan 1.5, dash 5/5
   |
primitives   PathGlyph(shape: diamond|ring, outline: solid|dashed, size, color)
             RelationStroke(kind: need|can|undetermined, axis: vertical|horizontal)
             RelationKindMark (15x2 beside the word)
   |
rail         PathRail: IntrinsicHeight row = 22 wide column
             (glyph + stroke above / below) + content
   |
components   TopBar subtitle mark        RelationForm.choosing
             (now)                       (now)
             ChoicePath, PathBuilder, RelationHead, RelationRow, ReasonChain (later)
```

- **Отрисовка.** Глифы и линии рисует `CustomPainter`. Пунктир строится одним помощником по длине штриха и промежутка из токенов.
- **Перечисления только с нынешними вариантами.** Круг действия и точечная линия добавятся новыми вариантами вместе со своими потребителями, и исчерпывающие `switch` укажут все места, где их нужно обработать.
- **`RelationForm` в режиме выбора** — только для чтения:
  - состояния полей — выбирается (с необязательным «Вместо: …»), заполнено (с признаком архива) или пусто;
  - вид связи;
  - готовые тексты.
  
  Нажатий, шевронов и переключателя вида у неё нет. Семантика называет роль, состояние поля и вид словами.

Отклонённая альтернатива — нарисовать рейку прямо в листе связи. Тогда следующие компоненты путей повторили бы отрисовку, а пользователь прямо попросил общую основу.

### 7. Проверки по границам

| Граница | Что проверяется |
|---|---|
| Репозиторий Drift | Порядок по названию в обоих направлениях с регистром, многосимвольной свёрткой «ß», «ё» и символами за пределами BMP; курсор без пропусков и повторов при равных ключах; числа типов при названии и тегах; условие «только без готовности» |
| Запрос и сводка | `compare` по названию совпадает с порядком SQL на том же наборе, включая `U+E000` против `U+1F600` |
| Модель каталога | Смена типа и порядка начинает новую выдачу; правка готовности переносит числа между типами; переименование перемещает строку по названию |
| Экран выбора | Заголовок и лист показывают текущий выбор до ответа новой первой порции, без прежних чисел; два последовательных переключения до ответа применяют правило порядка к последнему выбору; «Сбросить» исчезает сразу после сброса; закреплённый тип; «Показать оба типа»; лист «Что вы выбираете» возвращает поиск без изменений |
| Страницы | Подзаголовки и тела для создания и замены пути; описание выбора участника из формы новой и изменяемой связи |
| Дизайн-система | `CatalogHeader`, `OptionGroup`, `FlowSteps`, `RelationForm.choosing`, подзаголовок `TopBar`; со шрифтом Inter при стандартном масштабе текста на ширинах 360 и 390 dp оба подзаголовка создания дневного выбора фактически обрезаны многоточием в одной строке, шеврон видим, доступное название содержит полный подзаголовок |
| Схема | Снимок v6 и тесты bootstrap: маркер 5 — повреждение |
| Бенчмарк | Чтение первой и следующей порций по названию на большом каталоге |

## Risks / Trade-offs

- **[Порядок по кодовым точкам кажется ошибкой: «ё» после «я», латиница перед кириллицей]** → Компромисс принят и записан в требовании «Упорядочивание каталогов намерений». Название поля — «Название», а не «Алфавит».
- **[Расхождение порядка SQL и Dart даёт дубли и пропуски на стыке порций]** → Обе стороны используют один хранимый ключ. Значение-тип ключа не даёт сравнить его через `String.compareTo`. Проверка репозитория сравнивает оба порядка на наборе с граничными символами.
- **[Шесть новых индексов увеличивают стоимость записи и размер файла]** → Каждая запись намерения обновляет четыре из них: два полного охвата и два своего. Два индекса архивного охвата обновляются записью архивного намерения, архивированием и восстановлением, хотя до сортировки каталога графа их никто не читает. Владелец принял эту цену ради основы каталога графа без последующей миграции. Масштаб личного графа это допускает; бенчмарк импорта показывает цену массовой вставки.
- **[Подсчёт без условия готовности в поиске действия проходит больше строк]** → Тот же проход по индексу охвата, `SUM` считается в нём же; бенчмарк каталога покрывает чтение.
- **[В шапке обрезается часть названия роли]** → Тексты сохраняются; многоточие для обоих подзаголовков создания дневного выбора ожидаемо на ширинах 360 и 390 dp при стандартном масштабе текста. Проверка подтверждает обрезку и видимый шеврон, а не полное размещение. Полный подзаголовок доступен экранному диктору, а полная роль — в первом шаге листа.
- **[Названия в листе связи устаревают, пока поиск открыт]** → Спецификация называет их снимком на момент открытия; лист только напоминает.
- **[Схема 5 открывается как повреждённая]** → Исключение согласовано: production-установок нет, данные переносятся вручную.

## Migration Plan

1. На прежней сборке экспортировать граф в файл.
2. Установить сборку со схемой 6. Хранилище версии 5 откроется как повреждённое.
3. Очистить данные приложения в системных настройках и импортировать файл экспорта.

Откат: прежняя сборка сообщает о несовместимой более новой схеме и не меняет хранилище. Для отката нужны та же очистка и импорт; формат файла экспорта этим изменением не меняется.

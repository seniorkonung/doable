## Findings

### F5 · Medium — Проверка задачи 4.5 не наблюдает описание выбора, которое строит форма связи: поток, вид и участников из черновика

- **Evidence:** Критерий 4.5 требует, чтобы `RelationEditorPage` строила описание «в момент открытия поиска из черновика и `editorContext`: поток — создание для контекстов создания и изменение для редактирования; архивное состояние — из основы редактирования; участники и вид — из черновика». Проверка 4.5 на уровне редактора — «выбор участников из формы новой и изменяемой связи, занятая пара и отмена работают как прежде», на уровне поиска — исключение и охват по уже готовому описанию. Проверка 4.6 исполняет сценарии дельты на странице поиска с готовым описанием, а для редактора снова только «создание и изменение связи через поиск работают как прежде». Существующие сценарии редактора (`test/long_term_relation/presentation/editor/relation_participant_selection_scenarios.dart`, `relation_editor_page_test.dart`) наблюдают у открытого поиска только имя маршрута, `excludedIntentionId` и `scope` запроса каталога. Строка «Страницы» таблицы «Проверки по границам» design требует проверить «описание выбора участника из формы новой и изменяемой связи», а сценарий дельты «Изменение связи показывает заменяемого участника» начинается с того, что пользователь изменяет связь.
- **Impact:** Ошибка сопоставления в редакторе — вид из основы редактирования вместо черновика, участник этой роли из сохранённой связи вместо заменённого в черновике, «Новая связь» вместо «Изменение связи» — не нарушит ни исключения, ни охвата, и ни одна проверка пакета её не заметит. Неверное напоминание увидит только человек на устройстве, а ручная проверка не блокирует готовность фазы.
- **Required change:** Назвать в проверке 4.5 (или 4.6) наблюдаемое свидетельство на границе редактора: для новой связи из пустой формы и из группы соседства и для изменяемой, включая архивную, открытый маршрут поиска получает описание с потоком, видом и участниками текущего черновика — в том числе после смены вида и замены участника этой роли — и с архивным состоянием основы. Свидетельство может быть чтением поля страницы поиска, как `test/app/navigation/app_shell_page_matrix.dart` читает `selectionContext`, или подзаголовком и текстами листа в сценарии редактора.

### F6 · Low — Проверка задачи 4.6 не наблюдает слова ролей и состояний полей формы для экранного диктора

- **Evidence:** Требование «Назначение поиска участника связи» дельты `long-term-relation-management`: «Экранный диктор SHALL слышать роль каждого поля, его состояние и вид связи словами, а не только по отметкам и линиям». Роли полей в форме не видны: в блоке `remIsRelation` макета `ActionPicker.dc.html` поле подписано только «Choosing now», названием или «Not chosen yet», а роль несут ромб и кольцо с `aria-hidden`. Задача 4.4 получает названия ролей и состояний от потребителя (ADR-0030) и проверяет узлы с тестовыми текстами. Критерий 4.6 повторяет требование, но проверка 4.6 называет только видимые тексты листа, доступное название кнопки шапки и три guideline.
- **Impact:** Страница может передать форме неверные слова — перепутать исходное и связанное поле или не назвать архивность участника — и все проверки пакета пройдут, а единственное нормативное обязательство о доступности формы останется без свидетельства.
- **Required change:** Добавить в проверку 4.6 наблюдение семантики открытого листа на обоих языках: узел каждого поля называет роль, состояние — «Сейчас выбирается», название участника или «Ещё не выбрано» — и архивность архивного участника; узел строки вида называет слово вида. Образец — проверки `isSemantics` в `test/daily_choice/presentation/daily_choice_picker_context_test_support.dart`.

## Accepted risks

### AR1 · Индексы порядка по названию для архивного охвата не читает ни один запрос до сортировки каталога графа

- **Evidence:** Решение 3 design, ADR-0045 («Последствия») и задача 1.4 вводят шесть индексов порядка по названию, в том числе два для архивного охвата. Архивный охват выбирает только каталог графа намерений (`intention_catalog_page.dart`), а он, по proposal и дельте «Упорядочивание каталогов намерений», порядка по названию в этом изменении не получает. Поиски читают только активный (`IntentionCatalogViewModel`) или полный (`RelationParticipantSelectionContext`) охват. Задача 1.4 выполнена: `lib/src/data/local/schema/intention_schema.drift` содержит `intentions_archived_title_search_key_asc_id_asc` и `intentions_archived_title_search_key_desc_id_asc`. Каталог графа через `_OfferedCatalogOrder` по-прежнему предлагает только четыре порядка по времени, и задачи фаз 2–4 этого не меняют.
- **Potential impact:** Два неиспользуемых индекса в базовом снимке схемы 6 обновляются каждой записью архивного намерения, архивированием и восстановлением и занимают место в файле. Если каталог графа получит порядок по названию в другой форме, например по языковому ключу, индексы останутся мёртвыми, и убрать их можно будет только миграцией.
- **Acceptance rationale:** Владелец решил заложить основу сразу: сортировка по названию в каталоге графа, где есть архивный охват, — ближайшее следующее изменение. Базовая схема 6 без миграции — последний случай добавить индексы без пути обновления. Цена записи для масштаба личного графа мала.
- **Scope and assumptions:** Только два индекса `(title_search_key ASC|DESC, id ASC)` с условием архивного охвата в схеме 6. Предполагается, что каталог графа получит порядок по названию через тот же ключ сохранённой проекции по ADR-0045 и с тем же курсором `(ключ, id ASC)`.
- **Reopen when:** Сортировку по названию в каталоге графа отменят или отложат на неопределённый срок; её спроектируют на другом ключе, направлении или форме курсора; схема 6 перестанет быть базовой версией без миграции до реализации задачи 1.4.
- **Acceptance authority:** Явное решение владельца при разборе F4 25.10.2026: каталог намерений с сортировкой по названию будет сделан вскоре, и основу под него нужно заложить сразу, пока это можно сделать без миграции.
- **Originating finding:** F4
- **Acceptance lifetime:** Durable
- **Decision record:** `docs/adr/0045-order-titles-by-opaque-key-of-stored-search-projection.md` («Последствия»); решение 3 и «Risks / Trade-offs» в `design.md`.

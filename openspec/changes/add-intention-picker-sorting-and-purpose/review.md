## Findings

### F7 · Low — Задача 3.2 не определяет, растёт ли шапка при крупном тексте, а её критерии выполнимы только ограничением масштаба

- **Evidence:** Задача 3.2 требует, чтобы заголовок и строка были «одной кнопкой высотой 44», а при тексте масштаба 2 оставались «целыми строками внутри панели, без переполнения». README `TopBar`: «The bar is 44 high». Стили `title` (17/22) и `hint` (13/18) при линейном масштабе 2 занимают 44 + 36 = 80 px, а при масштабе 1,15, крупном системном шрифте Android, — около 46 px. `TopBar` в `lib/src/design_system/components/top_bar.dart` отдаёт постоянный `preferredSize` высотой 44 без доступа к масштабу текста, а `Scaffold` ограничивает панель этой высотой и системным отступом (`packages/flutter/lib/src/material/scaffold.dart:3048–3060` закреплённого Flutter 3.47.1). Сейчас заголовок масштабируется полностью: проверка «при тексте масштаба 2 заголовок по-прежнему вмещается в панель по центру» в `test/design_system/top_bar_test.dart` ждёт его высоту 44. В `lib/` масштаб текста нигде не ограничивается, а компоненты растут вместе с текстом, например `CatalogHeader` «высотой не меньше `tap-min`» из задачи 2.6.
- **Impact:** Все критерии задачи буквально выполняет только ограничение масштаба обеих строк примерно до 1,1. Оно уменьшило бы для людей с крупным шрифтом и заголовок, который сейчас масштабируется полностью. Рост шапки противоречит «высоте 44» из критерия и README и требует, чтобы высота `TopBar` зависела от масштаба текста. Исполнитель выберет вариант сам, и проверка масштаба 2 не отличит доступное поведение от регрессии.
- **Required change:** Задача 3.2 называет поведение шапки с подзаголовком при крупном тексте: шапка растёт и сохраняет масштаб пользователя или масштаб строк ограничен названным пределом. Критерий высоты кнопки и проверка масштаба 2 согласованы с этим решением.
- **Decision needed:** Должна ли шапка экрана выбора с подзаголовком расти при крупном системном шрифте, как растут другие компоненты, или масштаб заголовка и подзаголовка ограничивается, чтобы шапка оставалась высотой 44?

## Accepted risks

### AR1 · Индексы порядка по названию для архивного охвата не читает ни один запрос до сортировки каталога графа

- **Evidence:** Решение 3 design, ADR-0045 («Последствия») и задача 1.4 вводят шесть индексов порядка по названию, в том числе два для архивного охвата. Архивный охват выбирает только каталог графа намерений (`intention_catalog_page.dart`), а он, по proposal и дельте «Упорядочивание каталогов намерений», порядка по названию в этом изменении не получает. Поиски читают только активный (`IntentionCatalogViewModel`) или полный (`RelationParticipantSelectionContext`) охват. Задача 1.4 выполнена: `lib/src/data/local/schema/intention_schema.drift` содержит `intentions_archived_title_search_key_asc_id_asc` и `intentions_archived_title_search_key_desc_id_asc`. Каталог графа через `_OfferedCatalogOrder` по-прежнему предлагает только четыре порядка по времени, и задачи фазы 2 этого не меняют.
- **Potential impact:** Два неиспользуемых индекса в базовом снимке схемы 6 обновляются каждой записью архивного намерения, архивированием и восстановлением и занимают место в файле. Если каталог графа получит порядок по названию в другой форме, например по языковому ключу, индексы останутся мёртвыми, и убрать их можно будет только миграцией.
- **Acceptance rationale:** Владелец решил заложить основу сразу: сортировка по названию в каталоге графа, где есть архивный охват, — ближайшее следующее изменение. Базовая схема 6 без миграции — последний случай добавить индексы без пути обновления. Цена записи для масштаба личного графа мала.
- **Scope and assumptions:** Только два индекса `(title_search_key ASC|DESC, id ASC)` с условием архивного охвата в схеме 6. Предполагается, что каталог графа получит порядок по названию через тот же ключ сохранённой проекции по ADR-0045 и с тем же курсором `(ключ, id ASC)`.
- **Reopen when:** Сортировку по названию в каталоге графа отменят или отложат на неопределённый срок; её спроектируют на другом ключе, направлении или форме курсора; схема 6 перестанет быть базовой версией без миграции до реализации задачи 1.4.
- **Acceptance authority:** Явное решение владельца при разборе F4 25.10.2026: каталог намерений с сортировкой по названию будет сделан вскоре, и основу под него нужно заложить сразу, пока это можно сделать без миграции.
- **Originating finding:** F4
- **Acceptance lifetime:** Durable
- **Decision record:** `docs/adr/0045-order-titles-by-opaque-key-of-stored-search-projection.md` («Последствия»); решение 3 и «Risks / Trade-offs» в `design.md`.

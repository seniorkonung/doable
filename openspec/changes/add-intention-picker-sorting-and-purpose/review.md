## Findings

### F5 · Medium — Проверки листа и заголовка не наблюдают выбор до ответа новой порции

- **Evidence:** По требованию «Параметры показа в поиске для выбора» дельты `intention-management` выбор применяется сразу, а заголовок списка показывает новое состояние. По требованию «Заголовок списка поиска для выбора», пока выдача получается, заголовок показывает тип и сортировку без числа. По решению 4 design заголовок за листом следует выбору сразу, а правило порядка при смене поля применяет экран. README `OptionGroup` и `CatalogHeader` тоже требуют, чтобы выбор применялся сразу, а заголовок за листом следовал каждому нажатию. В коде `changeType` и `changeOrder` модели каталога вызывают `ref.invalidateSelf()`. До ответа первой порции riverpod 3.4.2 отдаёт как значение провайдера прежнее подтверждённое состояние с признаком загрузки. Его `selection` несёт прежние тип и порядок, а текущие параметры есть только в `notifier.selection`. `IntentionPickerView.build`, куда задача 2.4 переносит заголовок, уже читает `catalog.value?.selection ?? notifier.selection`. Задача 2.5 требует лишь, чтобы лист «перестраивался с каждым состоянием» модели, и не требует смотреть на лист и заголовок до ответа новой порции. При этом исходы её сценариев выполняются и после ответа. В задаче 2.4 тип и порядок ещё нельзя сменить из интерфейса, поэтому её проверка «пока получается выдача новых параметров» не отличает прежнее состояние от текущего по типу и порядку.
- **Impact:** Все запланированные проверки пройдёт реализация, которая берёт из последнего подтверждённого состояния выбранные варианты, подписи группы «Порядок», наличие «Сбросить», тип и сводку заголовка. Но до ответа новой порции лист будет показывать прежний выбор, а заголовок — прежние тип и сортировку, вопреки требованиям. Второе нажатие до ответа применит правило порядка к прежнему полю. Например, из «Создание, сначала старые» нажатия «Название» и затем «Изменение» дадут «Изменение, сначала старые» вместо «Изменение, сначала новые». После нажатия «Сбросить» действие останется в строке заголовка до ответа.
- **Required change:** Критерии приёмки и проверки задач 2.4 и 2.5 требуют, чтобы сразу после выбора в листе, ещё до ответа первой порции новых параметров, заголовок показывал новые тип и сводку без числа. Лист в это время показывает новый выбранный вариант, подписи группы «Порядок» по новому полю и «Сбросить» по новым параметрам. Проверка выбирает варианты, пока первая порция не получила ответа, в том числе два раза подряд, и подтверждает, что правило порядка при смене поля применяется к последнему выбору.

## Accepted risks

### AR1 · Индексы порядка по названию для архивного охвата не читает ни один запрос до сортировки каталога графа

- **Evidence:** Решение 3 design, ADR-0045 («Последствия») и задача 1.4 вводят шесть индексов порядка по названию, в том числе два для архивного охвата. Архивный охват выбирает только каталог графа намерений (`intention_catalog_page.dart`), а он, по proposal и дельте «Упорядочивание каталогов намерений», порядка по названию в этом изменении не получает. Поиски читают только активный (`IntentionCatalogViewModel`) или полный (`RelationParticipantSelectionContext`) охват. Задача 1.4 выполнена: `lib/src/data/local/schema/intention_schema.drift` содержит `intentions_archived_title_search_key_asc_id_asc` и `intentions_archived_title_search_key_desc_id_asc`. Каталог графа через `_OfferedCatalogOrder` по-прежнему предлагает только четыре порядка по времени, и задачи фазы 2 этого не меняют.
- **Potential impact:** Два неиспользуемых индекса в базовом снимке схемы 6 обновляются каждой записью архивного намерения, архивированием и восстановлением и занимают место в файле. Если каталог графа получит порядок по названию в другой форме, например по языковому ключу, индексы останутся мёртвыми, и убрать их можно будет только миграцией.
- **Acceptance rationale:** Владелец решил заложить основу сразу: сортировка по названию в каталоге графа, где есть архивный охват, — ближайшее следующее изменение. Базовая схема 6 без миграции — последний случай добавить индексы без пути обновления. Цена записи для масштаба личного графа мала.
- **Scope and assumptions:** Только два индекса `(title_search_key ASC|DESC, id ASC)` с условием архивного охвата в схеме 6. Предполагается, что каталог графа получит порядок по названию через тот же ключ сохранённой проекции по ADR-0045 и с тем же курсором `(ключ, id ASC)`.
- **Reopen when:** Сортировку по названию в каталоге графа отменят или отложат на неопределённый срок; её спроектируют на другом ключе, направлении или форме курсора; схема 6 перестанет быть базовой версией без миграции до реализации задачи 1.4.
- **Acceptance authority:** Явное решение владельца при разборе F4 25.10.2026: каталог намерений с сортировкой по названию будет сделан вскоре, и основу под него нужно заложить сразу, пока это можно сделать без миграции.
- **Originating finding:** F4
- **Acceptance lifetime:** Durable
- **Decision record:** `docs/adr/0045-order-titles-by-opaque-key-of-stored-search-projection.md` («Последствия»); решение 3 и «Risks / Trade-offs» в `design.md`.

## ADDED Requirements

### Requirement: Локальная долговечность данных приложения
Система MUST сохранять подтверждённые данные между полными перезапусками и совместимыми обновлениями в пределах одной установки приложения. Каждый поддерживаемый platform adapter MUST исключать локальное хранилище и его служебные файлы из системного cloud backup и переноса данных между устройствами. После удаления приложения, очистки его данных или утраты устройства система SHALL NOT представлять восстановление прежних данных в новой установке как доступную возможность. Экспорт, удалённое хранение и синхронизация данных не входят в эту capability.

#### Scenario: Сохранение данных после полного перезапуска
- **GIVEN** пользователь подтвердил изменения локальных данных приложения
- **WHEN** приложение полностью завершается и запускается снова в той же установке
- **THEN** система восстанавливает последнее подтверждённое состояние данных

#### Scenario: Исключение данных из облачной резервной копии
- **GIVEN** поддерживаемая платформа выполняет системный cloud backup данных приложения
- **WHEN** система применяет правила резервного копирования Doable
- **THEN** локальное хранилище и его служебные файлы не включаются в облачную резервную копию

#### Scenario: Исключение данных из переноса между устройствами
- **GIVEN** поддерживаемая платформа выполняет системный перенос данных на новое устройство
- **WHEN** система применяет правила переноса данных Doable
- **THEN** локальное хранилище и его служебные файлы не переносятся в новую установку

#### Scenario: Отсутствие восстановления после утраты установки
- **GIVEN** прежняя установка Doable удалена, её данные очищены либо устройство утрачено
- **WHEN** пользователь запускает новую установку без существующего локального хранилища
- **THEN** система начинает работу без прежних данных и не представляет их восстановление как доступную возможность

### Requirement: Целостность сохранённого пользовательского текста
Каждое сохранённое представление пользовательского текста MUST удовлетворять общей границе корректного Unicode без `U+0000` и полному контракту соответствующего поля. Локальная схема MUST запрещать `U+0000` в канонических текстовых полях и производных поисковых представлениях независимо от прикладной проверки. Система MUST проверять сохранённое представление до публикации успешной предметной модели или сводки и MUST возвращать non-retryable corruption при нарушении общей либо field-specific границы без усечения, замены символов или частичного успешного результата. Ограниченная сводка, которая не материализует полный текст описания, MUST тем не менее отличать допустимое присутствующее описание от предметно отсутствующего или недопустимого сохранённого значения; SQLite `length()` SHALL NOT заменять подсчёт расширенных графемных кластеров.

#### Scenario: Локальная схема отклоняет NUL
- **GIVEN** локальное хранилище находится в целостном состоянии
- **WHEN** поддерживаемый низкоуровневый путь пытается сохранить строку с `U+0000` в названии или описании либо вычислить из названия поисковое представление с `U+0000`
- **THEN** локальная схема атомарно отклоняет запись и сохраняет прежнее целостное состояние

#### Scenario: Каталог не публикует недопустимое описание как присутствующее
- **GIVEN** сохранённая строка намерения содержит ненулевое описание, которое является предметно отсутствующим либо превышает допустимую длину
- **WHEN** система читает ограниченную сводку этого намерения
- **THEN** система возвращает corruption без успешной сводки, ложного признака наличия описания или материализации полного описания в публичный результат

#### Scenario: Корректный пользовательский текст сохраняется после перезапуска
- **GIVEN** название и описание состоят из допустимых скалярных значений Unicode без `U+0000` и удовлетворяют правилам своих полей
- **WHEN** приложение сохраняет намерение, полностью завершается и снова открывает то же локальное хранилище
- **THEN** система возвращает название и описание посимвольно без дополнительной Unicode-нормализации или замены символов

### Requirement: Создание и версионирование локального хранилища
Система MUST атомарно создавать новую локальную схему и поддерживать прямое обновление локального хранилища с каждой ранее опубликованной версии схемы на текущую без установки промежуточных версий приложения. Первичное создание и каждая миграция MUST либо полностью подтвердить целевую схему вместе с необходимыми проверками целостности и маркером версии, либо оставить хранилище в последнем целостном состоянии без частичной схемы, удаления пользовательских данных или частично подтверждённого состояния, чтобы повторный запуск мог безопасно повторить операцию. Если версия локального хранилища новее поддерживаемой приложением, система MUST запретить запись, SHALL NOT выполнять downgrade, удалять или пересоздавать хранилище и MUST вернуть несовместимость версии вызывающему bootstrap.

#### Scenario: Прерывание создания нового локального хранилища
- **GIVEN** новая установка ещё не имеет подтверждённой локальной схемы
- **WHEN** создание схемы прерывается после создания части её объектов
- **THEN** система не сохраняет частичную схему или маркер версии и при следующем запуске безопасно повторяет создание с пустого целостного состояния

#### Scenario: Сохранение данных после обновления приложения
- **GIVEN** локальное хранилище содержит данные поддерживаемой предыдущей версии приложения
- **WHEN** пользователь впервые запускает обновлённую версию с новой совместимой схемой хранения
- **THEN** система завершает необходимую миграцию и сохраняет доступность прежних данных и их состояния

#### Scenario: Обновление с пропуском нескольких версий приложения
- **GIVEN** локальное хранилище содержит данные любой ранее опубликованной версии схемы
- **WHEN** пользователь сразу устанавливает текущую версию приложения без установки промежуточных версий
- **THEN** система последовательно применяет необходимые миграции и сохраняет доступность тех же данных в текущей версии схемы

#### Scenario: Прерывание миграции локального хранилища
- **GIVEN** локальное хранилище содержит данные ранее опубликованной версии схемы
- **WHEN** процесс приложения завершается до окончания миграции
- **THEN** система не подтверждает частично мигрированное состояние, не удаляет пользовательские данные и при следующем запуске безопасно повторяет обновление из последней целостной версии

#### Scenario: Более новая версия локального хранилища
- **GIVEN** локальное хранилище создано более новой версией приложения
- **WHEN** установленная версия приложения пытается открыть это хранилище
- **THEN** система не выполняет feature query или запись, не изменяет и не удаляет хранилище и возвращает несовместимость версии

### Requirement: Безопасный bootstrap локального хранилища
Система MUST завершить открытие локального хранилища, проверку совместимости версии и необходимые миграции, а также включить контроль внешних ключей до предоставления изменяющих возможностей приложения. Для уже текущей версии production bootstrap MUST подтвердить поддерживаемый маркер версии и MUST NOT создавать эталонную базу данных или выполнять полное семантическое сравнение определений таблиц, virtual tables, ограничений, triggers, indexes и лишних schema objects. Полная семантическая совместимость текущей схемы и каждого поддерживаемого пути миграции MUST быть доказана до признания production-артефакта готовым через committed snapshots и автоматизированные migration/file-backed tests; та же полная проверка SHALL оставаться доступной как явно выбираемая debug/internal operation вне production bootstrap. Обычное открытие уже текущей схемы MUST NOT выполнять полный аудит всех сохранённых записей или поискового индекса как часть каждого запуска. Пока bootstrap выполняется, система SHALL показывать состояние загрузки. Ошибка открытия или миграции, доказанно классифицированная системой как устранимая, SHALL предоставлять явную повторную попытку без автоматического удаления или пересоздания хранилища. Повреждение SQLite-файла или его структуры MUST возвращаться как отдельный non-retryable результат corruption, а не как временная недоступность. Причина отказа, которую система не может доказанно классифицировать как устранимую ошибку, повреждение или несовместимость версии, MUST возвращаться как отдельный non-retryable результат unexpected, SHALL NOT считаться повреждением или временной недоступностью и SHALL NOT представлять обычный повтор той же операции как восстановление. При несовместимой более новой версии система MUST оставить изменяющие возможности недоступными, SHALL NOT предлагать ложную повторную попытку и SHALL сообщить о необходимости установить совместимое обновление приложения.

#### Scenario: Ожидание готовности локального хранилища
- **WHEN** приложение ещё открывает, проверяет или мигрирует локальное хранилище
- **THEN** пользователь видит состояние загрузки, а изменяющие возможности приложения остаются недоступными

#### Scenario: Устранимая ошибка bootstrap
- **WHEN** открытие или миграция локального хранилища завершается устранимой ошибкой
- **THEN** пользователь видит безопасное сообщение и явную возможность повторить bootstrap, а система не удаляет и не пересоздаёт локальное хранилище автоматически

#### Scenario: Восстановление после повторной попытки bootstrap
- **GIVEN** bootstrap завершился устранимой ошибкой
- **WHEN** пользователь явно повторяет операцию и локальное хранилище становится доступным
- **THEN** система завершает bootstrap и предоставляет возможности приложения с подтверждёнными данными

#### Scenario: Неизвестная причина отказа bootstrap
- **WHEN** открытие, ограниченная проверка или миграция локального хранилища завершается причиной, которую система не может доказанно классифицировать как устранимую ошибку, повреждение или несовместимость версии
- **THEN** система возвращает отдельный non-retryable результат unexpected, закрывает неготовое соединение, оставляет изменяющие возможности недоступными, не изменяет и не удаляет локальное хранилище и не представляет повтор той же операции как восстановление

#### Scenario: Повреждённый SQLite-файл при bootstrap
- **GIVEN** локальный файл не является корректной SQLite database либо SQLite обнаруживает повреждение его структуры
- **WHEN** приложение выполняет bootstrap
- **THEN** система возвращает результат corruption, закрывает неготовое соединение и не представляет повтор той же операции как восстановление файла

#### Scenario: Несовместимое определение объекта выявляется до поставки
- **GIVEN** file-backed fixture имеет поддерживаемый маркер версии, но определение таблицы, virtual table, ограничения, trigger или index несовместимо с текущей схемой либо содержит лишний schema object
- **WHEN** полная семантическая проверка выполняется в migration/file-backed test или явно выбранной debug/internal operation
- **THEN** проверка завершается несоответствием и зависящая от неё production-сборка не признаётся готовой

#### Scenario: Обычное production-открытие текущей схемы остаётся ограниченным
- **GIVEN** локальное хранилище уже имеет текущую совместимую схему и содержит много намерений
- **WHEN** приложение выполняет обычный production bootstrap без миграции или выбранного восстановления
- **THEN** система подтверждает маркер версии, включает контроль внешних ключей, не создаёт эталонную базу данных, не сравнивает семантически все определения schema objects и не сканирует все записи или весь поисковый индекс до готовности

#### Scenario: Bootstrap с более новой версией хранилища
- **GIVEN** локальное хранилище имеет несовместимую более новую версию
- **WHEN** приложение выполняет bootstrap
- **THEN** пользователь видит требование установить совместимое обновление приложения без доступа к изменяющим возможностям и без предложения повторить bootstrap

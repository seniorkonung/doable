## Findings

### F1 · High — Завершение дневного выбора удаляет носитель успешного состояния до отказоустойчивого окончания перехода

- **Evidence:** [design.md](design.md), решение 9, предписывает сначала удалить подтверждение через `removeUntil` до `ChoicePathRoute`, затем заменить корень через `replace`; там же утверждается, что при отказе завершённая страница остаётся в истории и запрещает повторную отправку. Это не следует из выбранной последовательности: подтверждение уже удалено первым действием. В `package:auto_route/src/router/controller/routing_controller.dart` метод `removeUntil` самостоятельно меняет стек и уведомляет слушателей, а `replace` удаляет последнюю страницу до выполнения `_push`; общей транзакции этих действий нет. В текущем `lib/src/daily_choice/presentation/path/choice_path_page.dart:102` возврат из подтверждения снова разрешает открыть подтверждение и обновляет путь; `DailyChoiceCreationSucceeded` и запрет отправки принадлежат отдельной форме (`lib/src/daily_choice/presentation/editor/daily_choice_creation_state.dart:19`), а не корню потока. Дизайн не переносит это состояние и не определяет восстановление при частично выполненном переходе. Требование «Открытие созданной сущности» и [ADR-0022](../../../docs/adr/0022-complete-creation-flows-within-owned-route-boundaries.md) требуют сохранить успех и исключить повторную отправку оставшихся страниц.
- **Impact:** При отказе после удаления подтверждения, но до замены корня, может остаться активное построение уже сохранённого выбора. Повторное открытие подтверждения создаст новую форму без признака прежнего успеха; одинаковые дневные выборы допустимы, поэтому репозиторий не устранит такой повтор. При другом моменте отказа фактический стек также не соответствует обещанию о сохранённой завершённой странице. Это риск предложенного алгоритма, а не результат исполнения ещё не написанного кода.
- **Required change:** Через обновление планирования согласовать решение 9 с контрактом ADR-0022: определить владельца подтверждённого завершения, который сохраняет запрет повторной отправки при частичном изменении стека, и безопасный выход для каждого оставшегося состояния. В Phase 2 `plan.md` закрепить проверку отказов до удаления подтверждения, между удалением и заменой и после удаления корня, включая возврат из подтверждения и запоздалые callbacks. Проверяемый результат: одна запись, отсутствие повторного подтверждения в завершённом потоке, сохранённая исходная история и доступный выход. Задачи Phase 2 здесь не добавлять: её пакет ещё не сформирован.

### F2 · Medium — Контракт отмены не различает завершение потока, возврат на шаг и уход после принятия команды

- **Evidence:** [quick-creation/spec.md](specs/quick-creation/spec.md), требование «Запуск режима поверх текущей страницы», обещает возврат к исходной странице без создания сущности при отмене «на любом шаге»; сценарий иллюстрирует только закрытие первого поиска. [app-navigation/spec.md](specs/app-navigation/spec.md), требование «Панель на обычных страницах», сохраняет закрытие только верхней страницы системным «назад». Каноническая [сессия черновика намерения](../../specs/intention-management/spec.md), а также дельты намерений, связей и дневных выборов разрешают уход после принятия команды с её последующим успешным завершением. Дизайн описывает границу потока для успеха, но не задаёт различие отмены всего потока и возврата на предыдущую страницу. Сейчас явная кнопка отмены подтверждения дневного выбора вызывает только `Navigator.maybePop` (`lib/src/daily_choice/presentation/editor/daily_choice_creation_page.dart:279`), оставляя построение пути в истории.
- **Impact:** Исполнитель может сохранить прежнюю кнопку отмены, которая вернёт к пути вместо исходной страницы, либо заставить системное «назад» удалять весь поток вопреки навигационному контракту. Без границы принятия отправки фраза «без создания сущности» также обещает отмену уже принятой записи, прямо запрещённую контрактами сущностей. Разные проверки будут требовать несовместимых результатов.
- **Required change:** Развести в требованиях отмену ещё не отправленного потока, возврат на предыдущий шаг и уход после принятия команды. Сохранить уже установленные правила: системное «назад» закрывает только текущую страницу; принятая команда продолжается независимо от экрана. Для явной отмены определить доступное действие и удаление только собственных страниц потока с возвратом к исходной истории. Добавить различающие сценарии для отмены на подтверждении, обычного «назад» и ухода во время сохранения, согласовать дизайн и условие готовности Phase 2. Новые задачи этой фазы оставить её последующему планированию.

### F3 · Medium — Асинхронные записи режима не имеют установленного порядка

- **Evidence:** [quick-creation/spec.md](specs/quick-creation/spec.md), требование «Сохранение режима между запусками», требует немедленно применять выбор и сохранять его для следующего процесса. Решения 6–7 [дизайна](design.md) и [ADR-0021](../../../docs/adr/0021-separate-installation-preferences-from-personal-graph.md) задают асинхронную запись и атомарное переименование временного файла, но не определяют порядок нескольких незавершённых записей. Меню после выбора закрывается и может быть открыто снова до окончания записи. Раздел проверок дизайна охватывает одиночные запись и отказ, но не перестановку завершений. Единственный контроллер не обеспечивает последовательность сам по себе; последовательный исполнитель графа к этой настройке явно не применяется.
- **Impact:** Если человек выбирает сначала режим A, затем B, более медленная запись A может заменить уже сохранённый B. В процессе кнопка показывает B, а после перезапуска восстанавливается A, хотя обе операции были успешны. Атомарность отдельной замены предотвращает частичный файл, но не устаревшую запись; общий временный файл без согласования добавляет взаимное вмешательство операций.
- **Required change:** Определить у границы настроек порядок применения сохранений и поведение предыдущей незавершённой записи при новом выборе, сохранив мгновенное состояние интерфейса и диагностику отказов. После успешного завершения последовательных выборов более раннее сохранение не должно вытеснять последнее; отказ нового сохранения должен сохранять предусмотренное последнее успешно записанное значение. Добавить управляемые проверки задержанных записей, смены A → B, отказа одной из записей и чтения новым процессом; отразить этот результат в Phase 3 `plan.md` без создания её пакета задач на текущем этапе.

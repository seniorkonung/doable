## Context

[Предложение](proposal.md) заменяет показ результатов операций по одному объединением ожидающих результатов. Поведение задают дельты [управления намерениями](specs/intention-management/spec.md), [управления тегами](specs/tag-management/spec.md) и [управления долговременными связями](specs/long-term-relation-management/spec.md): отказы показываются раньше успехов, отказы объединяются только при совпадении итогового текста, все ожидающие успехи объединяются в одно сообщение с текстом последнего, состав сообщения фиксируется при выдаче, а сообщение смахивается в сторону.

Сейчас по [ADR-0012](../../../docs/adr/0012-centralize-graph-operation-result-presentation.md) `GraphCommandCoordinator` владеет исключительными claims и состоянием непредъявленных результатов, а `GraphOperationPresenter` владеет общей поверхностью `ScaffoldMessenger`. Регистрация оболочки получает от координатора по одному результату: `_nextAppPresentableEntry` выбирает самую раннюю ожидающую запись, у регистрации не больше одного неподтверждённого claim, а подтверждение после кадра с сообщением потребляет его operation token. Presenter показывает `SnackBar` со стандартными временем показа и направлением смахивания `DismissDirection.down` и запрашивает следующий claim только после закрытия текущего сообщения.

Объединение по итоговому тексту требует локализованного текста, который формирует только presenter. Координатор локализации не знает и не должен узнавать. Порядок ожидающих записей координатора совпадает с порядком публикации завершений, а публикация идёт последовательно в порядке принятия команд.

Схемы ниже — облегчённые C4-схемы уровня компонентов внутри одного приложения, как в прежних изменениях. Подписи в схемах даны латиницей: `Coordinator` — `GraphCommandCoordinator`, `Presenter` — `GraphOperationPresenter`, `Message Plan` и `MessagePlan` — новая чистая функция состава сообщения, `Messenger` — `ScaffoldMessenger`, `Screens` — экраны и их view models.

## Goals / Non-Goals

**Goals:**

- Реализовать правила объединения из дельт спецификаций, сохранив исключительность claims, однократное предъявление, подтверждение по завершённому кадру и возврат результатов при пересоздании presenter.
- Оставить координатор независимым от локализации и состава сообщений.
- Сосредоточить правила состава сообщения в одной функции, проверяемой без Flutter и координатора.
- Смахивать сообщение общей поверхности влево или вправо.

**Non-Goals:**

- Изменение времени показа `SnackBar`, его оформления или темы приложения.
- Изменение инлайн-предъявления ошибок открытой экранной сессией и передачи их оболочке.
- Список, журнал или повторный просмотр предъявленных результатов.
- Изменение исполнения команд, порядка публикации завершений и согласования данных.

## Decisions

Долговременное решение о форме права оболочки и владении составом сообщения выделено в [ADR-0023](../../../docs/adr/0023-collapse-pending-results-into-shared-surface-messages.md) — частичный пересмотр ADR-0012 (решения 1–2). Решения 3–4 реализуют спецификации в установленных границах.

### 1. Claim оболочки охватывает все ожидающие результаты, а подтверждение называет предъявленные

```text
+------------------------------------------------------------------------+
|                                                                        |
|                          Doable (Flutter app)                          |
|                                                                        |
|  +---------+  accept   +-------------+  nextClaim   +-----------+      |
|  | Screens | --------> | Coordinator | <----------  | Presenter |      |
|  +---------+           | claims,     |   confirm    +-----------+      |
|                        | pending     |   covered       |     |         |
|                        +-------------+            plan |     | show    |
|                                                        v     v         |
|                                              +---------+ +-----------+ |
|                                              | Message | | Messenger | |
|                                              | Plan    | +-----------+ |
|                                              | (pure)  |               |
|                                              +---------+               |
+------------------------------------------------------------------------+
```

`nextClaim()` сохраняет сигнатуру и момент выдачи: claim выдаётся, когда у самой ранней действующей регистрации есть запрос, нет неподтверждённого claim и ожидает хотя бы один результат оболочки. Выданный `GraphAppPresentationClaim` охватывает все ожидающие результаты оболочки на момент выдачи: непустой упорядоченный список пар completion и operation token в порядке записей координатора. Результаты, ставшие ожидающими позднее, в него не входят и ждут следующего claim. Так фиксируется состав сообщения при выдаче.

Подтверждение оболочки выполняет новая операция `confirmAppPresentation(claim, covered)`. `covered` — непустое подмножество tokens этого claim; иное значение является ошибкой программирования и приводит к `ArgumentError`. Для действующего claim операция атомарно удаляет записи из `covered`, возвращает остальные записи claim в ожидание на их прежних местах, снимает с регистрации выданный claim и запускает выдачу следующего. Для освобождённого, заменённого или завершённого вместе с координатором claim операция ничего не делает, как и нынешнее подтверждение. Освобождение регистрации возвращает в ожидание все записи её неподтверждённого claim.

`confirmPresentation` остаётся операцией права инициатора и принимает только `GraphInitiatorPresentationClaim`. После этого общая база двух видов claims теряет единственного потребителя, поэтому удаляется: claims инициатора и оболочки становятся самостоятельными типами с разной формой. Право инициатора по-прежнему охватывает один результат.

Альтернативы:

- Передавать координатору функцию выбора или итогового текста и вызывать её при выдаче: выдача выполняется и внутри цепочки публикации завершений, поэтому сбой кода presenter прервал бы публикацию всех последующих завершений, а координатор зависел бы от локализации.
- Выдавать снимок ожидающих результатов и отдельно захватывать выбранное подмножество: появляется устаревание снимка между двумя шагами, которое нужно определять и проверять.
- Выдавать несколько claims подряд по одному результату: нарушается инвариант одного неподтверждённого claim регистрации, на котором держатся возврат при пересоздании и отсутствие гонок.

### 2. Состав сообщения определяет чистая функция presentation-слоя

Функция `planGraphOperationMessage` получает непустой список результатов claim и функцию итогового текста результата и возвращает план сообщения: tokens охваченных результатов, текст показываемого результата и число остальных охваченных. Если среди результатов есть отказ, план охватывает самый ранний отказ и все отказы с тем же итоговым текстом. Иначе план охватывает все результаты и показывает текст последнего. Признак отказа берётся из `GraphCommandCompletion.isFailure`, итоговый текст — из существующей функции текста сообщения результата presenter.

Presenter строит план при каждой попытке показа из результатов текущего claim и текущей локализации. Субъектом свидетельства кадра становится показанный план, поэтому подтверждение охватывает ровно те результаты, которые учтены в видимом сообщении. Если неподтверждённое сообщение закрылось и показывается снова после смены локали, новый план строится из того же claim; неохваченные результаты claim вернутся в ожидание при подтверждении.

```text
Coordinator              Presenter              MessagePlan       Messenger
    |  1. nextClaim()        |                        |                |
    |<-----------------------|                        |                |
    |  2. claim(all pending) |                        |                |
    |----------------------->|                        |                |
    |                        | 3. plan(results, text) |                |
    |                        |----------------------->|                |
    |                        | 4. covered, text       |                |
    |                        |<-----------------------|                |
    |                        | 5. show SnackBar                        |
    |                        |---------------------------------------->|
    |                        | 6. frame evidence for the plan          |
    |  7. confirmApp(covered)|                        |                |
    |<-----------------------|                        |                |
    |  rest back to pending  | 8. closed: timeout or swipe             |
    |                        |<----------------------------------------|
    |  9. nextClaim()        |                        |                |
    |<-----------------------|                        |                |
```

Альтернативы: правила в координаторе требуют итогового текста и, значит, локализации; правила внутри состояния виджета смешивают выбор с жизненным циклом Flutter и проверяются только виджетными тестами.

### 3. Число остальных результатов добавляется к показанному тексту одной строкой локализации

Новая строка `graphOperationMessageWithOthers` принимает готовый текст сообщения и число остальных охваченных результатов: «{message} · ещё {count}» и «{message} · {count} more». Сообщение одного результата использует прежний текст без суффикса. Форма «ещё N» не требует склонения, поэтому plural-форма ICU не нужна. Итоговая строка становится и видимым текстом, и меткой live region, так что экранный диктор объявляет и число.

Альтернативы: отдельный визуальный счётчик требует собственной композиции семантики без пользы для смысла; обобщённое «Выполнено N действий» теряет отклик о последнем действии, ради которого сохраняется сообщение об успехе.

### 4. Направление смахивания задаёт владелец поверхности

Presenter создаёт `SnackBar` с `dismissDirection: DismissDirection.horizontal`. Flutter не сочетает горизонтальное смахивание со смахиванием вниз, поэтому вниз сообщение больше не снимается. Закрытие смахиванием проходит через существующую обработку закрытия: подтверждённое сообщение освобождает поверхность и presenter сразу запрашивает следующий claim. Тема приложения не меняется: других потребителей у этого решения нет.

## Risks / Trade-offs

- [Неохваченные результаты claim недоступны новой выдаче до подтверждения текущего сообщения] → presenter и без этого показывает не больше одного сообщения; при освобождении регистрации они возвращаются вместе с остальными, а их места в порядке сохраняются.
- [Claim, выданный в фоне, фиксирует состав до возвращения приложения, и результаты, завершившиеся в фоне, придут следующим сообщением] → это следует из правила фиксации состава при выдаче; хвост остаётся ограниченным одним дополнительным сообщением.
- [Поток отказов с разным итоговым текстом по-прежнему показывается по одному] → это принятое правило спецификации; приоритет отказов показывает первый из них не позже окончания текущего сообщения.
- [Горизонтальный свайп от края экрана Android воспринимается как системный жест «назад»] → поведение платформы для любых горизонтальных свайпов; смахивание из середины сообщения работает.
- [Изменение формы claim оболочки затрагивает многие тесты, использующие `nextClaim` и `confirmPresentation`] → правки механические; контракт выдачи, подтверждения и освобождения проверяется отдельными тестами координатора, правила состава — тестами чистой функции, показ, фиксация состава и смахивание — виджетными тестами presenter.

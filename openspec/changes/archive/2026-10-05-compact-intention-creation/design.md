## Context

Изменение [compact-intention-creation](proposal.md) заменяет отдельную форму создания быстрым вводом в модальной нижней панели. Поведение определяют delta-спецификации [намерений](specs/intention-management/spec.md), [тегов](specs/tag-management/spec.md), [избранного](specs/favorite-intention-management/spec.md) и [навигации](specs/app-navigation/spec.md), совместно с неизменёнными требованиями основных спецификаций.

Уточнение пользователя о «половине экрана» описывает компактность, а не размер: начальная высота зависит от содержимого и доступного места. Разворачивание на всю доступную высоту и возвращение к компактному виду меняют размер той же панели. Сравнение с Todoist задаёт характер быстрого ввода; точное копирование его оформления не требуется.

Он владеет поиском и прокруткой своего открытия; [TagCatalogViewModel](../../../lib/src/tag/presentation/catalog/tag_catalog_view_model.dart) ведёт выбор кандидата, актуальность тега и проверку существующего назначения. Простое нажатие строки не записывает назначение.

Начальных тегов и избранного в команде нет.
- [GraphCommandCoordinator](../../../lib/src/graph/application/graph_command_coordinator.dart) живёт на уровне приложения, удерживает принятые команды, блокирует повтор по ключу формы и публикует завершения независимо от времени жизни экрана. Нижняя панель должна занять место в этом стеке, чтобы обычные страницы тегов открывались над ней.
- В действующей схеме уже есть готовность намерения, назначения тегов и отдельная таблица избранных с положительным уникальным местом. Новых сохраняемых полей для этого сценария не требуется.

Принятые [ADR-0009](../../../docs/adr/0009-unify-personal-graph-module-and-revision.md), [ADR-0012](../../../docs/adr/0012-centralize-graph-operation-result-presentation.md) и [ADR-0013](../../../docs/adr/0013-load-complete-tag-snapshots.md) задают единую границу графа, ревизию, предъявление результатов и полные снимки тегов. [ADR-0014](../../../docs/adr/0014-host-primary-navigation-in-root-page-shell.md), [ADR-0015](../../../docs/adr/0015-keep-favorite-order-as-explicit-whole-list-places.md) и [ADR-0016](../../../docs/adr/0016-present-only-failure-for-self-evident-success.md) принадлежат уже архивированному изменению add-home-navigation-and-favorites, но по файлам остаются proposed. Они описывают присутствующие в коде навигацию, порядок избранного и особую политику сообщений перестановки и учитываются как контекст реализации; их статусы здесь не изменяются. Новые предложенные ADR данного change — [ADR-0018](../../../docs/adr/0018-manage-modal-creation-sessions-in-root-stack.md) и [ADR-0019](../../../docs/adr/0019-separate-tag-selection-context-from-persistence.md).

В [CONTEXT.md](../../../CONTEXT.md) определён черновик создания и согласована возможность выразить решение о готовности до создания намерения. Это предметное изменение данного change: в текущем коде намерение всегда создаётся неготовым, а целевые спецификации оставляют выключенное состояние умолчанием формы и допускают явный выбор при подготовке. Определение действия — полная выполнимость за один день и операционная понятность — сохраняется.

## Goals / Non-Goals

**Цели:**

- Быстрый компактный ввод всех начальных данных намерения с доступным сохранением при клавиатуре и увеличенном тексте.
- Один общий выбор тегов для существующего намерения и черновика с явно различимым моментом записи.
- Создание намерения, его начальной готовности, избранного и назначений одной транзакцией и одним подтверждённым результатом.
- Сохранение черновика при изменении размера, переходах в теги и ошибках; подтверждение перед его потерей.
- Сохранение действующих правил идентичности, текстовой валидации, отказов, согласования каталогов и однократного предъявления.

**Вне объёма:**

- Новое оформление подробного просмотра и редактирования существующего намерения, перестановки избранного или общего каталога тегов.
- Постоянное хранение черновиков и восстановление сессии после закрытия либо завершения процесса.
- Создание связей, дневного выбора, автоматическая готовность или наследование условий каталога в новом намерении.
- Новый источник данных, синхронизация, независимый репозиторий тегов и внешняя библиотека нижних панелей.

## Decisions

### 1. Сценарий создания владеет черновиком; модуль графа владеет записью

Панель и её ViewModel образуют одну экранную сессию, владеющую вводом, выбранными идентификаторами тегов и режимом размера. Общий выбор тегов получает узкую возможность прочитать и изменить набор этой сессии. Команды, ревизии, SQL и сохранение не входят в контракт черновика.

После принятия команды координатор владеет неизменяемыми данными отправки до результата. Закрытие панели освобождает её ресурсы и право предъявления, но не отменяет команду. Для сборки используются существующие Riverpod providers и зависимости, переданные контексту выбора; универсальный реестр сервисов не вводится.

Небольшая схема компонентов внутри Flutter-приложения показывает проектируемый поток. Стрелки означают использование непосредственной зависимости; точные классы новой панели и контекста выбора будут определены при реализации.

```text
+---------------------- Flutter application -----------------------+
|                                                                  |
|                              +--------------------+              |
|                              | Creation sheet     |              |
|                              +--------------------+              |
|                                        |                         |
|  +----------------+                    v                         |
|  | Tag selector   |          +--------------------+              |
|  +----------------+          | Creation session   |              |
|          |     draft tags    +--------------------+              |
|          +---------------------------> ^                         |
|          |                             |                         |
|          |                             v                         |
|          |   tag commands    +--------------------+              |
|          +-----------------> | Graph coordinator  |              |
|          |                   +--------------------+              |
|          |                             |                         |
|          |                             +-----+                   |
|          |                             |     v                   |
|          |                             | +---------------------+ |
|          |                             | | Result presentation | |
|          |                             | +---------------------+ |
|          |                             v                         |
|          |      tag reads     +--------------------+             |
|          +------------------> | Graph repository   |             |
|                               +--------------------+             |
|                                         |                        |
+-----------------------------------------|------------------------+
                                          v
                                 +-----------------+
                                 | SQLite database |
                                 +-----------------+
```

- Creation sheet — нижняя панель; Creation session — её черновик, режим размера и состояние отправки. Tag selector добавляет тег через контракт сессии только в контексте черновика.
- Graph coordinator удерживает одну принятую отправку и публикует подтверждённый пакет. Tag selector использует его для постоянных операций тегов и назначения существующему намерению.
- Graph repository — существующий PersonalGraphRepository; чтения тегов и атомарные записи остаются за ним. SQLite database обозначает постоянное хранилище, а не отдельный прикладной модуль.
- Result presentation — действующие общая и инлайн-поверхности с одним протоколом владения сообщением. Согласование данных подписчиков идёт по завершению команды независимо от показа сообщения.
- Предположение схемы: записи проходят через существующий экземпляр репозитория и его последовательный исполнитель. Другой процесс или синхронизация требуют отдельного решения за пределами change.

**Альтернатива:** создавать намерение при открытии панели и сразу изменять его существующими командами. Это оставляет предметную запись после отмены и нарушает требование единого сохранения; черновик остаётся самостоятельным состоянием интерфейса.

### 2. Одна управляемая модальная панель в общем корневом стеке

Долговечная граница сессии и исключение из полноэкранного открытия описаны в [ADR-0018](../../../docs/adr/0018-manage-modal-creation-sessions-in-root-stack.md); конкретное представление маршрута ниже остаётся решением этого дизайна.

Сохраняем IntentionEditorRoute как точку входа создания, задав ему opaque: false через CustomRoute существующего auto_route и заменив содержимое нижней панелью. Маршрут поддерживает состояние под страницами выбора и редактора тегов. Содержимое маршрута — фон модальности и нижняя панель; переход на отдельную страницу при разворачивании отсутствует.

Оболочка и каталог продолжают существовать под маршрутом. Фон модальности закрывает доступ к каталогу и всей основной навигации, включая фокус и семантику; верхняя часть каталога видна как контекст. TagCatalogRoute и TagEditorRoute открываются обычными полноэкранными маршрутами того же корневого стека. После их закрытия раскрывается прежняя панель с тем же вводом, режимом и прокруткой формы.

Автоматическое закрытие маршрута по фону отключается. Свой ModalBarrier с обработчиком запроса закрытия и жест на ручке панели вызывают одну процедуру сессии; системное «назад» перехватывается PopScope. Все программные закрытия, кроме успешного создания и подтверждённого завершения сессии, проходят ту же процедуру.

Это решение опирается на проверенный API auto_route 11.1.0: CustomRoute предоставляет opaque, maintainState и barrierDismissible. Стандартный [showModalBottomSheet](https://api.flutter.dev/flutter/material/showModalBottomSheet.html) предоставляет автоматическое закрытие по фону и свайпу; в установленном Flutter обработчик закрытия встроенной панели вызывает Navigator.pop напрямую. Поэтому [PopScope](https://api.flutter.dev/flutter/widgets/PopScope-class.html), управляющий back-навигацией, сам по себе не задаёт единую точку подтверждения всех этих действий.

**Альтернативы:** штатный showModalBottomSheet добавляет отдельное взаимодействие Navigator с декларативным корневым стеком и требует отдельной защиты встроенного закрытия. Постоянная панель Scaffold не обеспечивает требуемую модальность. Управляемый маршрут использует уже существующую маршрутизацию и явно владеет закрытием.

### 3. Размер панели адаптивный, сохранение закреплено отдельно от прокрутки

Режим размера представлен перечислением «компактный / развёрнутый», отдельным от предметных данных. Компактная высота определяется измеренным содержимым короткой формы и ограничением доступной области с резервом для видимого каталога. Ограничение выражает необходимые отступы и контекст над панелью, а не фиксированный процент экрана. Большой набор тегов или длинное описание прокручиваются внутри этого ограничения. Развёрнутый режим занимает всю область, доступную после безопасных отступов и клавиатуры.

Внутри панели размещаются ручка и доступная кнопка изменения размера, название, описание, выбранные теги и ряд быстрых действий. Поле описания начинает с одной строки без большой пустой области; дополнительный текст доступен через прокрутку. Теги показываются компактными элементами с актуальным названием и снятием. Действия выбора тегов, избранного и готовности используют существующие Material-иконки с локализованными подсказками; при узком экране ряд может переноситься.

«Сохранить», индикатор принятой отправки и необходимое исправление общего отказа располагаются в закреплённой области того же Scaffold панели. Поля и сообщения их ошибок находятся в прокручиваемой области; при отказе соответствующее поле и собственный текст ошибки доводятся до видимости. Общая поверхность SnackBar должна оставаться видимой над содержимым панели и не перекрывать «Сохранить». Второй ScaffoldMessenger или GraphOperationPresenter не создаётся.

Появление клавиатуры пересчитывает доступную геометрию, сохраняя перечисление режима. Клавиатура и автоматический фокус названия не являются командой разворачивания. Свайп вверх по ручке разворачивает панель; вниз из развёрнутого режима возвращает компактный вид, а попытка дальнейшего закрытия из компактного вызывает запрос закрытия. Прокрутка текста или тегов не закрывает панель. Кнопка размера обеспечивает те же действия без жеста.

**Альтернативы:** постоянные 50% экрана не отражают уточнение пользователя и плохо учитывают клавиатуру. Полноэкранное открытие либо автоматическое разворачивание при длинном вводе лишают форму согласованного компактного режима. Незакреплённая кнопка сохранения становится недоступной при большом содержимом.

### 4. Сессия сохраняет сырые данные и имеет явные состояния отправки и закрытия

Черновик содержит исходные строки названия и описания, неизменяемый набор TagId, IntentionReadiness и FavoriteMark. Начальные значения — пустые строки и набор, notReady и notFavorite. Идентификатор намерения в черновике отсутствует; он появится только при создании. Последние известные названия и состояния чтения выбранных тегов — проекция для показа, отдельная от набора их идентичностей.

Состояние отправки выражается вариантами, которые сохраняют черновик и необходимые данные результата: редактирование, выполняющаяся отправка с токеном, отказ с типизированной причиной и правом предъявления, успешное завершение. Существующий OperationState можно использовать вместе с расширенным IntentionEditorState; доступность команд определяется исчерпывающим разбором вариантов. Во время отправки ViewModel отвергает изменение всех исходных данных и повторную отправку, даже если callback уже поставлен в очередь интерфейсом.

| Событие | Действие сессии |
| --- | --- |
| Ввод, снятие или добавление тега, переключение иконки | Меняет только черновик в состоянии редактирования или допустимого исправления |
| Разворачивание, сворачивание, переход в теги | Сохраняет черновик и ключ сессии, не проверяет потерю данных |
| «Сохранить» | Фиксирует неизменяемую команду всех полей и передаёт её координатору один раз |
| Отказ создания | Сохраняет весь сырой ввод и набор, показывает типизированное исправление или допустимый повтор |
| Успех создания | Завершает именно эту сессию без подтверждения потери данных |
| Подтверждённое закрытие | Уничтожает сессию, передаёт непредъявленную ошибку общей поверхности и оставляет принятую команду выполняться |

Изменённость вычисляется сравнением текущих пяти предметных полей с начальными значениями. Сравниваются сырые строки: даже полностью пробельный введённый текст требует подтверждения потери ввода. Возврат всех полей к исходным значениям снимает изменённость. Размер панели, фокус, прокрутка, кандидат в выборе и поисковая строка тегов не меняют предметный черновик.

Один запрос закрытия обслуживает кнопку закрытия, свайп, фон и «назад». Для изменённого черновика открывается одно подтверждение с продолжением и сбросом. До отправки подтверждение объясняет потерю ввода; во время принятой отправки — также то, что сохранение продолжится. Продолжение возвращает прежнюю геометрию и черновик. Действие платформы, которое сначала скрывает клавиатуру, не завершает сессию.

Подтверждение и callbacks связываются с ключом сессии и актуальным состоянием отправки. Если команда успешно завершилась при открытом подтверждении, закрываются принадлежащие этой сессии подтверждение и панель; запоздалый ответ не закрывает другой маршрут или вновь открытую форму. После ухода новая форма получает новый ключ, и результат прежней попытки не восстанавливает её данные. Удаление экранных подписок и контроллеров не освобождает gate координатора до результата команды.

**Альтернативы:** глобальный provider одного черновика смешивает разные открытия. Нормализация текста при каждом вводе теряет исходные пробелы и затрудняет исправление ошибок. Подтверждение после фактического удаления маршрута не может сохранить прежнюю сессию.

### 5. Общий выбор тегов получает типизированный контекст действия

Отделение контекста интерфейса от постоянных назначений закреплено предложенным [ADR-0019](../../../docs/adr/0019-separate-tag-selection-context-from-persistence.md).

Расширяем существующий TagCatalogView, сохраняя общие список, поиск, порядок, выделение кандидата, создание и редактор тегов. Контекст интерфейса имеет закрытые варианты: просмотр каталога, назначение существующему намерению, добавление в черновик. Он определяет подписи, признаки включения и контракт явного действия.

Контекст интерфейса отделяется от существующего TagCatalogMode чтения репозитория. Для черновика используется обычный полный снимок каталога TagCatalogBrowseMode; признаки включения накладываются из локального набора сессии. Режим TagCatalogSelectionMode продолжает читать назначения существующему IntentionId. Сессионный ключ и данные черновика не попадают в контракт хранилища, фиктивный IntentionId не создаётся.

| Контекст | Нужная возможность | Эффект явного действия |
| --- | --- | --- |
| Существующее намерение | Проверить пару и отправить AssignTag через координатор | Подтверждённое постоянное назначение либо типизированный отказ |
| Черновик | Получить текущий набор сессии и добавить подтверждённый TagId | Немедленное локальное включение либо отказ при закрытой/отправленной сессии; записей графа нет |

Адаптер действия существующего намерения сохраняет текущие проверки назначения, блокировки, чтения и права предъявления. Адаптер черновика зависит только от контракта набора сессии. Сборка контекста и маршрутов принадлежит вызывающему сценарию; общий виджет не получает весь объект приложения. Набор передаётся как актуальное наблюдаемое состояние, чтобы добавление изменяло признаки строк без смены идентичности открытия, сброса поиска или перечитывания каталога.

Нажатие строки выбирает кандидата, а закреплённая область явного действия предлагает «Добавить» с семантикой добавления в черновик. Для уже включённого тега действие недоступно. Добавления нескольких тегов выполняются в том же открытии; возвращение в панель выполняется обычным закрытием выбора. Снятие из будущего набора доступно в панели. Выбор кандидата и изменение поискового запроса не меняют набор.

Каждое открытие выбора имеет свой TagCatalogOpening и поисковое состояние. Переход в редактор и назад сохраняет это открытие; закрытие выбора и новое открытие создают новое состояние поиска. Используются существующие правила корректного Unicode, последнего корректного фильтра, Case Folding Unicode 17.0.0, пустых состояний, отказов и актуальности выбранного кандидата.

«+» справа вверху всегда открывает существующий TagEditorRoute. Его принятая команда CreateTag сохраняется независимо от черновика; возврат тега позволяет показать кандидата, но не добавляет его в набор автоматически. Отмена редактора не меняет набор. Операция создания тега сохраняет собственный результат и сообщение по действующему протоколу.

Подтверждённое переименование обновляет проекцию названия выбранного TagId. Подтверждённое удаление оставляет идентификатор в наборе, показывая недоступный тег с последним известным названием и возможностью явного снятия. Ошибка чтения — отдельное состояние, она не означает удаление. Старые ответы не заменяют более новую проекцию. На общем выборе отсутствующий кандидат не разрешает добавление; уже включённый отсутствующий тег не теряется при уходе из выбора.

Проекцию тегов панели сессия поддерживает через существующий watchTag для выбранных идентификаторов. Из выбора передаётся последнее подтверждённое название для немедленного показа; дальнейшее наблюдение обновляет только проекцию. При снятии тега или завершении сессии соответствующие подписки освобождаются. Ревизия и поколение каждого наблюдения защищают от ответа после снятия и повторного добавления; ошибки наблюдения имеют собственное типизированное состояние и допустимое восстановление. Эта проекция не изменяет набор отправки и не заменяет проверки репозитория при сохранении.

**Альтернативы:** отдельная страница выбора для черновика дублирует интерфейс и нарушает согласованное требование общего компонента. Добавление сессионного режима в repository переносит интерфейсное состояние в модуль постоянных данных. Использование AssignTag для черновика потребовало бы преждевременного создания получателя.

### 6. Одна расширенная команда создания выполняется одной транзакцией

CreateIntention дополняется начальными IntentionReadiness, FavoriteMark и неизменяемым набором TagId с прежними значениями по умолчанию. Конструктор фиксирует коллекцию, исключая изменение отправки через внешнюю ссылку; отсутствие тегов выражено пустым набором. Сохраняются типизированные идентификаторы и существующая граница проверки сырого текста. IntentionSaved остаётся одним результатом создания.

Coordinator принимает команду по IntentionCreationFormKey. Набор не отправляется цепочкой существующих EnableIntentionReadiness, MarkIntentionFavorite и AssignTag. Существующие самостоятельные команды по-прежнему работают только с уже сохранёнными намерениями. Последовательный исполнитель репозитория упорядочивает создание относительно удаления тегов, отметки избранного и перестановки; актуальный порядок определяется в транзакции записи.

Внутренняя операция создания:

1. Проверяет и нормализует текст существующим IntentionText; проверяет выбранные теги по идентификаторам и подтверждает их сохранённые данные в транзакции.
2. При отсутствии хотя бы одного тега прерывает всё создание типизированным IntentionCreationTagsMissingFailure с непустым набором отсутствующих TagId. Это исправляемая ошибка выбора в категории validation, а не отсутствие намерения или повреждение базы.
3. Создаёт новый идентификатор и активное намерение сразу с выбранной готовностью, используя одно показание часов для createdAt и updatedAt.
4. Записывает все уникальные назначения с существующими ограничениями и порядком тегов.
5. При выбранном избранном добавляет его строку после текущего максимального места всего порядка, включая архивированные намерения. Внутренний примитив записи места переиспользуется со самостоятельной отметкой, сохраняя её отдельную проверку существующего намерения.
6. Получает и проверяет окончательный каталожный снимок с тегами, готовностью, избранным и счётчиками и подготавливает проверенные данные всех фактов результата. Все потенциально отказные чтения и проверки выполняются до commit. Только затем транзакция подтверждается.
7. После commit один раз продвигает ревизию и публикует единый подтверждённый результат и уведомления наблюдателей.

Любой отказ до commit откатывает намерение, FTS-проекцию, все назначения, отметку и её место. Самостоятельные теги, созданные ранее отдельной командой, уже имеют свои подтверждённые транзакции и сохраняются. Отказ не продвигает ревизию. Проверки существования в интерфейсе помогают человеку исправить выбор, но не заменяют транзакционную проверку.

Правила IntentionText остаются прежними: название после удаления окружающих пробелов содержит 1–255 графем; присутствующее описание сохраняется целиком до 4096 графем, полностью пробельное считается отсутствующим. Некорректный Unicode и NUL отклоняются до кодирования. Сырые данные формы не заменяются нормализованными значениями при отказе.

**Альтернативы:** последовательные публичные команды допускают частичный успех, несколько ревизий и разные timestamps. Откат компенсирующими командами не гарантирует исходное состояние после второго отказа. Дополнительная транзакционная граница поверх репозитория дублирует уже принятого владельца инвариантов.

### 7. Подтверждённый пакет сразу описывает всё созданное намерение

Успех содержит одну IntentionCatalogCreated с окончательным снимком и TagAssignmentChangedChange для каждого созданного назначения, все на одной ревизии. Состав IntentionSaved расширяется этими фактами без второго terminal outcome или повторной каталожной мутации на каждый тег. Отдельные успешные сообщения о готовности, избранном и назначениях не возникают.

Каталог намерений применяет пакет целиком по текущему протоколу ревизий: учитывает готовность и набор тегов при определении соответствия фильтрам, сохраняет условия и прокрутку. Новая строка не вставляется в неподходящую выдачу. Уже загруженная Главная получает актуализацию через избранное в окончательном каталожном снимке; это работает и для скрытой вкладки. Навигация по тегу и назначения получают подтверждённые факты того же пакета.

Результат маршрута используется только для завершения интерфейсного перехода. Каталог и Главная не получают отдельный путь обновления из возвращённого намерения; локальные и глобальные слушатели не применяют запись дважды.

**Альтернативы:** один результат с неполным каталожным снимком оставляет неверную принадлежность фильтрам. Отдельные сообщения или мутации после создания показывают частичные состояния и нарушают однократное предъявление.

### 8. Существующая политика ошибок сохраняется и дополняется исправлением набора тегов

| Отказ | Поведение открытой панели |
| --- | --- |
| Ошибка названия или описания | Сохраняет весь ввод, показывает ошибку поля; исправление этого поля разрешает новую отправку |
| Отсутствующие выбранные теги | Сохраняет идентификаторы и остальные данные, показывает недоступные теги; явное исправление набора разрешает новую проверку всей команды |
| Доказанно устранимая unavailable | Сохраняет все данные и предоставляет явный повтор с новым токеном |
| Остальные conflict, corruption и unexpected | Сохраняет черновик и безопасное сообщение; обычный повтор той же операции не предлагается |

Новый вариант ошибки входит в исчерпывающие обработчики формы, общих сообщений и диагностических категорий. Исправление нерелевантного поля не сбрасывает неповторяемый отказ. Проверки UI и ViewModel согласуют canSubmit с типом ошибки; сохранение данных не обещает успешного восстановления после любого отказа.

Право ошибки открытой формы передаётся существующему OperationFailurePresentation. При потере фокуса, открытом подтверждении над формой или временной невидимости живого renderer оно сохраняется до пригодного кадра. После окончательного закрытия или удаления renderer до предъявления право переходит общей поверхности. Успех всегда предъявляет существующий GraphOperationPresenter один раз и не задерживает закрытие панели. Политика «только отказ» перестановки избранного не распространяется на создание.

**Альтернативы:** новый локальный SnackBar создаёт второго владельца результата. Подавление общего успеха для создания меняет действующую спецификацию предъявления; такое поведение не входит в change.

### 9. Доступность и диагностика входят в тот же сценарий

Первая фокусируемая область — название; переход в выбор тегов и обратно сохраняет ввод и не создаёт новую сессию. Кнопка «+» имеет подсказку «Создать намерение» и семантическое название без видимой надписи. Кнопки избранного и готовности передают включённость через форму значка и семантику, а не один цвет.

Перед явным включением готовности интерфейс объясняет оба критерия действия. Объяснение можно показать компактным подтверждением из иконки; после явного решения меняется только черновик. Отказ не включает готовность, выключение происходит локально. Временная поверхность объяснения сохраняет черновик так же, как другие переходы внутри сессии.

Тексты кнопок, ошибок, подтверждений, подсказок и семантики добавляются в существующие русские и английские ARB; пользовательские названия и описания не переводятся. Для увеличенного текста сохраняются переносы, прокрутка и доступное закреплённое действие; затенённый каталог исключается из доступной семантики и фокуса.

Диагностика использует существующий DiagnosticsSink. Команда имеет один исход создания, длительность и безопасную категорию отказа. Для расширенного создания фиксируется этап проверки, записи или проверки результата, чтобы различать отказ выбранных тегов и сбой записи; это типизированное дополнение существующего события create. Переключения иконок и локальные изменения набора не выдаются за постоянные команды и не создают диагностические события назначения. В события не включаются тексты, идентификаторы и названия тегов, состав избранного, SQL или путь базы; ошибка диагностики не меняет исход операции.

**Альтернативы:** отдельная подсистема логирования не имеет самостоятельного потребителя. Запись каждой локальной правки создаёт шум и раскрывает личные данные без пользы для диагностики атомарного сохранения.

## Risks / Trade-offs

- [Обход подтверждения штатным закрытием] -> Все источники пользовательского закрытия обслуживает одна процедура; автоматические фон и drag-pop отключены. Проверки вызывают реальный фон, жест и системное «назад», а не только метод ViewModel.
- [Клавиатура или увеличенный текст заполняют почти всё доступное пространство] -> Поля прокручиваются, сохранение закреплено, высота пересчитывается без смены режима. Проверяются маленький экран, landscape, безопасные отступы и максимальный системный текст; точная геометрия не фиксируется процентом.
- [Общее сообщение остаётся за панелью или перекрывает сохранение] -> Scaffold панели подключается к действующей общей поверхности, а его геометрия оставляет обе области доступными. Проверяется настоящий GraphOperationPresenter при открытой панели, диалоге и возврате к каталогу.
- [Поздний ответ тега или формы изменяет другую сессию] -> Используются ключи открытия, поколения чтения и сравнение ревизий; размер и набор не меняют идентичность открытия. Подписки уничтожаются вместе с владельцем.
- [Тег удалён между выбором и сохранением] -> Отсутствие проверяется в транзакции; весь набор отклоняется, выбранный идентификатор остаётся доступен для явного исправления. Подмена по названию исключена.
- [Отказ записи после части операций] -> Общая транзакция и проверенный окончательный снимок до commit; fault-injection проверяет откат на каждом этапе, включая избранное и FTS.
- [Одновременная перестановка и создание избранного] -> Репозиторий сериализует транзакции; место определяется текущим полным порядком, а не данными открытия панели.
- [Общий компонент выбора становится сложнее] -> Разница эффектов принадлежит двум узким адаптерам контекста; общий список, поиск и актуальность остаются едиными. Регрессии существующего назначения проверяются теми же контрактами.
- [Завершение процесса прерывает сессию] -> Сохранение черновика после процесса не обещается. Постоянный результат остаётся целым по действующим гарантиям SQLite; продолжение принятой команды обещается только в работающем процессе.
- [Архив исходного change не согласован со статусами его ADR] -> ADR-0014–0016 учитываются по фактическому статусу proposed; проверка отражена в adr.md. Исключение для модального создания описано в ADR-0018; финализация чужих записей остаётся за исходным изменением.

### Проверки при реализации

| Граница | Необходимое доказательство |
| --- | --- |
| Сессия и ViewModel | Все поля до отправки локальны; сырые строки и набор переживают ошибки и переходы; двойная отправка и callbacks прежнего открытия не меняют новую форму |
| Общий выбор тегов | Тот же компонент в обоих контекстах; выделение отдельно от добавления; поиск не снимает скрытые выбранные теги; новый тег сохраняется независимо и добавляется только явно |
| Маршруты и панель | Компактное открытие с видимым каталогом; разворачивание и сворачивание той же формы; реальный Back, фон и свайп; сохранение режима после тегов; запрет взаимодействия с навигацией |
| Представление отказа | Понятное исправление отсутствующего тега; отказ чтения не считается удалением; неповторяемые причины не получают обычный повтор; сообщения и исправление доступны при прокрутке и клавиатуре |
| Координатор и поверхности | Операция продолжает выполняться после подтверждённого ухода; один результат, правильная передача ошибки и один видимый SnackBar; успех при открытом подтверждении закрывает только свою сессию |
| Реальный Drift adapter | Все сочетания начальных опций, отсутствие и переименование тегов, единые timestamps, актуальный конец полного избранного порядка, одна ревизия и окончательный пакет |
| Откат и долговечность | Отказы после вставки намерения, назначения и избранного не оставляют частей или новой ревизии; отдельные теги сохраняются; подтверждённый результат читается после повторного открытия файловой базы |
| Согласование данных | Текущие текстовые и теговые фильтры, порядок и прокрутка каталога сохраняются; скрытая Главная и навигация по тегу отражают полный результат без двойного применения |
| Доступность и диагностика | Экранный диктор различает назначение и черновик, состояния и размер; действия доступны без жеста; безопасные события содержат категорию и этап, ошибка sink не влияет на запись |

Эти проверки определяют объём будущих задач и критерии корректности решения; создание данного design.md не является выполнением проверок приложения.

## Migration Plan

1. Расширить контракт CreateIntention и состав подтверждённого результата, сохраняя прежние значения по умолчанию для вызывающих сторон. Реализовать атомарный путь в существующем адаптере и типизированный отказ отсутствующих тегов.
2. Подключить контекст черновика к общему компоненту выбора и сессионному состоянию. Сохранить существующий путь назначения и самостоятельного создания тегов.
3. Перевести представление IntentionEditorRoute в управляемую нижнюю панель, заменить кнопку каталога значком «+», подключить закрытие, локализацию и доступность. Удалить прежнее полноэкранное представление создания как альтернативный пользовательский путь.
4. Проверить реальные маршруты, поверхности сообщений, базу и согласование данных с целевыми спецификациями и согласованным CONTEXT.md. Порядок конкретных инкрементов определяется последующим plan.md и задачами.

Версия схемы и данные существующих намерений не меняются: нужные таблицы и ограничения уже есть. Новая готовность сохраняется сразу в строке намерения, избранное — в существующей таблице, назначения — в существующих строках тегов. Процесс не пересоздаёт базу, не добавляет таблицу черновиков и не требует исправления прежних данных. Генерируемые маршруты и Riverpod/локализации обновляются штатными средствами репозитория.

Для отката интерфейс и расширенные команды возвращаются согласованным набором изменений. Уже созданные намерения, готовность, теги и избранное остаются обычными допустимыми данными прежней схемы; откат не удаляет их. Сведение активных спецификаций и предметной формулировки с фактически выпускаемым поведением обязательно.

## Open Questions

Продуктовых вопросов, блокирующих дизайн, не осталось. Следующие детали уточняются при реализации внутри принятых требований:

- Конкретные отступы, резерв видимого каталога, длительность анимации и пороги жеста выбираются по реальной форме на телефоне; фиксированной доли экрана нет.
- Контрактные имена новых контекстов и состояний определяются в существующих модулях без дублирования выбора тегов.

Квалификация долговечных решений и согласование с ADR завершены в [манифесте проверки](adr.md). Статусы ранее существовавших ADR сохранены.

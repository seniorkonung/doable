## Context

Изменение реализует поведение из [proposal.md](proposal.md) и трёх delta-спецификаций: [поиск намерений](specs/intention-management/spec.md), [дневные выборы](specs/daily-choice-management/spec.md) и [участники долговременных связей](specs/long-term-relation-management/spec.md). Требования к интерфейсу поиска по тегам согласованы пользователем: наблюдаемое взаимодействие задаёт спецификация поиска намерений, оформление и размещение — решение 7.

Четыре контекста уже используют общий `IntentionCatalogViewModel` и `IntentionCatalogQuery`. Назначение поиска задаёт архивный охват и готовность к действию. `DriftPersonalGraphRepository` получает точное количество и первую порцию в одной транзакции, продолжает выдачу курсорами по ключу сортировки и согласовывает изменения через общую ревизию графа. Сейчас запрос содержит только существующие условия охвата, готовности и названия, а `IntentionSummary` не содержит тегов.

Назначения находятся в `tag_assignments`, идентичность тега задаёт `TagId`, а переименование сохраняет этот идентификатор. Удаление тега каскадно удаляет назначения. Подтверждённые команды тегов публикуют `TagChange`, однако каталожное согласование пока не учитывает эти изменения. Общий `IntentionSummaryView` используется также вне поиска; расширение его данных само по себе не должно включать отображение тегов во всех местах использования.

Изменение `remove-relation-tags` удалило назначения тегов долговременным связям; оно влито в `main` и архивировано (коммит `abbae0419f22f893252c1ea7a2af66a1cc63569d`). Ветка этого изменения включает его результат первой задачей третьей фазы, и с этого момента design описывает объединённые контракты. Тег — метка только намерения, как в `CONTEXT.md` из `main`. Назначение адресуется `IntentionId`; типов `TagTarget` и `LongTermRelationTagTarget` нет. Столбец `tag_assignments.intention_id` обязателен, уникальное ограничение `(tag_id, intention_id)` и индекс `(intention_id, tag_id)` сохранены. Навигация по тегу читает помеченные намерения через `getTaggedIntentionsPage`. Хранилище открывается в единственной версии схемы 1 без путей обновления. Этот design использует только эти контракты и не меняет схему хранения и правила удаления назначений.

## Goals / Non-Goals

**Goals:**

- Один контракт поиска для каталога, действия дневного выбора, исходного намерения и участника долговременной связи.
- Одновременное применение названия, всех обязательных тегов и отсутствия всех исключённых тегов по полному допустимому каталогу.
- Полные подтверждённые теги каждого результата, точное количество, ограниченные порции и корректное продолжение.
- Немедленное применение изменения условий по тегам и согласование подтверждённых изменений без возврата устаревшей выдачи.
- Сохранение выбранного идентификатора после переименования или удаления самого тега, включая успешную пустую выдачу при удалении обязательного тега.
- Единый согласованный интерфейс строки тегов результата, выбранных условий и выбора тега для условия во всех четырёх контекстах.

**Non-Goals:**

- Работа с описаниями, конструктор запросов, логика «ИЛИ» и наследование тегов по связям.
- Добавление тегов в дневной путь, отдельные представления соседей и другие представления без поиска.
- Удаление тегов у связей, изменение правил назначения тегов и постоянное сохранение поисковых условий между перезапусками приложения.

## Decisions

### 1. Расширить общий каталог и сохранить назначение поиска как границу допустимости

Все четыре потребителя передают параметры в существующий общий каталог. Контекстные ограничения выводятся из типизированного `IntentionCatalogPurpose` и входят в запрос до подсчёта и получения порций. Для поиска участника добавить в запрос необязательный `excludedIntentionId`: второй участник исключается в репозитории, а не только после получения порции. Это устраняет порции, занятые недопустимым кандидатом, и делает количество согласованным с допустимым результатом.

| Контекст | Архивный охват | Готовность | Исключённое намерение |
| --- | --- | --- | --- |
| Каталог | Выбранный пользователем | Любая | Нет |
| Действие дневного выбора | Активные | Только готовые | Нет |
| Исходное намерение | Активные | Любая | Нет |
| Участник активной связи | Активные | Любая | Второй участник по `IntentionId` |
| Участник архивированной связи | Активные и архивированные | Любая | Второй участник по `IntentionId` |

Компактная схема компонентов показывает зависимости внутри существующего приложения. `Catalog`, `Repository` и `Commands` обозначают общий поиск, единый репозиторий личного графа и координатор подтверждённых команд соответственно.

```text
Components inside Flutter application

+---------------------------+        +---------------------------+
| Catalog / Action / Source | -----> | Catalog                   |
| Relation participant      |        | Query + ViewModel         |
+---------------------------+        +---------------------------+
                                              |          ^
                                              | reads    | changes
                                              v          |
                                    +--------------+  +------------+
                                    | Repository   |  | Commands   |
                                    | Drift / SQL  |  | + revision |
                                    +--------------+  +------------+
                                              ^          |
                                              | writes   |
                                              +----------+
```

- Четыре поиска используют один источник выдачи и сохраняют независимые условия по назначению поиска.
- Репозиторий владеет транзакциями, назначениями, фильтрацией, количеством и курсорами; SQL не выходит в представления.
- Координатор передаёт подтверждённый пакет с одной ревизией. Каталог применяет его целиком и ровно один раз.
- Предположение схемы: сохраняются существующие локальное хранение и единая последовательность команд и чтений. Новые сервисы и внешние зависимости не требуются.

Альтернатива: отдельные реализации фильтра для каждого поиска. Она дублирует правила и создаёт риск разного поведения при удалении тегов, подгрузке и смене охвата.

### 2. Представлять условия двумя неизменяемыми наборами `TagId`

Добавить прикладное значение `IntentionTagFilter` с наборами обязательных и исключённых `TagId`. Пустое значение не ограничивает поиск. `IntentionCatalogQuery` и `IntentionCatalogSelection` содержат это значение целиком; название тега не участвует в предикате. Повторы внутри набора устраняются, а равенство не зависит от порядка добавления условий.

Для собственных назначений `T(i)`, обязательных `R` и исключённых `E` принадлежность определяется так:

```text
eligible(i) AND titleMatches(i) AND R subsetOf T(i) AND E intersection T(i) = empty
```

Если один идентификатор присутствует в обоих наборах, совокупность условий логически невыполнима и даёт успешный пустой результат. Ни одно условие не удаляется автоматически. Это следствие «И», а не дополнительный режим поиска.

Проверка запроса подтверждает тип и допустимость идентификаторов, но не требует существования выбранного тега в текущем каталоге тегов. После физического удаления обязательный идентификатор остаётся в `R` и не встречается в назначениях; исключённый остаётся в `E` и никого не отсекает. Новый одноимённый тег имеет другой идентификатор. Во второй фазе выбранные условия хранятся только идентификаторами в `IntentionTagFilter`, без названий и признаков удаления. Сведения для предъявления выбранного условия — актуальное название после переименования и предъявление после физического удаления — принадлежат третьей фазе и определяются спецификацией поиска намерений и решением 7. Они строятся по `TagId` из актуальных данных тегов отдельно от предиката: последнее подтверждённое название и подтверждённое удаление не должны терять сам `TagId`. Ошибка чтения каталога тегов не считается подтверждением удаления.

Альтернатива: искать теги по названиям или автоматически оставлять только существующие идентификаторы. Она меняет смысл сохранённого запроса после переименования и удаления. Строковое выражение запроса добавляет ненужный язык и допускает состояния, которые можно выразить точными типами.

### 3. Применять один SQL-предикат до количества, сортировки и ограничения порции

Расширить `_catalogCondition` проверками собственных назначений намерения. Для обязательных условий используется отсутствие выбранного обязательного тега без назначения этому намерению; для исключённых — отсутствие назначения любого выбранного исключённого тега. Условия входят в тот же предикат, что охват, готовность, название и исключённый участник. Первая порция, точное количество, продолжение и восстановление используют одну реализацию этого предиката.

Внешняя выборка остаётся выборкой намерений: назначения проверяются как принадлежность намерения множеству, отобранному по условиям, и не размножают строки. Пустые наборы естественно не ограничивают результат. Существующие правила буквального сопоставления названия и сортировки с дополнительным ключом `IntentionId` сохраняются.

Чтобы число выбранных тегов не упиралось в число параметров одного SQL-выражения, адаптер передаёт каждый набор идентификаторов одним связанным параметром — JSON-массивом канонических строк — и читает его в предикате через встроенную табличную функцию `json_each(?)`. Этот приём уже используется адаптером для неограниченных наборов в чтениях пути выбора. Каждое чтение передаёт свои наборы вместе с выражением, поэтому состояние условий не живёт на соединении и не смешивается между запросами. Наборы не входят в долговечную схему и не сохраняют пользовательский запрос. Тот же подход применяется к набору уже загруженных идентификаторов при согласовании массового изменения.

Чтения каталога, навигации и согласования не выполняют записей на соединении: ни в предметные таблицы, ни во временные отношения. Поэтому они не меняют предметные данные и не делают снимки соседних чтений устаревшими. В частности, курсор `getTaggedIntentionsPage` остаётся действительным после первой порции и продолжения `getCatalogPage` на неизменных данных, эпохе и ревизии, включая чтение, завершившееся отказом и откатом. Продолжение навигации не требует повторной первой порции и не теряет уже загруженную границу.

Владелец этой гарантии — `DriftPersonalGraphRepository`. Его внутренняя версия хранилища для чтений тегов строится из сигналов физического соединения: маркера соединения, `total_changes()` и `data_version`. Гарантия держится на отсутствии записей в чтениях, а не на учёте служебных изменений: `total_changes()` учитывает любые вставки и удаления на соединении, включая TEMP, и очистка не возвращает его к прежнему значению. Поэтому ручной учёт или вычитание служебных записей в состоянии экземпляра репозитория не используется. Единственная допустимая служебная операция чтения — идемпотентное создание маркера соединения, принадлежащего самому сигналу версии и не меняющего `total_changes()`. Новое служебное чтение адаптера, которому нужен неограниченный набор значений, использует тот же параметр `json_each(?)`, а не временную таблицу. Реальные изменения на том же соединении и сигнал изменения через `data_version` на другом соединении продолжают обнаруживаться. Нельзя заменить проверку версии одним сравнением `GraphRevision`, безусловно обновлять свидетельство курсора или пропускать проверку ссылок. Различение остаётся внутри адаптера; наружу выходят прежние непрозрачные курсоры и типизированные исходы, без новой постоянной схемы, миграции или пути записи.

Каждый набор условий читается из своего параметра один раз на выполнение запроса, а не заново для каждого кандидата. Предикат не коррелирует `json_each(?)` с текущим намерением. Он некоррелированно отбирает идентификаторы намерений по назначениям выбранных тегов через индекс `(tag_id, intention_id)` уникального ограничения. Для исключённых условий это намерения, у которых есть назначение хотя бы одного исключённого тега. Для обязательных — намерения, у которых число назначений обязательных тегов равно числу различных обязательных идентификаторов. В объединённой схеме каждое назначение принадлежит намерению, поэтому отбору не нужна отдельная ветвь для других получателей. Кандидат проверяется одним адресным поиском в уже отобранном множестве, поэтому стоимость его отсечения не растёт с числом условий. Однократный отбор зависит от числа назначений выбранных тегов, а не от произведения числа кандидатов на число условий. Промежуточные структуры, которые SQLite строит для одного выполнения, не являются записями на соединении и не меняют `total_changes()`. Существующие индексы порядка сохраняются для сортировки и продолжения. План и стоимость сложного фильтра проверяются на больших воспроизводимых данных. Нужно сравнить малое и большое число условий, в том числе поиск только с исключениями среди многих кандидатов. Ограничение материализации порции не означает постоянного времени подсчёта всего результата.

Альтернатива: отфильтровать полученные 100 намерений или соединить назначения с внешней выборкой и затем устранять повторы. Первый подход пропускает совпадения и даёт неверное количество, второй усложняет точный подсчёт и границы порций. Отдельное SQL-условие с параметром на каждый тег проще для малых наборов, но требует искусственного предела либо отдельного обхода ограничений SQL. Временные отношения, заполняемые пачками вставок, снимают этот предел, но служебные записи меняют `total_changes()` соединения. Сохранение действительности соседних курсоров тогда требует ручного учёта каждой такой записи, и любая будущая запись в обход учёта незаметно возвращает сброс навигации. Цена выбранного `json_each(?)`: у набора в параметре нет собственного индекса. Коррелированная проверка, которая для каждого кандидата перебирает весь набор и ищет каждое значение по `(intention_id, tag_id)`, отвергнута. Её стоимость растёт как произведение числа кандидатов на число условий: на 25 000 кандидатов при 1201 исключённом условии это секунды вместо десятков миллисекунд. Поэтому набор обрабатывается один раз на запрос, как описано выше, а стоимость подтверждается на больших наборах условий.

### 4. Получать полные теги кратких данных вместе с порцией

Расширить `IntentionSummary` подтверждённым неизменяемым списком собственных `Tag`. Успех получения порции означает, что состав назначений каждой возвращённой строки известен полностью; пустой список означает проверенное отсутствие назначений. Неизвестный состав не кодируется пустым списком или необязательным полем успешной сводки.

После получения ограниченной порции намерений репозиторий читает назначения только её идентификаторам пакетно, в той же транзакции и на той же ревизии, что строки и количество первой порции. Общий декодер проверяет идентичности, названия и согласованность технического порядка назначений по действующим правилам чтения тегов. Соединение не должно скрывать повреждённую ссылку как отсутствие назначения. Порядок тегов соответствует существующему порядку создания тегов; число назначений одного намерения не ограничивается размером порции намерений.

Ошибка чтения назначений завершает чтение порции явным отказом существующей категории. При отказе обновления сохраняется прежнее подтверждённое содержимое с состоянием неудавшегося обновления. Частично прочитанные теги не выдаются за полную сводку. Методы копирования сводки, в том числе обновление счётчика связей, сохраняют подтверждённый состав тегов.

Краткие снимки до и после команд изменения намерений также содержат собственные теги: иначе изменение названия, готовности или архивного состояния невозможно корректно согласовать при действующих условиях по тегам. Снимок до физического удаления получается до каскадного удаления назначений.

Альтернатива: отдельный watcher или чтение подробностей на каждую строку. Это добавляет запросы на число строк и смешивает ревизии намерения и назначений. Отдельная необязательная загрузка тегов потребовала бы дополнительного протокола частичных состояний, хотя данные уже доступны в общей транзакции.

### 5. Считать весь совместный фильтр единым набором параметров поиска

Изменение любого набора тегов сразу заменяет параметры, отменяет ожидающий debounce названия, инвалидирует старые запросы и начинает первую порцию с текущим введённым названием. Название проходит существующую проверку: недопустимый ввод не подменяется предыдущим корректным значением. При обычном вводе названия сохраняется существующий debounce живого поиска.

Все пути создания запроса, включая продолжение, повтор чтения и восстановление, передают оба набора тегов и контекстные ограничения. Курсор хранит каноническую идентичность всего запроса: охват, готовность, название, обязательные и исключённые идентификаторы, исключённое намерение и порядок. Курсор другого сочетания условий отклоняется. Одного сравнения числа тегов недостаточно.

Поколение запросов в `IntentionCatalogViewModel` защищает первую порцию, продолжение и асинхронное согласование. Ответ старого поколения не публикуется. Смена охвата сохраняет название и оба набора; разные `IntentionCatalogPurpose` не разделяют изменяемое состояние фильтра. Физическое удаление тега меняет данные графа, но не параметры поиска и не снимает условие.

Альтернатива: применять выбранные теги только при следующем вводе названия или общей отправке формы. Она противоречит немедленному применению, подтверждённому пользователем. Независимые состояния трёх частей фильтра увеличивают риск публикации запроса, содержащего смесь старых и новых условий.

### 6. Согласовывать одиночные назначения через снимки, массовое удаление — через недостающую часть выдачи

Расширить обработку подтверждённых пакетов каталога событиями тегов. Ревизия отражает действительно согласованное содержимое; наличие `TagChange` нельзя считать пустым изменением и просто продвинуть ревизию.

| Подтверждённое изменение | Согласование открытого поиска |
| --- | --- |
| Назначение или снятие у одного намерения | До и после операции получить полные краткие снимки этого намерения в транзакции команды и добавить `IntentionCatalogMutation` в тот же подтверждённый пакет. Применить существующие правила соответствия, точного количества и загруженной границы. |
| Переименование | По `TagId` заменить название в подтверждённых тегах загруженных строк. Выбранные условия хранятся только идентификаторами и не меняются; предъявление их названий относится к третьей фазе. Состав, порядок и количество не меняются. |
| Удаление обязательного тега | Сохранить условие; согласовать успешный пустой результат, количество ноль и отсутствие продолжения. |
| Удаление только исключённого тега | Удалить тег из сводок, сохранить условие и согласовать появившиеся совпадения и точное количество по описанному ниже протоколу. |
| Удаление тега вне условий | Удалить тег из загруженных сводок; принадлежность, количество и порядок остаются прежними. |
| Создание без назначения или повтор без изменения | Не менять состав намерений и не применять изменения количества. |

Для одиночного назначения компактный `TagAssignmentChangedChange` остаётся фактом изменения пары, а дополнительный снимок каталога относится к той же ревизии. Это не перечисление всех получателей общего тега. Каталог применяет изменение принадлежности только через `IntentionCatalogMutation`, чтобы наличие двух связанных фактов в пакете не изменяло количество дважды. Такой снимок учитывается и для намерения вне загруженной части. Команды тегов не меняют временные метки намерения.

Расширенный пакет получают и существующие потребители `IntentionCatalogMutation` вне поиска: наблюдатели намерения в репозитории, чтения и модели дневных выборов и предложений пути, подробности намерения и долговременной связи, окрестность связи и выбранные связи. Для них каталожная мутация команды тега — изменение кратких данных существующего намерения, а не его создание или удаление. Затронутый потребитель обновляется не более одного раза на пакет по действующему контракту обработки мутации того же намерения: сохраняет собственное подтверждённое состояние, незавершённую форму и выбор, не показывает удаление или отказ и не меняет видимое содержимое, кроме уже предъявляемых тегов этого намерения. Потребители, не наблюдающие затронутое намерение, пакет не обрабатывают. Других получателей тега в объединённой схеме нет, поэтому каждое подтверждённое изменение назначения даёт каталожную мутацию ровно одного намерения.

Глобальное удаление исключённого тега может открыть много совпадений до уже загруженной границы. `TagDeletedChange` сохраняет компактный контракт с одним `TagId`; команда удаления не материализует всех получателей. Для этого случая добавить чтение согласования каталога в общий репозиторий со следующим контрактом:

1. Запрос содержит текущий совместный фильтр и типизированную границу: частично загруженный префикс с ключом сортировки либо результат, ранее загруженный до конца. Передаются идентификаторы сохранённых строк. Модель представления связывает запрос со своим поколением поиска. Пустой ранее завершённый результат также обрабатывается как завершённый результат. Сохранённые строки передаются не целиком, а скользящим окном: курсор согласования с ключом сортировки и не более размера порции запроса идентификаторов сохранённых строк, следующих за курсором в действующем порядке. Окно, превышающее размер порции, отклоняется как недопустимый ввод. Верхний край окна — ключ его последней строки; если окно содержит последнюю сохранённую строку области, верхним краем становится граница области: граница частичного префикса либо конец выдачи для ранее завершённого результата. Поэтому размер входа одного чтения не зависит от числа сохранённых строк, и поддерживается согласуемая область любого размера без предела и без сброса выдачи.
2. Репозиторий считает абсолютное количество по полному предикату. Отдельно получает не более одной порции соответствующих намерений после курсора согласования и не дальше верхнего края окна, которых нет среди идентификаторов окна; все сохранённые строки этого промежутка входят в окно, поэтому исключение точно. Если порция заполнена, следующий курсор — ключ её последней строки, иначе — верхний край окна. Модель представления сдвигает окно по сохранённому содержимому до исчерпания области, так что суммарная работа согласования растёт линейно с числом сохранённых и недостающих строк, а не с их произведением на число порций. Условия области и уже загруженных идентификаторов не ограничивают общий подсчёт. Обычное продолжение после границы остаётся отдельным чтением.
3. Сохранённые строки обновляются по известным фактам удаления и другим подтверждённым пакетам. Недостающие строки добавляются в правильном порядке; предшествующие порции сохранённых строк не перечитываются. Для ранее завершённой выдачи недостающие совпадения читаются до нового конца ограниченными порциями.
4. Количество, недостающие строки и теги каждой порции сопровождаются ревизией. Все порции одного согласования должны отражать одну ревизию. Если между чтениями появились изменения, кандидат остаётся неопубликованным, очередь подтверждённых пакетов применяется к сохранённому содержимому и получение недостающей части повторяется для актуальной ревизии. Продолжение согласования связано также с границей области, своим курсором и окном сохранённых идентификаторов.
5. Публикуется целиком согласованный префикс с абсолютным количеством и ревизией. Для частичного префикса сохраняется обычная граница продолжения. Позиция просмотра привязывается к оставшемуся видимому намерению либо ближайшему соседу по действующему контракту. Изменения до опубликованной ревизии не применяются к количеству повторно.

Во время согласования новые пакеты объединяются и обрабатываются последовательно; запрос прежних параметров или старой ревизии не может вернуть удалённый тег, старое количество либо прежний состав. Отказ обновления сохраняет последнее целиком подтверждённое содержимое и явное состояние отказа. Он не превращается в пустой результат. Состояния чтения согласования различают успешную порцию, необходимость повторить согласование из-за новой ревизии и безопасно классифицированный отказ.

Отказ согласования области не блокирует выдачу молча и бессрочно. Пока отказ не снят, опубликованное содержимое остаётся прежним. Обычное продолжение после границы не читается, потому что захватило бы строки, не учтённые согласованием. Подтверждённые пакеты применяются к сохранённому содержимому области. Выйти из отказа можно без смены условий поиска двумя путями:

- **Автоматический повтор.** Каждый подтверждённый пакет, полученный после отказа, применяется к сохранённому содержимому и сразу запускает новое чтение недостающей части той же области на актуальной ревизии. Это действует для любой категории отказа. Повтор запускается только событием пакета: таймеров, циклов и повторов без нового пакета нет. Очередной отказ снова переводит область в отказ, не заменяя содержимое. Каждое такое чтение записывает обычное диагностическое событие чтения согласования.
- **Явный повтор.** Он доступен пользователю по действующим правилам ошибок получения каталога: действие повтора предлагается для недоступности хранилища, а при повреждении и неожиданной ошибке показывается их безопасное сообщение без действия, как для отказа продолжения. Явный повтор запускает то же чтение, что и автоматический.

На время повторного чтения состояние отказа сменяется обычным состоянием согласования, как при любом другом чтении согласования. Очередной отказ снова публикует отказ с его категорией поверх того же содержимого. Успешная публикация целиком согласованного префикса завершает согласование и возобновляет обычное продолжение. Смена фильтра, охвата или порядка, как и прежде, начинает новую выдачу без отказа.

Каждая из четырёх страниц поиска предъявляет состояние отказа обновления поверх сохранённой выдачи. Предъявление использует общее представление состояния обновления рядом с существующим представлением состояния продолжения. Сообщение явно говорит, что показанная выдача не обновлена. Для исходного пустого результата оно отличает отказ от успешного отсутствия совпадений. Действие повтора вызывает явный повтор модели. Предъявление отказа не заменяет загруженный список и не меняет позицию просмотра.

Размещение отказа относительно выдачи одинаково на всех четырёх страницах и принадлежит одному общему элементу выдачи поиска. Над загруженным списком отказ ложится поверх его верхнего края и не сжимает область списка: при появлении и снятии отказа сохраняется не только смещение прокрутки, но и экранное положение строк прокрученного списка. Место под отказ отводится перед началом выдачи, поэтому первые строки остаются достижимыми; список, стоявший в начале выдачи, остаётся в начале — его строки уходят из-под появившегося отказа и возвращаются на место после снятия. Над пустой выдачей отказ стоит над сообщением о пустоте. Размещение отказа в столбце над списком, при котором строки сдвигаются на высоту отказа, не применяется ни на одной странице.

Тот же общий элемент владеет правилом требования «Согласованность параметров совместного поиска» [спецификации поиска намерений](specs/intention-management/spec.md) — смена параметров поиска по решению 5 начинает выдачу с верхней позиции: страницы не повторяют ни слушателя условий, ни собственного перехода к началу. Правило действует и тогда, когда список в момент смены не показан.

Альтернатива: только явный повтор. Тогда выдача остаётся замороженной, пока пользователь сам не нажмёт кнопку, а последующие подтверждённые изменения не появляются, хотя модель уже получила их. Другая альтернатива — автоматический повтор по таймеру с нарастающей паузой. Он выполняет фоновые чтения при постоянном отказе и не даёт пользователю ручного выхода.

Позиция просмотра сохраняется существующим якорем страницы каталога, который фиксирует видимое намерение только при переходе между загруженными состояниями с тем же объектом запроса. Поэтому согласование после одиночного изменения назначения и публикация целиком согласованного префикса после массового согласования переводят `IntentionCatalogLoaded` в `IntentionCatalogLoaded` с тем же экземпляром `IntentionCatalogQuery`: без промежуточного состояния загрузки, пересоздания запроса и прокрутки к началу. Ожидание, повтор и отказ согласования не заменяют загруженный список. Сохранение позиции наблюдается на странице каталога, где она существует: при вставке совпадений или удалении строк перед видимым намерением оно остаётся на прежнем месте экрана, а при его исчезновении позиция переходит к ближайшему соседу. Страницы выбора действия, исходного намерения и участника связи отдельного якоря не имеют и получают те же переходы состояния без промежуточной загрузки. Якорь видимого намерения и место под кнопку создания намерения — единственные отличия каталога от страниц выбора в выдаче; каталог подключает их к общему элементу выдачи явно, а не собственной копией размещения отказа.

Чтение согласования записывает в репозитории собственный тип диагностического события, отличный от события обычной порции каталога, чтобы согласование было различимо в диагностике. Событие фиксирует начало, завершение с длительностью и типизированным видом исхода — успешная порция или повтор из-за новой ревизии — и отказ с длительностью и существующей безопасной категорией. Повтор из-за новой ревизии не записывается как отказ. Кроме размера порции, вида исхода, длительности и категории отказа, событие ничего не содержит: названия, `TagId`, `IntentionId`, наборы условий, сохранённые идентификаторы, ключи сортировки и SQL-параметры в него не попадают. Отказ диагностического приёмника не меняет результат чтения.

Альтернатива: каждый `TagChange` сбрасывает каталог на первую порцию. Она теряет загруженный префикс и позицию просмотра. Локальное удаление тега только из видимых строк не учитывает новые совпадения и количество. Перечисление всех получателей при глобальном удалении переносит стоимость согласования в предметную команду и нарушает компактность её результата.

### 7. Подключать предъявление тегов явно в четырёх результатах поиска

Расширенные краткие данные передаются четырём страницам поиска. Подключение предъявления тегов должно быть явным на этих местах использования; наличие списка тегов в модели не включает его во всех вызовах общего представления намерения. Дневной путь и самостоятельные представления участников и соседей не становятся потребителями поиска по тегам.

Контракт данных и поведения: собственные теги доступны вместе с названием без открытия подробностей, а изменение условий вызывает общий поиск и не изменяет граф. Общая модель не должна связывать эти действия с командами назначения или снятия тегов.

Интерфейс поиска по тегам согласован пользователем. Наблюдаемое взаимодействие задают требования [спецификации поиска намерений](specs/intention-management/spec.md) «Теги в результатах поиска намерений», «Выбранные условия по тегам в поиске намерений», «Выбор тега для условия поиска» и «Сохранение условия после физического удаления тега». Это решение задаёт их оформление и размещение, одинаковые во всех четырёх контекстах:

| Элемент | Оформление и размещение |
| --- | --- |
| Строка тегов результата | Под названием намерения: «Теги: Здоровье, Отдых» — названия через запятую в порядке сводки, с переносом и без обрезки. Подтверждённый пустой состав — «Без тегов». Строка входит в объединённую семантику результата; новых целей нажатия нет. `IntentionSummaryView` выводит строку только при явной передаче тегов. |
| Раздел условий | Под полем названия. Условия — чипы в порядке добавления с переносом на новые строки. Обязательный тег — значок ✓ и название («✓ Здоровье»), исключённый — значок ⊘ и «не» («⊘ не Спорт»). Диктор читает «Здоровье, должен быть» и «Спорт, должен отсутствовать». |
| Действия с условием | Нажатие на чип переключает надобность, крестик на чипе снимает условие. Кнопка «+ Тег» стоит после чипов и открывает выбор тега с текущими условиями. |
| Условие удалённого тега | Чип с последним известным названием, прежним значком надобности и пометкой «(тег удалён)»; снимается крестиком, как любое условие. |
| Выбор тега для условия | Отдельный полноэкранный маршрут с полем поиска по названию и списком тегов. У каждого тега действия «Есть» (должен быть) и «Нет» (должен отсутствовать); выбор закрывает экран и возвращает типизированный результат с тегом, надобностью и ревизией снимка тегов. Уже выбранный тег отмечен текущей надобностью. |
| Отказ обновления выдачи | Над списком результатов, по решению 6: сообщение, что выдача не обновлена, и действие «Повторить» только при недоступности хранилища. Отказ лежит поверх верхнего края списка и не сдвигает строки прокрученного списка ни на одной из четырёх страниц. |
| Пустая выдача по условиям | Собственное сообщение об отсутствии совпадений по условиям на месте списка, отличное от сообщения о пустом охвате. |

Строка тегов, раздел условий, выбор тега и предъявление отказа обновления — общие элементы; страницы четырёх контекстов подключают их, а не реализуют собственные варианты. Общим является и элемент выдачи поиска: он один владеет размещением отказа обновления относительно загруженной и пустой выдачи и переходом к верхней позиции при смене параметров, как описано в решении 6. Страница передаёт ему состояние выдачи своего назначения и построение своих строк; повторять на странице компоновку отказа или слушателя условий нельзя. Все подписи локализованы на русский и английский, названия тегов выводятся без перевода и преобразования. Смысл надобности передаётся значком и текстом, а не только цветом. Цели нажатия, подписи и контраст соответствуют действующим ориентирам доступности проекта, в том числе при увеличенном тексте и открытой клавиатуре.

Выбранные условия для предъявления хранит отдельная модель представления на каждое назначение поиска: упорядоченные условия с `TagId`, надобностью, предъявляемым названием и признаком подтверждённого удаления. Из неё выводится `IntentionTagFilter` решения 2; порядок добавления — свойство предъявления и в предикат не входит. Выбор тега читает полный снимок каталога тегов с собственным состоянием, не разделяемым с каталогом тегов и другими открытиями. Ревизия снимка в результате выбора позволяет предъявить выбор с актуальным названием или признаком удаления, если тег изменился после получения снимка, без бессрочного журнала изменений.

Альтернатива: автоматически показывать новое поле во всех `IntentionSummaryView`. Это распространяет поиск и теги на контексты, которые пользователь явно исключил из объёма. Альтернатива для условий: два отдельных раздела обязательных и исключённых тегов. Она допускает один тег в обоих разделах и требует отдельного действия для смены надобности; единый список с переключением делает невыполнимое сочетание непредставимым в интерфейсе. Альтернатива для выбора тега: встроенный выпадающий список на странице поиска. Он конкурирует за место со списком результатов при открытой клавиатуре и увеличенном тексте и не вмещает состояния получения каталога тегов.

## Risks / Trade-offs

- **Массовое удаление исключённого тега открывает много новых совпадений** → порции согласования ограничены, сохранённые строки не перечитываются, подтверждённый префикс публикуется согласованно. Для ранее полностью загруженного результата область может быть большой, поэтому сохранённые идентификаторы передаются скользящим окном не больше размера порции: вход и материализация одного чтения ограничены порцией, а общее время и накопленные данные растут линейно с числом сохранённых строк и новых совпадений внутри области.
- **Много назначений у одной строки или много условий** → пакетное чтение только нужных намерений, передача каждого набора условий одним параметром через `json_each(?)` и отсутствие скрытого предела тегов по размеру порции. Предикат обрабатывает каждый набор один раз на запрос, а не для каждого кандидата. Стоимость отсечения кандидата не растёт с числом условий. Проверить запросы, материализацию и зависимость стоимости от числа условий на больших фикстурах, включая поиск только с исключениями среди многих кандидатов.
- **Количество, сводки и продолжение отражают разные моменты** → единая транзакция каждого чтения, общая ревизия, поколение запроса и повтор неопубликованного согласования при изменении ревизии. Непрерывные изменения могут задерживать завершение; сохранять подтверждённое содержимое с состоянием обновления.
- **Служебные записи поиска меняют версию соседнего чтения** → чтения не пишут на соединение, наборы передаются параметрами; ручной учёт служебных записей не используется. Проверка фиксирует, что чтения каталога, включая отказавшие, не меняют `total_changes()` соединения; контроль реальных изменений и ссылочной целостности сохраняется. Одна сериализация запросов или очистка временных строк этой гарантии не даёт.
- **Снимок команды содержит неполные или старые теги** → один проверенный путь построения кратких данных для чтений и команд, снимки в транзакции и проверки устаревших ответов. Количество совпадений изменяется только один раз на пакет.
- **Расширение общего представления затрагивает дневной путь** → явное подключение данных тегов только в четырёх поисках и проверки отсутствия нового отображения в исключённых контекстах.
- **Перенос поведения первых двух фаз на результат `remove-relation-tags`** → вливание `main` меняет типы получателей, чтения назначений и версию схемы под уже реализованным поиском. Поведение переносится без изменений; ветви и проверки, существовавшие только ради назначений связям, удаляются или заменяются выразимыми на новой схеме, остальные утверждения не ослабляются. Противоречие объединённого результата спецификациям или этому design возвращается в планирование, а не устраняется молча в коде.
- **Диагностика раскрывает запрос или пользовательские данные** → использовать существующие безопасные категории и длительности чтений. Названия, `TagId`, `IntentionId`, наборы условий, назначения и SQL-параметры не записываются в диагностические события.

### Проверка выбранного подхода

Проверить контракт фильтра и курсора; совместный положительный и отрицательный отбор с названием; точное количество и совпадение за пределами прежней первой порции; отсутствие повторов между порциями; полные теги и классификацию отказов. Отдельные проверки покрывают немедленное изменение условий во время debounce, поздние первые порции и продолжения, независимость назначений поиска и их ограничения.

На реальном адаптере проверить цепочку: первая порция навигации по тегу → совместное чтение каталога → продолжение исходной навигации. Обязательные условия, исключения и их сочетание проверяются после первой порции, продолжения, повторных чтений и отказа чтения. Данные и ревизия остаются прежними, а навигация получает следующую порцию без сброса, пропусков и повторов. Отдельные отрицательные проверки сохраняют отклонение старого курсора после предметной команды и сырой записи на том же либо другом физическом соединении, а новое начальное чтение обнаруживает повреждённые ссылки. Проверка соединения `TagNavigationViewModel` с настоящим репозиторием подтверждает сохранение загруженной выдачи без повторной первой порции.

Проверить одиночное назначение вне загруженного префикса, переименование, физическое удаление обязательного и исключённого тегов, одноимённый новый тег, удаление условия из фильтра и массовое согласование при изменениях между его порциями. Нужны случаи частичного, пустого и полностью загруженного результата, сохранение позиции просмотра и отсутствие двойного изменения количества. Проверки производительности фиксируют планы SQL, число чтений и объём материализации на больших локальных данных; они не подменяют поведенческие проверки.

Сохранение позиции просмотра существующей страницы каталога при одиночном и массовом согласовании проверяется во второй фазе виджет-тестом этой страницы. Элементы интерфейса из решения 7 проверяются в третьей фазе: каждый общий элемент — отдельно, подключение — на каждой из четырёх страниц, доступность — на обоих языках при увеличенном тексте и открытой клавиатуре, сценарии спецификаций — сквозными проверками через приложение. Этот документ не утверждает, что реализация или такие проверки уже выполнены.

## Migration Plan

1. Итоговый контракт назначений сверен с результатом `remove-relation-tags` в `main` и записан в Context. Перед подключением интерфейса ветка включает этот результат merge-коммитом без переписывания опубликованной истории, а поведение первых двух фаз переносится на объединённые контракты.
2. Расширить прикладные значения, запросы, краткие данные, идентичность курсора и подтверждённые снимки; затем реализовать единый предикат и пакетное получение тегов в существующем репозитории.
3. Добавить согласование событий тегов, включая чтение недостающей части после массового изменения, и проверить ревизии, количество и загруженную границу.
4. По согласованным требованиям к интерфейсу из решения 7 подключить совместный фильтр и предъявление тегов в четырёх поисках через общий контракт. Выполнить соответствующие проверки поведения, ошибок и доступности.

Новые постоянные поля и таблицы, перенос пользовательских тегов и дополнительная миграция базы этому поиску не требуются. Наборы условий и загруженных идентификаторов передаются параметрами запросов; временные отношения для них не создаются. Объединение сохраняет схему хранения `main`: единственную версию 1 без путей обновления и без назначений связям. Это изменение не добавляет версий схемы и миграций и не дублирует схему и правила удаления назначений из `main`.

Откат прикладных изменений поиска не требует обратного преобразования пользовательских данных. Схема хранения `main` при откате поиска не меняется. Курсоры и состояния запроса остаются данными текущей сессии и не требуют восстановления после перезапуска процесса.

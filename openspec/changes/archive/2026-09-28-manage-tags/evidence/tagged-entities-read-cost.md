# Стоимость смешанной выдачи и редкого архивного охвата, задача 3.5

Измерение 28 сентября 2026 года подтверждает ограниченную материализацию и полный последовательный обход обоих охватов на двух файловых графах. Основной запрос продолжает чтение по индексу назначения; аудит ссылок выполняется один раз за обход неизменного снимка. Избыточных повторных полных проходов и неприемлемой задержки отдельной порции в этой среде не обнаружено.

## Воспроизведение и среда

```sh
mise exec --no-deps -- flutter test test/graph/data/drift_tagged_entities_read_cost_test.dart test/graph/data/drift_tagged_entities_read_test.dart --reporter expanded
```

Команда завершилась с 25 успешными тестами. [Исходные метрики](tagged-entities-read-cost.jsonl) содержат сведения о среде, две фикстуры, 12 полных обходов и 36 замеров первой, средней и последней страниц. Каждая выбранная страница прочитана пять раз, включая чтение при обходе; длительности всех повторений сохранены без усреднения исходных данных.

Среда: Linux 7.0.0-34-generic x86_64, Intel Core i5-9300H 2.40 GHz, 8 логических процессоров, Flutter 3.47.1, Dart 3.13.1, SQLite 3.53.4. Режим — `flutter test`, debug; база — временный файл с журналом `delete`, обычной настройкой соединения приложения и настоящим Drift-репозиторием. Между чтениями кэши не сбрасываются. Подготовка фикстуры, получение планов, инструментированные повторы и проверки ожидаемых результатов исключены из измеренной длительности вызова репозитория.

## Данные и полнота

Фикстура `seedLargeTaggedEntitiesFixture` создаёт два тега, одно непомеченное исходное намерение и пары «намерение / долговременная связь». Назначения обоих видов получателя чередуются по созданию. Между ними вставляются назначения другого тега тем же получателям: они проверяют, что запрос и аудит ограничены выбранным тегом. Архивировано каждое сороковое намерение и каждая двадцатая связь; половина архивных связей имеет активных участников. Активная выдача плотная, архивная занимает около 3,8% назначений выбранного тега.

## Запросы, материализация и планы

Первая порция выполняет четыре SELECT: версию хранилища, точечное чтение тега, аудит ссылок и основную выдачу. Продолжение выполняет три SELECT, без повторного аудита. Транзакционные BEGIN/COMMIT в счётчик SELECT не входят. При `P` порциях и `R` результатах полный обход делает `3P + 1` SELECT и материализует `R + 3P − 1` строк суммарно: результаты, дополнительные строки и две служебные строки на порцию. Аудит исправных ссылок материализует ноль строк, хотя просматривает все назначения выбранного тега.

Основной результат ограничен `pageSize + 1`: максимум 2, 51 или 101 строка соответственно. Число SELECT одинаково для намерений и связей и не зависит от числа строк порции. Во всех перехваченных запросах проверяется отсутствие OFFSET, COUNT, SELECT *, чтения дневных выборов и шагов пути. Точные подсчёты выполняются только один раз для проверки размеров подготовленной фикстуры, вне чтений репозитория и их метрик.

Планы первой, средней и последней страниц сохранены рядом с точным SQL без параметров в JSONL. И основной запрос, и аудит используют `SEARCH a USING INDEX tag_assignments_tag_order (tag_id=?)`; продолжение добавляет `creation_sequence>?`. Получатели и текущие участники связи читаются индексированными JOIN по идентичностям. В планах нет полного сканирования таблицы назначений или временной сортировки. Проверка версии использует виртуальную таблицу `pragma_data_version`; её SCAN не означает загрузку графа.

## Фактическая работа SQLite

Для каждого основного запроса и каждого аудита исполняется копия перехваченного SQL с нейтральной функцией-счётчиком в предикате выбранного тега. Она считает посещённые назначения, включая отсеянные охватом и не возвращённые строки. Планы исходного и инструментированного SQL сравниваются на первой, средней и последней страницах и для каждого аудита. Для каждой страницы число посещений дополнительно сверяется с промежутком между известной границей фикстуры и дополнительной строкой, либо концом назначений.

Счётчик измеряет посещения назначений, а не все инструкции виртуальной машины, обращения к индексам JOIN или физические чтения диска. Время получено на исходном SQL без функции-счётчика: `selectElapsedMicroseconds` измеряет исполнение через Drift и материализацию, `pageElapsedMicroseconds` — весь вызов репозитория, включая транзакцию и строгое декодирование. Инструментированные повторы дополнительно прогревают кэш; это измерение работы на прогретой базе.

При порции 1 дополнительная строка и промежуток до неё повторно просматриваются на следующем запросе; это объясняет почти двукратное число посещений основным запросом. Во всех обходах оно ограничено двумя проходами назначений, а аудит — одним. Иные назначения не посещаются. Порция 1 также увеличивает число транзакций и служебных чтений: полный активный обход большого графа занимает около 19,3 секунды суммарного времени вызовов против 0,67 секунды при порции 50. Это стоимость полного обхода через выбранный размер порции, а не задержка одной страницы.

Малая материализация архивной порции не означает малой работы отбора: для средней страницы размера 100 на большом графе материализуется 101 строка при 2719 просмотренных назначениях. На той же странице активного охвата достаточно 104 посещений. Медиана времени основного архивного SELECT составляет 2,74 мс против 0,68 мс активного; медиана всего вызова — 3,52 мс против 1,46 мс. Первая архивная страница размера 50 посещает 1322 назначения ради 51 строки, а средняя порция размера 1 — 79 ради двух.

## Задержки и границы вывода

Аудит при росте выбранных назначений с 10 006 до 30 006 увеличивается с примерно 10,2 до 34,8 мс по медианам повторных чтений. Первая страница большого графа имеет медиану 35,3–38,4 мс в зависимости от охвата и размера; максимальное значение среди всех 180 замеров страниц — 39,90 мс. Продолжения выполняют только точечное чтение тега, проверку версии и ограниченный основной запрос; максимальный замер продолжения — 6,06 мс.

Для этих файлов и среды стоимость отдельной порции приемлема: повторного полного аудита, N+1, OFFSET и избыточной сортировки не выявлено, поэтому изменение продуктового запроса не потребовалось. Тест защищает ограниченность материализации, число запросов, индексируемое продолжение и фактическую работу при полном обходе; нестабильные пороги времени в автоматизированные проверки не добавлены.

Вывод ограничен распределением и размерами этих фикстур, прогретой файловой базой и debug-средой Linux. При более редком или неравномерном архиве запрос может пройти значительно больше назначений ради одной порции, вплоть до всех оставшихся назначений выбранного тега. Постоянное время SQL, результаты реального Android-устройства, стоимость кадров, пригодность пользовательской прокрутки и холодное чтение диска этим свидетельством не установлены. Проверка интерфейса относится к задаче 3.16.

Измерения выполнены 27 сентября 2026 года на Linux x64, Dart 3.13.1, SQLite 3.53.4, в режиме debug и файловой базе с журналом `delete`. Фикстуры содержат 203 или 1203 тега и соответственно 170 или 1003 назначения. Намерению назначен каждый второй тег, долговременной связи — каждый третий. Полный машинный вывод обходов находится в [JSONL](assignment-reference-check-cost.jsonl). Длительности зависят от среды и не служат порогом приёмки.

## Фактическая работа проверки

Тест перехватывает SQL каждого чтения. Для запроса отсутствующих тегов он исполняет копию с нейтральной функцией-счётчиком на каждой проверяемой строке назначения. `EXPLAIN QUERY PLAN` исходного и инструментированного запросов совпадает; счётчик измеряет просмотренные строки, включая те, которые не возвращаются результатом. Это не счётчик всех инструкций SQLite. Проверка существования получателя и основной запрос учитываются отдельно. Один полный проход выполняется на первой порции; продолжения без изменения хранилища его не повторяют.

План проверки использует покрывающий индекс назначений по виду получателя и индекс идентичности тега. На продолжениях остаются чтение версии хранилища, проверка существования получателя и основной запрос. Планы основного запроса назначений всё ещё показывают временную сортировку; её устранение относится к задаче 2.28. Основной запрос выбора идёт по последовательности создания тегов и индексированному `EXISTS`. Эти затраты не включены в число просмотренных строк проверки ссылок.

Тесты поведения отдельно подтверждают отказ при отсутствующем теге за пределами первой порции и при повреждении между порциями для обоих видов получателя и обоих чтений. При изменившемся хранилище продолжение заново проверяет ссылки: повреждение возвращается как повреждение, исправные изменившиеся данные — как истёкший снимок. Обычный проход использует курсор только при неизменной ревизии и неизменных счётчиках SQLite.

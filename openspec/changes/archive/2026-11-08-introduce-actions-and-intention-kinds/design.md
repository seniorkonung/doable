## Context

Изменение заменяет дневные выборы действиями и вводит вид намерения с каскадным архивированием, удалением и восстановлением (`proposal.md`, спеки `action-management`, `action-paths`, `intention-cascade` и дельты остальных возможностей).

Сейчас приложение — один Flutter-процесс с личным графом в одной базе Drift/SQLite (ADR 0002, 0009). Все изменения графа проходят через `GraphCommandCoordinator` и выполняются в `_writeGraph` одной транзакцией с захватом фактов триггерами (ADR 0034) и одной ревизией графа. Чтения идут через контракты, собранные в `PersonalGraphRepository`. Статистика использует снимок связей, который строится вне очереди записи (ADR 0026, 0027). Каталог и поиски для выбора строятся одним модулем поиска (ADR 0049). Формат данных — предметный формат версии 1 (ADR 0035), замена графа атомарна (ADR 0036).

Дневной выбор занимает модуль `lib/src/daily_choice/` (около 60 файлов). Путь хранится цепочкой шагов `daily_choice_path_steps`, каждый ссылается на связь с `ON DELETE RESTRICT`, поэтому путь блокирует удаление связей, а дневной выбор — удаление намерений. Готовность к действию — столбец `intentions.is_action_ready`. `CalendarDate` и наблюдатель местного дня живут внутри `daily_choice`, хотя их импортируют статистика, формат данных, перенос данных и страница намерения.

Ограничения:

- Данные не переносятся: новая базовая версия схемы без миграции, как прежние сбросы до публикации; это решение только этого изменения.
- Профиль нагрузки — до 50 000 намерений и 150 000 связей с циклами (ADR 0005, 0026); время измеряется только бенчмарками.
- Один процесс и одна очередь записи; будущая синхронизация (ADR 0038) применяет чужие факты, проверяя только постоянные инварианты.

## Goals / Non-Goals

**Goals:**

- Модуль действий вместо модуля дневных выборов с общими типами даты и местного дня в общем модуле.
- Путь как последовательность намерений, который не блокирует удаление и показывает удалённое таким, каким оно было при удалении, без перезаписи действий.
- Вид намерения, удержание и один планировщик каскада для предпросмотра и исполнения с проверкой конфликта по выбранному варианту.
- Новая базовая схема и новый состав формата данных, журнала фактов, снимков и резервных копий.
- Статистика действий по ролям в сохранённом пути.
- Лист нового действия, экран пути, второй черновик и вопрос перед сбросом истории.
- Удаление кода, строк и тестов дневных выборов и готовности к действию.

**Non-Goals:**

- Дублирование действия, множественное выделение, лимит плана, синхронизация, поиск по действиям.
- Перенос старых данных и чтение файлов экспорта прежних сборок.

## Decisions

### D1. Модуль действий и общие типы

Новый модуль `lib/src/action/` со слоями `domain`, `application`, `presentation` заменяет `lib/src/daily_choice/`. `CalendarDate` переходит в `lib/src/shared/domain/`, наблюдатель и поставщик местного дня — в `lib/src/shared/presentation/local_day/`. Контракты каскада живут в `lib/src/intention/application/cascade/`: им пользуются и намерения, и связи, а модуль связей уже зависит от предметной области намерений. Чтения действий собираются в `ActionReadContract`, который подмешивается в `PersonalGraphRepository`, как контракты тегов и статистики. Отдельного репозитория действий нет: проверка пути, каскад и надгробия должны выполняться в той же транзакции, что и изменения графа (ADR 0009).

Альтернативы: переименовать модуль на месте и оставить `CalendarDate` в нём — статистика продолжила бы зависеть от модуля возможности ради типа даты; выделить ещё и модуль пути — шов с единственным потребителем.

Облегчённая C4-схема компонентов внутри приложения (`action` — действия, `intention/cascade` — каскад, `holding index` — индекс удержания, `tombstones` — надгробия удалённых звеньев):

|                             Doable (Flutter app)                           |
|                                                                            |
|  +---------------------+  +------------------------+  +----------------+  |
|  | action/presentation |  | intention/presentation |  | statistics/    |  |
|  | day, panel, sheet,  |  | catalog, page, kind,   |  | presentation   |  |
|  | path screen, tab    |  | cascade dialogs        |  +----------------+  |
|  +---------------------+  +------------------------+          |           |
|        | commands, reads        | commands, preview          | reads       |
|        v                        v                            v             |
|  +----------------------------------------------------------------------+  |
|  | graph/application: GraphCommandCoordinator, PersonalGraphRepository   |  |

|        | one write queue, one transaction per command                      |
|        v                                                                   |
|  +----------------------------------------------------------------------+  |
|  | graph/data (Drift adapter)                                            |  |
|  |  +------------------+  +----------------+  +------------------------+ |  |
|  |  | command bodies   |  | cascade planner|  | holding index          | |  |
|  |  | (_writeGraph)    |->| (pure Dart)    |<-| (per revision, isolate)| |  |
|  |  +------------------+  +----------------+  +------------------------+ |  |

- Направление зависимостей прежнее: представление → контракты приложения → адаптер данных; `shared` не зависит ни от чего.
- Модуль действий зависит от идентификаторов намерений и общих типов, но не от модуля связей: звено пути — пара соседних намерений, а не идентификатор связи.
- Планировщик каскада и индекс удержания — внутренние части адаптера данных; наружу выходят предпросмотр, команды и отметки удержания.

### D2. Действие и путь в хранилище

Таблица `actions` хранит действие: `creation_sequence` (автоинкремент, порядок создания по ADR 0010), уникальный `id`, название, описание, дату, час `0..23` или `NULL` для «Весь день», приоритет `1..4`, выполнение и показания времени создания и изменения. Таблица `action_path_items(action_id, position, intention_id, previous_intention_id)` хранит путь: первичный ключ `(action_id, position)`, уникальность `(action_id, intention_id)` запрещает повторы, индексы `(intention_id, action_id)` для поиска строк намерения и `(previous_intention_id, intention_id)` для звеньев. Внешних ключей на намерения и связи нет; `previous_intention_id` делает пару звена локальной для строки. Удаление действия каскадно удаляет его строки пути.

Роли следуют из позиций: корневое — `position = 0`, конечное — нет строки на `position + 1`, промежуточные — остальные; путь из одного намерения даёт и корневое, и конечное. Строка пути хранит свою роль: «корневое», «промежуточное», «конечное» или «единственное» для пути из одного намерения, которое попадает и в список «Корневое», и в список «Конечное». Путь перезаписывается целиком только при сохранении нового пути, поэтому роль строки не меняется; её задаёт пишущий путь по длине пути, а триггер вставки отклоняет роль, не согласованную с позицией и ролью предыдущей позиции.

Строка пути хранит и копию ключа порядка своего действия: дату, час или `-1` для «Весь день» и `creation_sequence`. Индекс `(intention_id, роль, дата DESC, час DESC, creation_sequence DESC)` отдаёт строки роли намерения в порядке списка вкладки «Действия» и находит продолжение по курсору без сортировки и без прохода по остальным строкам намерения (D10). Триггер вставки отклоняет копию, не совпадающую с действием; триггер `AFTER UPDATE OF date, scheduled_hour` на `actions` переписывает копии в строках пути действия, а триггер неизменности строк пути разрешает менять только скопированные столбцы. Роль и копия — производные данные хранилища: формат данных и факты журнала их не содержат, а изменение копии отмечается изменением самого действия. Схема меняется внутри базовой версии 8 без миграции (D14).

Альтернатива — цепочка шагов со ссылками на связи, как у дневного выбора, — противоречит идентичности пути по последовательности намерений и снова требует блокировок удаления.

### D3. Удалённые звенья — общие надгробия

Запись: ADR 0055.

Удалённое хранится один раз на всё приложение, а не в каждом пути. `deleted_intentions(intention_id, title)` хранит название удалённого намерения, `deleted_relation_pairs(source, related, type)` — тип удалённой связи пары. Триггеры поддерживают их без участия команд:

- после удаления намерения (`AFTER DELETE`, по значениям `OLD`) создаётся его надгробие, если на намерение ссылается хоть одна строка пути;
- после удаления связи (`AFTER DELETE`, по значениям `OLD`) обычной вставкой создаётся надгробие пары, если пара встречается как звено пути; конфликта с прежним надгробием пары нет, потому что по следующему правилу у пары есть либо связь, либо надгробие;
- после создания связи надгробие её пары удаляется: у пары либо есть строка связи, либо надгробие, поэтому заново созданная связь снимает разрыв, а архивная показывается как разрыв «В архиве» с её текущими данными;
- после удаления строк пути удаляются надгробия, на которые больше никто не ссылается;
- триггеры отклоняют строку пути, чьё намерение не найдено ни среди намерений, ни среди надгробий, и надгробие существующей сущности; надгробия создаются после удаления, поэтому это правило их не отклоняет.

Показ пути берёт текущие данные существующих намерений и связей и данные надгробий для удалённых. Удаление намерения из K путей пишет один факт надгробия и ни одного факта действий, поэтому резервные копии не считают такие действия изменёнными (решение по `graph-backups`) и синхронизация не получает лавину фактов.

Альтернативы: записывать данные удалённого в строки каждого пути — K перезаписей и K фактов действий на одно удаление, ложные «изменённые» действия в копиях и повторная лавина при пересоздании связи; реестр узлов пути — дублирует намерения и не даёт целостности сверх надгробий.

### D4. Вид намерения и его инвариант

`intentions.kind` хранит `main` или `supporting` (`NOT NULL`, по умолчанию `main`, `CHECK`) и отображается в перечисление Dart вместо `is_action_ready`. Инвариант «у активного вспомогательного есть активная входящая связь» проверяется в транзакции каждой команды, которая может его нарушить, по затронутым намерениям; выразить его `CHECK` или триггером нельзя, а полный обход на каждую запись слишком дорог. Смена вида, в том числе превращение в главное по «только это» и восстановление главным, обновляет показание времени изменения. В формате поле называется `intentionKind`: имя `kind` уже различает виды записей.

`AddLongTermRelations` получает кандидатов с признаком «стать вспомогательным при создании связи», поэтому намерение, созданное в поиске участника, становится вспомогательным в той же транзакции, что и связь.

### D5. Индекс удержания

Запись: ADR 0056.

Удержание вычисляет индекс, который строится на ревизию графа вне очереди записи и вне потока интерфейса, по образцу снимка связей статистики (ADR 0026). Индекс держит компактную смежность всех связей с признаком архива, вид и архивное состояние намерений и множество удерживаемых: обход в ширину от всех активных главных по активным связям через вспомогательные. Индекс сбрасывается изменениями связей, смены вида и архивирования, восстановления и удаления намерений; создание, изменение и удаление действий его не трогают. Каталог и поиски для выбора, пока видимы, перечитывают отметки загруженных вспомогательных строк после каждой такой ревизии (образец ADR 0024, 0027).

Отметка удержания — закрытый тип: удерживается, не удерживается или ещё вычисляется. Пока индекс для текущей ревизии строится, вспомогательная строка показывает обычную отметку вида без красного состояния: ложная красная отметка хуже короткой задержки.

Альтернативы: рекурсивный запрос на страницу — неограниченная стоимость на допустимых неудерживаемых циклах и работа внутри очереди записи; хранимый признак удержания — запись в `intentions` на каждое изменение удержания с фактами, сменой времени изменения и переиндексацией названий, а уменьшение достижимости в циклах всё равно требует полного пересчёта.

### D6. Один планировщик каскада

Состав каскада вычисляет чистая функция Dart над индексом удержания; её используют и предпросмотр, и исполнение. Для элемента X:

- D — вспомогательные ниже X: при архивировании по активным связям и намерениям, при удалении — и по архивным;
- удержание намерений вне D не меняется, поэтому удерживаемые внутри D находятся обходом внутри D от намерений с входящей связью от главного или от удерживаемого намерения вне D, не через X;
- уходят X и неудерживаемые из D; при «только это» непосредственные дочерние X среди уходящих становятся главными, остальное остаётся;
- при удалении второй проход по графу после удаления находит активные вспомогательные без активной входящей связи и архивирует их вместе со всем ниже, что не удерживают активные главные;
- восстановление идёт вниз по архивным связям через архивные вспомогательные и останавливается на главных и активных намерениях; восстановленное без активного намерения выше становится главным.

Порядок списков для показа — обход в глубину от элемента по порядку связей (сначала «нужно», затем приоритет, затем порядок создания), как требует `intention-cascade`.

### D7. Предпросмотр, выбор и проверка конфликта

Запись: ADR 0057.

Предпросмотр — отдельное чтение `previewCascade(subject, operation)`, где субъект — намерение или связь, а операция — архивирование, удаление или восстановление. Оно возвращает составы обоих вариантов и признак, нужен ли вопрос; отказ чтения отличим от «каскада нет». Подсказки пунктов меню намерения и связи используют то же чтение. Предпросмотр удаления намерения на той же ревизии возвращает и признак участия намерения хотя бы в одном сохранённом пути действия: по нему пояснение под «Удалить» без каскада выбирает между пометкой «Удалено» в путях и сохранением тегов. Признак читает проверка существования по индексу `action_path_items_intention_action`, а не страница вкладки «Действия». Отвергнут признак в данных страницы намерения с реактивным обновлением. Команды архивирования, удаления и восстановления намерения и связи получают обязательный `CascadeExecution(choice, expected)`, поэтому команда без вычисленного состава непредставима. Для операции без вопроса `expected` — состав, вычисленный при её запуске.

В `_writeGraph` тот же планировщик пересчитывает выбранный вариант по текущему состоянию. Сравниваются множества идентификаторов намерений выбранного варианта: уходящие, ставшие главными, архивируемые по инварианту, восстанавливаемые. Порядок показа и число связей не сравниваются: они производны и дали бы ложные конфликты. При расхождении команда завершается конфликтом без записи, а следующая попытка снова читает предпросмотр.

Отказ чтения предпросмотра на странице намерения — отказ самой операции архивирования, восстановления или удаления. Координатор принимает такую операцию сразу завершённой типизированным отказом предпросмотра, отличимым от отказов хранилища, и не запускает команду. Завершение проходит прежний протокол предъявления ADR 0012, ADR 0016 и ADR 0023 с политикой этой операции. Отвергнуты приём операции координатором до чтения предпросмотра и показ отказа на самой странице: второе противоречит требованию «Независимость принятой операции с намерением от экрана». Панель связи показывает отказ чтения внутри себя с «Повторить».

Альтернативы: ответ «нужно решение» из самой команды — вносит незавершённый результат в канал координатора; защита по ревизии графа — даёт конфликт на любое постороннее изменение вопреки сценарию «Изменение, не затрагивающее выбранный вариант, не вызывает конфликта».

  |                   |                     |                       |

  |    (lists, choice)|                     |                       |

### D8. Исполнение каскада, факты и изменения графа

Тело команды пишет в фиксированном порядке, которого требуют существующие триггеры: при удалении — связи до намерений, при архивировании — связи до намерений, при восстановлении — намерения до связей; списки идентификаторов делятся на части под предел переменных SQLite. После записи проверяется инвариант вида по затронутым намерениям. Факты пишут триггеры захвата по одному на изменённую строку, включая надгробия.

Пакет изменения несёт `LongTermRelationChange` на каждую затронутую связь (иначе снимок связей статистики не сбросится), мутацию каталога на каждое затронутое намерение, абсолютные количества связей каждого затронутого намерения по ADR 0011 и 0043, `IntentionHoldingChanged` для индекса удержания и `CascadeOutcome` для сообщения (ADR 0057). Количества получаются одним пакетным агрегатом по идентификаторам; если бенчмарк крупного каскада покажет, что это выходит за бюджет, способ согласования счётчиков пересматривается отдельной записью. Триггер полнотекстового индекса названий сужается до `UPDATE OF title`: каскад меняет состояние и вид многих намерений, и каждая такая запись сейчас без нужды переиндексирует название.

Политика представления результата зависит от исхода: архивирование и восстановление показывают сообщение, только если исход затронул другие намерения или вернул элемент главным; удаление показывает всегда; тексты собирает представитель результатов из `CascadeOutcome` (ADR 0012, 0023).

### D9. Команды действий и вида

- `CreateAction(title, description, path, date, schedule, priority)` создаёт невыполненное действие; `UpdateActionFields(id, patch)`, `SetActionPath(id, path)`, `DeleteAction(id)`.
- Путь команды — непустая последовательность различных идентификаторов намерений. Транзакция проверяет, что все намерения активны и каждая соседняя пара соединена активной связью; иначе — `ActionPathConflictFailure` без записи, и поля остаются в листе.
- Создание и удаление объявляются по общим правилам; изменение полей, пути и выполнения успех не объявляют (ADR 0016, 0046).
- Лист держит один ключ формы на сессию; ключ освобождается по завершении, поэтому открытый лист создаёт следующие действия.
- `ChangeIntentionKind(id, kind)` заменяет команды готовности; результат несёт `IntentionHoldingChanged`.

### D10. Модели чтения

- **День.** `ActionDayQuery(date, section)` сохраняет секции и снимок дня на одной ревизии (ADR 0033); строка получает корень и длину пути поиском по первичному ключу строк пути.
- **Отметки календаря.** Агрегат по `actions(date, is_completed)` в отдельной модели окна календаря (ADR 0024, 0025).
- **Панель действия.** `watchAction(id)` отдаёт поля и сохранённый путь с текущими данными и надгробиями; перечитывается на своё изменение и на изменения намерений и связей из последнего прочитанного пути.
- **Вкладка «Действия».** `getIntentionActionsPage(intentionId, role, pageSize, cursor)`: первая страница возвращает счётчики ролей и строки на одной ревизии; загруженная часть согласуется с изменениями действий и корней строк. Порция и продолжение читают строки роли по индексу роли с копией ключа порядка (D2), а курсор сравнивает эту копию; списки «Корневое» и «Конечное» сливают упорядоченные диапазоны своей роли и роли «единственное». План запроса не строит временного B-дерева, и работа порции ограничена её размером, а не числом действий намерения; только числа ролей первой страницы проходят все строки пути намерения. Бенчмарк на профиле статистики, где одно намерение входит в пути до 60 действий в день за несколько лет, держит p95 продолжения в глубине списка в пределах 10 мс, а первой страницы вместе с числами ролей — в пределах 200 мс: чтение идёт в общей очереди с записями графа, как пересчёт статистики месяца с тем же бюджетом очереди.
- **Кандидаты пути.** `getPathCandidates(draft, half, pageSize, cursor)` возвращает целый начальный участок черновика, точные числа обеих половин без намерений пути и первую порцию; продолжение привязано к ревизии. Загрузка, отказ и пустая половина различимы.
- **Каталог и поиски.** Фильтр и счётчики вида заменяют фильтр готовности; назначения `dailyChoiceAction` и `dailyChoiceSource` заменяет `pathStart`, которое переиспользует создание намерения из поиска и выбирает созданное корнем.

### D11. Лист нового действия — маршрут с сессией

Запись: ADR 0058.

Лист — прозрачный маршрут `ActionEditorRoute` над корневым навигатором (образец ADR 0018, 0032), а не лист без маршрута. Каждое открытие — плюс, кнопка пустого дня, «Добавить» на вкладке — создаёт свою сессию черновика с собственным ключом (ADR 0028), поэтому второй лист поверх страницы из поиска не трогает первый. Сессия переходит «ввод → создание → ввод с очищенными названием и описанием»; завершающего состояния нет, поздний результат только согласует данные и сообщение. Закрытие при непустых названии или описании и без идущего создания спрашивает «Отменить новое действие?».

Сброс истории пунктом нижней панели перехватывается в `AppNavigation.onSelected`: он просматривает стек корневого маршрутизатора, находит сессии `ActionEditorRoute` и один раз спрашивает, если хоть в одной введён текст. Одна точка покрывает панель оболочки и панели обычных страниц.

Альтернатива — лист без маршрута, как панель действия (ADR 0054): стек маршрутизатора его не видит, и перехват сброса потребовал бы отдельного глобального реестра сессий.

### D12. Экран пути

Запись: ADR 0059.

`PathRoute` — страница-задача без нижней панели в двух назначениях: для нового действия возвращает путь в лист; для существующего действия сам выполняет `SetActionPath`, закрывается при успехе и показывает отказ на экране. Уход во время выполняющейся замены закрывает экран без вопроса, не отменяя её: успех панель получает обычным согласованием данных, а отказ показывает общая поверхность результатов. Последнее отступает от правила ADR 0022 «результат возвращается вызывающему»: иначе отказ появился бы в панели, куда человек ещё не вернулся. Изменённый путь спрашивает «Отменить изменения?» при уходе. Кандидаты перечитываются после подтверждённых изменений намерений и связей, а черновик обрезается перед звеном, ставшим разрывом.

### D13. Быстрое создание и навигация

`QuickCreationMode.dailyChoice` становится `action` с ключом `action` без старого синонима: после очистки данных старого ключа нет, а неизвестный ключ уже приводит к «Новое намерение». Стартовый лист «От намерения / От действия» удаляется, режим открывает `ActionEditorRoute`. `AppDestination.dailyChoices` становится `actions`.

### D14. Базовая схема и состав формата

Версия схемы 7 сменяется базовой версией 8 без миграции (образец коммита `a62d625d`): `daily_choice_schema.drift` заменяет `action_schema.drift`, снимок схемы `drift_schemas/` заменяется, проверка `mise run codegen-check` следит за сгенерированным. Все `INDEXED BY` с именами индексов дневных выборов переписываются и покрываются проверками плана запросов, как существующие `*_read_cost_test.dart`. Полнотекстовый поиск по действиям не нужен: ни одна спека его не требует.

Версия формата остаётся 1 с новым составом: до публикации номер не повышается (ADR 0035), а функции обновления для прежнего состава нет. Разделы идут так, чтобы каждая запись ссылалась только на предыдущие: теги, намерения, надгробия намерений, назначения тегов, связи, надгробия пар, действия с путями. Заголовок перечисляет счётчики всех разделов. Файл прежней сборки отклоняется при чтении заголовка или первой несовместимой записи существующим отказом «не экспорт Doable или повреждён». Замена графа (ADR 0036) удаляет и вставляет те же разделы; сводка экспорта не считает надгробия. Предел записи 1 МиБ вмещает путь примерно из 26 000 намерений, поэтому ограничения длины пути не вводится.

### D15. Статистика действий

Запись: ADR 0060.

Корневые, промежуточные и конечные намерения считаются запросами по позициям строк пути; соединение с `intentions` исключает удалённые. Для вида «Через связи» начальными точками действия служат существующие намерения его пути, обход идёт по снимку текущих активных связей (ADR 0026). Снимок по-прежнему сбрасывают только изменения связей, включая связи из каскадов; смена вида на достижимость не влияет.

### D16. Дизайн-система

Компоненты `ChoiceCheck`, `ChoiceHead`, `ChoiceRow` становятся `ActionCheck`, `ActionHead`, `ActionRow`; `ChoicePath` переписывается в `ActionPath`: строки намерений, конечное выделено, действие не рисуется, удалённые строки не нажимаются. Без изменений переиспользуются `ReasonChain`, `PathGlyph`, `RelationRow`, `PickerRow`, `PriorityPicker`, `ActionSheet`, `OptionRow`, `TimeDial`, `DateGrid`, календарь, `FlowSteps`, `Tabs`, `CountTiles`, `Badge`. Новые: `SegmentedControl`, `PathBrief`, `ValueChip`, `PathAction`, `StepOption`, `PathBuilder`. Компоненты остаются презентационными (ADR 0030); свойства выделения из дизайна не добавляются.

### D17. Что удаляется

Модуль `daily_choice` целиком, включая поиски действия и исходного намерения, построение снизу вверх, страницу создания, поток создания и шаги пути; команды, столбец и интерфейс готовности; блокировки удаления (`_hasBlockingRelations`, `IntentionHasBlockingRelationsFailure`, `LongTermRelationReferencedByDailyPathFailure`, `LongTermRelationPermissions`); группы связей дневных выборов и их счётчики; стартовый лист быстрого создания; маршруты дневных выборов; строки локализации и события диагностики дневных выборов и готовности; тесты, фикстуры и бенчмарки старой схемы.

## Risks / Trade-offs

- [Первое построение индекса удержания на большом графе задерживает отметки и предпросмотр каскада] -> Бенчмарк построения и обновления индекса на 50 000 намерениях и 150 000 связях; закрытое состояние «вычисляется» без ложных красных отметок; при недостаточной скорости — инкрементальное обновление индекса по списку изменений, как в ADR 0026.
- [Очень большой каскад даёт большой пакет фактов и длинный список мутаций каталога] -> Бенчмарк каскада на крупном подграфе; при превышении бюджета — изменение «перечитать каталог» вместо списка мутаций.
- [Каскад затрагивает намерения, которые координатор не резервирует] -> Корректность держится на единственной очереди записи и сравнении состава в транзакции; тесты на одновременные операции из `intention-cascade` и `long-term-relation-management`.
- [Триггеры надгробий и путей усложняют схему] -> Тесты схемы на каждое правило триггеров и на отклонение неверных строк, как у существующих схемных тестов.
- [Объём переписывания тестов, фикстур и строк] -> Фазы плана отделяют модель данных, потоки действий, каскад и статистику, чтобы каждая фаза заканчивалась проверками.
- [Синхронизация (ADR 0038) должна проверять целостность надгробий и не может проверить удержание как постоянный инвариант] -> Вне объёма; ADR 0038 получает пересмотр списка инвариантов, решение о согласовании вида между устройствами остаётся за изменением синхронизации.

## Migration Plan

- Сборка с базовой версией схемы 8 на устройстве с версией 7 показывает существующее состояние повреждённых локальных данных; README объясняет, что перед установкой нужно очистить данные приложения, и что перенос не предусмотрен.
- Файлы экспорта прежних сборок отклоняются как повреждённые; импортировать можно только файлы новой сборки.
- Откат: прежняя сборка не открывает версию 8, поэтому откат тоже требует очистки данных и теряет созданное новой сборкой.
- Решение действует только для этого изменения, пока у приложения нет опубликованных установок.

## Open Questions

Блокирующих вопросов нет. Согласование вида и удержания между устройствами при синхронизации решается в изменении синхронизации.

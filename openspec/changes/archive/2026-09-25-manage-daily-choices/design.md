## Context

Изменение реализует датированный выбор действия с сохранённым основанием согласно [proposal](proposal.md) и спецификациям [дневного выбора](specs/daily-choice-management/spec.md), [намерений](specs/intention-management/spec.md) и [долговременных связей](specs/long-term-relation-management/spec.md). Термины используются в смысле [CONTEXT.md](../../../CONTEXT.md): связь «я сегодня» самостоятельна, путь сохраняет ссылки на долговременные связи, а выполнение относится только к дневному выбору.

Сейчас Flutter-приложение хранит намерения и долговременные связи в локальной Drift/SQLite-базе версии 2. `PersonalGraphRepository` владеет чтениями и изменениями всего личного графа; `DriftPersonalGraphRepository` последовательно исполняет транзакции и присваивает подтверждённым изменениям общую `GraphRevision`. `GraphCommandCoordinator` удерживает принятые операции независимо от экрана, а `GraphOperationPresenter` однократно предъявляет результат. Эти границы уже закреплены в [ADR-0009](../../../docs/adr/0009-unify-personal-graph-module-and-revision.md) и [ADR-0012](../../../docs/adr/0012-centralize-graph-operation-result-presentation.md).

Новая возможность затрагивает не только отдельные экраны: шаги пути изменяют допустимость удаления и редактирования существующего графа. Пользователю нужны достоверное основание выбора и сохранность данных; разработчику — одна проверяемая граница согласования всех операций. Действуют прежние ограничения одной установки, bootstrap, миграций и резервного копирования из [local-data-lifecycle](../../specs/local-data-lifecycle/spec.md). Новые внешние зависимости не требуются.

## Goals / Non-Goals

**Цели:**

- Построение пути в обоих направлениях, повтор прежнего маршрута и сохранение ровно подтверждённой цепочки.
- Каталог, полный просмотр, независимое изменение полей, атомарная замена пути и подтверждённое удаление дневного выбора.
- Общие транзакционные гарантии дневных выборов, намерений, долговременных связей и массового удаления зависимостей.
- Сохранность существующего графа при обновлении, проверка читаемых данных, доступный интерфейс на русском и английском и безопасная диагностика.

**Вне области изменения:**

- Общее исследование графа, новый общий поиск, управление тегами, автоматическое построение выбранного маршрута и рекомендации действий по содержимому.
- Синхронизация, импорт, экспорт, удалённое хранение и восстановление после утраты установки.
- История названий, версий пути или переключений выполнения; приоритет, теги и архивирование дневного выбора.
- Автоматическое изменение готовности, создание намерений, завершение намерения или перенос невыполненного выбора на другую дату.

## Decisions

### 1. Дневной выбор расширяет единый модуль личного графа

Типы и представления дневного выбора размещаются в `lib/src/daily_choice/{domain,application,presentation}`. Публичной границей чтений и команд остаётся `PersonalGraphRepository`; реализация транзакций, проверок зависимостей и согласования находится за ней в `lib/src/graph/data`. Схема и миграции принадлежат `lib/src/data/local`. Отдельный репозиторий дневных выборов и второй канал записи не вводятся.

Облегчённая C4-схема компонентов показывает целевое устройство внутри одного приложения. `DailyChoiceUI` и операции дневного выбора — новые части; остальные компоненты существуют и расширяются.

```text
+---------------- Flutter application ----------------------+
|                                                           |
|  +------------------+       +-------------------------+   |
|  | DailyChoiceUI    |       | Intention / Relation UI |   |
|  | Pages, ViewModels|       | Pages, ViewModels       |   |
|  +------------------+       +-------------------------+   |
|           | commands                    | commands        |
|           +--------------+--------------+                 |
|                          v                                |
|              +-------------------------+                  |
|              | GraphCommandCoordinator |---- results --+  |
|              +-------------------------+               |  |
|                          | execute                     v  |
|                          v                         +-----+|
|  UI ---- reads --> +-------------------------+      | GOP ||
|                   | PersonalGraphRepository |      +-----+|
|                   | Drift adapter           |             |
|                   | Validation, sequencer   |             |
|                   +-------------------------+             |
|                          | transactions                   |
|                          v                                |
|                   +-------------------------+             |
|                   | AppDatabase             |             |
|                   | Drift / SQLite          |             |
|                   +-------------------------+             |
+--------------------------|--------------------------------+
                           v
                 +--------------------+
                 | Local SQLite file  |
                 +--------------------+
```

- `DailyChoiceUI` — экраны и модели представления дневного выбора. Их черновики не изменяют граф до подтверждения.
- `PersonalGraphRepository` — единый владелец предметных проверок и подтверждённых снимков. Drift adapter является его реализацией, а не дополнительной публичной границей.
- `GOP` обозначает существующий `GraphOperationPresenter`: он использует общий протокол предъявления результатов, включая передачу ошибки от исчезнувшего экрана оболочке.
- Предполагается прежняя модель одного живого экземпляра репозитория и поддерживаемой записи только через него. SQLite-файл — локальное хранилище, отдельного сервера нет.

Альтернатива с независимыми репозиториями потребовала бы ещё одного владельца общих транзакций и ревизий. Проверки только в интерфейсе не защищают операции, пересекающиеся с изменением графа.

### 2. Структурно корректный путь и допустимый новый выбор — разные состояния

Добавляются отдельные UUID-типы `DailyChoiceId` и `ChoicePathStepId` по существующему подходу к идентификаторам. `DailyChoice` содержит идентификатор, исходное и выбранное намерения, `CalendarDate`, описание и выполнение. Проверенный путь содержит непустую неизменяемую цепочку шагов. Шаг хранит только собственный идентификатор, владельца, `LongTermRelationId` и необязательный идентификатор предыдущего шага; намерения и отображаемый текст в него не копируются.

`CalendarDate` представляет год, месяц и день григорианского календаря в диапазоне 0001–9999 с проверкой реального числа дней и високосного года. Это техническая граница календарного ввода, а не ограничение относительно текущего дня. Значение сохраняется как каноническое `YYYY-MM-DD` и не преобразуется через UTC, epoch или часовой пояс. Интерфейс может предложить текущую локальную дату, но передаёт в команду явно показанное календарное значение. Смена зоны не меняет его. Выполнение — обязательное значение команды создания; новая форма начинает с выключенной отметки. Времени переключения и истории нет.

Для описания используется отдельный тип с существующими правилами пользовательского текста: сначала корректный Unicode без `U+0000`, затем определение отсутствующего значения и предел 4096 расширенных графемных кластеров. Непробельный текст сохраняется целиком. Ошибка поля оставляет исходный ввод в форме. При чтении недопустимое сохранённое значение становится повреждением, а не нормализуется повторно.

Внутренний проверяющий модуль различает:

| Проверка | Где применяется | Что проверяет |
| --- | --- | --- |
| Целостность сохранённого пути | Чтение и изменение существующего выбора | Все ссылки, один владелец, единственный первый шаг, непрерывная цепочка без ветвлений, циклов и лишних шагов, согласованные границы, отсутствие повторных намерений |
| Допустимость нового пути | Создание, повтор, полная замена | Целостность плюс существование и активность всех намерений и связей и готовность конечного намерения |
| Соответствие подтверждённому смыслу | Создание, повтор, полная замена | Те же идентификаторы, направление, участники и тип каждой показанной долговременной связи |

Черновик обхода — закрытые варианты «сверху вниз» и «снизу вверх», допускающие ноль переходов. Подтверждаемое предложение пути создаётся только после хотя бы одного перехода. Оно содержит упорядоченные ссылки и ожидаемые тройки «исходное намерение, тип, связанное намерение» каждой связи. Эти данные живут в памяти в рамках подтверждения и не становятся снимком в сохранённом пути.

Альтернатива с одним признаком `valid` смешала бы повреждение с допустимым архивированием. Передача только идентификаторов связей позволила бы незаметно сохранить новый тип связи, изменённый после показа формы. Использование `DateTime` как даты хранения создало бы лишнюю зависимость от времени и зоны.

### 3. Путь хранится в отдельных строках с ограничениями ссылок

Версия схемы повышается с 2 до 3. Добавляются две таблицы:

| Таблица | Основные поля и назначение |
| --- | --- |
| `daily_choices` | Неизменяемый уникальный `id`, техническая `creation_sequence INTEGER PRIMARY KEY AUTOINCREMENT`, `source_intention_id`, `selected_intention_id`, `choice_date`, `description`, `is_completed` |
| `daily_choice_path_steps` | `id`, `daily_choice_id`, `long_term_relation_id`, допускающий NULL `previous_step_id` |

Последовательность создания нужна для устойчивого порядка и отбора недавних записей; она не является временем выполнения или ревизией графа. Уникальность даты, участников и маршрута не вводится. Идентичность и последовательность создания дневной связи защищаются от изменения.

Ограничения схемы:

- Оба прямых участника ссылаются на `intentions` с `ON DELETE RESTRICT` и `ON UPDATE RESTRICT`; участники должны различаться. Типы хранения даты и выполнения проверяются, выполнение допускает только 0 и 1, дата — канонический формат. Полная календарная проверка выполняется при записи и чтении предметного значения. Описание получает такую же защиту от NUL в SQLite, как описания существующих связей.
- Шаг ссылается на владельца с `ON DELETE CASCADE`, а на долговременную связь — с `ON DELETE RESTRICT` и `ON UPDATE RESTRICT`. Каскад удаляет только принадлежащие выбору шаги.
- Составной внешний ключ `(daily_choice_id, previous_step_id)` ссылается на уникальную пару `(daily_choice_id, id)` таблицы шагов. Он использует `NO ACTION DEFERRABLE INITIALLY DEFERRED`, чтобы удаление всей цепочки и каскад владельца не зависели от порядка удаления строк. Ссылка на самого себя запрещена.
- Частичный уникальный индекс на `daily_choice_id WHERE previous_step_id IS NULL` разрешает не более одного первого шага. Уникальность `(daily_choice_id, previous_step_id)` для непустого предшественника запрещает ветвление. Полный валидатор отдельно доказывает существование первого шага, отсутствие отсоединённых циклов и включение всех шагов в одну цепочку.
- Триггер долговременной связи запрещает фактическое изменение типа или участников при наличии ссылающихся шагов. Передача прежних значений не считается изменением. Приоритет, описание и архивное состояние этим триггером не ограничиваются.

Составные и отложенные внешние ключи, а также различие `RESTRICT` и `NO ACTION` поддерживаются SQLite; выбор отложенного ограничения относится именно к внутренним ссылкам цепочки. [Документация SQLite о внешних ключах](https://www.sqlite.org/foreignkeys.html). Единственный первый шаг ограничивается средствами частичного уникального индекса. [Документация SQLite о частичных индексах](https://www.sqlite.org/partialindex.html).

Индексы покрывают каталог `(choice_date, creation_sequence)`, выборы каждого прямого участника в том же порядке, отбор последних выборов по каждому участнику и `creation_sequence`, все шаги одного владельца и обратные ссылки по `long_term_relation_id`. Существующие индексы долговременных связей обслуживают входящие и исходящие переходы. Дополнительные индексы добавляются только по измерениям запросов.

Схема не пытается доказывать всю цепочку после каждого отдельного `INSERT`: во время транзакции построение ещё не завершено. Единственный поддерживаемый путь записи проверяет полный результат перед commit; низкоуровневые ограничения защищают ссылки, локальную структуру и используемый смысл. Читающий валидатор обнаруживает повреждения вне этого пути записи. JSON-массив маршрута лишил бы шаги проверяемых внешних ключей; снимки названий и типов противоречат модели текущего графа.

### 4. Команды проверяют и сохраняют весь результат атомарно

Через общий `execute` добавляются типизированные команды создания, изменения полей, полной замены пути и удаления. Повтор маршрута использует обычную команду создания с новым идентификатором. Идентификаторы генерируются внутри модуля; коллизия не превращается в обновление существующей записи.

Изменение полей задаёт только запрошенные дату, описание и выполнение; тип изменения различает «оставить», «установить» и, для описания, «очистить». Это позволяет независимо менять одно поле или атомарно сохранять несколько. Полная замена пути принимает обоих участников и весь новый путь и не принимает замену остальных полей.

Создание и замена выполняются в последовательном исполнителе репозитория одной транзакцией:

1. Проверить входные значения; при замене прочитать существующий выбор и проверить его структурную целостность.
2. Прочитать актуальные намерения и долговременные связи предложенного пути. Проверить активность, готовность конца, направление, границы, простоту и соответствие ожидаемым типам и участникам всех переходов.
3. При замене удалить прежние шаги и заменить прямых участников, сохранив идентификатор, последовательность создания, дату, описание и выполнение. Создать все новые шаги в порядке от первого к последнему.
4. Перечитать и проверить сохранённый результат и необходимые проекции зависимостей внутри той же транзакции. Любое нарушение откатывает всю операцию.
5. После commit опубликовать одну новую ревизию и единый пакет изменений. Ошибка и операция без фактического изменения не продвигают ревизию.

Если тип или участники связи изменились первыми, команда возвращает конфликт подтверждённого маршрута и требует актуализации с новым подтверждением. Если дневной выбор сохранён первым, шаги уже блокируют такую правку связи. Независимое изменение графа не становится конфликтом только из-за другой общей ревизии: транзакция проверяет относящиеся к операции факты. Названия, приоритеты и описания не замораживаются; в подтверждении используются актуальные отображаемые данные.

Изменение даты, описания и выполнения проверяет существование и сохранённую целостность выбора, но не допустимость пути для нового выбора. Удаление после подтверждения удаляет владельца и все его шаги одной транзакцией без проверки активности, даты или готовности; не затрагивает намерения и долговременные связи. Отсутствующий выбор не создаётся заново.

`GraphCommandCoordinator` получает ключ формы создания и ключ существующего `DailyChoiceId`. Принятая команда блокирует повтор этого подтверждения и конфликтующие команды того же выбора до завершения независимо от маршрута экрана. Новое сознательное создание дубликата получает новую форму/подтверждение. Срок жизни и предъявление результата используют существующий протокол; навигация не служит вторым каналом обновления.

Альтернатива с несколькими независимо подтверждаемыми записями оставила бы окно для неполного пути. Автоматический сброс выполнения при замене действия нарушил бы независимость полей.

### 5. Зависимости вычисляются по фактическим ссылкам

Разрешения долговременной связи получают отдельную типизированную причину `referencedByDailyPath`. Она запрещает удаление и фактическую смену типа либо участников, но разрешает описание, приоритет, архивирование и допустимое восстановление. Проверка выполняется до записи всей составной правки; недопустимая смена типа вместе с допустимым описанием отклоняет всю команду. Хранимого флага блокировки нет.

Сводка зависимостей намерения сохраняет восемь прежних количеств долговременных связей и получает два отдельных количества дневных выборов: в роли исходного намерения и выбранного действия. Дневные количества не включаются в «активные» или «архивированные». Общий запрет удаления учитывает все десять групп. Счётчики вычисляются в хранилище на согласованном снимке по подходу [ADR-0011](../../../docs/adr/0011-derive-relation-counts-from-graph-snapshots.md); они не меняют поля или временные метки намерения.

Группы зависимостей и ссылки выбранного набора становятся закрытыми вариантами: долговременная связь со своим идентификатором либо дневной выбор со своим. Это исключает строковый признак вида, неоднозначные UUID и вымышленное архивное состояние дневной связи. Промежуточное намерение не получает прямую дневную зависимость: его защищают долговременные связи пути.

Массовое удаление резервирует ключ намерения и ключи всех явно выбранных связей обоих видов. В одной транзакции оно сначала проверяет существование, прямую принадлежность и допустимость удаления **всего** набора, и только затем выполняет удаления. Любой шаг, ссылающийся на выбранную долговременную связь до начала удалений, отклоняет весь набор — даже если владелец шага включён в этот же набор. Порядок исполнения не может обойти проверку. Пользователь отдельно удаляет дневной выбор, затем получает актуальные зависимости и подтверждает новый набор.

Подтверждение фиксирует только виды и идентификаторы выбранных записей. Подгрузка, переключение групп или появление новых связей не расширяют набор. После успеха выбор очищается, и на той же странице можно начать следующий. После замены пути прежняя прямая принадлежность дневного выбора также проверяется заново.

Альтернатива с последовательным удалением и каскадным освобождением связей внутри одного подтверждения нарушила бы явно согласованное правило двух операций. Кэшированный флаг зависимости устаревал бы при исчезновении последнего шага.

### 6. Пошаговый выбор проверяет достижимость с учётом черновика

Публичный запрос продолжений принимает направление обхода и весь текущий черновик. Модуль сначала проверяет его актуальность; устаревший префикс возвращает конфликт, а не набор новых ветвей. Результат содержит ревизию, подтверждённое состояние текущего шага, возможность завершения и ограниченную порцию продолжений. В интерфейсе видна вся пройденная цепочка. При возврате отбрасывается только последующая часть черновика; граф не изменяется.

Для выбора сверху вниз множество `S` содержит все уже посещённые намерения, включая текущий конец. Рассматривается активный граф без вершин `S`. В нём вычисляется множество вершин `R`, из которых достижимо хотя бы одно активное действие: обратный обход от всех оставшихся активных действий. Из текущего конца предлагаются только активные исходящие связи к вершинам из `R`. Таким образом, действие подходит непосредственно, а иной кандидат подходит только при продолжении без возвращения в префикс. Любая достижимость в этом конечном графе имеет простой путь; перечислять все возможные пути не требуется.

В Drift adapter расчёт выполняется рекурсивным SQL-запросом с единственным идентификатором вершины в рекурсивном наборе и `UNION`, исключающим повторное посещение. Показанная страница выбирается после расчёта допустимости: лимит страницы не ограничивает глубину поиска и не превращает необследованную ветвь в тупик. Семантика исключения повторов подтверждается [документацией SQLite о рекурсивных запросах](https://www.sqlite.org/lang_with.html). Это проектное применение механизма к правилам дневного выбора.

Для выбора снизу вверх исходное действие фиксировано. Каждый переход выбирает активную входящую связь от ещё не посещённого намерения. Отдельная проверка достижимости не нужна: уже построенный суффикс ведёт от кандидата к фиксированному действию. В памяти порядок обхода и порядок сохранённого пути различаются явно; при подтверждении путь нормализуется от основания к действию. На каждом шаге после первого можно подтвердить основание независимо от его готовности.

В обоих направлениях сохраняются группы «нужно»/«можно», приоритет P1–P4 и последовательность создания. Порции — 50 строк по умолчанию, допустимый размер 1–100. Верхний обход на достигнутом действии одновременно показывает команду завершения и допустимые продолжения. Исходное действие без переходов не даёт права завершить выбор. Нижний обход без входящего допустимого перехода также не подтверждается.

SQL работает на существующем исполнительном пути базы вне UI isolate. Результат привязан к поколению черновика и ревизии; старый ответ после возврата, смены ветви или графа отбрасывается. Ошибка вычисления или ещё выполняющийся запрос отображаются отдельными состояниями. Произвольное ограничение глубины, автоматическое сокращение пути и подмена выбором из списка всех достижимых действий отвергнуты как меняющие поведение.

### 7. Подсказки прежних маршрутов ограничены и не объединяют записи

В начале выбора сверху вниз подсказки привязаны к исходному намерению, снизу вверх — к выбранному действию. Для замены пути используются те же входы и правила. Из хранилища берутся последние 20 дневных выборов подходящего участника по `creation_sequence DESC`, независимо от их даты и выполнения. Каждый из этих кандидатов проверяется на целостность, затем на текущую допустимость нового выбора. Недопустимые маршруты исключаются до ограничения выдачи; их не показывают и они не занимают место среди пяти подсказок. Из допустимых текущих цепочек формируются до пяти различных маршрутов в порядке новизны; совпадение определяется последовательностью идентификаторов долговременных связей. При совпадении остаётся подсказка наиболее недавно созданной записи. Ограничение 20 применяется до проверки допустимости и устранения повторов: более старые записи не читаются ради добора пяти, поэтому подсказок может быть меньше пяти или не быть вовсе.

Каждая подсказка показывает основание, действие и доступ к полному пути. Архивирование намерения или долговременной связи и утрата готовности конечного действия делают маршрут недопустимым для новой записи, но сохраняют исходный дневной выбор. Если все рассмотренные маршруты недопустимы, выдача пуста. Повреждение любого из 20 прочитанных кандидатов, включая исключённый по допустимости или повтору, является ошибкой получения подсказок, а не причиной молча пропустить запись. При подтверждении допустимость и показанный смысл проверяются повторно в транзакции; если ранее показанный маршрут утратил допустимость, конфликт объясняет причину и сохраняет исходный выбор.

Повтор создаёт новый выбор с явно заданными датой, описанием и выполнением; новая форма не наследует описание или выполнение исходной записи автоматически. При замене существующего пути подсказка заменяет только участников и цепочку, сохраняя остальные поля заменяемого выбора. Объединение касается только визуальных подсказок, а исходные дневные связи остаются самостоятельными.

Альтернатива с анализом всей истории не нужна для этой возможности и не ограничивает стоимость первого открытия. Ранжирование по последнему выполнению потребовало бы отсутствующей в предметной модели истории. Ограниченный набор последних записей делает отбор воспроизводимым без нового хранимого индекса маршрутов.

### 8. Каталог и подробности читаются ограниченными согласованными снимками

Каталог по умолчанию показывает **все даты и оба состояния выполнения**, в порядке `choice_date DESC, creation_sequence DESC`. Доступны явный фильтр одной календарной даты и фильтр выполнения; сброс фильтров возвращает полный охват. Выполнение записи не меняет фильтр автоматически. Размер страницы — 50 по умолчанию, диапазон 1–100. Полные дубликаты занимают разные строки и открываются по `DailyChoiceId`; техническая последовательность не подменяет пользовательскую дату.

Краткая строка содержит каноническую формулировку, дату и выполнение. Повторяющиеся строки получают различимые доступные подписи с порядковым номером в текущей выдаче; этот номер не является идентичностью и не сохраняется. Полный путь раскрывается только в подробностях. При входе снизу вверх доступен ограниченный каталог активных готовых намерений с существующим буквальным фильтром названия; описание и переход к подробностям помогают различать одинаковые названия. Новая общая поисковая возможность не вводится.

Курсор дневного каталога непрозрачен и привязан к запросу, размеру порции, эпохе, ревизии и последнему ключу порядка. Он следует существующему протоколу групп связей: продолжение другой ревизии требует новой основы. При изменении показанных данных заново получаются ограниченными порциями уже загруженная часть и точное количество; они заменяются вместе. До замены доступны прежние подтверждённые данные с состоянием обновления или ошибки. Постороннее изменение требует новой основы перед следующей подгрузкой. Поколение запроса и принятая ревизия не позволяют старому ответу возвращать прежнюю дату, выполнение или удалённую запись.

Для первой порции читаются только выбранные дневные записи и нужные им данные. До успешной публикации каждой строки внутренний валидатор проверяет её поля и всю структуру принадлежащего ей пути. Для этого нужны шаги и минимальные данные ссылок выбранной порции, но не развёрнутые описания всех промежуточных сущностей, остальные дневные пути или весь граф. Ограничение количества строк не обещает постоянную стоимость проверки длинного пути. Точные количества вычисляются агрегатами, без получения всех дневных записей в Dart.

Подробный просмотр восстанавливает порядок по ссылкам на предыдущий шаг, проверяя единственный корень, единственного преемника и совпадение числа пройденных шагов с числом всех шагов владельца. Он получает текущие данные намерений и долговременных связей из одной транзакции, включая архивные отметки и текущую готовность конца. Отсутствующая ссылка, лишняя цепочка или неверные границы дают повреждение целого результата. Последний переход сохраняет тип «нужно»/«можно», выбранное действие обозначается отдельно. Каждую сущность пути можно открыть.

Наблюдение подробностей регистрирует зависимости по участникам и связям текущего пути. Переименование, изменение описания/приоритета, архивирование и готовность инициируют перечитывание затронутых открытых представлений. После замены маршрута набор наблюдаемых зависимостей заменяется вместе со снимком. Нет отдельного сохранённого текста формулировки.

Альтернатива с полной загрузкой истории и всех раскрытых путей нарушила бы ограниченность каталога. Оптимистическое изменение строки до подтверждения записи создало бы ложное состояние при ошибке.

### 9. Единая ревизия согласует новые и существующие представления

Пакет подтверждённой команды расширяется изменениями дневных выборов до/после, прежними и новыми прямыми участниками, идентификаторами долговременных связей освобождённого и занятого пути, актуальными разрешениями затронутых связей и абсолютными количествами зависимостей затронутых намерений. Это позволяет обновить ограничения удаления сразу после появления или исчезновения последней ссылки, даже если собственные поля долговременной связи не менялись.

Изменения намерений и долговременных связей по-прежнему публикуются своей ревизией и дополнительно инвалидируют зависимые дневные проекции и незавершённые проверки маршрута. Наблюдатели получают минимально необходимые признаки изменения; все дневные пути не добавляются в каждое событие и не перечитываются целиком. Замена, каскад и смешанное массовое удаление остаются одним атомарно применяемым пакетом. Ревизия существует только в памяти экземпляра и не становится сохраняемой версией дневного выбора.

Альтернатива с отдельной ревизией дневных выборов затруднила бы согласование путей с разрешениями долговременных связей. Ориентация только на изменение строки связи пропустила бы изменение её зависимостей.

### 10. Представление ошибок, доступность и диагностика используют общие механизмы

В навигацию добавляются каталог дневных выборов, подробности, редактор полей и экран построения/замены пути. Каталог доступен из основной навигации; верхний обход — из активного намерения, нижний — из выбора активного действия. В подробностях доступны редактирование полей, замена пути и отдельное подтверждение удаления с указанием конкретной записи и необратимости. Дата показывается рядом с формулировкой, чтобы слово «сегодня» не принималось за дату просмотра.

Состояния чтения явно различают загрузку, данные, пустой результат, отсутствие записи, конфликт актуальности и ошибку. Команды используют существующие категории `validation`, `notFound`, `conflict`, `unavailable`, `corruption`, `unexpected`; для пути добавляются типизированные причины конфликта и ошибки поля. Только доказанная временная недоступность допускает обычный повтор; конфликт требует актуализации и нового подтверждения. Повреждение и неизвестный отказ не запускают исправление, очистку или пересоздание данных. Исключения и SQL не попадают в сообщения.

Открытая форма сохраняет исправимый ввод и предъявляет локализованную ошибку через общий модуль; исчезнувшая поверхность передаёт право предъявления оболочке по ADR-0012. Успех показывается после commit. Результат принятой операции предъявляется один раз и после ухода с экрана, пока процесс продолжает работу.

Строки добавляются в существующие русские и английские ARB с прежним выбором локали и английским fallback. Формулировки используют локализованные системные шаблоны и текущий пользовательский текст без грамматических преобразований. Семантические подписи передают порядок пути, направление и тип связи, основание, выбранное действие, дату, выполнение, архивность и причину недоступности. Эти признаки доступны без цвета и жестов; большие размеры текста поддерживаются прокруткой и переносами.

`DiagnosticsSink` получает типизированные события чтения, проверки пути и команд с этапами проверки, записи и чтения результата; миграции используют существующие события. Разрешены вид операции, этап, категория результата и длительность. Запрещены дата выбора, идентификаторы, маршрут, названия, описания, параметры SQL и исходные исключения. Ошибка при записи диагностики не меняет результат предметной операции. Новая внешняя телеметрия не вводится.

Альтернатива с локальными очередями результатов и собственными `SnackBar` повторила бы уже решённые проблемы времени жизни экранов. Запись исключений целиком могла бы раскрыть содержимое личного графа.

### 11. Проверки привязаны к инвариантам и наблюдаемому поведению

Это проект проверок последующей реализации, а не утверждение об их выполнении:

- Контрактные проверки репозитория: все операции и оба порядка пересекающихся команд, независимые поля после архивирования/утраты готовности, неизменность выполнения при замене, допустимые дубликаты, снятие только последней зависимости и отказ всего смешанного набора до удаления первой записи.
- Проверки маршрутов: одношаговые и длинные цепочки, циклы графа, возврат к посещённому основанию, тупики, действие в середине пути, оба направления и смена ветви. На малых сгенерированных графах результат фильтрации сравнивается с независимым перебором простых путей.
- Проверки хранилища: перезапуск, внешние ключи и триггеры, удаление цепочки без зависимости от порядка строк, повреждённые ссылки/границы/циклы/ветвления/лишние шаги, строгий Unicode и описание по графемам, корректность календарных дат, отказ после каждого существенного шага транзакции без частичного результата.
- Проверки согласования: устаревшие ответы и курсоры, смена эпохи, изменение полей участников, появление зависимости без изменения самой долговременной связи, замена пути, повторное открытие экрана во время команды и однократное предъявление результата.
- Пользовательские проверки: верхний и нижний обход, повтор и замена через подсказку, явная запись выполненного, сохранение выполнения при смене действия, все даты и состояния в каталоге, подтверждение конкретного удаления, русская/английская локали, экранный диктор и увеличенный текст.
- Проверки стоимости на больших циклических графах, длинных путях и больших соседствах: ограниченная материализация страниц, отсутствие полного чтения истории для подсказок, отсутствие перечисления всех простых путей и полного аудита при bootstrap. Отдельно измеряются достижимость и время ожидания следующих команд в общем исполнителе.
- Проверки диагностики подтверждают категории и этапы и отсутствие содержимого графа как при успехе, так и при исключениях хранилища.

## Risks / Trade-offs

- **Большой граф делает точную достижимость дорогой** → рекурсивный набор хранит вершины, а не все пути; вычисление выполняется в базе вне UI isolate и измеряется на циклических и разветвлённых данных. Ограничение страницы не выдаётся за ограничение стоимости поиска. Отказ расчёта не становится пустым результатом.
- **Длинные чтения задерживают команды общего исполнителя** → запросы не удерживают транзакцию между пользовательскими шагами; повторные запросы от устаревших черновиков не запускаются, готовые устаревшие ответы отбрасываются. До поставки проверяется задержка команд на больших фикстурах; изменение модели исполнения требует отдельного обоснования согласованности.
- **Локальных SQL-ограничений недостаточно для всей цепочки** → полный валидатор вызывается перед commit и при чтении, а тесты повреждений охватывают нарушения, допускаемые отдельными ограничениями. Архивирование при этом не считается повреждением.
- **Подсказки могут показывать меньше пяти разных маршрутов и пропускать старые** → политика последних 20 записей явна; полный каталог остаётся доступным, а выбор можно построить пошагово. История не объединяется и не удаляется.
- **Изменение даты перемещает строку в каталоге** → новая согласованная основа заменяет уже загруженную часть целиком; сортировка не зависит от часов создания или выполнения.
- **Разрешение связи меняется без изменения её полей** → пакет графа содержит изменения зависимостей, и все затронутые открытые представления получают актуальные разрешения.
- **Ошибочная миграция угрожает прежнему графу** → добавочная схема, единая атомарная миграция, проверки всех поддерживаемых исходных версий и отказ без пересоздания файла.

## Migration Plan

1. Добавить схему версии 3, её committed snapshot и переход 2 → 3. Сохранить путь 1 → 2 → 3 в существующем механизме `stepByStep` внутри общей атомарной миграции. Новая установка создаёт сразу версию 3. Старые таблицы, UUID, описания, архивность, поисковые данные и последовательность создания долговременных связей сохраняются; новые таблицы пусты.
2. Создать новые таблицы, индексы и триггер защиты используемой долговременной связи в той же транзакции. Проверить внешние ключи и существующие обязательные проверки перед обновлением маркера версии. Каноническая настройка каждого SQLite-соединения остаётся обязательной. Новые проверки чтения, если им нужны SQL-функции, регистрируются как закрытые чистые функции запросов; сохраняемая схема на них не ссылается и существующие долговечные функции схемы не меняются.
3. На постоянном хранилище доказать совпадение новой схемы и результатов всех миграций с committed snapshot, сохранность данных и отсутствие дневных выборов после обновления. Проверить прерывания создания и переходов, повторное открытие, удаление/замену цепочки и отказ старого приложения при более новой версии. Расширить существующий verifier новыми объектами, не переносить полный аудит в production bootstrap.
4. Перед поставкой реализации выполнить предусмотренные репозиторием генерацию и проверки, контрактные, пользовательские и миграционные тесты из этого дизайна. После успешного bootstrap новые экраны работают с тем же внутренним файлом и прежними ограничениями backup и переноса; отдельное хранилище не появляется.

До commit миграции сбой откатывает и схему, и маркер версии; следующий запуск начинает с последнего целостного состояния. После подтверждённого перехода на версию 3 автоматического downgrade нет. Откат поставки допустим только на сборку, понимающую версию 3 и сохраняющую её данные; иначе требуется исправляющее обновление. Старой сборке нельзя удалять таблицы, понижать версию или пересоздавать файл ради запуска.

## Open Questions

Открытых продуктовых решений для этого артефакта нет. Зафиксированы порядок и фильтры каталога, отбор подсказок, границы календарной даты, модель зависимостей и атомарных операций. Значения размера страницы и числа кандидатов подсказок являются выбранной политикой представления; их проверка на больших данных входит в реализацию. Фактическая стоимость SQL-планов и доступность экранов должны быть подтверждены предусмотренными выше проверками, без ослабления предметных правил при обнаружении проблем.

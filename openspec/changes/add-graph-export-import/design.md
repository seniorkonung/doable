## Context

Мотивация и границы — в `proposal.md`, требования — в `specs/`. Здесь описано, как их выполнить в текущей архитектуре.

Текущее состояние:

- Граф хранится в одной базе SQLite через Drift (ADR-0002). Production открывает одно соединение в фоновом изоляте (`createBackgroundConnection`, без пула чтения) в режиме журнала отката по умолчанию; кроме `foreign_keys` и `user_version`, PRAGMA не задаются. Схема — версия 2 с переходом с версии 1.
- `PersonalGraphRepository` — единственная граница графа (ADR-0009). Все чтения и записи проходят через последовательный исполнитель `_AsyncSequencer`. Записи выполняются восемью отдельными блоками: каждый сам открывает транзакцию, после COMMIT продвигает номер ревизии и уведомляет наблюдателей. Эпоха ревизий создаётся один раз на экземпляр репозитория.
- `GraphCommandCoordinator` принимает команды с блокировками по сущностям, без монопольного режима, и публикует результаты. `GraphOperationPresenter` показывает сообщения только для результатов команд графа (ADR-0012, ADR-0023).
- Корневые страницы живут в `IndexedStack` оболочки. Их модели хранят параметры в полях, которые переживают `invalidate`: Riverpod 3 сохраняет экземпляры notifier. Экземпляр каталога дневных выборов и текст фильтра каталога намерений хранятся в состоянии виджетов.
- Доступа к файлам и собственных платформенных каналов нет. Хост — `FlutterActivity`; при смене дисплея движок переносится в другую Activity (ADR-0031). Проверка `tool/check_android_privacy_manifest.dart` допускает ровно одно разрешение, правила резервного копирования исключают весь `app_flutter/`.
- `SQLITE_FULL` классифицируется как неизвестный отказ.

Ограничения: ADR-0002, ADR-0003, ADR-0004 (модель угроз пересматривается до появления экспорта), ADR-0006, ADR-0007, ADR-0008, ADR-0009 (без метаданных синхронизации без собственного поведения; импорт требует решения о порядке изменений), ADR-0010, ADR-0012, ADR-0021, ADR-0023, ADR-0026, ADR-0030, ADR-0032.

Решение владельца продукта: миграций не делаем — установок с данными сейчас нет.

## Goals / Non-Goals

**Goals:**

- Каждое подтверждённое изменение графа попадает в лог фактов в той же транзакции, а полноту лога обеспечивает база, а не дисциплина кода команд.
- Экспорт не блокирует работу; импорт и восстановление — атомарная замена графа с отменой; резервная копия — позиция в логе.
- Потребление памяти не зависит от размера графа и файла.
- Один предметный версионируемый формат для файлов экспорта и снимков.
- Без новых разрешений Android.
- Границы модулей, которые переиспользует будущая синхронизация.

**Non-Goals:**

- Синхронизация, сервер, шифрование и очередь команд.
- Объединение импортируемых данных с текущими, удаление всех данных, остальные разделы настроек.
- Перенос хранилищ предварительных сборок.
- Режим WAL, пул соединений чтения, системный планировщик фоновых задач.

## Decisions

### 1. Новая базовая схема версии 3 без миграции

Схема версии 3 содержит текущие таблицы графа и объекты лога из решения 4. `onCreate` создаёт её атомарно, как и сейчас. Переход 1 → 2 удаляется вместе с его тестами и снимками `drift_schema_v1.json` и `drift_schema_v2.json`. Для любой более старой версии `onUpgrade` отказывает, как сейчас для неподдерживаемого перехода, результатом corruption, не изменяя и не удаляя файл. Механизм пошаговых миграций (`runAtomicMigration`) остаётся для будущих версий. README объясняет, что хранилище предварительной сборки нужно очистить вручную.

Номер 3, а не снова 1: иначе файл версии 1 прошёл бы проверку маркера при другой структуре. Новый номер делает несовместимость обнаружимой.

Альтернативы:
- изменить схему версии 2 на месте — тихое расхождение структуры, как уже было с удалением избранного;
- написать переход 2 → 3 — владелец продукта решил, что сейчас он не нужен.

- **GraphFormat** не зависит от Flutter и SQLite: его используют фоновые изоляты, а позже — синхронизация.

### 4. Лог фактов в той же базе

Новые объекты схемы версии 3 (названия рабочие):

- **`graph_log_marks(kind, entity_key, first_op)`** — отметки сущностей, затронутых текущей транзакцией. Их ставят триггеры `AFTER INSERT/UPDATE/DELETE` на таблицах графа через `INSERT OR IGNORE`, поэтому сохраняется первая операция. Изменение шагов пути отмечает свой дневной выбор, назначение тега — пару «тег, намерение». Триггеры срабатывают, только пока включён флаг `graph_log_control.capture`; выключает его лишь замена графа.
- **`graph_log_packages(position, recorded_at, kind, format_version, payload)`** — пакеты:
  - `position` — `INTEGER PRIMARY KEY AUTOINCREMENT`, номера не переиспользуются (ADR-0010);
  - `recorded_at` — показание часов устройства, то есть наблюдение (ADR-0006);
  - `kind` — «изменение» или «сброс»;
  - `format_version` — версия формата, в которой записаны факты пакета «изменение»; у пакета «сброс» её нет, версию его снимка хранит реестр снимков;
  - `payload` — факты в кодировке формата (решение 6) либо ссылка на снимок для сброса.
- **`graph_snapshots(id, position, format_version, file_name, byte_size, checksum)`** — реестр снимков.
- **`graph_backups(id, position, kind, made_at, summary)`** — реестр копий.

Позиция 0 — пустой граф: у каждой установки лог начинается с создания базы.

Почему в той же базе: изменение и его факт подтверждает одна транзакция. Лог в файлах разошёлся бы с базой при падении между COMMIT и записью файла.

Почему постоянные триггеры, а не факты в коде команд: путей записи восемь, а каскады внешних ключей коду команды не видны. Удаление тега удаляет его назначения, удаление дневного выбора — шаги пути. Триггеры дочерних таблиц срабатывают и на каскадных удалениях: это проверено на SQLite 3.53.1 и закрепляется тестом. Временные триггеры `TEMP` отклонены: их пришлось бы ставить на каждом соединении, а временные таблицы этой сборки живут в памяти (`SQLITE_TEMP_STORE=2`).

Почему версия формата в каждом пакете: после обновления приложения, сменившего версию формата, в логе остаются пакеты прежней версии, и без неё их не отличить. Альтернативы отклонены:
- переписывать хранимые пакеты миграцией базы при каждой смене формата — формат оказался бы связан со схемой хранения вопреки ADR-0035, а ошибка повышения остановила бы запуск приложения;
- журнал «с позиции P — версия N» — отдельное правило согласования ради экономии одного числа на пакет.

### 5. Единый путь записи

Восемь блоков записи сводятся к одному внутреннему методу репозитория. Внутри `_sequencer.run` метод:
1. открывает транзакцию и выполняет тело команды;
2. превращает отметки в пакет фактов;
3. проверяет, что отметок не осталось;
4. подтверждает транзакцию;
5. продвигает ревизию, публикует пакет изменений для представлений и уведомляет наблюдателей.

Оба нынешних способа вычисления ревизии сводятся к одному: следующая ревизия известна внутри транзакции, а публикуется после COMMIT. Последовательный исполнитель делает это безопасным.

Факт — полное состояние сущности после транзакции в записи формата либо удаление. Классификация по первой операции и текущему существованию:
- первая операция — вставка, сущность есть: создана;
- первая операция — не вставка, сущности нет: удалена;
- создана и удалена в одной транзакции: факта нет;
- иначе — изменена.

Команда без изменений не оставляет отметок, не пишет пакет и не продвигает ревизию — как и сейчас. Пакеты изменений для согласования представлений (`GraphChange`) не меняются: факты — отдельная полная запись.

```text
Coordinator         GraphRepository           SQLite DB
  |                     |                        |
  | 1. execute(command) |                        |
  |-------------------->|                        |
  |                     | 2. BEGIN               |
  |                     |----------------------->|
  |                     | 3. domain writes       |
  |                     |----------------------->| 4. triggers add marks
  |                     | 5. read marks and rows |
  |                     |----------------------->|
  |                     | 6. append package,     |
  |                     |    clear marks         |
  |                     |----------------------->|
  |                     | 7. COMMIT              |
  |                     |----------------------->|
  | 8. completion,      |                        |
  |    revision + 1     |                        |
  |<--------------------|                        |
```

Альтернатива: обернуть все транзакции Drift. Это захватило бы и чтения, и замену графа, а явная точка записи проще проверить.

### 6. Формат данных графа

- **Модуль.** Новый модуль на чистом Dart:
  - типы записей: тег, намерение, назначение, долговременная связь, дневной выбор с путём и удаление сущности;
  - кодек «запись ↔ объект JSON»;
  - заголовок;
  - потоковое построчное чтение и запись JSON Lines.
- **Каноничность.**
  - Порядок полей фиксирован.
  - Время пишется в UTC в ISO-8601 с микросекундами.
  - Перечисления пишутся стабильными строками (`need`/`can`, `P1`…`P4`).
  - Время дня пишется как `HH:MM`, «весь день» — как `null`.

  Одно состояние всегда даёт одни байты: экспорт после импорта совпадает с исходным файлом, а снимок из лога — с выгрузкой базы.
- **Порядок.** Секции идут в порядке теги → намерения → назначения → долговременные связи → дневные выборы. Внутри секции записи идут в порядке создания: по `creation_sequence`, а намерения — по времени создания и идентификатору.
- **Чтение.**
  - Заголовок читается в пределах нескольких килобайт, у строк записей — большой потолок длины.
  - Неизвестное поле или вид записи известной версии — повреждение.
  - Версия новее текущей — отдельный отказ.
- **Версии.** Номер версии — целое число. Повышение версии — чистые построчные функции «запись версии N → записи версии N+1», они никогда не удаляются.
  - Версию несёт носитель записей: заголовок файла экспорта или снимка и строка пакета лога (решение 4). Записи любого носителя повышаются от его версии до текущей одной цепочкой, поэтому хранимые снимки и пакеты при смене формата не переписываются.
  - Повышение охватывает и записи удаления, которые бывают только в пакетах.
  - Эталонный файл и эталонный пакет фактов со всеми видами записей, включая удаление, каждой опубликованной версии хранятся в тестах несжатыми.
- **Проверка.**
  - Поля проверяют существующие предметные типы: `IntentionText`, типы описаний, `TagName`, `CalendarDate`, `DailyChoiceSchedule`, приоритеты.
  - Инварианты графа проверяет схема при вставке.
  - Непрерывность пути проверяет общая логика `_validateStoredChoicePathLinks`.
- **Контейнер.** Файл экспорта и снимок — поток gzip поверх JSON Lines с расширением `.jsonl.gz`. Сжатие и распаковка потоковые (`dart:io`). Чтение начинается с проверки заголовка gzip, поэтому чужой файл отклоняется сразу. Эталонные файлы в тестах хранятся несжатыми и сжимаются в самом тесте.

### 7. Снимки и сжатие лога

- **Снимок** — неизменяемый файл `app_flutter/graph_snapshots/<id>` в формате экспорта. Запись идёт так: временный файл в том же каталоге → flush → fsync → атомарное переименование → fsync каталога → регистрация в `graph_snapshots` короткой транзакцией. При запуске удаляются незарегистрированные и временные файлы. Контрольная сумма проверяется при чтении: файл вне SQLite журналом не защищён, и повреждённый снимок не должен тихо стать графом.
- **Состояние на позиции p** собирается потоково: ближайший снимок не новее p плюс пакеты после него.
  - Записи снимка и пакетов читаются по их сохранённой версии и повышаются до текущей (решение 6).
  - Итог фактов диапазона держится в памяти по ключам сущностей. Это изменения диапазона, а не весь граф.
  - Снимок читается построчно: изменённые сущности заменяются на своих местах, удалённые выбрасываются.
  - Созданные сущности встают в порядок решения 6, тот же, что у выгрузки базы:
    - в секциях с последовательностью создания — после сущностей снимка, по позиции пакета последнего создания и порядку внутри пакета;
    - в секции намерений — по времени создания и идентификатору.

    Сущность, удалённая и снова созданная с тем же ключом, считается созданной в пакете повторного создания и покидает прежнее место, в том числе в снимке. Так назначение тега, снятое и назначенное повторно, уходит в конец тега, как и в базе: новая строка получает новую последовательность создания.
- **Сжатие лога** — фоновая задача в отдельном изоляте. Когда пакетов после последнего снимка становится больше порога, собирается новый снимок. Пороги подбираются по бенчмарку.
- **Повтор после отказа.** Неудачное сжатие не повторяется на каждом новом пакете. Следующая попытка — при следующем запуске приложения или когда после неудачной попытки записано ещё не меньше порога пакетов. Так даже постоянный отказ, например нехватка места, стоит не больше обычного ритма сжатия, а таймеры и новые значения не нужны.
- **Пересборка из базы.** Последний снимок может не пройти проверку: не совпали размер или контрольная сумма, файла нет или его записи не читаются. Тогда сжатие собирает снимок текущего состояния не из него, а из базы:
  1. фиксирует позицию P0 не позже первой порции;
  2. читает таблицы графа короткими порциями в каноническом порядке решения 6 во временный файл каталога снимков, между порциями команды выполняются как обычно;
  3. фиксирует позицию P1 не раньше последней порции;
  4. собирает состояние на P1 из временного файла как базового состояния и пакетов после P0 и записывает его обычным снимком.

  Порции могут застать разные моменты между P0 и P1. Но каждое изменение этого промежутка есть в пакетах полным состоянием сущности или удалением, а ключ порядка строки — последовательность создания или время создания с идентификатором — не меняется, поэтому итог совпадает с базой на P1. Автоматический повтор неудачной пересборки подчиняется тому же правилу повтора. Повреждённый снимок остаётся в реестре, пока его не удалит граница хранения.

  Чтение истории, которому нужен повреждённый снимок, отказывает своей операцией. Если повреждён последний снимок, такое чтение запускает пересборку и вне порога, если она ещё не идёт, поэтому экспорт после неё повторяется успешно. Копии, состояние которых собирается из повреждённого снимка, не восстанавливаются и уходят по сроку.
- **Хранение истории.** Снимок или пакет удаляется, только если он не нужен:
  - идущему чтению истории — сборке состояния для экспорта, восстановления копии или сжатия и поиску прежних состояний для сводок копий;
  - ни одной хранимой копии любого вида, пока копия не удалена по сроку;
  - позиции любого момента в пределах срока хранения копий (решение 8): на неё может сослаться ежедневная копия, которую ещё предстоит дописать.

  Позиция момента — позиция последнего пакета, записанного до него, как у ежедневной копии. Граница хранения — наименьшая из позиций базовых снимков идущих чтений, хранимых копий и момента «сейчас минус срок хранения копий». Сохраняются последний снимок, базовые снимки идущих чтений, ближайший снимок не новее границы и все пакеты после него; остальные снимки и пакеты удаляются из реестра одной короткой транзакцией, затем удаляются их файлы. Граница действует и до появления копий, поэтому первые ежедневные копии, дописанные задним числом, собираются и на данных, накопленных до них.
- **Идущие чтения истории** отмечаются в памяти SnapshotStore не позже выбора базового снимка и до конца чтения. Удаление, отложенное из-за отметки, выполняет следующее сжатие, поэтому чтение не прерывается и не повторяется. Отметки не сохраняются: после завершения процесса идущих чтений нет.
- **Жизненный цикл задач.** Фоновые задачи запускаются в `AppRuntime` после подготовки хранилища. При выключении приложения их дожидаются так же, как координатора.

Почему из файлов: сжатие не держит единственное соединение, база получает только короткие чтения пакетов, а при пересборке — и порций графа.

Альтернативы пересборки:
- одно чтение всей базы — проще, но на всё его время единственное соединение занято, и подтверждения команд ждут;
- не пересобирать — после повреждения последнего снимка экспорт и сжатие отказывали бы до конца жизни установки, а лог рос бы без предела.

### 8. Резервные копии как позиции лога

- **Копия** — строка `graph_backups` с позицией, данных она не копирует.
- **Ежедневная копия дня D** — позиция последнего пакета, записанного до 03:00 местного времени дня D. Недостающие ежедневные копии в пределах срока хранения копий дописываются лениво: при запуске, при возвращении в приложение и перед показом списка. Отсчёт начинается с первого непустого состояния. Поэтому копия появляется и за дни, когда приложение не запускалось, без системного планировщика.
- **Ручная копия** — текущая позиция.
- **Копия перед заменой** — строка в транзакции замены (решение 10), если прежний граф не пуст.
- **Срок хранения копий** — одно именованное значение, сейчас 7 дней по `graph-backups`. Копии старше него удаляются там же, где дописываются ежедневные, а граница хранения истории (решение 7) выводится из него же.
- **Сводка «что изменилось с предыдущей копии»** считается при создании копии и хранится в строке.
  - Это итог фактов между позициями по сущностям; назначения тегов относятся к своему намерению.
  - Для изменённых в диапазоне сущностей итоговое состояние сравнивается с состоянием на предыдущей позиции: из пакетов или потоковым поиском по базовому снимку. Поэтому правка с возвратом к прежнему значению изменением не считается.
- **Подсчёт «с тех пор»** в подтверждении восстановления идёт так же, между позицией копии и текущей.
- **Замена графа между позициями.** Если в промежутке есть пакет «сброс», сводка не считается: строка копии хранит признак замены, и список показывает «Данные заменены». Подтверждение восстановления в таком случае сообщает «С тех пор данные заменялись». Точные числа потребовали бы полного сравнения двух состояний графа ради редкого случая, а их смысл для человека невелик.
- **Часы устройства.** Показания часов — наблюдения (ADR-0006): перевод часов может сместить суточную отсечку, но целостность не нарушает.

### 9. Экспорт

- **Состав в панели** берётся коротким агрегатным чтением.
- **Сборка файла.** После выбора места фиксируется текущая позиция P. В фоновом изоляте состояние на P собирается по решению 7 во временный файл в `app_flutter/tmp/` в каноническом формате. Плагин копирует его в выбранный документ, затем временный файл удаляется.
- **Согласованность.** Пакеты до P неизменяемы, а отметка идущего чтения (решение 7) не даёт сжатию удалить базовый снимок и пакеты до P, пока файл не собран. Поэтому файл отражает одно состояние даже при изменениях и сжатии во время экспорта. База при этом не блокируется.
- **Ход** — доля записанных записей от количеств заголовка. Одновременно идёт не больше одного экспорта.

Альтернатива: читать таблицы одной транзакцией. Это тоже согласованно, но держит единственное соединение всё время экспорта.

### 10. Замена графа: импорт и восстановление

Импорт:
- Плагин копирует выбранный документ во временный файл.
- Читается только заголовок: маркер, версия, дата, количества. При пустом графе подтверждение не показывается.
- Под модальным прогрессом выполняются две фазы.
  - **Фаза 1, без блокировки базы.** Файл читается построчно и повышается до текущей версии, поля проверяются предметными типами, количества сверяются с заголовком. Результат пишется в канонический снимок, пока не зарегистрированный.
  - **Фаза 2.** Координатор входит в монопольный режим (решение 11), затем внутри исполнителя репозитория выполняется одна транзакция верхнего уровня:
    1. захват выключается;
    2. прежний граф удаляется небольшими пакетами операторов;
    3. записи снимка вставляются небольшими пакетами: ссылки, уникальность и активность участников проверяет схема, непрерывность пути — общая проверка;
    4. сверяются количества;
    5. добавляется строка копии перед заменой с позицией до сброса;
    6. регистрируется снимок;
    7. записывается пакет «сброс» со ссылкой на снимок;
    8. захват включается;
    9. COMMIT.

Восстановление отличается только фазой 1: она собирает состояние на позиции копии в снимок по решению 7.

```text
SettingsUI          DataTransfer         DocAccess          Coordinator        SQLite DB
  |                   |                    |                  |                  |
  | 1. import         |                    |                  |                  |
  |------------------>|                    |                  |                  |
  |                   | 2. open document   |                  |                  |
  |                   |------------------->|                  |                  |
  |                   | 3. copy to temp    |                  |                  |
  |                   |<-------------------|                  |                  |
  |                   | 4. read header     |                  |                  |
  | 5. date, counts   |                    |                  |                  |
  |<------------------|                    |                  |                  |
  | 6. confirmed      |                    |                  |                  |
  |------------------>|                    |                  |                  |
  |                   | 7. convert, check, |                  |                  |
  |                   |    write snapshot  |                  |                  |
  |                   | 8. replace graph   |                  |                  |
  |                   |-------------------------------------->|                  |
  |                   |                    |                  | 9. transaction:  |
  |                   |                    |                  |----------------->| delete old graph,
  |                   |                    |                  |                  | insert new graph,
  |                   |                    |                  |                  | check counts,
  |                   |                    |                  |                  | add copy, reset,
  |                   |                    |                  |                  | COMMIT
  | 10. replaced      |                    |                  |                  |
  |<-----------------------------------------------------------|                  |
  | 11. reset pages,  |                    |                  |                  |
  |     show result   |                    |                  |                  |
```

Гарантии атомарности:
- одна транзакция верхнего уровня, а не savepoint;
- небольшие операторы: журналы операторов и savepoint в этой сборке живут в памяти;
- любая ошибка прерывает всю транзакцию, перехвата с продолжением нет;
- режим журнала и `synchronous` не ослабляются, и это закреплено тестом.

Отмена кооперативная: признак проверяется между строками и пакетами операторов. В фазе 1 удаляются временные файлы. В фазе 2 исключение откатывает транзакцию, затем удаляется незарегистрированный снимок. «Отмена…» показывается до конца отката.

Поисковый индекс FTS обновляется триггерами намерений. Если бенчмарк покажет, что это доминирует, индекс перестраивается командой `rebuild` в той же транзакции.

Почему сначала снимок: фаза 2 читает уже проверенные канонические данные, а сам снимок сразу становится базой для следующих копий и экспорта.

### 11. Монопольный режим, новая эпоха и поколение корневых страниц

- **Монопольный режим.** Координатор получает операцию замены графа. Пока она идёт, новые команды отклоняются с результатом «занято», а уже принятые дожидаются завершения. Интерфейс в это время закрыт модальным прогрессом, поэтому отклонений человек практически не увидит.
- **Новая эпоха.** После COMMIT репозиторий:
  - начинает новую эпоху: эпоха перестаёт быть final, на это и рассчитан комментарий `_GraphEpoch`;
  - сбрасывает кэши, в том числе снимок связей статистики по ADR-0026;
  - публикует результат «граф заменён» с ревизией новой эпохи. Без него Главная ждала бы ревизию прежней эпохи и перечитывала данные бесконечно.
- **Поколение корневых страниц.** Оболочка хранит номер поколения графа и увеличивает его по этому результату.
  - Корневые страницы в `IndexedStack` получают ключ поколения, поэтому состояние их виджетов создаётся заново: контроллеры, экземпляр каталога дневных выборов.
  - Модели корневых страниц следят за поколением и задают всё состояние в `build()`, а не в полях.
  - Страница «Настройки» над Главной остаётся открытой.
- **Почему поколение, а не обработка изменения в моделях.** Существующие переключатели `GraphChange` с веткой по умолчанию новое изменение не заметят, поэтому сброс выполняет поколение.

Альтернативы:
- пересоздать `ProviderContainer` — теряется навигация и открытая страница «Настройки»;
- только `invalidate` провайдеров — поля состояния его переживают.

### 12. Результаты и отказы операций с данными

- **Новые операции координатора.** Экспорт, импорт, восстановление и ручная копия становятся типизированными операциями координатора со своими видами результата. `GraphOperationPresenter` получает для них ветки сообщений: новая поверхность подключается через тот же протокол, как требует ADR-0012.
- **Кто показывает результат.**
  - Отказ импорта и восстановления принадлежит строке страницы через существующие заявки инициатора, успех — общей поверхности.
  - Успех ручной копии виден в строке и списке, поэтому сообщения он не показывает: координатор задаёт этой операции политику «только отказ» по [ADR-0016](../../../docs/adr/0016-present-only-failure-for-self-evident-success.md).
  - Отказ экспорта показывается на общей поверхности с действием «Повторить», поэтому сообщение получает действие.
- **Категории отказов.**
  - Не экспорт Doable или файл повреждён, включая нарушение ограничений схемы при вставке.
  - Более новая версия формата.
  - Нехватка места: `SQLITE_FULL` и ошибка файловой системы `ENOSPC` — новая категория классификатора.
  - Документ не прочитан.
  - Документ не записан.
  - Неизвестная причина.

  Отмена человеком отказом не считается.

### 13. Доступ к документам Android

- **Плагин.** Встроенный Kotlin-плагин (`FlutterPlugin` + `ActivityAware`) добавляется к движку при его создании в `DisplayHostActivity.configureFlutterEngine`, с защитой от повторной регистрации на перенесённом движке.
  - Канал методов: создать документ, открыть документ, скопировать документ во временный файл, скопировать временный файл в документ.
  - Диалоги — `ACTION_CREATE_DOCUMENT` и `ACTION_OPEN_DOCUMENT` через `startActivityForResult` и слушатель результатов.
  - Копирование идёт потоками `ContentResolver` в фоновом потоке. Байты через канал не передаются.
- **Перенос движка при смене дисплея** заново привязывает плагин к новой Activity. Ответ диалога приходит до `onResume`, поэтому перенос его обычно не теряет. Если Activity отсоединяется с ожидающим запросом, запрос завершается как отмена.
- **Манифест** не меняется: без разрешений и `FileProvider`, проверка набора разрешений остаётся зелёной.
- **Тип документа.** Экспорт создаёт документ с типом `application/gzip`. Открытие принимает любой тип: часть поставщиков указывает тип неверно, а файл всё равно проверяется по содержимому.
- **Временные файлы** лежат в `app_flutter/tmp/` и удаляются после операции и при запуске.

Альтернативы:
- готовые плагины выбора файлов — неизвестные записи манифеста и API, которые отдают файл целиком в памяти;
- `package:jni` — нет интеграции с результатами Activity;
- передача байтов через канал порциями — сложнее копирования файла.

### 14. Диагностика

Новые события существующей границы диагностики:
- экспорт, импорт, восстановление;
- копии: создание и удаление по сроку;
- снимки: запись, сжатие, пересборка из базы, очистка.

События различают этап и безопасную категорию отказа, в том числе повреждение снимка, и не содержат текста, идентификаторов, путей, URI и содержимого. `developer_diagnostics_sink` получает новые ветки исчерпывающего переключателя.

### 15. Проверки

- **Эталон полноты лога.** В контрактных тестах репозитория после каждого вида команды выгрузка базы совпадает с состоянием, собранным из снимка и лога.
- **Формат.** Эталонные файлы и пакеты фактов версий, повторное чтение и запись, построчное повышение версий, потолки длины строк.
- **Долговечность** (тесты `flutter_process`).
  - Процесс прерывается в ходе замены: после удаления, посреди вставок, до и после COMMIT. После повторного открытия граф должен быть либо прежним, либо новым целиком.
  - Процесс прерывается при записи снимка, до и после переименования. Реестр снимков должен остаться согласованным с файлами.
- **Внедрённые ошибки** через `LocalDatabaseConnectionObserver`. Нехватку места даёт `PRAGMA max_page_count`. На production-соединении закрепляются `journal_mode = delete` и `synchronous = 2`.
- **Виджетные тесты** сценариев страницы «Настройки».
- **Бенчмарки.**
  - Экспорт, импорт и восстановление большого графа с замером памяти. Профиль — 1 000 000 сущностей, пример владельца продукта.
  - Накладные расходы лога на команды, включая каскадное архивирование.

### 16. Направление синхронизации

Фиксируется ADR и в этом изменении не реализуется:
- тонкий сервер хранит только зашифрованные файлы и создаёт файл, только если его ещё нет;
- пакеты лога становятся пронумерованными файлами;
- устройство переносит очередь своих команд поверх чужих фактов;
- новое устройство начинает со снимка;
- пакеты связаны хеш-цепочкой.

Текущее изменение не добавляет ничего, нужного только синхронизации (ADR-0009). Идентификаторы устройств, хеши пакетов и очередь команд появятся вместе с ней.

## Risks / Trade-offs

- [Каждая команда пишет отметки и пакет фактов, запись дорожает] → факты пишутся только для затронутых сущностей; бенчмарк накладных расходов, включая каскад.
- [Путь записи в обход единого метода] → отметки ставят триггеры независимо от кода; единый метод требует пустых отметок перед COMMIT; эталон полноты в контрактных тестах.
- [Транзакция замены долгая и требует места под журнал — почти весь прежний граф] → модальный прогресс с отменой, отдельное сообщение о нехватке места, бенчмарк.
- [Журналы операторов и savepoint в памяти при `SQLITE_TEMP_STORE=2`] → транзакция верхнего уровня и небольшие операторы; замер памяти в бенчмарке.
- [После падения посреди замены следующий запуск дольше: SQLite возвращает страницы из журнала] → принято; bootstrap в это время показывает загрузку.
- [Повреждение файла снимка вне SQLite] → контрольная сумма; повреждённый последний снимок пересобирается из базы короткими порциями, и экспорт после этого повторяется; копии, собираемые из повреждённого снимка, не восстанавливаются и уходят по сроку.
- [Постоянный отказ сжатия, например нехватка места] → повтор только при следующем запуске или после ещё порога пакетов; диагностика отказа.
- [Перевод часов смещает суточную отсечку и срок хранения копий] → показания часов — наблюдения (ADR-0006), целостность не нарушается.
- [Ожидающий запрос документа при переносе Activity] → завершается как отмена, человек повторяет действие.
- [Будущая версия формата без функции повышения или эталона] → тест читает эталонный файл и эталонный пакет фактов каждой опубликованной версии.
- [Рост занятого места: снимки и пакеты за срок хранения копий, в том числе до появления копий, и история, удержанная долгим чтением] → сжатие лога, граница хранения и gzip; удержанное чтением удаляет следующее сжатие.
- [Эпоха сменилась без результата с ревизией новой эпохи] → результат «граф заменён» всегда несёт такую ревизию, корневые модели пересоздаются.

## Migration Plan

- Данные не переносятся: база версии 3 создаётся заново. Хранилище предварительной сборки версии 1 или 2 приложение не изменяет и не удаляет, а показывает существующий отказ. README просит очистить данные приложения перед установкой.
- Откат на сборку до этого изменения требует очистки данных: прежние сборки не открывают версию 3.
- Будущие изменения схемы добавляют пошаговые миграции с версии 3, а изменения формата — функции повышения и эталоны. Хранимые снимки и пакеты при смене формата не переписываются: их записи повышаются при чтении по сохранённой версии.

## Context

Каталог дневных выборов живёт в `DailyChoiceCatalogBody`. Календарь уже сделан по дизайну, а секции, карточки и состояния выдачи собраны из виджетов Material прямо в этом файле. Подробный просмотр `DailyChoiceDetailsPage` и форма `DailyChoiceEditPage` — обычные маршруты без дизайна. Страница сама держит состояние удаления, а форма отправляет все поля разом.

Чтение уже даёт всё нужное. По [ADR-0033](../../../docs/adr/0033-coordinate-daily-choice-sections-on-one-revision.md) первая порция обеих секций приходит независимо от раскрытия, вместе с точным количеством и признаком времени. Подробный просмотр подписан на `watchDailyChoice` и получает путь с архивными состояниями. Поэтому менять чтение и схему не нужно.

Дизайн от 01.11.2026 лежит в `context/doable-design/` и `context/doable-design-system/`. Папка игнорируется git и есть только в основном checkout. При расхождении макета и README верим README, как велит сам дизайн. Главные источники правил: README `ChoiceRow`, `ChoiceCheck`, `ReasonChain`, `SectionHeader`, `TimeGroup`, `ChoiceHead`, `ChoicePath`, `DetailRow`, `DateGrid`, `TimeDial`, `ScrollTopButton`.

Параллельно идёт `add-relations-in-batches`. Его фаза 2 приносит `PriorityPicker`, полосу редактирования листа и подробный просмотр связи как лист без маршрута. Фаза 2 ещё не начата.

## Goals / Non-Goals

**Goals:**

- Привести список дня к дизайну, не трогая календарь и модель выдачи.
- Заменить две страницы одной нижней панелью, где выбор меняется на месте.
- Иметь один блок полей даты, времени и приоритета на панель и страницу подтверждения создания.
- Убрать замену пути целиком, без остатков в типах и ветвлениях.
- Не копировать то, что появится в параллельном изменении.

**Non-Goals:**

- Изменение схемы и формата данных. Минуты остаются в домене и хранилище, а защиты неизменности пути в базе нет.
- Новые команды. Строка дат и «Дублировать на даты» идут отдельным изменением.
- Множественное выделение: карточка не получает его параметры.
- Редизайн остальной страницы подтверждения создания и шагов построения пути.
- Строка выбора на вкладке «Выборы» страницы намерения.

## Decisions

Диаграммы ниже упрощённые, в духе C4, как в `add-relations-in-batches`. Они показывают только то, что трудно передать словами.

```text
+-- catalog page / intention page ---------------------+
|  ChoiceRow, SectionHeader   <-- CatalogViewModel      |
+-------------------+-----------------------------------+
                    | tap: showDailyChoiceSheet(id)
                    v
+-- DailyChoiceSheet (root navigator, pageless) --------+
|  ChoiceHead, Tabs                                     |
|  Overview: note, DailyChoiceDetailFields              |
|  Path: ChoicePath                                     |
+-------------------+-----------------------------------+
                    | change(patch), delete()
                    v
           DailyChoiceDetailsViewModel --read--> Repository
                    |                                ^
                    +--write--> Coordinator ---------+
```

- `catalog page / intention page` — каталог на день и вкладка «Выборы» страницы намерения.
- `DailyChoiceSheet` — новая панель. Других экранов просмотра и изменения выбора нет.
- `DailyChoiceDetailFields` — общий блок полей, его же использует подтверждение создания.
- `Coordinator` — `GraphCommandCoordinator`, `Repository` — `PersonalGraphRepository`. Границы модулей не меняются.

### D1. Панель — лист без маршрута

Единственная точка входа `showDailyChoiceSheet` показывает лист через `showDoableSheet` с `hostsMessages: true` по [ADR-0032](../../../docs/adr/0032-present-design-system-sheets-over-root-navigator.md) и [ADR-0042](../../../docs/adr/0042-show-shared-surface-messages-over-operating-sheets.md). `DailyChoiceDetailsRoute`, `DailyChoiceEditRoute` и обе страницы удаляются. Входы — карточка каталога и строка вкладки «Выборы». Подход совпадает с подробным просмотром связи в `add-relations-in-batches`, а долговечная часть решения закреплена в [ADR-0053](../../../docs/adr/0053-show-and-change-daily-choice-in-one-routeless-sheet.md).

Отклонено:

- Маршрут `auto_route`, нарисованный как лист: второй способ показа листов вместо ADR-0032.
- Сохранить страницу и открывать панель только из каталога: появились бы два подробных просмотра одного выбора.

### D2. Запись идёт через одну модель

`DailyChoiceDetailsViewModel` уже владеет подпиской на выбор и получает запись: `change(DailyChoiceFieldsPatch)` и `delete()`. Дата, время, приоритет, описание и выполнение — один вызов с разным патчем, поэтому отдельных обработчиков нет. Модель живёт вместе с панелью, как раньше со страницей.

Состояние операции — закрытый тип: простой, запись, отказ с правом предъявления. Состояние удаления переезжает сюда из `setState` страницы, и обе операции делят один токен. Пока запись идёт, поля и флажок выключены. Отправка второй команды исключена уже интерфейсом, а `DailyChoiceCommandAlreadyRunning` от записи из каталога становится обычным отказом в панели.

Отказ следует протоколу [ADR-0012](../../../docs/adr/0012-centralize-graph-operation-result-presentation.md): модель берёт право через `claimInitiatorFailure`, панель показывает `OperationFailurePresentation` внутри `Notice`, а закрытие панели до результата освобождает право, и отказ предъявляет общая поверхность. Новое значение появляется из подписки после подтверждения, поэтому оптимистичного состояния нет.

`DailyChoiceEditState.toPatch` содержит правило пробельного описания. Оно переезжает в построение `DailyChoiceDescriptionPatch` из текста, потому что форма удаляется, а правило нужно панели.

Отклонено:

- Отдельные модели полей: дублировался бы протокол токена и отказа.
- Оптимистичное обновление: спецификация разрешает показывать значение только после подтверждения записи.

```text
Person      Sheet         ViewModel          Coordinator      Repository
  | 1 tap P1  |               |                   |               |
  |---------->| 2 change      |                   |               |
  |           |-------------->| 3 update command  |               |
  |           | 4 controls off|------------------>|-------------->|
  |           |<--------------|                   |  5 one tx     |
  |           |               | 6 completion      |<--------------|
  |           |               |<------------------|               |
  |           |               | 7 watch: new snapshot             |
  |           |               |<----------------------------------|
  | 8 P1, controls on         |                   |               |
  |<----------|<--------------|                   |               |
```

При отказе шаг 7 не наступает: панель показывает прежнее значение и `Notice`.

### D3. Успех изменения выбора не объявляется

`DailyChoiceCommandKind.update` получает политику «успех без сообщения» из [ADR-0046](../../../docs/adr/0046-keep-edit-failures-on-screen-without-success-message.md). Оба условия ADR выполнены: спецификация запрещает сообщение, а результат виден на месте. Политику задаёт вид операции, поэтому молчит и флажок карточки, как просит дизайн. Строка `dailyChoiceUpdated` удаляется. Создание и удаление остаются на обычной политике: их экран закрывается.

### D4. Лист получает вариант без заголовка

`Sheet.expandable` требует `title`, `text` и `footer`, а у панели их нет: шапка выбора идёт как `pinned`, а нижней кнопки нет. Делать эти параметры необязательными нельзя, потому что появятся бессмысленные сочетания, например заголовок без пояснения. Поэтому `_ExpandableParts` получает закрытый вариант шапки, а `Sheet` — именованный конструктор раскрываемого листа без заголовка с доступным названием. Отступ тела под ручкой такой, как в README `Sheet`.

Компактная высота — общий предел 534 из [ADR-0041](../../../docs/adr/0041-expand-design-system-sheets-by-header-drag.md) и `bottom-sheets`, хотя README `Sheet` рисует панель выбора высотой 560. Отдельный предел ради 26 пикселей сломал бы общее правило раскрываемых листов.

Полоса редактирования приходит из фазы 2 параллельного изменения как параметр листа. Здесь она должна работать и в раскрываемом варианте: появление полосы переводит лист в полный размер и отключает перетаскивание, а её исчезновение оставляет лист полным. Это декларативный параметр, поэтому метод управления размером наружу не выходит.

Несохранённое описание защищает `PopScope`: системное «назад» — единственный выход, потому что с полосой лист не перетаскивается, а затемнения в полном размере нет.

### D5. Один блок полей для панели и создания

`DailyChoicePlanningFields` заменяется `DailyChoiceDetailFields`: строки `DetailRow` с датой, временем и приоритетом и колбэками значений. Панель передаёт их в `change`, подтверждение создания — в свою модель. Блок владеет открытием листов даты и времени, поэтому панель и создание не отличаются. Текстовый ввод даты, `_TimeInputDialog` и `ChoiceChip` удаляются.

Запрет минут живёт в одном месте: циферблат отдаёт `DailyChoiceTime` с нулевыми минутами. Домен не сужается, поэтому схема не меняется, а сохранённое значение с минутами показывается как есть. Подписи времени и даты сейчас собираются в трёх файлах и сводятся к одной функции подписи.

Лист даты использует отметки дней без каталога. Провайдер `dailyChoiceCalendarDayMarksViewModelProvider` привязан к идентичности `DailyChoiceCatalogInstance`, поэтому лист создаёт свой экземпляр и работает и со страницы намерения, и из создания. Отказ получения отметок листа ничего не показывает: дни просто остаются без отметок. Строка отказа принадлежит каталогу.

### D6. Список дня собирается из новых компонентов

В модуль основ добавляются чистые представления без предметных типов по [ADR-0030](../../../docs/adr/0030-keep-design-system-components-presentational.md):

| Компонент | Из чего собран |
|---|---|
| `ChoiceCheck`, `ReasonChain` | Новые, общие для карточки и шапки панели |
| `ChoiceRow`, `ChoiceHead` | Новые, на `ChoiceCheck` и `ReasonChain` |
| `SectionHeader`, `ScrollTopButton`, `DetailRow` | Новые |
| `ChoicePath` | `PathRail`, `PathGlyph` с новой формой круга, `RelationStroke` |
| `DateGrid` | `CalendarHeader` без действия заголовка, `MonthGridWeekday`, `MonthGridDay` |
| `TimeDial` | Новый, переключатель половины суток на `Tabs` |

Подпись группы времени остаётся элементом строки списка, как сейчас. Контейнер `TimeGroup` не нужен: README сам описывает подпись как ещё один элемент `SliverList`, а ленивое построение важнее буквального виджета.

Приоритет передаётся компонентам одним перечислением модуля основ вместо `RelationRowPriority`. Цвет и тон считает модуль, а домен переводится в него на границе. Если `PriorityPicker` из фазы 2 принесёт такое перечисление, берётся оно.

`DailyChoiceCatalogLoaded` получает признак времени всего дня как дизъюнкцию признаков секций. Заголовки секций показываются только с подтверждёнными данными, поэтому при первой загрузке и отказе под заголовком дня стоит `ListState`. Пустой день даёт `EmptyState` в `SliverFillRemaining`.

`_Banner`, `_Status` и `_SliverStatus` удаляются. Для обновления выдачи `ListState` получает вариант `refreshing` из своего README. Устаревшая выдача показывает `Notice` с повтором. `_CompletionSurface` остаётся: он владеет правом отказа карточки. Из `_completionFeedback` уходят тексты хода записи, а `OperationFailurePresentation` остаётся внутри `Notice`.

Ключи `daily-choice-row-*`, `daily-choice-section-*` и `daily-choice-completion-*` сохраняются, чтобы правка тестов шла по смыслу, а не по поиску виджетов.

### D7. Подгрузка следует за построением

Подвал секции с продолжением показывает `ListState.more` и после кадра вызывает `loadMore` той же секции, как `IntentionChoicesSliver._scheduleLoadMore`. Построение подвала означает близость конца, потому что `SliverList` строит элементы с запасом. Вызов идёт только при актуальной выдаче и простаивающей порции, а отказ показывает `ListState.error` с повтором, если он доказанно временный. Правило повтора остаётся прежним.

### D8. Кнопка возврата к началу — кнопка `Scaffold`

`ScrollTopButton` ставится в `floatingActionButton`. Flutter сам размещает плавающее сообщение над такой кнопкой, поэтому сообщение её не перекрывает и никакого сигнала от `GraphOperationPresenter` не нужно. Положение по макету задаёт своя `FloatingActionButtonLocation`.

Кнопку знает только тело каталога, а `Scaffold` стоит выше и у двух страниц разный. Поэтому `DailyChoiceCatalogBody` принимает каркас функцией от тела и кнопки, а `OrdinaryPageScaffold` получает параметр `floatingActionButton`. Вложенный `Scaffold` не подходит: сообщение рисуется в каждом `Scaffold` под `ScaffoldMessenger` и появилось бы дважды.

Отклонено: кнопка в `Stack` с подпиской на показ сообщений. Так получится ровно как в README: кнопка над сообщением. Но это новый сигнал из презентера ради одной анимации. Разница принята: сообщение стоит над кнопкой, а не наоборот.

### D9. Завершение создания закрывает поток

`completeDailyChoiceCreation` снимает подтверждение и корень потока, не заменяя корень маршрутом подробного просмотра. Это частично пересматривает [ADR-0022](../../../docs/adr/0022-complete-creation-flows-within-owned-route-boundaries.md), пересмотр записан в ADR-0053. Снятие совпадает с `leaveDailyChoiceCreation` с разницей в проверке состояния, поэтому общий цикл выносится в одну функцию. Сообщение о создании предъявляет общая поверхность по обычной политике. Идентификатор созданного выбора в `DailyChoiceCreationFlowSaved` и `claimOpening` становится ненужным и удаляется, а защита от второй попытки завершения остаётся. Проверка верхнего безымянного маршрута тоже остаётся.

В `app-navigation` правило «Переход к созданной сущности» теперь закрывает страницы-задачи всегда, а открывает сущность только если этого требует её capability.

### D10. Замена пути удаляется без следов

Удаляются поток из четырёх файлов, `ReplaceDailyChoicePath`, `DailyChoicePathReplaced`, `acceptDailyChoiceReplace`, `DailyChoiceCommandKind.replace`, `_replaceDailyChoicePath`, `ChoicePathPage.forReplacement` и `ChoicePathPurpose.replace`.

Закрытые типы, у которых остался один вариант, тоже уходят: `DailyChoicePickerContext` сводится к его единственному варианту с `launch`, а `DailyChoicePathCommandDiagnosticsType` — к диагностике создания. Назначение поиска `dailyChoicePickerPurpose` теряет ось потока и зависит только от начала. `ConfirmedChoicePath`, `ChoicePathDraft` и поиски остаются ради создания.

Журнал фактов и формат данных не знают отдельного вида замены, поэтому прежние журналы читаются. Тесты слоя данных, которые готовили состояние заменой, выражают его удалением и созданием.

### D11. Страница над листом

Шаг пути открывает страницу намерения обычным `context.router.push`, а связь — лист подробного просмотра из фазы 2 параллельного изменения. `PagelessRoutesObserver` считает верхним маршрут из `didChangeTop`, поэтому над листом страница снова считается верхней, и проверки потоков создания на ней работают. При закрытии страницы лист возвращается, а сброс истории снимает его вместе со страницей под ним. Фаза панели начинает с виджет-теста этих двух переходов.

### D12. Порядок с `add-relations-in-batches`

Список дня и удаление замены не зависят от параллельной ветки и идут от `main`. Перед панелью в эту ветку вливается `change/add-relations-in-batches` с готовой фазой 2, поэтому `PriorityPicker`, полоса листа и лист связи берутся оттуда. Это изменение вливается и архивируется после него.

Дельты этого изменения в семи требованиях опираются на его текущий текст. Перед архивацией они сверяются с итоговым, а сообщение валидатора о ненайденном `Сброс истории пунктом панели` снимается его архивацией.

Отклонено:

- Общий PR с компонентами в `main`: прервал бы фазу 2 ради компонентов без потребителя, а порядок архивации всё равно фиксирован.
- Своя реализация с последующим объединением: две версии одного компонента.

## Risks / Trade-offs

- [Фаза 2 параллельного изменения не готова к началу панели] -> Панель ждёт только её. Список дня и удаление замены приносят ценность без неё.
- [Параллельное изменение поправит общие требования или решит иначе вопрос страницы над листом] -> Дельты сверяются перед архивацией, а D11 проверяется тестом первым.
- [Дельты опираются на требования, которых нет в `main`] -> Валидатор сообщает об этом как `INFO`, CI не падает, а архивация до параллельного изменения отклоняется сама.
- [Сообщение стоит над кнопкой возврата, а в README наоборот] -> Принятое отступление ради отсутствия нового сигнала.
- [Панель на 26 пикселей ниже, чем в README `Sheet`] -> Принятое отступление ради общего предела раскрываемых листов.
- [Флажок выключается на время записи и может мигать] -> Запись локальная и занимает миллисекунды, а вид выключенного флажка не меняет раскладку.
- [Сохранённое 18:30 не отмечено на циферблате] -> Новых значений с минутами не появляется, а такое значение показывается в поле и заменяется выбором часа.
- [Страница подтверждения создания остаётся наполовину без дизайна] -> Меняется только блок полей, остальное идёт отдельным изменением.
- [Переписывается много тестов: 24 файла ссылаются на удаляемые страницы и маршруты, 20 — на старые карточки] -> Ключи строк сохраняются, а старый путь уходит только после появления замены, поэтому покрытие не проседает.

# OpenSpec Change Review: add-tag-colors

## Assessment

**Format version:** 1
**Result:** Changes needed
**Coverage status:** Complete
**Summary:** Предложение, три дельты спецификаций, дизайн, манифест ADR, двухэтапный план и пакет задач этапа 1 согласованы между собой и с кодом. Цвет проходит через тип тега, схему, проекции чтения, захват фактов, общий кодек и замену графа. Найдены все потребители заменяемого контракта переименования и все места, где сравнивается только название, и каждое покрыто задачей. Продуктовые решения не оспариваются, а необходимое поведение не теряется. Две находки касаются исполнения этапа 1. Задача 1.1 делает поле `color` обязательным и добавляет цветной тег в эталон формата раньше, чем база научится хранить и вставлять цвет, поэтому проверки замены и импорта остаются красными до задачи 1.8 (F1). Пересмотр базовых схемы 3 и формата 1 на месте не отражён в README и не определяет поведение сборки на прежней тестовой установке (F2). Избыточны: повторное описание и проверка цвета в общих механизмах копий и переноса (F3), отдельный файл проверки перезапуска (F4) и промежуточная контрольная задача 1.6 (F6). Абзац о версиях схемы в «Локальное сохранение и миграция тегов» снимает действующее обязательство (F5). Принятых остаточных рисков нет.
**Validation:** `mise exec --no-deps -- openspec validate add-tag-colors --strict --no-interactive` завершилась успешно, а `openspec status` показывает 6/6 готовых артефактов; валидация проверяет структуру, а не смысловую полноту. Аудит планирования не запускал тесты, анализатор и сборки. Выводы о падающих проверках сделаны по коду проверок, фикстур и кодека, без запуска.

## Findings

### F1 · Medium — Задача 1.1 ломает проверки замены и импорта до задачи 1.8

- **Evidence:** `tasks.md`, задача 1.1 (строки 9–12): кодек требует поле `color`, а эталоны файла и пакета версии 1 «содержат цветной и бесцветный теги». Проверка задачи — только `test/tag/domain`, `test/graph_format` и `flutter analyze`. После замены графа эталонный файл `test/graph_format/golden/graph_format_v1.jsonl` построчно сравнивается с выгрузкой базы: `test/graph/data/drift_graph_replacement_test.dart:208` (`expect(await graphLines(), _recordLines(golden))`) и `test/data_transfer/graph_import_test.dart:278` (эталон читается через `test/support/graph_import_files.dart:9`). Цветной тег проходит через базу только после трёх задач: 1.2 добавляет столбец, 1.3 — проекции чтения, 1.8 — вставку цвета при замене. Сейчас `lib/src/graph/data/drift_personal_graph_repository_replacement.dart:245` вставляет `TagsCompanion.insert(id:, name:)`, а пропуск nullable-столбца Drift не вызывает ошибки компиляции. Эти проверки впервые запускают задачи 1.8 и 1.10. Кроме того, `test/app/navigation/app_shell_graph_generation_test.dart:361` вручную пишет запись тега без `color` в снимок замены. После 1.1 `_JsonFields._read` (`lib/src/graph_format/graph_format_codec.dart:645`) отклонит её как повреждение. Этот файл не назван ни в одной задаче и выполнится только в `mise run check` задачи 1.18. Оркестратор выполняет задачи по одной в порядке файла. `.claude/rules/testing-scope.md` требует перед завершением задачи запускать проверки изменённых модулей и их прямых потребителей.
- **Impact:** Если запустить прямых потребителей эталона, задачу 1.1 не завершить без работы задач 1.2, 1.3 и 1.8. Если ограничиться узкой проверкой 1.1, набор проверок остаётся красным на протяжении задач 1.1–1.7. Поломку снимка из `app_shell_graph_generation_test.dart` тогда обнаружит только итоговая задача 1.18, в которой не предусмотрено правок файлов.
- **Required change:** Упорядочить работу так, чтобы после каждой задачи этапа 1 проходили проверки, читающие изменённые фикстуры формата. Цветной тег попадает в общий эталон файла не раньше задачи, после которой схема, проекции чтения и вставка при замене переносят цвет. Все рукописные записи формата, включая снимок в `app_shell_graph_generation_test.dart`, обновляются в той задаче, которая делает `color` обязательным. Проверка каждой такой задачи запускает затронутых потребителей эталона.

### F2 · Medium — Пересмотр базовых схемы 3 и формата 1 на месте не отражён в README и не определяет поведение сборки на прежней установке

- **Evidence:** `design.md`, «Migration Plan» (строки 156–158): номера схемы БД 3 и формата 1 сохраняются, а их определения меняются на месте. Там же сказано, что перед проверкой новой сборки на прежней установке нужен свежий набор данных, а для отката — набор прежнего кода. Ни одна задача 1.1–1.18 не меняет `README.md`; задача 1.18 лишь сообщает в сессии о ручных проверках «на согласованном наборе тестовых данных». Раздел `README.md:13–34` «Local data before launch and rollback» — действующая инструкция для таких случаев. Он требует очищать данные только для схем 1–2 и для сборок схемы 3 без вида факта и описывает откат только к сборкам без схемы 3. При открытии хранилища сборка проверяет лишь `PRAGMA user_version` (`lib/src/data/local/migrations/migration_strategy.dart:128`, `_verifyStoredSchemaVersion`). Поэтому база прежней сборки с маркером 3 без `tags.color` проходит bootstrap. Первый запрос со столбцом `color` получает ошибку SQLite `no such column`, которую `lib/src/data/local/sqlite_failure_classifier.dart:48` относит к `SqliteUnexpectedFailure`. Снимки и пакеты без `color` новый кодек отклоняет как повреждённые; после отката прежний кодек так же отклонит неизвестное поле `color`. Архивный дизайн `add-graph-export-import`, решение 1 (строка 42), выбрал новый маркер 3, потому что иначе «файл версии 1 прошёл бы проверку маркера при другой структуре»; последующие пересмотры схемы 3 на месте отражались в README. По `.claude/rules/testing-scope.md` пользователь проверяет сборку этапа на своём устройстве.
- **Impact:** Если поставить сборку этапа 1 поверх текущей тестовой установки, приложение откроется. Но каталог тегов, краткие данные намерений с тегами и команды тегов будут завершаться непредвиденной ошибкой, а копии — отказом из-за повреждения, и ничто не подскажет, что данные нужно очистить. README при этом утверждает, что такие сборки схемы 3 совместимы, а откат к сборке без цвета не описывает.
- **Required change:** Запланировать обновление раздела README «Local data before launch and rollback». В нём указать, что данные установок, созданных сборками до этого изменения (схема 3 и формат 1 без цвета тега вместе со снимками, логом и копиями), очищаются перед первым запуском новой сборки и что та же очистка нужна при откате к такой сборке. В дизайне указать, как новая сборка ведёт себя на такой установке.
- **Decision needed:** Сохранить маркер 3? Тогда прежняя тестовая база проходит bootstrap и отказывает при первом чтении тегов непредвиденной ошибкой. Или ввести новый базовый маркер без миграции, чтобы bootstrap сообщал о повреждённых локальных данных, как для схем 1–2? От выбора зависит, увидит ли пользователь при проверке на устройстве понятный отказ при запуске или разрозненные ошибки на экранах.

### F3 · Medium — Цвет повторно описан и проверен в общих механизмах копий и переноса, которые уже переносят его вместе с записью тега

- **Evidence:** В `specs/graph-backups/spec.md` требование «Список резервных копий» меняет только пример сценария (строка 13: «изменил цвет одного тега» вместо «изменил описание одного намерения»). Требование «Восстановление копии» добавляет сценарий «Восстановление возвращает цвета тегов на момент копии» (строки 39–43), не меняя текста требования. Действующие требования уже дают этот результат. Копия хранит граф «в том же составе, что и файл экспорта», а цвет в этот состав добавляет дельта `graph-export-import`. Восстановление заменяет граф состоянием копии. Изменённым считается тег, который «изменялся между ними». `GraphChangeTally` (`lib/src/graph_backups/graph_change_summary.dart:39–142`) считает только виды фактов и ключи сущностей, не читая содержимого записей. `GraphRestore` (`lib/src/data_transfer/application/graph_restore.dart:102–182`) собирает состояние на позиции копии, пишет из него снимок замены и передаёт его в `GraphReplacement`. Абзац `specs/graph-export-import/spec.md:8` повторяет два правила: независимость цвета от темы и языка из нового требования «Цвет тега» и сохранение данных сущностей из требования «Импорт с заменой графа». От этих повторов происходят три задачи. Задача 1.9 не меняет кода и повторно проверяет сводки и восстановление с цветами. Второй критерий 1.10 добавляет примеры повреждённого цвета на уровне импорта, хотя 1.1 проверяет их в общем кодеке, а импорт одинаково отклоняет любое повреждение формата. Второй критерий 1.7 расширяет проверки сборки состояния, сжатия и пересборки снимка, а эти механизмы переносят `TagRecord` с обязательным цветом через кодек (задача 1.1) и чтение записей из базы (задача 1.3).
- **Impact:** План содержит задачу размера M и расширения ещё трёх наборов проверок. Они не ловят потерь цвета сверх проверок кодека, проекций, вставки при замене и эталона полноты, но их придётся сопровождать. Кроме того, `graph-backups` выглядит изменённой в поведении, которое на деле не меняется.
- **Required change:** Убрать из дельты `graph-backups` изменения требований «Список резервных копий» и «Восстановление копии», оставив изменение «Копии после обновления приложения». Из «Состав файла экспорта» убрать абзац о переносе цвета, сохранив изменение состава и пример сквозного переноса. Проверять цвет в истории и переносе только там, где он может потеряться: в кодеке, проекциях и захвате фактов, вставке при замене, эталоне полноты и существующей сквозной проверке экспорта и импорта. Для этого удалить задачу 1.9, примеры повреждённого цвета из 1.10 и расширения проверок сборки состояния, сжатия и пересборки снимка из 1.7. Согласовать с этим предложение, таблицу проверок и раздел рисков дизайна.

### F4 · Medium — Задача 1.5 создаёт второй файл проверки перезапуска вместо расширения существующего

- **Evidence:** `tasks.md`, задача 1.5 (строки 46–53), создаёт `test/graph/data/file_backed_tag_color_test.dart`. После повторного открытия файловой БД эта проверка сверяет цвета, а также идентификаторы, назначения активному и архивированному намерениям и их порядок. Существующая проверка `test/graph/data/file_backed_tag_durability_test.dart:112` («чтение, назначение архивированному действию, навигация и снятие сохраняются после перезапусков») уже создаёт тег, назначает его активному и архивированному намерениям и после нескольких перезапусков сверяет каталог, назначения и упорядоченную навигацию. Именно она подтверждает сценарий «Теги сохраняются после полного перезапуска», в который дельта добавила синий цвет. Запись и чтение цвета, правку только цвета и явный `NULL` проверяет задача 1.4 на том же репозитории. Значение столбца в одном файле SQLite после повторного открытия сохраняется одинаково для любого поля, а репозиторий не кэширует теги.
- **Impact:** Два файла с отдельными фикстурами проверяют один сценарий перезапуска. Задача размера S и зависимость от неё добавляют работу, но не ловят новых регрессий.
- **Required change:** Удалить задачу 1.5 и её отдельный файл. Если в сценарии «Теги сохраняются после полного перезапуска» остаётся цвет, подтвердить его в существующей проверке перезапуска: добавить в неё цветной тег и правку только цвета, не проверяя повторно идентификаторы, назначения и порядок. Обновить зависимости, которые ссылаются на 1.5.

### F5 · Low — Абзац о версиях схемы снимает действующее обязательство и описывает устройство схемы

- **Evidence:** `specs/tag-management/spec.md`, требование «Локальное сохранение и миграция тегов» (строка 89), заменяет канонический абзац `openspec/specs/tag-management/spec.md:373`. Из него удалено правило: хранилище с маркером версии схемы, отличным от текущего, MUST NOT приводиться к текущей схеме и изменяться. Удаление такого хранилища по-прежнему запрещает следующий абзац требования. Взамен добавлены фраза «Текущая базовая схема SHALL непосредственно хранить цвет тега» и утверждения, что миграции не требуются. `local-data-lifecycle` запрещает изменять только хранилище более новой версии. Проверки `test/data/local/bootstrap/local_data_bootstrap_test.dart:255–279` подтверждают, что хранилище предварительных схем 1 и 2 классифицируется как повреждение и не изменяется. Сохранение цвета уже обещает перечень данных в первом предложении того же требования (строка 85).
- **Impact:** После архивации ни одна спецификация не запретит изменять хранилище неподдерживаемой предварительной версии, и существующие проверки останутся без требования. Каноническая спецификация вместо наблюдаемого обещания получит описание устройства схемы.
- **Required change:** Сохранить запрет приводить к текущей схеме и изменять хранилище неподдерживаемой версии либо явно обосновать отказ от него и привязать проверки к другому требованию. Цвет упоминать только в перечне сохраняемых данных, без фразы о базовой схеме.

### F6 · Low — Промежуточная задача 1.6 повторяет проверки, которые уже выполняют соседние задачи

- **Evidence:** `tasks.md`, задача 1.6 (строки 55–62), не меняет файлов и повторно запускает проверки задач 1.1–1.5 и `openspec validate`, а задачи 1.7–1.16 зависят от неё. Задача 1.18 снова выполняет `mise run check` и `openspec validate`. Шаблон задач схемы (`openspec/schemas/intent-driven/templates/tasks.md`) предусматривает одну контрольную задачу — в конце пакета. `.claude/rules/testing-scope.md` ограничивает проверку задачи изменёнными модулями и их прямыми потребителями. До 1.6 не запускается только одна из её проверок — `test/tag/application/tag_read_contract_test.dart`. Она создаёт `Tag` (`:231`), то есть её затрагивает изменение конструктора в задаче 1.1.
- **Impact:** Оркестратор тратит отдельный запуск задачи на проверки, которые ничего не добавляют к проверкам соседних задач. Повторная валидация OpenSpec во время реализации проверяет неизменившиеся артефакты.
- **Required change:** Удалить задачу 1.6, перенести `tag_read_contract_test.dart` в проверку задачи 1.1 и указать в зависимостях задач 1.7–1.16 те задачи, которые создают нужные им контракты.

## Review coverage

Выполнен первичный широкий аудит изменения по схеме `intent-driven`: proposal → specs → design → adr → plan → tasks. Все шесть артефактов на месте, а `review.md` создан впервые. Прочитаны предложение и три дельты (`tag-management`, `graph-export-import`, `graph-backups`) вместе с соответствующими каноническими спецификациями. Прочитаны также `local-data-lifecycle` и требования `intention-management` о тегах в совместном поиске, черновике создания и временных отметках. Изучены манифест ADR, ADR-0002, ADR-0009, ADR-0012, ADR-0013, ADR-0016, ADR-0019, ADR-0029, ADR-0030 и ADR-0034–ADR-0036, словарь `CONTEXT.md`, описания `TagDot`, `TagColorPicker` и `TagChip` из дизайн-системы, правила `.claude/rules`, шаблоны схемы, `README.md` и задачи `mise`. Задачи этапа 2 ещё не составлены: их запланирует оркестратор, поэтому этап 2 проверен только на уровне плана.

Каждое обязательство прослежено от предложения через требования и решения 1–7 дизайна до задач 1.1–1.18 и их проверок. Проверены тип `TagColor` и обязательный параметр `Tag.color`; ограничение `CHECK` столбца; общий декодер, отличающий отсутствующий столбец от `NULL`; проекции чтения каталога, назначений, наблюдения, порций записей и захвата фактов; существующий триггер обновления тега. Проверены также поле `color` в каноническом порядке кодека и вставка при замене графа. Для командного контракта проверены `UpdateTag`, `TagUpdated` и `TagUpdatedChange` с ключом `ExistingTagKey`, а также предъявление «Тег изменён» и тип диагностики. Среди потребителей проверены каталог, назначения, навигация, краткие данные намерений, условия фильтра, черновик и редактор. Все пути из задач существуют, кроме двух, помеченных как новые. Ошибки вида «новое обязательство без работы» или «работа без обоснования» помимо F3, F4 и F6 не найдены.

С кодом сверены `Tag`, `TagCommand`, `TagCommandSuccess` и `TagChange`, репозиторий команд, чтений, лога фактов и замены, `GraphFactCapture`, `stored_graph_rows.dart`, схемы `tag_schema.drift` и `graph_log_schema.drift`, стратегия миграций и классификатор отказов SQLite. Сверены также кодек, записи и эталоны формата, `GraphChangeTally`, `GraphRestore`, `GraphCommandCoordinator`, `GraphOperationPresenter`, `diagnostics_sink.dart`, локализации, модели каталога, назначений, навигации, каталога намерений, условий фильтра, черновика и редактора, `IntentionSummaryView` и маршрутизатор. Из проверок и фикстур просмотрены потребители эталонов формата, рукописный снимок замены, файловая проверка перезапуска тегов, проверки bootstrap для предварительных маркеров и эталонная выгрузка полноты лога.

Рассмотрены и не записаны в замечания следующие вопросы. Наблюдение `_watchTag` и проверки согласованности навигации сравнивают только название, но лишь при одной и той же ревизии, а правка цвета ревизию меняет. Каталог, назначения и краткие данные намерений заменяют тег целиком, поэтому цвет дойдёт до них после смены типа события. Потерять правку цвета из-за двух одновременно открытых редакторов нельзя: редактор открывается в корневом стеке поверх оболочки. Проверка наличия столбца `color` в декодере повторяет существующую практику `requiredStoredString`. Перечень мест показа в требовании «Отображение цвета тега» совпадает с местами, где интерфейс сейчас выводит название тега. Диагностика не получает данных тега. Рост записи формата пренебрежимо мал. Новой долговременной ADR изменение не требует. Статус `proposed` у ADR архивных изменений — общее состояние репозитория, и манифест его раскрывает. Затронуты области данных, миграции, поставки и отката, публичного формата, надёжности лога фактов и ревизий, пользовательского опыта, доступности и документации. Существенных вопросов безопасности, приватности и производительности не выявлено.

## Findings

### F9 · Low — Задача 4.4 меняет тип отметки строки тега, но не обновляет и не проверяет его потребителей

- **Evidence:** Критерий задачи 4.4 требует, чтобы «отметки выбора и фильтра различались типом». Сейчас `TagRow.mark` имеет тип `enum TagRowMark { none, checked }` (`lib/src/design_system/components/tag_row.dart`). Его используют панель (`lib/src/tag/presentation/panel/tags_panel.dart:424`) и помощники проверок, которые читают `TagRow.mark` как `TagRowMark`: `test/tag/presentation/panel/tags_panel_test.dart:1255` и `test/app/tag_assignment_app_flow_test.dart:254`. В предполагаемых файлах и проверке 4.4 есть только `tag_row_test.dart` и `doable_icon_test.dart`, а `flutter analyze` нет. Панель и её проверки впервые компилируются в задаче 4.6. `tag_assignment_app_flow_test.dart` впервые проверяет `flutter analyze` задачи 4.8, а затем тесты задачи 4.9.
- **Impact:** Если 4.4 меняет тип `mark`, как предполагает её критерий, после неё панель и два набора проверок не компилируются. Задачи 4.5–4.7 выполняются с ошибками анализатора. Задача 4.8 упирается в ошибку в файле вне своего охвата и исправляет её работой, которая ей не принадлежит.
- **Required change:** После задачи 4.4 пакет компилируется. Задача либо сохраняет совместимость текущих вызовов и чтений отметки выбора, либо сама обновляет `tags_panel.dart` и помощники в `tags_panel_test.dart` и `tag_assignment_app_flow_test.dart`. Проверка 4.4 включает `flutter analyze` и запуск изменённых потребителей.

### F10 · Low — Задача 4.11 удаляет единственные проверки непарного surrogate в поле поиска, которое остаётся в панели

- **Evidence:** Панель использует `TagCatalogSearchController` (`lib/src/tag/presentation/panel/tags_panel.dart:62`). По комментарию в `lib/src/tag/presentation/catalog/tag_catalog_search_controller.dart` контроллер обозначает недопустимые символы только при отрисовке, потому что движок Flutter не строит абзац с непарным UTF-16 surrogate. Единственные проверки этого поведения на уровне виджета — `test/tag/presentation/catalog/tag_catalog_search_page_test.dart` (строки 688, 747, 905 и 1061–1100) и его части `tag_catalog_draft_search_scenarios.dart` (строки 44 и 157) и `tag_catalog_search_recovery_scenarios.dart` (строка 25). Они подтверждают, что поле с непарным surrogate, в том числе внутри области набора, сохраняет ввод, показывает ошибку, оставляет последний корректный фильтр и не бросает исключения. Задача 4.11 удаляет `test/tag/presentation/catalog/`, кроме `tag_catalog_filter_test.dart`. Оставшийся набор проверяет фильтр, а не поле. Проверки панели вводят только `U+0000`: `test/tag/presentation/panel/tags_panel_test.dart:247` и `:263`, `tags_panel_view_model_test.dart:208`, `:297` и `:449`. Требование `tag-management` «Обработка некорректного поискового запроса» обязывает панель сохранять оба вида некорректного ввода с ошибкой поля.
- **Impact:** После фазы 4 ни одна проверка не поймает регресс в сохранённом контроллере. Достаточно упростить `_displayText` или заменить контроллер при следующей перерисовке, и вставленный текст с непарным surrogate снова вызовет исключение отрисовки. Поиск панели перестанет сохранять такой ввод с ошибкой, как требует спецификация.
- **Required change:** До удаления проверок прежнего каталога фаза 4 переносит проверку непарного surrogate на панель. Поле должно сохранять значение с непарным surrogate, в том числе внутри области набора, показывать ошибку ввода, оставлять последний корректный фильтр и не бросать исключений, а исправленный ввод — сразу применяться. Задача, которая удаляет прежние проверки, запускает перенесённую.

## Accepted risks

### AR1 · Задачи 1.2 и 1.5 требуют полных прогонов тестов вместо проверок затронутых потребителей

- **Evidence:** [Задача 1.2](tasks.md) требует `mise run check:tests -- 0 1` и `mise run check:process-tests`, задача 1.5 — повторный `mise run check:tests -- 0 1`. По [mise.toml](../../../mise.toml) и [tool/test_shard.sh](../../../tool/test_shard.sh) это все 342 обычных набора и все наборы с вложенным Flutter. [AGENTS.md](../../../AGENTS.md), Test execution scope, ограничивает проверку задачи изменёнными модулями и непосредственными потребителями, а полный `mise run check` оставляет завершению фазы — он уже есть в задаче 1.7. Поиск по `test/` показывает, что задача 1.2 затрагивает около 133 наборов: они собирают `Tag`, вставляют строки `tags` или зависят от `tag_storage_fixture.dart` и `graph_log_completeness_reference.dart`. Тегов касаются три из пяти наборов с меткой `flutter_process`.
- **Potential impact:** До проверки фазы в задаче 1.7 весь набор прогоняется ещё дважды, и около 60% наборов в этих прогонах не связаны с тегами. Сбой несвязанного набора задерживает задачу. Исполнитель получает расходящиеся указания задачи и правила репозитория.
- **Acceptance rationale:** Задача 1.2 и так затрагивает около 40% наборов, поэтому полный прогон даёт простую страховку от пропущенного потребителя при переходе общего контракта тега и при смене видимого порядка в 1.5. Её ценность человек ставит выше лишнего времени исполнения.
- **Scope and assumptions:** Только проверки задач 1.2 и 1.5 фазы 1 в их текущей формулировке. По этому решению указание задачи о полном прогоне имеет приоритет над правилом охвата для этих двух задач. Проверку фазы задачей 1.7 приёмка не меняет и не распространяется на другие задачи и фазы.
- **Reopen when:** Задачи 1.2 или 1.5 перепланируются либо меняются их проверки. Новая задача копирует полный прогон со ссылкой на эту приёмку. Правило Test execution scope или порядок исполнения задач оркестратором запрещают полные прогоны внутри задачи. Полный прогон внутри задачи не удаётся завершить.
- **Acceptance authority:** Явное решение пользователя при разрешении F4 22.10.2026: «Принять риск» — оставить полные прогоны в задачах 1.2 и 1.5 и записать остаточный риск.
- **Originating finding:** F4
- **Acceptance lifetime:** Change-scoped

## Review coverage

Аудит ограничен планированием фазы 4. Пакет задач 4.1–4.13 сопоставлен с фазой 4 плана — целью, результатом, входящими и исключёнными границами и условием готовности, а также с направлением плана и ограничением «Удаление в конце». Источниками сверки служили proposal, delta-спецификации `tag-management`, `intention-management`, `app-navigation` и `graph-export-import`, решения 5–12 и раздел «Migration Plan» дизайна, манифест ADR, ADR-0040 и ADR-0042. Сверены также README компонентов `TagRow`, `Sheet` и `Button` и исходный SVG отметки `row.no` в `TagsPanel.dc.html`.

Сценарии фазы прослежены до задач и их проверок. Для черновика в панели это отметки и изменение набора без записи, поиск, возврат из листа изменения, удалённый тег, отметка созданного и продублированного тега и закрытие листа или панели до подтверждения. Для панели над панелью создания — взаимное исключение с сохранением, «назад», возврат той же панели с черновиком и самостоятельный тег при сбросе и отказе создания. Для фильтра — текущие условия, переключение по кругу, «Сбросить», созданный в фильтре тег, создание без назначений, удаление тега в фильтре другого поиска, локализация и однократное объявление надобности. Для навигации — панель фильтра над каталогом намерений, шапка без кнопки тегов и позднее удаление намерения при открытой панели фильтра. Охваты сценариев «Каскад сохраняет разные назначения» и «Восстановление меняет охват только намерения» проверяются каталогом с условием по тегу вместо навигации по тегу. Пробелов покрытия и лишних задач, кроме F9 и F10, не найдено.

Коммит 44bc6886 только дописал пакет фазы 4: 154 строки добавлено, ни одной не удалено. Задачи фаз 1–3 не изменены и отмечены выполненными, новые задачи не отмечены, заголовок пакета совпадает с планом. Каждая задача стоит после своих зависимостей, поэтому файловый порядок совпадает с порядком исполнения. Контрольная задача 4.13 проверяет условие готовности через `mise run check`, строгую проверку OpenSpec, `mise run codegen-check`, поиск удалённых имён и сборку APK и перечисляет ручные проверки на устройстве. Все пути из задач существуют; новым помечен только `exclude.svg`. Задачи не требуют устройства и замеров времени в тестах.

Исходные точки задач сверены с кодом. Для 4.1: у `TagsPanelContext` пока только вариант назначения, модель панели считает снимок режима просмотра неожиданным, а `IntentionDraftTagSet` даёт только добавление. Для 4.2: панель создания открывает прежний каталог маршрутом с `TagDraftContext` и флагом выбора тегов уже исключает отправку и повторное открытие. Для 4.3 и 4.8: модель условий меняет условия через `applySelection`, `toggleRequirement` и `remove`, отбрасывает удалённые теги и передаёт фильтр модели каталога. Для 4.4 и 4.5: в `Button` нет вида text, у `Sheet.expandable` нет действия шапки, у `TagRow` нет отметок фильтра, иконки исключения нет. Для 4.12: удаление индекса на месте не мешает прежним установкам, потому что при открытии приложение проверяет только отсутствие схемы в новом хранилище и маркер версии (`lib/src/data/local/migrations/migration_strategy.dart`).

Поиском по `test/` и `benchmark/` прослежены потребители удаляемых и меняемых имён. Это выбор условия и передача выбора, вход выбора тегов в панели создания, кнопка `catalog-open-tags`, маршруты и страницы каталога, редактора и навигации, `TagSelectionContext` с вариантами и действиями, `tagCatalogViewModelProvider`, `getTaggedIntentionsPage` и `getTagAssignmentStatus` с событиями диагностики. Бенчмарки удаляемых имён не используют.

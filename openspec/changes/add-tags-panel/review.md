## Accepted risks

### AR1 · Задачи 1.2 и 1.5 требуют полных прогонов тестов вместо проверок затронутых потребителей

- **Evidence:** [Задача 1.2](tasks.md) требует `mise run check:tests -- 0 1` и `mise run check:process-tests`, задача 1.5 — повторный `mise run check:tests -- 0 1`. По [mise.toml](../../../mise.toml) и [tool/test_shard.sh](../../../tool/test_shard.sh) это все 342 обычных набора и все наборы с вложенным Flutter. [AGENTS.md](../../../AGENTS.md), Test execution scope, ограничивает проверку задачи изменёнными модулями и непосредственными потребителями, а полный `mise run check` оставляет завершению фазы — он уже есть в задаче 1.7. Поиск по `test/` показывает, что задача 1.2 затрагивает около 133 наборов: они собирают `Tag`, вставляют строки `tags` или зависят от `tag_storage_fixture.dart` и `graph_log_completeness_reference.dart`. Тегов касаются три из пяти наборов с меткой `flutter_process`.
- **Potential impact:** До проверки фазы в задаче 1.7 весь набор прогоняется ещё дважды, и около 60% наборов в этих прогонах не связаны с тегами. Сбой несвязанного набора задерживает задачу. Исполнитель получает расходящиеся указания задачи и правила репозитория.
- **Acceptance rationale:** Задача 1.2 и так затрагивает около 40% наборов, поэтому полный прогон даёт простую страховку от пропущенного потребителя при переходе общего контракта тега и при смене видимого порядка в 1.5. Её ценность человек ставит выше лишнего времени исполнения.
- **Scope and assumptions:** Только проверки задач 1.2 и 1.5 фазы 1 в их текущей формулировке. По этому решению указание задачи о полном прогоне имеет приоритет над правилом охвата для этих двух задач. Проверку фазы задачей 1.7 приёмка не меняет и не распространяется на другие задачи и фазы.
- **Reopen when:** Задачи 1.2 или 1.5 перепланируются либо меняются их проверки. Новая задача копирует полный прогон со ссылкой на эту приёмку. Правило Test execution scope или порядок исполнения задач оркестратором запрещают полные прогоны внутри задачи. Полный прогон внутри задачи не удаётся завершить.
- **Acceptance authority:** Явное решение пользователя при разрешении F4 22.10.2026: «Принять риск» — оставить полные прогоны в задачах 1.2 и 1.5 и записать остаточный риск.
- **Originating finding:** F4
- **Acceptance lifetime:** Change-scoped

## Review coverage

Аудит ограничен планированием фазы 4. Пакет задач 4.1–4.13 сопоставлен с фазой 4 плана — целью, результатом, входящими и исключёнными границами и условием готовности, а также с направлением плана и ограничением «Удаление в конце». Источниками сверки служили proposal, delta-спецификации `tag-management`, `intention-management`, `app-navigation` и `graph-export-import`, решения 5–12 и раздел «Migration Plan» дизайна, манифест ADR, ADR-0040 и ADR-0042. Сверены также README компонентов `TagRow`, `Sheet` и `Button` и исходный SVG отметки `row.no` в `TagsPanel.dc.html`.

Сценарии фазы прослежены до задач и их проверок. Для черновика в панели это отметки и изменение набора без записи, поиск, возврат из листа изменения, удалённый тег, отметка созданного и продублированного тега и закрытие листа или панели до подтверждения. Для панели над панелью создания — взаимное исключение с сохранением, «назад», возврат той же панели с черновиком и самостоятельный тег при сбросе и отказе создания. Для фильтра — текущие условия, переключение по кругу, «Сбросить», созданный в фильтре тег, создание без назначений, удаление тега в фильтре другого поиска, локализация и однократное объявление надобности. Для навигации — панель фильтра над каталогом намерений, шапка без кнопки тегов и позднее удаление намерения при открытой панели фильтра. Охваты сценариев «Каскад сохраняет разные назначения» и «Восстановление меняет охват только намерения» проверяются каталогом с условием по тегу вместо навигации по тегу. Пробелов покрытия и лишних задач не найдено.

Коммит 44bc6886 только дописал пакет фазы 4: 154 строки добавлено, ни одной не удалено. Задачи фаз 1–3 не изменены и отмечены выполненными, новые задачи не отмечены, заголовок пакета совпадает с планом. Каждая задача стоит после своих зависимостей, поэтому файловый порядок совпадает с порядком исполнения. Контрольная задача 4.13 проверяет условие готовности через `mise run check`, строгую проверку OpenSpec, `mise run codegen-check`, поиск удалённых имён и сборку APK и перечисляет ручные проверки на устройстве. Все пути из задач существуют; новым помечен только `exclude.svg`. Задачи не требуют устройства и замеров времени в тестах.

Исходные точки задач сверены с кодом. Для 4.1: у `TagsPanelContext` пока только вариант назначения, модель панели считает снимок режима просмотра неожиданным, а `IntentionDraftTagSet` даёт только добавление. Для 4.2: панель создания открывает прежний каталог маршрутом с `TagDraftContext` и флагом выбора тегов уже исключает отправку и повторное открытие. Для 4.3 и 4.8: модель условий меняет условия через `applySelection`, `toggleRequirement` и `remove`, отбрасывает удалённые теги и передаёт фильтр модели каталога. Для 4.4 и 4.5: в `Button` нет вида text, у `Sheet.expandable` нет действия шапки, у `TagRow` нет отметок фильтра, иконки исключения нет. Для 4.12: удаление индекса на месте не мешает прежним установкам, потому что при открытии приложение проверяет только отсутствие схемы в новом хранилище и маркер версии (`lib/src/data/local/migrations/migration_strategy.dart`).

Поиском по `test/` и `benchmark/` прослежены потребители удаляемых и меняемых имён. Это выбор условия и передача выбора, вход выбора тегов в панели создания, кнопка `catalog-open-tags`, маршруты и страницы каталога, редактора и навигации, `TagSelectionContext` с вариантами и действиями, `tagCatalogViewModelProvider`, `getTaggedIntentionsPage` и `getTagAssignmentStatus` с событиями диагностики. Каждый потребитель указан в задаче, которая его задевает, или в более ранней. Проверка непарного surrogate в поле поиска, которую задача 4.11 удаляет вместе с `test/tag/presentation/catalog/`, переносится той же задачей в `test/tag/presentation/panel/tags_panel_test.dart` до удаления: панель продолжает использовать `TagCatalogSearchController`, а проверки панели вводили только `U+0000`. Потребители `TagRow.mark` — панель тегов и помощники `tags_panel_test.dart` и `tag_assignment_app_flow_test.dart` — указаны в задаче 4.4, которая меняет тип отметки, вместе с `flutter analyze` и запуском их наборов. Общие помощники проверок покрывает `flutter analyze` задач 4.8, 4.9, 4.11 и 4.12. Бенчмарки удаляемых имён не используют.

## Findings

### F2 · Medium — Поиск с окружающими пробелами одновременно должен скрывать и показывать совпадающий тег

- **Evidence:** В [спецификации тегов](specs/tag-management/spec.md) требование «Создание тега из панели» и сценарий «Совпадающее название не предлагает создание» требуют показать «Дом» для запроса `  дом  ` и убрать строку создания. Требование «Поиск тегов в панели» сохраняет буквальное вхождение запроса и не определяет удаление его окружающих пробелов. [Дизайн](design.md), решение 5, переносит существующий поисковый фильтр. [TagCatalogFilter.fromInput](../../../lib/src/tag/presentation/catalog/tag_catalog_filter.dart) сохраняет пробелы, а [тест фильтра](../../../test/tag/presentation/catalog/tag_catalog_filter_test.dart), «сохраняет окружающие пробелы запроса», явно проверяет, что ` дом ` не находит «Дом». При этом исходный [макет TagsPanel](../../../context/doable-design/design/TagsPanel.dc.html) использует `st.q.trim()` для поискового значения.
- **Impact:** При переносе существующего фильтра запрос с пробелами скрывает точное совпадение, а проверка уникальности одновременно запрещает предложить создание. Пользователь получает отсутствие результатов для существующего тега, вопреки новому сценарию. Реализатору приходится самостоятельно выбирать между общим правилом поиска и примером.
- **Required change:** Согласовать общее правило поиска и дизайн с уже заданным результатом для `  дом  `: явно определить применяемый запрос, сохранение исходного текста поля и смысл внутренних пробелов. В фазе 2 предусмотреть изменение существующей проверки пробелов вместе с фильтром; проверка должна показывать существующий тег и отсутствие предложения дубликата.

### F3 · Medium — Индекс навигации удаляется за три фазы до её потребителя

- **Evidence:** [Задача 1.6](tasks.md) удаляет `tag_assignments_tag_order` и прямо оставляет навигацию по тегу без этого индекса до фазы 4. Между тем [план](plan.md), Direction и Plan Constraints, сохраняет работоспособность прежних страниц до их замены. [Текущий запрос навигации](../../../lib/src/graph/data/drift_personal_graph_repository_tagged_intentions.dart), `_readTaggedIntentionsPage`, получает каждую порцию по `tag_id`, границе `creation_sequence` и `ORDER BY a.creation_sequence LIMIT …` внутри общего последовательного исполнителя. Индекс из [tag_schema.drift](../../../lib/src/data/local/schema/tag_schema.drift) соответствует именно этому запросу и не зависит от удаляемого `tag_creation_sequence`. В проверке `EXPLAIN QUERY PLAN` на минимальной SQLite-схеме с теми же ключами запрос с индексом использовал `(tag_id=? AND creation_sequence>?)`; без него — индекс уникальности `(tag_id, intention_id)` и `USE TEMP B-TREE FOR ORDER BY`.
- **Impact:** Пока прежняя страница остаётся доступной, каждая следующая порция снова обрабатывает назначения выбранного тега и сортирует подходящие строки. Это ухудшает стоимость просмотра тега с большим числом намерений и может задерживать другие операции общей очереди. Малое число самих тегов, на которое ссылается дизайн, не ограничивает число их назначений. Текущий [тест стоимости чтения](../../../test/graph/data/drift_tagged_entities_read_cost_test.dart) считает возвращённые строки и такого ухудшения плана SQL не обнаруживает; замеры времени в аудите не выполнялись.
- **Required change:** Сохранить `tag_assignments_tag_order` в фазе 1 и удалить его вместе с запросом навигации в фазе 4. Согласовать задачу 1.6 и решение 3 дизайна, а отложенное удаление отразить в границах фазы 4 `plan.md`. Удаление копии порядка тега и действительно потерявших потребителей объектов в фазе 1 этому не препятствует.

### F4 · Medium — Задачи требуют полных прогонов вместо проверок затронутых потребителей

- **Evidence:** [Задача 1.2](tasks.md) требует `mise run check:tests -- 0 1` и `mise run check:process-tests`, задача 1.5 — повторный `mise run check:tests -- 0 1`. По [mise.toml](../../../mise.toml) и [tool/test_shard.sh](../../../tool/test_shard.sh) это весь обычный набор и весь набор тестов с вложенным Flutter, а не выбор затронутых модулей. [AGENTS.md](../../../AGENTS.md), Test execution scope, ограничивает проверку отдельной задачи изменёнными модулями и непосредственно затронутыми потребителями. Механическое добавление поля `Tag` и изменение порядка требуют проверки этих потребителей, но не всех независимых компонентов проекта.
- **Impact:** Пакет закрепляет избыточную работу и противоречит правилам исполнения задач: полный набор повторяется внутри фазы независимо от фактического охвата правок. При последовательном исполнении задач это становится обязательной повторяющейся проверкой без отдельного проверяемого результата.
- **Required change:** Заменить полные прогоны в задачах 1.2 и 1.5 явным охватом затронутых модулей и их непосредственных потребителей; при механической адаптации фикстур расширять этот охват только соответствующими наборами. Полные проверки оставить стадии завершения фазы по правилам репозитория и оркестратора.

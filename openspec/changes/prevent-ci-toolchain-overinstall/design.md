## Context

`mise-action` восстанавливает кэш, выполняет переданный `mise install` и сразу
сохраняет каталог mise. В текущем workflow setup-шаги намеренно устанавливают
частичные наборы инструментов, однако последующие `mise run` и `mise exec`
работают с полным корневым `mise.toml` и автоматически материализуют все
отсутствующие инструменты. Особенно дорого это для OpenSpec job: ему нужны только
Node.js и OpenSpec, но перед валидацией он устанавливает Flutter.

Workflow уже разделяет ответственность между project, OpenSpec и Android jobs,
а `mise-action` экспортирует пути установленных инструментов для следующих
шагов. Изменение должно сохранить эти границы, точные версии и стандартную
семантику безопасных GitHub cache scopes.

## Goals / Non-Goals

**Goals:**

- Сделать setup-шаг каждого job единственным владельцем установки инструментов.
- Сохранить mise-задачи как единый источник проектных команд без автоматической
  установки полного toolchain.
- Сделать действующее кэширование частичных установок явным и независимо
  проверяемым.
- Защитить workflow от возврата поздней установки инструментов.

**Non-Goals:**

- Прогревать кэши ветки `main` или обходить изоляцию кэшей pull request.
- Добавлять отдельные Pub, Gradle или Flutter first-use caches.
- Менять версии инструментов, задачи `mise.toml` или продуктовый код.

## Decisions

### Setup-шаг является единственным установщиком

Workflow задаёт `MISE_AUTO_INSTALL: "false"`, а вызовы проектных задач используют
`mise run --skip-tools`. Глобальная настройка является fail-closed политикой для
всего workflow, а флаг у каждой задачи выражает локальный контракт вызова.
Явный `mise install`, выполняемый `mise-action`, остаётся разрешённым.

Альтернатива — установить весь `mise.toml` в каждом job — отвергнута, потому что
она сохраняет ненужную загрузку Flutter в OpenSpec job. Полагаться только на
дисциплину отдельных команд также недостаточно: новый незащищённый вызов мог бы
вернуть прежнее поведение.

### OpenSpec запускается из экспортированного PATH

После частичной установки Node.js и OpenSpec workflow вызывает `openspec`
напрямую. Это использует документированный экспорт PATH со стороны action и не
заставляет `mise exec` повторно разрешать полный набор проекта.

Альтернатива — сохранить `mise exec` при отключённом auto-install — технически
работоспособна, но оставляет лишний слой разрешения toolchain и хуже выражает
границу ответственности setup-шагa.

### Стандартные cache keys сохраняются

Все вызовы action явно задают `cache: true` и `cache_save: true`, но не
переопределяют `cache_key`. Поэтому hash `install_args` продолжает разделять
Flutter и Node.js/OpenSpec toolchains, а hash mise-конфигурации инвалидирует их
при смене версий.

Общий ключ без `install_args` отвергнут: параллельные jobs могли бы сохранить под
ним разные неполные наборы и сделать результат зависимым от гонки.

### Регрессия проверяется существующим CI contract test

Focused shell-тест scope detector дополняется проверками workflow-инвариантов:
общий auto-install отключён, проектные mise-задачи используют `--skip-tools`, а
OpenSpec job не выполняет `mise exec`. Новый тестовый runtime или YAML-зависимость
не добавляются.

## Risks / Trade-offs

- **Изменение экспорта PATH в будущей версии action** -> прямой вызов OpenSpec
  завершится ошибкой вместо скрытого использования незакреплённого инструмента;
  action закреплён по commit SHA, поэтому изменение будет явным обновлением.
- **Хрупкость текстовой проверки workflow** -> проверять только три существенных
  инварианта и обновлять тест вместе с намеренным изменением структуры workflow.
- **Cold miss всё ещё скачивает объявленный toolchain** -> принять это как
  корректную семантику текущего scope; отдельно измерить необходимость trusted
  cache warmer после устранения лишних установок.

## Migration Plan

Изменение применяется атомарно к workflow и его focused тесту. Перед слиянием
локальные проверки подтверждают статический контракт, а pull-request CI должен
подтвердить отсутствие установок необъявленных инструментов в рабочих шагах.
Откат состоит в возврате одного workflow-изменения и соответствующих тестовых
утверждений; данные и артефакты приложения не мигрируют.

## Findings

### F1 · High — Оформление системной области не определено для поддерживаемых Android API 24–28

- **Evidence:** [Спецификация оформления](specs/app-appearance/spec.md), требование «Светлое и тёмное оформление по системной настройке», обещает продолжение фона панели и различимость системных кнопок на Android без ограничения версии. [Дизайн](design.md), решение 2, и [задача 1.2](tasks.md) опираются на `SystemUiMode.edgeToEdge`, прозрачную системную подложку и яркость кнопок по теме; для конфигураций без нужного режима предусмотрен явный вызов того же API. Между тем [конфигурация сборки](../../../android/app/build.gradle.kts) использует `flutter.minSdkVersion`: в закреплённом Flutter 3.47.1 значение равно 24, а `targetSdkVersion` — 36 (`packages/flutter_tools/gradle/src/main/kotlin/FlutterExtension.kt`, строки 26 и 34). `SystemUiMode.edgeToEdge` действует только начиная с API 29; тёмные системные кнопки доступны начиная с API 26. Эти ограничения подтверждены [контрактом SystemUiMode](https://api.flutter.dev/flutter/services/SystemUiMode.html) и [контрактом яркости кнопок](https://api.flutter.dev/flutter/services/SystemUiOverlayStyle/systemNavigationBarIconBrightness.html), а также проверены в `PlatformPlugin.java` закреплённого SDK: ветка `EDGE_TO_EDGE` ограничена API 29, настройка цвета и яркости нижней панели — API 26. В [палитре приложения](../../../lib/src/design_system/doable_colors.dart) светлый `raised` — белый. Собственной совместимой настройки в Android-хосте нет. Проверки задачи 1.4 сосредоточены на Redmi и не проверяют эти границы API.
- **Impact:** Достаточно запустить приложение с тремя системными кнопками на поддерживаемом API 24–28: явный вызов выбранного режима не обеспечит отрисовку под нижней системной областью. Для API 24–25 дополнительно нельзя получить обещанные тёмные кнопки на белом фоне указанным способом. Если оставить системную подложку, не выполняется обещание единого фона; если сделать её прозрачной отдельным нативным способом, светлые кнопки на белом `raised` потеряют различимость. Это вывод из ограничений платформы, а не результат воспроизведения на телефоне. Исполнителю придётся самостоятельно выбирать исключение из визуального контракта либо менять поддержку Android.
- **Required change:** Согласовать достижимый контракт системной области для всех поддерживаемых версий Android, затем отразить его в спецификации, решении 2 дизайна и работе фазы 1. Для API 26–28 определить работающий способ оформления окна; для API 24–25 определить допустимый вид панели, сохраняющий контраст, либо явно согласовать изменение поддержки. Проверка должна наблюдать фактический фон, различимость кнопок и безопасные отступы на соответствующих границах API; передача `SystemUiOverlayStyle` в виджет-тесте этого не доказывает. Работа должна предшествовать итоговой проверке фазы 1 в порядке файла задач.
- **Decision needed:** Какой вариант оформления допустим на API 24–25, где система не поддерживает тёмные навигационные кнопки: исключение из единого светлого фона или изменение области поддержки? В артефактах такого продуктового решения нет; аудит его не принимает.

## Review coverage

Прочитаны `AGENTS.md`, `CONTEXT.md`, конфигурация и схема `intent-driven`, её шаблоны и все существующие артефакты изменения: proposal, обе delta-спецификации, design, ADR-манифест, plan и tasks. Изменённые требования сопоставлены с каноническими `daily-choice-management` и `app-appearance`, а влияние панели — с `app-navigation`. Проверены необходимость сценариев и работ, отсутствие потери прежних обязательств и владельцы общих правил.

По индексу ADR проверены записи 0014, 0017, 0020, 0025, 0028–0031. Их статус `proposed` учтён как контекст текущей реализации. Новых принадлежащих изменению ADR нет. План содержит три последовательные фазы; задачи 1.1–1.4 представляют только фазу 1 и идут после своих зависимостей. Отсутствие пакетов фаз 2 и 3 соответствует поэтапной схеме, их результаты и проверки заданы планом и дизайном.

Проверены `DailyChoiceCalendar`, выбор периода, общий `DailyChoiceCatalogBody` обоих каталогов, окно отметок, `CalendarHandle` и `PeriodPicker`, а также соответствующие проверки переходов, выбора периода, семантики, локализации и раскладки. Окно отметок уже покрывает шестинедельные сетки текущего и соседних месяцев независимо от представления: раскрытие с прежней датой просмотра не требует нового механизма чтения. В `table_calendar` 3.3.0 проверены управление высотой, события страниц и владение контроллером. Дизайн учитывает изоляцию `PageStorage`, отмену жеста, смену направления, остановку перелистывания и сохранение открытой страницы выбора периода.

Прослежены `NavBar` → `AppNavigationBar` → оболочка с `AppShellTabInsets` и `OrdinaryPageScaffold`, их проверки и примеры Widgetbook. Общий размер панели используется потребителями; расчёт 531 dp после увеличения панели сохраняет каноническую границу полезной высоты 528 dp. Проверены палитра, Android-хост, темы окна и конфигурация сборки. Платформенные ограничения сверены с исходниками закреплённого Flutter и официальными контрактами.

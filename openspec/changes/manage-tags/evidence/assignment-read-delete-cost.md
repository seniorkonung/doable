# Стоимость чтения назначений и удаления общего тега

## Воспроизведение

Локальная проверка: `mise exec --no-deps -- flutter test test/graph/data/drift_tag_assignment_read_cost_test.dart test/graph/data/drift_tag_delete_test.dart --reporter expanded`. Исходные обезличенные результаты: [linux-assignment-read-delete-cost.jsonl](linux-assignment-read-delete-cost.jsonl).

Файловая SQLite-база чтения содержит 1 203 тега и 1 003 назначения: 602 тега у намерения и 401 у долговременной связи. Для каждого получателя, размера порции 1/50/100 и чтения назначений/выбора тест проверяет первую, промежуточную и последнюю порции, пять повторов этих порций и полный обход без пропусков и повторов. Измеренная длительность включает вызов репозитория и декодирование, но исключает заполнение базы и `EXPLAIN QUERY PLAN`. Время не является порогом прохождения теста.

Наблюдатель фиксирует три `SELECT` на порцию: существование получателя (одна строка), отсутствие повреждённой ссылки (ноль строк) и основную выдачу (не более `pageSize + 1` строк). Количество запросов не растёт с числом строк порции. Основной запрос не использует `OFFSET`, `COUNT` или `SELECT *`; выбор вычисляет признак назначения индексированным `EXISTS` для строк порции. При полном обходе суммарная материализация включает строки проверки продолжения и одну строку проверки получателя на каждую порцию. Все планы и точные длительности повторов сохранены в JSONL.

План выборки тегов идёт по `creation_sequence`: первая порция сканирует `tags` под `LIMIT`, продолжения используют `SEARCH tags USING INTEGER PRIMARY KEY (rowid>?)`; коррелированный `EXISTS` использует уникальный индекс пары тег/получатель. План назначений использует индексы `tag_assignments_intention` или `tag_assignments_long_term_relation` и поиск тега по `id`. Для порядка создания тегов SQLite применяет `USE TEMP B-TREE FOR ORDER BY`. Это ограничивает материализацию в Dart, но не делает стоимость SQL постоянной; отбор и сортировка могут дорожать с ростом списка.

Отдельная файловая фикстура содержит 1 200 намерений и 1 200 долговременных связей, из них по 600 активных и архивных каждого вида, с одним общим тегом на всех 2 400 получателях. Пять удалений на заново заполненных базах заняли 9,339 / 8,404 / 8,398 / 8,362 / 8,672 мс (медиана 8,404 мс). Команда выполнила один `SELECT` тега с одной строкой и один `DELETE FROM tags`; отдельного чтения или удаления списка назначений в Dart не было. Из второго SQLite-соединения до commit были видны все прежние 2 400 назначений, после завершения не осталось ни тега, ни его назначений. Результат содержал ровно одно изменение `TagDeletedChange`; другой тег, его назначение, все получатели и внешние ключи сохранились. Отдельная проверка отказа внутри каскада подтверждает полный откат.

## Проверка интерфейса

Команда: `mise exec --no-deps -- flutter test test/tag/presentation/assignments/tag_assignments_read_cost_widget_test.dart --reporter expanded`. Автоматизированный widget-сценарий в тестовом окне 600 × 900 с масштабом текста 1 загрузил по 350 назначений намерения и долговременной связи из большой фикстуры. Для каждого вида получателя выполнено шесть продолжений после первой порции и 20 жестов прокрутки вниз и вверх. Проверены порядок первой и последней загруженной строки, изменение и возврат положения прокрутки, сохранность 350 строк в состоянии и отсутствие исключений. Оба сценария завершились успешно.

Эта проверка подтверждает доступность подгрузки и прокрутки в тестовом окружении Flutter; она не измеряет время кадров или задержки на Android. Замеры на реальном устройстве исключены из оставшихся задач изменения, поэтому указанные локальные числа нельзя переносить на другое оборудование без отдельной проверки.

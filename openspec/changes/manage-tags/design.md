## Контекст

Изменение реализует [предложение](proposal.md) и спецификации [управления тегами](specs/tag-management/spec.md), [намерений](specs/intention-management/spec.md) и [долговременных связей](specs/long-term-relation-management/spec.md). Тег — самостоятельная переиспользуемая метка личного графа; назначение связывает её с конкретным намерением или долговременной связью. Связь «я сегодня» собственных тегов не имеет. Термины соответствуют [предметной модели](../../../CONTEXT.md).

Приложение использует Flutter, Riverpod, AutoRoute и локальную Drift/SQLite-базу версии 3. `PersonalGraphRepository` уже объединяет намерения, долговременные связи, дневные выборы и пути; `DriftPersonalGraphRepository` упорядочивает чтения и транзакции общим исполнителем. `GraphCommandCoordinator` удерживает принятые команды независимо от экранов, публикует результаты с `GraphRevision` и совместно с `GraphOperationPresenter` обеспечивает однократное сообщение результата. Тегов и назначений в текущей схеме нет.

Дизайн сохраняет границы [ADR-0009](../../../docs/adr/0009-unify-personal-graph-module-and-revision.md), правила регистрации SQLite-функций [ADR-0008](../../../docs/adr/0008-treat-sqlite-schema-functions-as-durable-contract.md) и предъявления результатов [ADR-0012](../../../docs/adr/0012-centralize-graph-operation-result-presentation.md). Одна установка и один живой репозиторий остаются границей поддерживаемой записи; сервер, импорт чужих баз и синхронизация не добавляются.

## Цели и границы

**Цели:**

- Сохранить идентичность тегов, единые правила названия и независимые назначения обоим допустимым видам сущностей.
- Обеспечить атомарность, долговечность и согласованное отображение создания, переименования, назначения, снятия и удаления.
- Дать последовательный доступ к большим каталогам, назначениям и помеченным сущностям через ограниченные порции.
- Встроить управление тегами в существующие подробности активных и архивированных сущностей, сохранив ограничения дневных путей и физического удаления.
- Обеспечить миграцию, безопасную диагностику, русскую и английскую локализацию и доступность всех новых сценариев.

**За границами:** общий поиск по графу, фильтрация по нескольким тегам, иерархия или архивирование тегов, автоматическое назначение и объединение тегов, синхронизация, изменение правил дневных выборов. Теги не добавляются в каждую строку существующих каталогов: назначения доступны в подробностях, выборе тега и специальной навигации.

## Решения

### 1. Теги расширяют единый модуль личного графа

В `lib/src/tag/` размещаются предметные типы, прикладные контракты и представления тегов по образцу существующих возможностей. Чтения добавляются в `PersonalGraphRepository`, команды — в его общий `execute`. Реализация запросов и транзакций остаётся в `lib/src/graph/data/`, схема и миграция — в `lib/src/data/local/`. Отдельный репозиторий тегов со своим соединением, координатором или ревизией не вводится: назначение и физическое удаление пересекают существующие сущности и требуют одной транзакционной границы.

Упрощённая C4-схема компонентов показывает целевое расширение внутри одного приложения. Стрелки обозначают вызовы; обратная доставка результатов описана ниже.

```text
+------------------------------------------------------------------+
| Doable: Flutter application                                       |
|                                                                  |
|  +-----------------------+     +-------------------------------+  |
|  | Tag views / ViewModels|     | Intention / Relation details  |  |
|  +-----------------------+     +-------------------------------+  |
|              |                             |                     |
|              +-------------+---------------+                     |
|                            | commands                            |
|                            v                                     |
|                 +-------------------------+                      |
|                 | GraphCommandCoordinator |                      |
|                 +-------------------------+                      |
|                            | execute                             |
|  ViewModels -- reads -->   v                                     |
|                 +-------------------------+                      |
|                 | PersonalGraphRepository |                      |
|                 | Drift adapter           |                      |
|                 +-------------------------+                      |
|                            | SQL                                 |
|                            v                                     |
|                 +-------------------------+                      |
|                 | Local SQLite database   |                      |
|                 | Graph + Tags            |                      |
|                 +-------------------------+                      |
+------------------------------------------------------------------+
```

- `Tag views / ViewModels` — каталог, редактор, выбор тега, порции назначений и навигация по тегу. Подробности намерений и связей подключают общий блок назначений с типизированным получателем.
- `PersonalGraphRepository` скрывает SQLite, технические порядки, ключ сопоставления названия и устройство курсоров. Представления получают проверенные неизменяемые модели и различимые результаты.
- Координатор передаёт подтверждённые пакеты открытым представлениям, а `GraphOperationPresenter` сообщает результаты команд через существующий протокол. Результат маршрута не служит вторым каналом изменения данных.
- Предположение схемы: все поддерживаемые изменения проходят через один экземпляр репозитория. SQLite — встроенное локальное хранилище, а не отдельный сервис; внешних сетевых зависимостей у тегов нет.

Альтернатива с независимым `TagRepository` потребовала бы общей транзакции и согласования поверх двух владельцев. Хранение списков тегов внутри моделей намерения и связи усложнило бы общее переименование и порционное чтение.

### 2. Идентичности, названия и получатели выражены отдельными типами

`TagId` следует принятому подходу типизированных UUID: генератор создаёт новую идентичность, декодирование проверяет внешнее представление. Идентификатор не зависит от названия. Тег содержит `TagId` и проверенное `TagName`; собственных архивного состояния и времени изменения ему не требуется.

`TagTarget` — закрытое объединение `IntentionTagTarget(IntentionId)` и `LongTermRelationTagTarget(LongTermRelationId)`. Варианта для дневного выбора нет. Команды, страницы назначений и параметры маршрутов используют этот тип вместо пары строк «вид + id». Декодирование внешнего входа отклоняет неподдерживаемый вид до вызова записи; прикладной код не может передать `DailyChoiceId` как допустимого получателя.

Создание `TagName` из пользовательского текста выполняет по порядку:

1. Проверку исходных UTF-16 code units через существующий `UnicodeText`: только корректные Unicode scalar values без NUL, до любой обработки и кодирования.
2. Удаление окружающих пробелов тем же `trim()`, который использует `IntentionText.normalizeTitle`.
3. Проверку непустого результата и длины 1–255 расширенных графемных кластеров через уже используемый пакет `characters`.
4. Сохранение полученного написания без преобразования регистра, внутренних пробелов или Unicode-нормализации.

Причины отказа различимы: недопустимый Unicode, пустое название, превышение длины. `TagName` предоставляет отдельное строгое декодирование сохранённых данных: оно проверяет уже каноничную форму и никогда не исправляет, не обрезает и не нормализует повреждённую строку при чтении.

Для уникальности используется полный Default Case Folding **Unicode 17.0.0**, статусы C и F, без S, T и дополнительной нормализации, как определено [официальными данными Unicode](https://www.unicode.org/Public/17.0.0/ucd/CaseFolding.txt). Уже имеющаяся таблица из `title_search_key.dart` переносится в общий модуль с явно версионированным именем `UnicodeDefaultCaseFolding17`; поисковый ключ намерения сохраняет прежнее поведение через свою обёртку. Новый ключ тега обращается к версии 17 напрямую, а не к изменяемой обёртке поиска намерений. Фикстура `test/fixtures/unicode/CaseFolding-17.0.0.txt` и её SHA-256 служат источником воспроизводимой проверки полного набора отображений.

`Straße` и `STRASSE` конфликтуют, «Все» и «Всё» различаются; канонически эквивалентные строки без одинаковой последовательности после folding не объединяются автоматически. Совпадение с собственным ключом разрешает сменить написание тега. Полностью одинаковое сохранённое название даёт успех без изменения и без новой ревизии.

Альтернативы `toLowerCase`, SQLite `NOCASE`, сравнение по локали и вызов `titleSearchKey` как постоянного контракта тегов отвергаются: они либо не выражают заданное сопоставление, либо связывают уникальность с будущим изменением поисковой проекции. Версионированный общий алгоритм позволяет переиспользовать таблицу без такого связывания.

### 3. Две новые таблицы обеспечивают целостность и устойчивый порядок

Схема версии 4 добавляет `tags` и `tag_assignments`, не перестраивая существующие таблицы графа.

| Таблица | Существенные поля и ограничения |
| --- | --- |
| `tags` | `creation_sequence INTEGER PRIMARY KEY AUTOINCREMENT`, положительный; `id TEXT NOT NULL UNIQUE`; `name TEXT NOT NULL`; `name_key TEXT GENERATED ALWAYS AS (doable_tag_name_key_v1(name)) STORED NOT NULL COLLATE BINARY UNIQUE` |
| `tag_assignments` | `creation_sequence INTEGER PRIMARY KEY AUTOINCREMENT`, положительный; обязательный `tag_id`; nullable `intention_id` и `long_term_relation_id`, из которых CHECK требует ровно одно ненулевое значение |

`name` дополнительно проверяется на текстовый тип, отсутствие NUL и каноническую допустимую форму. Чистая детерминированная schema-function `doable_tag_name_valid_v1(TEXT)` возвращает 1 только для декодированного, уже обрезанного допустимого названия длиной 1–255 графем. Функция ключа использует закреплённый folding; для недопустимого декодированного аргумента возвращает NULL, который отвергается ограничениями. Для значений SQLite других типов функции возвращают соответственно 0 и NULL без неявного преобразования в текст. Недекодируемый UTF-8 в SQLite `TEXT` вызывает ошибку SQL до вызова функций и не сохраняется. Обе функции не выполняют I/O и не включают исходный аргумент в исключения. Проверка на границе Dart остаётся обязательной, поскольку некорректный UTF-16 нельзя безопасно передавать кодировщику.

Декодер `sqlite3` удаляет начальный `U+FEFF` из SQLite `TEXT` до передачи аргумента функции. Поэтому ограничение таблицы отдельно отвергает такой исходный текст через `CHECK (substr(name, 1, 1) <> char(65279))`; после этого строгая проверка функцией совпадает с декодированием `TagName` и не допускает сохранения неканоничного названия. Эта проверка входит в схему версии 4 и проверяется на прямых SQL-записях вместе с остальными ограничениями названия.

Имена, сигнатуры и семантика этих функций становятся долговечным контрактом согласно ADR-0008. Они регистрируются каноническим connection setup до первого обращения к схеме на всех физических соединениях, включая фоновые executors и средства проверки миграций. Правила `v1`, включая используемые данные сегментации и обрезки пробелов, не должны молча изменяться при обновлении SDK или `characters`: зависимость `characters` закреплена точной версией, совместимость проверяется отдельно, а необходимое изменение оформляется новой функцией и миграционным решением. Ключ названия вычисляется самой базой; вызывающая сторона не может сохранить произвольный ключ, не соответствующий названию. Возможность ограничений и индекса на generated column опирается на [контракт SQLite](https://www.sqlite.org/gencol.html).

Назначение имеет внешние ключи к тегу и двум возможным получателям с `ON UPDATE RESTRICT ON DELETE CASCADE`. CHECK исключает обе заполненные или обе пустые ссылки. Уникальные ограничения `(tag_id, intention_id)` и `(tag_id, long_term_relation_id)` исключают повторение пары для каждого вида. Самостоятельного предметного идентификатора назначения нет: его идентичность задаётся тегом и типизированным получателем; sequence остаётся внутренним ключом порядка.

Триггеры запрещают изменение идентичности и sequence тега, а также подмену тега, получателя или sequence существующего назначения. Снятие и новое назначение создают новую строку. `AUTOINCREMENT` сохраняет возрастание относительно ранее подтверждённых значений даже после удаления последней строки; пропуски последовательности допустимы и пользователю не видны. Это осознанное принятие дополнительных расходов [SQLite AUTOINCREMENT](https://www.sqlite.org/autoinc.html) ради устойчивого порядка без опоры на часы.

Индексы обслуживают `(tag_id, creation_sequence)`, обратные ссылки `(intention_id, tag_id)` и `(long_term_relation_id, tag_id)`; уникальные индексы тегов обслуживают поиск по id и ключу имени. Каталог и назначения сущности сортируются по `tags.creation_sequence ASC`, результаты тега — по `tag_assignments.creation_sequence ASC`. Один общий порядок назначений сразу задаёт полный порядок смешанной выдачи обоих видов.

Альтернатива с двумя таблицами назначений дала бы простые отдельные внешние ключи, но потребовала бы дополнительного общего распределителя порядка для смешанной выдачи. Выбранная таблица использует две настоящие ссылки и ограничение «ровно одна», сохраняя проверяемую целостность. Универсальная строковая ссылка без внешнего ключа и хранение массивов id внутри сущностей не принимаются.

### 4. Изменения выполняются атомарно через существующий координатор

Закрытый набор команд включает `CreateTag`, `RenameTag`, `DeleteTag`, `AssignTag` и `RemoveTagAssignment`. Создание принимает проверенное название, остальные команды — конкретные идентичности; удаление содержит подтверждение охвата «этот тег и все назначения на момент выполнения». Создание из выбора тега использует только `CreateTag`; последующее назначение требует отдельного явного действия.

В общем последовательном исполнителе каждая команда заново проверяет существование затронутых сущностей и выполняет проверки, изменение и подготовку результата в одной транзакции. Успех публикуется после commit; фактическое изменение увеличивает `GraphRevision` ровно на единицу. Отказ не продвигает ревизию. Повторное назначение или снятие при существующих теге и получателе возвращает подтверждённый успех без изменений; он содержит типизированный неизменившийся результат, совместимый с требованием непустого `ConfirmedGraphResult`, и не вызывает повторную запись.

Уникальный индекс ключа имени обеспечивает окончательную атомарную защиту создания и переименования. Конфликт возвращает различимый отказ с идентичностью существующего тега для действия «Использовать существующий»; это действие актуализирует тег по id и не выдаёт его за результат создания. Отсутствие тега и отсутствие получателя — разные отказы. Проверка существования предшествует признанию назначения или снятия операцией без изменений. Широкие `INSERT OR IGNORE` и `REPLACE` не используются: они способны скрыть другой отказ или заменить идентичность.

Координатор получает `TagCreationFormKey` и `ExistingTagKey`. Переименование и удаление резервируют ключ тега; назначение и снятие атомарно резервируют ключ тега и существующий `ExistingIntentionKey` либо `ExistingLongTermRelationKey`. Тем самым операции назначений конфликтуют с обычными изменениями того же получателя. Все ключи удерживаются до конечного результата независимо от ухода с экрана; повторная отправка отклоняется без очереди. Массовое удаление связей сохраняет уже существующее резервирование выбранных сущностей.

Удаление тега не перечисляет и не блокирует в памяти всех получателей: общая последовательность транзакций и внешние ключи упорядочивают его с другими операциями. Назначение, успевшее подтвердиться раньше удаления, удаляется вместе с тегом; операция после удаления получает отсутствие. Переименование не меняет выбранную идентичность, архивирование получателя не делает её недопустимой. Принятые команды продолжаются после закрытия маршрута и дожидаются завершения при штатном закрытии базы.

Альтернативы с экранными блокировками или отдельными координаторами позволяют обойти выполняющуюся операцию повторным входом. Проверка уникальности только до транзакции допускает гонку; повторное выполнение команды для восстановления экрана может дублировать уже подтверждённое действие.

### 5. Назначения удаляются каскадно, остальные правила графа сохраняются

`DeleteTag` удаляет строку `tags`; база в той же транзакции удаляет все её назначения, включая назначения вне загруженных порций и обоих архивных охватов. Ни получатели, ни пути не удаляются. Подтверждение объясняет этот полный охват и привязано к `TagId`, поэтому новый одноимённый тег не может стать случайной целью.

Допустимое физическое удаление намерения или долговременной связи удаляет принадлежащие ему назначения через тот же механизм внешних ключей. Это расширяет последствия уже существующих команд, сохраняя их проверки зависимостей. Назначения не становятся блокирующей зависимостью. Если намерение защищено связью или дневным выбором, либо долговременная связь защищена шагом пути, транзакция не удаляет ни сущность, ни назначения. Поведение каскада и ограничений соответствует [SQLite foreign keys](https://www.sqlite.org/foreignkeys.html).

При массовом удалении сначала проверяется весь явно подтверждённый набор и все зависимости, затем удаляются выбранные связи и их назначения. Выбранный вместе со связью дневной выбор не позволяет обойти защиту его шагов. Подтверждение массового удаления дополняется объяснением снятия назначений с удаляемых связей при сохранении тегов. Ошибка в любой части откатывает весь набор.

Архивирование, восстановление и редактирование полей получателей не переписывают назначения. Изменения тегов и назначений не обновляют время создания или изменения намерения, его поисковую проекцию, порядок долговременной связи или данные дневных выборов. Изменение полей самого намерения по-прежнему следует прежнему контракту времени.

Альтернатива с удалением назначений отдельными командами после удаления родителя оставляет частичный результат при сбое. Обратный каскад, удаляющий неиспользуемый тег вместе с последним назначением, противоречит его переиспользуемому жизненному циклу.

### 6. Все коллекции читаются ограниченными страницами

Новые контракты чтения не добавляют неограниченные списки в `IntentionDetails` или подробности связи.

| Чтение | Вход и возвращаемая проекция |
| --- | --- |
| `getTagCatalogPage` | Обычный каталог либо типизированный режим выбора для `TagTarget`; строка содержит тег и в режиме выбора — подтверждённый признак назначения этому получателю |
| `getTagAssignmentsPage` | `TagTarget`; строки содержат текущие теги получателя в порядке создания тегов |
| `getTaggedEntitiesPage` | `TagId`, охват `active` или `archived`; заголовок тега и строки закрытого объединения «намерение / долговременная связь» |
| `watchTag` | Один `TagId`; текущее название, различимое отсутствие или отказ, без загрузки назначений |

Каждый запрос страницы принимает проверяемый размер 1–100, по умолчанию 50, и непрозрачный курсор. Размер — ограничение одной порции, не лимит доступных данных. Страница содержит ревизию и возможность продолжения; точное общее количество тегов или назначений для новых экранов не требуется. Репозиторий читает не более `pageSize + 1` записей основного результата, проверяет и дополнительную строку, а наружу отдаёт не более `pageSize`. Наличие следующей порции определяется дополнительной строкой.

Курсор принадлежит конкретному виду запроса, выбранным идентичностям, режиму, охвату, размеру порции, экземпляру репозитория, эпохе, ревизии и последнему ключу порядка. Он не сериализуется и не используется как внешний идентификатор. Продолжение использует сравнение с последним sequence, а не OFFSET. Чужой курсор даёт ошибку входа; смена ревизии или эпохи — `SnapshotExpired` с требованием начать чтение заново. SQL-транзакция не удерживается между прокрутками.

Получатель или тег проверяются даже при пустом результате. Каталог выбора определяет признак назначения через индексированный `EXISTS` только для строк страницы, без загрузки всех назначений. Навигация объединяет оба вида получателей по порядку назначения; собственное архивное состояние получателя отбирается в SQL **до LIMIT**. Формулировка связи собирается интерфейсом из языконезависимого типа и текущих названий участников, полученных на том же снимке. Названия участников читаются соединением или ограниченным пакетным запросом, без запроса на каждую строку и без загрузки дневных путей.

Декодирование проверяет типы, идентичности, названия и ссылки, прежде чем выдавать успешную модель. Соединения не должны молча скрывать назначение с отсутствующим тегом или получателем: используются проверки отсутствующих ссылок, включая строки, которые иначе исчезли бы при JOIN или отборе охвата. Повреждение возвращает отказ чтения всей порции, а не «исправленную» строку или пропуск. Это не требует чтения всех строк личного графа при каждой странице.

Ограниченная материализация не обещает постоянного времени SQL: отбор архивного охвата может просмотреть много назначений, а порядок тегов получателя требует соединения и сортировки. На больших фикстурах проверяются план запроса, число и размер материализованных строк и задержки. Дополнительная денормализация архивного состояния и порядка не вводится без измерений, чтобы не усложнять каскадное архивирование.

Альтернативы с загрузкой всего каталога для выбора, тегами внутри полного объекта получателя и фильтрацией уже загруженной порции нарушают ограничение чтения или полноту навигации. Порядок по названию и времени устройства не соответствует заданной устойчивости.

### 7. Согласование использует общую ревизию без перечисления всех назначений

Успешные команды тегов публикуют компактные `GraphChange`: изменение самого тега с моделями до/после, изменение одной пары назначения с подтверждённым состоянием либо удаление тега по id. Переименование и удаление общего тега не материализуют все его назначения ради пакета. Существующие команды удаления, архивирования и редактирования получателей продолжают публиковать свои изменения на общей ревизии; новые представления учитывают и эти пакеты.

Для новых списков выбирается консервативное правило: любое фактическое продвижение общей ревизии делает продолжение непригодным и запускает обновление открытого списка с первой порции. Сохраняются `TagId` или `TagTarget`, режим и охват; ранее накопленные порции не смешиваются с новой основой. Изменение названия участника поэтому автоматически обновляет формулировку помеченной связи, даже если участник сам не помечен. Точечные ревизии списков и долговечный журнал изменений не нужны.

ViewModel подписывается на завершения до начального чтения и хранит поколение запроса, требуемую и отображаемую ревизии и не более одного текущего запроса страницы. Смена тега или охвата создаёт новое поколение, очищает старую выдачу для нового выбора и отменяет её право публикации. Поздние ответы другого поколения, экземпляра или ревизии ниже уже подтверждённой отбрасываются. Более свежая первая страница может стать новой основой; последующее завершение уже включённой операции повторно её не изменяет. Продолжение объединяется только с основой той же ревизии и один раз.

На время обновления прежний согласованный список может оставаться видимым только с явным состоянием обновления или ошибки актуализации и без действий, предполагающих его актуальность. Подтверждённое переименование немедленно обновляет известные названия, удаление тега убирает его строки и переводит открытую навигацию в состояние отсутствия; старое чтение не может их вернуть. Если компактный пакет не позволяет точно обновить остальные строки, они не объявляются текущими до нового снимка. Ошибка обычной подгрузки без изменения ревизии сохраняет полученные строки и курсор для допустимого повтора.

`GraphOperationPresenter` получает новые типы результатов; успех принадлежит общей поверхности, ошибки открытой формы — существующему модулю инлайн-предъявления. Если форма закрыта, результат получает оболочка. Очередь сообщений, свидетельство доступного кадра и защита от вытеснения сохраняются. Ошибка чтения после успешной записи сообщает об актуализации и повторяет только чтение. Ошибка команды сохраняет ввод в открытой форме; явный выход заканчивает её экранную сессию.

Существующие потребители пакетов графа должны принимать продвижение общей ревизии и при изменении только тегов, сохраняя свои правила каталогов, счётчиков и продолжений. Для этого не создаются фиктивные изменения полей намерений или дневных выборов. Проверки перестановки страниц и завершений распространяются на новый вид пакетов.

Альтернатива с полным перечнем затронутых получателей в результате удаления делает размер команды зависимым от всех назначений. Обновление только при повторном открытии экрана оставляет подтверждённые изменения невидимыми. Выбранное правило требует лишних ограниченных чтений при посторонних изменениях графа, но сохраняет простой проверяемый порядок.

### 8. Интерфейс сохраняет различия между тегом, назначением и получателем

Основной интерфейс получает переход «Теги». Каталог открывает навигацию по `TagId`, создание, переименование и отдельное подтверждение удаления. Навигация по тегу при входе выбирает активный охват, предоставляет архивный и показывает оба вида сущностей в общей последовательности. Название, вид и архивное состояние различимы текстом и семантическими подписями; переход передаёт типизированный id в уже существующие подробности.

Общий блок назначений в подробностях намерения и долговременной связи получает своего `TagTarget`, собственные состояния чтения и продолжения, действия снятия и перехода по тегу. Он доступен и в архиве, в том числе у связи из дневного пути. Выбор использует тот же каталог в отдельном режиме, показывает уже назначенные теги и разрешает создать новый без автоматического назначения. После конфликта занятого названия можно перейти к существующему тегу; его назначение остаётся явным действием.

Удаление тега визуально и семантически отделено от снятия назначения. Подтверждение называет тег и объясняет удаление всех его назначений активным и архивированным сущностям, в том числе невидимым в текущей порции, при сохранении самих сущностей и дневных выборов. Число загруженных строк не используется как охват подтверждения.

Все новые состояния имеют русские и английские строки в ARB. Пользовательский текст не переводится. Формы, ошибки, длинные названия, переключатели и подтверждения используют переносы, доступную прокрутку и семантику, проверяемые с экранным диктором и увеличенным текстом. Первичная загрузка, пустой каталог, отсутствие назначений, пустой охват, удалённая сущность и отказ имеют отдельные представления.

Альтернатива с одним действием «Удалить» для тега и назначения скрывает различный охват. Привязка маршрута к названию ломает переименование и создаёт риск подмены после удаления и повторного создания.

### 9. Ошибки и диагностика проходят через существующие границы

Команды и чтения получают отдельные типизированные причины внутри существующих категорий `validation`, `notFound`, `conflict`, `unavailable`, `corruption`, `unexpected`. Дополнительно различаются занятое название, отсутствующий тег, отсутствующий получатель, недопустимое продолжение и истёкший снимок. Повтор предлагается только при доказанно временной недоступности; для ввода требуется исправление, для конфликта — актуализация выбора, для устаревшей страницы — новое чтение от начала. Повреждение и неизвестная причина не представляются временным сбоем.

SQLite-ошибки классифицируются внутри адаптера по известным кодам и предметным проверкам. Наружу и в диагностику не передаются SQL, параметры или исходные исключения. `DiagnosticsSink` расширяется конечными видами операций тегов и этапами проверки, чтения, записи и миграции. События содержат исход, безопасный код отказа и длительность, но не названия, id сущностей, ключи сопоставления, состав назначений или пути. Отказ диагностического приёмника подавляется существующей безопасной обёрткой и не меняет результат предметной операции.

Альтернатива с единым «что-то пошло не так, повторите» не различает исправление ввода, повтор чтения и уже подтверждённую запись. Запись исходного исключения затрудняет соблюдение границы личных данных.

### 10. Проверка охватывает контракты и взаимодействие со старым графом

Проверки реализации строятся вокруг наблюдаемых сценариев спецификаций:

- Предметные типы: обе формы получателя, невозможность дневного назначения, непарные surrogate и NUL до обработки, 255/256 графем, окружающие и внутренние пробелы, полная таблица folding 17.0.0, собственное и конфликтующее переименование, строгое чтение повреждённого названия.
- База и репозиторий: уникальность в конкурирующих командах, идемпотентность при существующих сущностях, отсутствие по id после удаления и повторного создания имени, гонки назначения и удаления, ошибки до commit и при каскадах, неизменность остальных полей и времени намерения.
- Жизненный цикл графа: оба архивных состояния, каскад и восстановление, замена участников связи, связь в дневном пути, одиночное и массовое удаление с сохранением прежних блокировок и полным откатом назначений при конфликте.
- Порции и согласование: большие каталоги и смешанные охваты, полный последовательный обход, порядок после перезапуска и повторного назначения, исключение N+1, смена охвата во время чтения, повторная подгрузка, все значимые перестановки страниц и завершений, новая эпоха, отсутствие зависания существующих представлений на новой ревизии.
- Интерфейс: создание из выбора без назначения, различие снятия и удаления, явное подтверждение полного охвата, уход и возвращение во время команды, сохранение ввода при отказе, однократное предъявление, ошибка актуализации после commit, обе локали, семантика и масштабирование текста.
- Долговечность: файловая база, полный останов и новый процесс, сохранение тегов и порядка, отсутствие возврата удалённых данных, все поддерживаемые миграции и инъекции сбоев, отсутствие личных данных в диагностике и отказ самого приёмника.

Проверки производительности фиксируют размер порций и материализации, SQL-планы и задержки чтения и каскадного удаления на больших фикстурах. Стоимость одной страницы не подменяется утверждением о постоянной стоимости всех соединений и сортировок. Общие проверки репозитория и генерации дополняют предметные проверки; этот документ определяет подход, но не утверждает, что будущая реализация уже проверена.

## Риски и компромиссы

- **Дрейф Unicode или сегментации** → folding закреплён за версией 17; долговечные функции v1 проверяются на совместимость при обновлении зависимостей, поисковая обёртка не определяет уникальность тегов.
- **Незарегистрированная schema-function при открытии или миграции** → единый канонический setup и проверки всех путей соединения, свежей схемы и обновлений.
- **Повторная загрузка после постороннего изменения графа** → ограниченная первая порция и объединение сигналов обновления в один текущий запрос; выбранные идентичности и охват сохраняются. Точечные ревизии потребовали бы более сложного протокола.
- **Длительная операция над тегом с множеством назначений** → индексированные внешние ключи и каскад внутри базы, без материализации всех получателей в Dart; измерения подтверждают приемлемую задержку. Разбиение удаления на частичные commits недопустимо.
- **Дорогой отбор редкого архивного охвата или сортировка назначений** → измерения SQL-планов и больших фикстур; материализация ограничена размером порции, время запроса не объявляется постоянным.
- **Изменение времени намерения или обход защиты дневного пути по ошибке интеграции** → назначения хранятся отдельно, прежние проверки удаления сохраняются, регрессионные сценарии охватывают одиночные и массовые команды.
- **Повреждённая ссылка скрыта соединением таблиц** → проверки отсутствующих ссылок и строгое декодирование; ошибка не превращается в пустой результат или частично успешную страницу.

## План миграции

1. Добавить версионированные функции проверки и ключа названия в каноническую настройку SQLite-соединения до открытия базы. Существующие функции и их поведение сохранить.
2. Поднять `AppDatabase.currentSchemaVersion` с 3 до 4. Добавить шаг 3 → 4, создающий только таблицы тегов и назначений, индексы и ограничения. Для новой установки создать ту же конечную схему. Старые пути 1 → 2 → 3 → 4 и 2 → 3 → 4 продолжают использовать штатную цепочку.
3. Выполнять весь переход и изменение `user_version` в существующей атомарной миграции. Проверки внешних ключей и целостности FTS сохраняются. Теги и назначения из имеющегося текста не создаются; исходный каталог пуст. Строки и порядки существующего графа не переписываются.
4. Получить schema snapshot версии 4 и шаги миграции штатной генерацией при реализации. Проверить равенство контрактов свежей установки и всех поддерживаемых обновлений, наличие функций на физических соединениях, сохранение прежнего графа и повтор после прерванной миграции.
5. Подключить новые представления только после штатной готовности хранилища. При ошибке открытия использовать существующий результат `local-data-lifecycle` без удаления или пересоздания файла.

До commit миграции сбой оставляет прежнюю схему и данные, следующий запуск повторяет переход. После успешной миграции безопасный откат интерфейса требует сборки, которая продолжает понимать схему 4 и её функции. Старый бинарный файл со схемой 3 не является способом отката: он должен отказать в открытии более новой схемы без её изменения. Автоматическое понижение схемы, удаление таблиц тегов или восстановление пустой базы не предусматриваются; исправление выпускается совместимым обновлением.

## Открытые вопросы

Неразрешённых предметных или архитектурных решений для этого дизайна нет. Размер порции 50 при максимуме 100, общая ревизия и отсутствие точных общих счётчиков новых списков приняты как решения реализации и не ограничивают число доступных сущностей.

При реализации необходимо получить измерения чтения редкого охвата, сортировки назначений и удаления широко используемого тега на целевых устройствах, а также проверить совместимость долговечных функций при генерации и миграции. Это проверка выбранного подхода, а не основание откладывать атомарность, полноту навигации или обработку ошибок.

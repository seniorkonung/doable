## Context

Изменение переводит корневую страницу «Граф намерений» на дизайн по [proposal](proposal.md) и delta-спецификациям [намерений](specs/intention-management/spec.md) и [навигации](specs/app-navigation/spec.md).

Источники внешнего вида:
- макеты [Catalog](../../../context/doable-design/design/Catalog.dc.html) и [CatalogParts](../../../context/doable-design/design/CatalogParts.dc.html) с их состояниями `Catalog*.dc.html`;
- README компонентов в `context/doable-design-system/components/`: `CatalogRow`, `CatalogHeader`, `SearchField`, `FilterButton`, `SelectRow`, `OrderButton`, `EmptyState`, `ListState`, `TagLine`, `Badge`.

Макет задаёт замысел, решения proposal и спецификаций важнее его. Правила дизайн-системы уступают решениям проекта по [ADR-0029](../../../docs/adr/0029-represent-design-system-as-foundation-module.md) и [ADR-0030](../../../docs/adr/0030-keep-design-system-components-presentational.md).

В текущем коде:

- **Страница каталога.** `IntentionCatalogPage` (`lib/src/intention/presentation/catalog/`) собрана из виджетов Material:
  - `AppBar`, выпадающие списки охвата и порядка, `TextField`;
  - условия под полем — `IntentionTagConditionsSection`;
  - строки — `IntentionSummaryView` с текстовыми признаками.

  `IntentionSearchLayout` прокручивает параметры вместе с выдачей. `IntentionSearchResults` держит позицию списка якорем первой видимой строки и `PageStorage`, рисует состояния собственными видами Material (`intention_catalog_status_views.dart`). Пустую выдачу из-за одного фильтра названия страница называет пустым охватом и не показывает количество.
- **Экраны выбора** уже на дизайне: `IntentionPickerView`, `IntentionPickerResults`, `IntentionPickerRow`, лист `intention_picker_show_and_sort_sheet.dart`. Все они типизированы `IntentionPickerPurpose`, хотя лист и выдача читают только общую модель каталога.
  - У выдачи экрана выбора нет якоря видимой строки: `ScrollController(keepScrollOffset: false)`, новая выдача только прыгает наверх.
  - Лист сбрасывает параметры двумя вызовами модели и сам считает, можно ли сбросить.
  - Тексты загрузки и отказов, ключи и `namesKind` выбирает `IntentionPickerKind.of`, который разбирает только назначения выбора.
- **Модель.** `IntentionCatalogViewModel` — семейство по `IntentionCatalogPurpose`. У корневого каталога один ключ `BrowseIntentionCatalog` на процесс ([ADR-0028](../../../docs/adr/0028-scope-opening-parameter-state-to-page-instances.md)).
  - Для каталога тип закрыт: `IntentionTypeNotOffered`. `changeType` ничего не делает, числа типов не запрашиваются.
  - `changeOrder` уже принимает порядок по названию, курсор и индексы архивного охвата для него есть ([ADR-0045](../../../docs/adr/0045-order-titles-by-opaque-key-of-stored-search-projection.md)). Запрещает его только страница через `_OfferedCatalogOrder`.
  - Сбросом при замене графа занимается `_resetParameters` по [ADR-0036](../../../docs/adr/0036-replace-graph-atomically-with-new-epoch-and-generation.md). Тип там уже сбрасывается.
- **Чтение.** `_readFirstCatalogPage` всегда выполняет один запрос подсчёта: `COUNT(*)` и `COUNT(*) FILTER (WHERE is_action_ready)` при условиях охвата, исключения, тегов и названия. Без запроса чисел типов их отбрасывают. Запрос задаётся флагом `IntentionCatalogQuery.requestsTypeCounts`, а `IntentionCatalogFirstPage.typeCounts` — необязательное поле.
- **Согласование.** `_reconcileTypeCounts` поправляет числа типов на ±1 по подтверждённым снимкам «до» и «после» ([ADR-0005](../../../docs/adr/0005-use-bounded-catalog-snapshots.md), [ADR-0009](../../../docs/adr/0009-unify-personal-graph-module-and-revision.md)).
- **Сохранение страницы.** Вкладки живут в `IndexedStack` под `KeyedSubtree(ObjectKey(generation))`. Каталог не размонтируется при переключении пунктов и при открытии страниц над оболочкой, а после замены графа создаётся заново.
- **Дизайн-система.** Есть `CatalogHeader`, `SearchField`, `FilterButton`, `SelectRow`, `OrderButton`, `EmptyState`, `ListState`, `TagLine`, `PickerRow`. Нет `CatalogRow`.
- **Проверки.** Около 25 файлов тестов находят каталог по старым ключам (`catalog-scope-control`, `catalog-order-control`, `catalog-filter-field`, `intention-tag-conditions-add`), по `AppBar` или `IntentionSummaryView`. У каждого свои копии помощников `_selectScope`, `_prepareIntentionCatalog` и других. Общего файла сценарных шагов нет, хотя для каталога дневных выборов он есть (`test/support/daily_choice_catalog_controls.dart`).

## Goals / Non-Goals

**Goals:**

- Страница каталога по макету: закреплённые заголовок, поиск с кнопкой фильтра и заголовок списка; прокручивается только список.
- Один лист «Показать и упорядочить», одна выдача и одно правило содержания строки для каталога и экранов выбора.
- Тип и сортировка по названию в каталоге, точные числа по охватам и типам одним чтением.
- Пустые состояния по спецификации, включая «Нет активных намерений» при непустом архиве.
- Позиция списка каталога сохраняется по прежним правилам после перехода на новую выдачу.
- Без следов старой страницы: компоновка, выдача, раздел условий, виды состояний и неиспользуемые строки удаляются.

**Non-Goals:**

- Множественное выделение, удержание строки, панель выделения и пакетные действия. `CatalogRow` не получает параметров выделения.
- Компонент `Snackbar` дизайн-системы и сообщения о результатах: общая поверхность остаётся прежней.
- Изменение схемы хранилища, индексов, формата графа или журнала фактов.
- Переименование общих строк локализации `intentionPicker*` в нейтральные имена: поведение от этого не меняется.
- Изменение `IntentionPickerView`, его шапки и листа назначения.

## Decisions

### 1. Общие части поиска выносятся в `presentation/search/`

Каталог и экраны выбора показывают один поиск с разной обвязкой. Общие части переезжают из `picker/` в новую папку `lib/src/intention/presentation/search/` и принимают `IntentionCatalogPurpose`. Специфичное остаётся на месте: экран выбора — в `picker/`, страница каталога — в `catalog/`. Долговременное правило этого разделения записано в [ADR-0049](../../../docs/adr/0049-build-intention-catalog-and-pickers-from-one-search-module.md).

На схеме `IntentionPickerView` — экран выбора, `IntentionCatalogPage` — страница «Граф намерений», `CatalogVM` — `IntentionCatalogViewModel`, `TagConditionsVM` — модель условий по тегам, `ShowAndSortSheet` — лист «Показать и упорядочить».

```text
+--------------------------------------------------------------------------+
| presentation/                                                            |
|                                                                          |
|  picker/                              catalog/                           |
|  +----------------------+             +-----------------------------+    |
|  | IntentionPickerView  |             | IntentionCatalogPage        |    |
|  | TopBar, purpose sheet|             | display title (heading)     |    |
|  | IntentionPickerRow   |             | IntentionCatalogRow         |    |
|  +----------+-----------+             | catalog empty-scope texts   |    |
|             |                         +--------------+--------------+    |
|             |         uses                           |                   |
|             +-------------------+--------------------+                   |
|                                 v                                        |
|  search/                                                                 |
|  +--------------------------------------------------------------------+  |
|  | IntentionSearchKind     texts, keys, screen title, names kind      |  |
|  | IntentionSearchBar      SearchField + FilterButton -> tags panel   |  |
|  | IntentionListHeader     CatalogHeader + summary + a11y label       |  |
|  | ShowAndSortSheet        Show? | Type | Sort + OrderButton | Reset   |  |
|  | IntentionSearchList     list, paging, ListState, EmptyState        |  |
|  | ResultsScrollKeeper     first visible row anchor                   |  |
|  | IntentionRowContent     tag order, marks, accessible label         |  |
|  +--------------------------------+-----------------------------------+  |
|                                   |                                      |
+-----------------------------------+--------------------------------------+
                                    v
              CatalogVM (by purpose) + TagConditionsVM (by purpose)
                                    |
                                    v
                PersonalGraphRepository.getCatalogPage
```

- `IntentionSearchKind.of(IntentionCatalogPurpose)` заменяет `IntentionPickerKind` и `intentionPickerKeyPrefix` и остаётся единственным исчерпывающим разбором назначения в `search/`. Один исчерпывающий `switch` даёт тексты загрузки, подгрузки и отказов, заголовок страницы или экрана выбора, префикс ключей и признак `namesKind`, поэтому виджеты не разбирают назначения сами. Слова заголовка списка `IntentionSearchKind` не даёт: их выбирает разбор `selection.scope` и `selection.type` (решение 3).
  - Вариантов четыре, по одному на назначение: каталог, выбор действия, выбор исходного намерения для дневного выбора, выбор участника долговременной связи. Их префиксы ключей — `intention-catalog`, `daily-choice-action`, `daily-choice-source`, `participant-picker`. Три варианта не хватает: выбор исходного намерения и выбор участника различаются только префиксом, а слитые в один вариант они дали бы одному из экранов чужие ключи.
  - Выбор исходного намерения и выбор участника дают те же тексты, заголовок экрана выбора и `namesKind`, что нынешний вид `intention`; выбор действия — тексты нынешнего вида `action`; каталог — существующие тексты каталога.
- `IntentionPickerView` остаётся на `IntentionPickerPurpose`: комментарий `intention_catalog_purpose.dart` запрещает передавать экрану выбора назначение каталога, и шапка с крестиком каталогу не нужна. Общей становится только начинка под шапкой.
- Ключи и тексты экранов выбора не меняются.

**Альтернативы:**
- Отдать каталогу `IntentionPickerView` с флагами. Тогда экран выбора принимал бы назначение каталога, а шапка, лист назначения и `onPick` стали бы необязательными, и проверку перенесли бы из компилятора в рантайм.
- Собрать каталог из копий частей экранов выбора. Лист, выдача и правило строки разошлись бы при первой правке, а спецификация задаёт их одним требованием.

### 2. Каркас страницы каталога

```text
+------------------------------------------+
| SafeArea(top)                            |
| "Intention graph"   DoableType.display   |  heading
| [SearchField              ] [Filter N]   |  IntentionSearchBar
| Active actions [7]   (Name, A to Z)      |  IntentionListHeader -> sheet
+------------------------------------------+
| Expanded: IntentionSearchList            |  scrolls
|   CatalogRow ... ListState | EmptyState  |
+------------------------------------------+
  AppShell: navigation bar (outside the tab body)
```

На схеме подписи даны английским макетом. По-русски это заголовок «Граф намерений», заголовок списка «Активные действия» и сводка «Название, от А до Я».

- **Раскладка.** `Scaffold` вкладки с `Column`: закреплённые части сверху, выдача в `Expanded`. Так же устроены экран выбора и каталог дневных выборов. Отступы по макету: заголовок 20 по бокам; поиск 12 под заголовком; заголовок списка 2 под поиском; список 20 по бокам и 6 сверху.
- **Заголовок.** Стиль `DoableType.display`, семантика заголовка первого уровня. Требование `app-navigation` о заголовке, совпадающем с названием пункта, им выполняется. Стиль системной строки задаёт `AnnotatedRegion`, как у каталога дневных выборов.
- **Низ списка.** Конец тела вкладки — верхний край панели навигации: это обеспечивает оболочка через `AppShellTabInsets`. Под последней строкой остаётся отступ 24 по макету (`space6`). Экран выбора сохраняет свои 40, поэтому отступ — параметр выдачи.
- **Ошибка фильтра.** Ошибку недопустимого фильтра названия показывает `SearchField`, как в экранах выбора.
- **Что удаляется.** Со старой раскладкой уходят `IntentionSearchLayout` и правило «трети высоты»: при закреплённых частях прокручивается только список.

**Альтернатива:** `CustomScrollView` с закреплёнными sliver-заголовками. Он позволил бы заголовку уходить под край при нехватке высоты, но в макете заголовок закреплён, а экран выбора уже живёт с `Column`. Риск нехватки высоты описан ниже.

### 3. Модель: тип открыт, охват выбирается, сброс одним действием

- **Тип.** Ветка `BrowseIntentionCatalog()` в `selection.type` переходит к `IntentionTypeOpen(_type)`. `IntentionTypeNotOffered` больше никто не создаёт, и он удаляется из закрытой иерархии: компилятор покажет все разборы. Готовность, `changeType` и сброс `_type` начинают работать для каталога без отдельного кода.
- **Охват.** `IntentionCatalogSelection.scope` становится закрытым типом доступности, по образцу `IntentionTypeAvailability`:

  ```text
  IntentionScopeAvailability (sealed)
    IntentionScopeOpen(IntentionScope selected)    browse catalog
    IntentionScopeFixed(IntentionScope scope)      pickers: by purpose
  ```

  Лист показывает строку «Показать» по разбору `selection.scope`, а не проверкой `purpose is BrowseIntentionCatalog`. `changeScope` действует только при открытом охвате.
- **Сброс.** Модель получает `canResetShowParameters` и `resetShowParameters()`. Начальное состояние: охват «Активные» при открытом охвате, тип «Все» при открытом типе, `createdAtDescending`. Сброс меняет все отличающиеся параметры и начинает одно новое чтение. Название и условия по тегам не трогает: условия принадлежат `IntentionTagConditionsViewModel`. Лист больше не считает признак сброса и не делает два вызова.
- **Порядок.** Страница больше не фильтрует порядки: сортировка по названию приходит из общего листа.

**Альтернатива:** признак «охват открыт», выведенный из назначения в виджете. Тогда разбор назначения повторялся бы в листе, заголовке и пустых состояниях.

### 4. Числа по охватам и типам — одно чтение матрицы

Флаг `requestsTypeCounts` заменяется перечислением вида подсчёта, а необязательные числа первой порции — закрытым типом:

```text
IntentionCatalogQuery.counting:  totalOnly | byType | byScopeAndType

IntentionCatalogCounts (sealed)          in IntentionCatalogFirstPage
  TotalOnly
  ByType(IntentionTypeCounts)                       current scope
  ByScopeAndType(active: IntentionTypeCounts,
                 archived: IntentionTypeCounts)     all = active + archived
```

- **Кто что запрашивает.** Модель выбирает вид по `selection`:
  - каталог (охват и тип открыты) — `byScopeAndType`;
  - экран выбора с открытым типом — `byType`;
  - закреплённый тип — `totalOnly`.

  `_mapPage` проверяет, что вид чисел соответствует запросу и что `totalCount` равен числу текущих охвата и готовности. При расхождении — `IntentionCatalogUnexpected`, как сейчас.
- **SQL.** Для `byScopeAndType` запрос подсчёта не включает охват в `WHERE` и считает четыре агрегата `countAll(filter: …)`: активные, активные действия, архивные, архивные действия. Остальные условия — исключение, теги, название — те же. Запрос строк порции не меняется и по-прежнему идёт по частичным индексам охвата. Подсчёт уже выполняется при каждом чтении первой порции; меняется только то, что для каталога он проходит строки обоих охватов.
- **Согласование.** `_reconcileTypeCounts` обобщается до матрицы. Подтверждённые снимки «до» и «после» сравниваются с запросом без охвата и готовности (`withAnyScopeAndReadiness()`). Поправка ±1 идёт в ячейку по архивному состоянию и готовности снимка, поэтому архивирование и восстановление переносят намерение между охватами. Несогласуемые числа — отрицательные или превышающие сумму — ведут к новому чтению, как сейчас.
- **Хранение.** Числа живут только в подтверждённом состоянии выдачи. Состояние даёт производные `typeCounts` (типы в текущем охвате) и `scopeCounts` (охваты при текущем типе). Пока выдача получается или после отказа, их нет. Поэтому лист показывает числа только для подтверждённой выдачи без отдельной логики, а замена графа сбрасывает их вместе с состоянием.
- **Пустое состояние.** Признак «в архиве есть намерения» для пустого активного охвата берётся из той же матрицы (`archived.all > 0`). Третья причина пустой выдачи проверяется только без фильтров, поэтому числа матрицы совпадают с «есть ли архивные вообще».

**Альтернативы:**
- Числа охватов только при текущем типе. Они не отвечают на вопрос пустого активного охвата при типе «Только действия», а меню «Тип» всё равно требует чисел типов в охвате.
- Отдельное чтение чисел по открытию меню. Оно добавляет второй источник, ревизию и состояние загрузки меню. Спецификация требует чисел подтверждённой выдачи, которые уже согласуются с операциями.
- Три отдельных запроса подсчёта. Это втрое больше проходов по тем же строкам, без выигрыша.

### 5. Одна выдача с хранителем позиции

`IntentionSearchList` в `search/` строится на структуре выдачи экрана выбора: `CustomScrollView`, `SliverList.separated` с интервалом 8, `ListState` для подгрузки и отказов, `EmptyState` в `SliverFillRemaining`. Параметры:

- `purpose: IntentionCatalogPurpose`;
- `rowBuilder(context, loaded, summary)`: экран выбора строит `IntentionPickerRow`, каталог — `IntentionCatalogRow`;
- `emptyScope(empty)` — содержание третьей причины: одна строка у экрана выбора, три варианта у каталога (решение 7);
- `onResetFilters` и нижний отступ.

Первые две причины пустой выдачи (фильтры, тип) выдача выбирает сама: правило у них общее.

Якорь первой видимой строки переносится из старой выдачи каталога в класс `ResultsScrollKeeper`. Он владеет:
- `ScrollController`;
- `GlobalKey` строк;
- исходным запросом выдачи;
- снятием якоря в `ref.listen` до перестройки и восстановлением после кадра;
- переходом наверх при новой выдаче и очисткой ключей;
- мгновенным, без анимации, переходом наверх, когда вместо строк показывается пауза ввода, загрузка или отказ первой порции: прокрутка одна, и иначе состояние возвращалось бы к началу пружиной от прежнего смещения.

Хранитель работает для всех назначений, без флага. Экраны выбора тоже согласуют выдачу с подтверждёнными операциями, и сохранение места им не вредит. Флаги «для каталога» из этой части уже однажды убирали.

`PageStorage` не переносится. Каталог не размонтируется ни при переключении пунктов, ни при открытии страниц над оболочкой, а между загрузкой, пустой выдачей и строками прокрутка теперь одна и не пересоздаётся. После замены графа страница создаётся заново и должна начинаться сверху.

**Альтернатива:** якорь в модели. Нельзя: он измеряет раскладку и должен сниматься до перестройки, а это слой виджетов.

### 6. Строка каталога

- **`CatalogRow` в дизайн-системе.** Карточка `fill` с углами `radius-lg`; вся строка — одна кнопка (`InkWell(onTap)`); название, до двух строк описания и `TagLine` по README.
- **Общая колонка текста.** Колонку текста `PickerRow` и `CatalogRow` делят через общий внутренний виджет модуля дизайн-системы. Правила текста одни, а различаются только области нажатия.
- **API по образцу `PickerRow`.** `CatalogRow` принимает:
  - `name`;
  - `description?`;
  - `archived` — приглушает название;
  - `marks: List<Badge>`;
  - `tags: List<TagChip>`;
  - `label`;
  - `onOpen`.

  README предлагает флаги `archived` и `action`, по которым строка рисует метки сама, но Flutter-версия `PickerRow` уже принимает готовые метки от потребителя. Одинаковый API позволяет одному помощнику кормить обе строки и следует [ADR-0030](../../../docs/adr/0030-keep-design-system-components-presentational.md).
- **Без параметров выделения.** `selecting`, `selected`, `onSelect` и `onHold` из README не добавляются: у них нет вызывающей стороны.
- **`IntentionRowContent` в `search/`.** Выносит из `IntentionPickerRow` то, что не зависит от назначения:
  - порядок тегов: обязательные применённого запроса первыми, внутри групп ручной порядок;
  - метки архива и молнии с тоном по архивному состоянию;
  - выделение обязательных тегов;
  - части доступного названия.

  `IntentionPickerRow` и новый `IntentionCatalogRow` строятся из него. Каталог называет тип («действие» / «намерение») по `IntentionSearchKind`, как поиски исходного намерения и участника. Доступное название строки каталога начинается с «Открыть: …» / «Open: …».

### 7. Пустые состояния каталога

Выбор идёт в порядке причин из спецификации:

```text
Empty(query, counts)
  byTitle or byTags?                      -> filter message + "Reset filters"
  type open, not all, counts.inScope.all > 0
                                          -> type message + "Show both types"
  else emptyScope(empty):
    picker                                -> "Nothing to choose from"
    catalog: active and archived.all > 0  -> "No active intentions" (+ Show hint)
             active or all                -> "No intentions yet" (+ plus hint)
             archived                     -> "Nothing in the archive"
```

Подписи на схеме даны английскими текстами. По-русски это «Сбросить фильтры», «Показать оба типа», «Выбрать не из чего», «Нет активных намерений», «Намерений пока нет» и «В архиве ничего нет».

Сообщение о пустом типе в каталоге называет охват:

| Охват | Только действия | Только намерения |
|---|---|---|
| Активные | «Нет активных действий» | «Нет активных намерений» |
| Архивные | «Нет действий в архиве» | «Нет намерений в архиве» |
| Все | «Действий пока нет» | «Намерений пока нет» |

Текст под заголовком по макету: «Здесь появится намерение, отмеченное как действие.» / «Здесь всё отмечено как действия.» Значки берутся из макета:
- поиск — для фильтров;
- молния — для пустых действий;
- знак намерения — для пустых намерений и пустого графа;
- архив — для пустого архива.

У экранов выбора первые две причины и их тексты не меняются.

## Risks / Trade-offs

- **[Высота под списком]** Закреплённые заголовок, поиск и заголовок списка при открытой клавиатуре и крупном системном тексте могут оставить списку мало места или переполнить `Column`. → Тест раскладки при двукратном масштабе с открытой клавиатурой на узком экране проверяет, что переполнения нет и список получает высоту. Экран выбора уже живёт с той же раскладкой.
- **[Цена подсчёта]** Для активного охвата подсчёт каталога проходит и архивные строки. → Это тот же один проход, что сейчас делает охват «Все». Бенчмарк фиксирует разницу; экраны выбора форму запроса не меняют.
- **[Согласование матрицы]** Ошибка поправки ±1 даст неверные числа меню без видимого отказа. → Проверка инварианта суммы ведёт к новому чтению; модельные тесты покрывают каждый вид мутации, включая переход между охватами.
- **[Поведение экранов выбора]** Хранитель позиции меняет поведение выдачи экранов выбора после подтверждённых операций: вместо прыжка наверх сохраняется видимая строка. → Требования экранов выбора не обещают прыжка наверх после согласования, а сохранение видимой строки следует тому же правилу, что «Сохранение состояния загруженного каталога». Тесты экранов выбора проверяют, что новая выдача начинается сверху, а согласование сохраняет место.
- **[Объём правки тестов]** Около 25 файлов. → Сначала общий файл шагов, затем перевод тестов. Поведенческие проверки старой страницы переносятся, а не теряются.
- **[Длинная подпись типа]** «Намерения и действия» длиннее «Всё» в меню экранов выбора. → `SelectRow` переносит текст по спецификации; тест ширины меню обновляется.

## Migration Plan

Данные не мигрируют: схема, индексы, формат графа и журнал фактов не меняются. Новые числа считает существующий запрос подсчёта с другим набором агрегатов. Откат — возврат кода. Сохранённых параметров каталога нет: они живут только в процессе.

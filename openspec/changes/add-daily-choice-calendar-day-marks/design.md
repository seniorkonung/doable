## Context

Изменение добавляет отметки состояния дней во встроенный календарь каталога дневных выборов. Мотивация и границы заданы в [proposal.md](proposal.md), обязательное поведение — в [дельте daily-choice-management](specs/daily-choice-management/spec.md). Термины «дневной выбор», «дата дневного выбора» и «выполнение» используются по [CONTEXT.md](../../../CONTEXT.md). «Состояние дня» определено в глоссарии; «отметка дня» — его изображение в календаре.

Текущая реализация даёт следующую основу:

- `DailyChoiceCatalogPage` владеет просмотром календаря (`DailyChoiceCalendarViewport`), а `DailyChoiceCatalogViewModel` — выбранной датой, фильтром выполнения и выдачей одного дня. Первая порция выдачи читает строки, шаги путей, связи и намерения и проверяет их целостность.
- `DailyChoiceCalendar` по [ADR-0017](../../../docs/adr/0017-isolate-inline-calendar-behind-app-component.md) скрывает `table_calendar` и строит дни собственной ячейкой `DailyChoiceCalendarDay`. Хранилище и часы календарь не читает.
- `table_calendar` строит страницы через `PageView.builder`, поэтому соседняя страница отрисовывается уже во время перетаскивания. Свайп недели сдвигает дату просмотра на семь дней, а свайп месяца переносит её на первое число соседнего месяца.
- В `daily_choices` есть канонический текст `choice_date` (`YYYY-MM-DD`), `is_completed` (0 или 1) и индекс `daily_choices_date_creation_order (choice_date, creation_sequence)`. Поле `creation_sequence` служит псевдонимом `rowid`.
- `GraphCommandCoordinator` живёт всё время процесса и рассылает завершения подтверждённых команд с ревизией графа по [ADR-0009](../../../docs/adr/0009-unify-personal-graph-module-and-revision.md). Чтения и команды `DriftPersonalGraphRepository` выполняются по очереди одним `_AsyncSequencer`.
- [ADR-0011](../../../docs/adr/0011-derive-relation-counts-from-graph-snapshots.md) уже выбрал для счётчиков связей агрегаты внутри SQLite вместо хранимых счётчиков и запретил «ложный ноль» при отказе. Подробности намерения показывают отказ обновления счётчика пассивной строкой без повтора (`intention_summary_view.dart`).
- `DeveloperDiagnosticsSink` пишет события только в `dart:developer`, поэтому в релизной сборке они не сохраняются.

## Goals / Non-Goals

**Goals:**

- Показывать состояние каждого видимого дня, не загружая дневные выборы в приложение и не создавая второго хранимого источника истины.
- Согласовывать отметки с любым подтверждённым изменением так, чтобы будущие команды не требовали доработок ради отметок.
- Показывать отметки соседнего периода уже во время свайпа.
- Отделить чтение отметок от выдачи каталога: их отказ не влияет на выдачу, выбор дня и перелистывание.

**Non-Goals:**

- Хранимая сводка по дням, триггеры для её поддержки и миграции схемы.
- Количество выборов на днях и сохранение отметок между запусками.
- Постоянный журнал ошибок и передача диагностики разработчику.
- Изменение протокола общей поверхности сообщений ([ADR-0012](../../../docs/adr/0012-centralize-graph-operation-result-presentation.md), [ADR-0023](../../../docs/adr/0023-collapse-pending-results-into-shared-surface-messages.md)).

## Decisions

### 1. Вынести отметки в отдельную модель представления

Решение закреплено в [ADR-0025](../../../docs/adr/0025-load-calendar-day-marks-in-separate-viewport-model.md). Оно частично пересматривает ADR-0017: просмотр может запускать чтение отметок, но не чтение выдачи.

Упрощённая C4-схема показывает компоненты внутри одного Flutter-приложения. `Catalog VM` — существующая `DailyChoiceCatalogViewModel`, `Marks VM` — новая модель отметок.

```text
+------------------------+  uses   +-----------------------------+
| DailyChoiceCatalogPage |-------->| DailyChoiceCalendar         |
| owns viewport          |         | day marks, failure line     |
+------------------------+         +-----------------------------+
    |              |
    | watches      | watches, reports viewport
    v              v
+------------+  +----------------+  listens  +-------------------------+
| Catalog VM |  | Marks VM (new) |---------->| GraphCommandCoordinator |
+------------+  +----------------+           +-------------------------+
    |                  |                                 |
    | reads pages      | reads day statuses (new)        | executes commands
    v                  v                                 v
+-----------------------------------------------------------------------+
| PersonalGraphRepository (Drift adapter)                               |
+-----------------------------------------------------------------------+
                                   |
                                   | SQL aggregate by date (new)
                                   v
+-----------------------------------------------------------------------+
| SQLite: daily_choices                                                 |
+-----------------------------------------------------------------------+
```

- Модель каталога по-прежнему слушает координатор; эта стрелка опущена, чтобы схема не перекрещивалась.
- Модель отметок зависит от периода просмотра, а модель каталога — от выбранного дня. У них разные поводы для чтения и разные правила отказа.
- Страница остаётся владельцем просмотра. Все изменения просмотра (свайп, команда шапки, раскрытие, выбор дня) проходят через один метод страницы, который обновляет просмотр и сообщает его модели отметок. Так новый путь изменения просмотра не может обойти отметки.
- Начальное окно модель строит при первом построении от выбранной даты каталога: от неё же страница начинает просмотр. Это исключает изменение провайдера во время построения страницы и чтение без окна.
- Модель отметок, как и модель каталога, живёт вместе со страницей. Оболочка сохраняет страницу при переходах между разделами, поэтому отметки продолжают согласовываться, пока каталог не виден.

**Альтернативы:**

- Встроить отметки в модель каталога. Это смешивает просмотр с поколениями выдачи, а модель и так сложна; кроме того, отказ отметок пришлось бы изолировать от состояний выдачи.
- Считать отметки в странице. Тогда View подписывается на координатор и репозиторий, а это нарушает правило «View знает только свою модель».

### 2. Вычислять состояния дней агрегатом SQLite без хранимой сводки

Решение закреплено в [ADR-0024](../../../docs/adr/0024-derive-calendar-day-states-from-saved-daily-choices.md). `PersonalGraphRepository` получает одно чтение: состояния дней за диапазон дат. Запрос внутри адаптера:

```text
SELECT choice_date, MIN(is_completed) AS all_completed
FROM daily_choices INDEXED BY daily_choices_date_creation_order
WHERE choice_date BETWEEN :first AND :last
GROUP BY choice_date
```

- Дня нет в ответе — выборов нет. `all_completed = 1` означает «все выполнены», `0` — «есть невыполненный». Канонический текст даты упорядочен так же, как сами даты, поэтому `BETWEEN` даёт точный диапазон.
- `INDEXED BY` закрепляет поиск диапазона по индексу даты, как в соседних агрегатах репозитория: без индекса запрос завершится ошибкой, а не перейдёт к полному сканированию.
- Чтение выполняется в транзакции через общий `_sequencer` и возвращает `GraphSnapshot` с ревизией этого снимка. Подтверждённое изменение и снимок, который его отражает, сравниваются той же ревизией, что и выдача.
- Адаптер декодирует каждую дату через `CalendarDate.parseCanonical`, проверяет попадание в диапазон и значения `0` или `1`. Любое нарушение означает отказ всего чтения, без частичного результата и без ложного нуля, как в ADR-0011. Пути выборов агрегат не проверяет: отметкам нужны только дата и выполнение, а повреждение пути проявится при чтении выдачи этого дня.
- Запрос задаёт тип `DailyChoiceDayStatusQuery`: первая дата не позже последней, а длина не больше наибольшего окна решения 3 — 14 недель. Предел сохраняет контракт ограниченного чтения ADR-0009: неограниченные чтения в интерфейс не входят, и через эту границу нельзя запросить весь граф.
- Результат имеет вид `GraphResult<GraphSnapshot<DailyChoiceDayStatuses>, DailyChoiceDayStatusesReadFailure>`. `DailyChoiceDayStatuses` хранит диапазон и состояния `DailyChoiceDayStatus { allCompleted, hasIncomplete }` только для дней с выборами. Отказ — один тип без категорий, потому что ни один потребитель их не различает. Категорию (недоступность, повреждение, неизвестный отказ) адаптер классифицирует через `classifySqliteFailure` и записывает новым событием `DailyChoiceDayStatusesReadDiagnosticsEvent` без дат и диапазона.
- По оценке, сетка из 14 недель при 20 выборах в день — около 2000 записей индекса с поиском строки по `rowid`. Это легче первой порции выдачи. Покрывающий индекс `(choice_date, is_completed)` в изменение не входит (см. Risks).

**Альтернативы:**

- Таблица-сводка с триггерами SQLite. Чтение было бы по ключу, но появились бы второй источник истины, миграция с заполнением, проверка согласованности сводки и отдельное ADR о материализации, которое ADR-0011 требует до такого шага.
- Счётчики, которые обновляют Dart-команды. Каждая будущая команда должна была бы помнить о сводке, а это прямой путь к рассогласованию.
- Отметки из порций выдачи. Выдача ограничена одним днём и загружает полные строки с путями, поэтому для периода не подходит.

### 3. Читать одним запросом окно из трёх месяцев вокруг месяца даты просмотра

Окно — от понедельника недели, содержащей первое число предыдущего месяца, до воскресенья недели, содержащей последнее число следующего месяца, с обрезкой по диапазону `CalendarDate`. Оно зависит только от месяца даты просмотра и не зависит от представления. Длина окна не превышает 14 недель. Окно вычисляет чистая функция рядом с моделью отметок. Календарная арифметика выполняется над техническим `DateTime.utc`, как в компоненте календаря.

| Событие | Окно | Чтение отметок |
| --- | --- | --- |
| Первое открытие каталога | Вокруг месяца выбранной даты | Да |
| Свайп недели или выбор дня в пределах того же месяца | Без изменений | Нет; после отказа — да |
| Раскрытие или сворачивание | Без изменений | Нет; после отказа — да |
| Свайп или выбор дня, меняющий месяц даты просмотра | Сдвигается | Да |
| Новая подтверждённая ревизия | Без изменений | Да |
| Ответ для прежнего окна или старее последней известной ревизии | — | Отбрасывается, читается текущее окно |

- Успешный ответ целиком заменяет хранимый результат. Учёта свежести по отдельным месяцам нет, и память ограничена одним окном.
- Каждая ревизия перечитывает всё окно вместе с соседями, поэтому соседний месяц при переключении показывает актуальные данные. Новый запрос после смены месяца нужен ради нового дальнего соседа.
- Соседняя неделя любой недели месяца и соседние месяцы всегда входят в окно, поэтому во время жеста их дни уже имеют отметки.
- После отказа любое изменение просмотра запрашивает отметки заново, даже если окно не изменилось. Так соблюдается правило спецификации о повторе при следующем перелистывании без отдельной команды повтора.

**Альтернативы:**

- Читать только видимый период. Соседняя страница во время свайпа выглядела бы пустой, то есть «без выборов».
- Хранить предыдущий, текущий и следующий месяцы отдельно и следить за свежестью каждого. Это больше состояния при том же поведении.
- Накапливать все прочитанные периоды. Память растёт, а устаревшие периоды пришлось бы отдельно инвалидировать.

### 4. Согласовывать отметки по ревизиям без фильтрации изменений

```text
User            EditPage        Coordinator     Repository      MarksVM         Calendar
|               |               |               |               |               |
| 1. mark done  |               |               |               |               |
|-------------->|               |               |               |               |
|               | 2. accept     |               |               |               |
|               |-------------->|               |               |               |
|               |               | 3. execute    |               |               |
|               |               |-------------->|               |               |
|               |               | 4. commit r2  |               |               |
|               |               |<--------------|               |               |
|               |               | 5. completion r2              |               |
|               |               |------------------------------>|               |
|               |               |               | 6. read window|               |
|               |               |               |<--------------|               |
|               |               |               | 7. statuses r2|               |
|               |               |               |-------------->|               |
|               |               |               |               | 8. new marks  |
|               |               |               |               |-------------->|
```

`EditPage` — страница изменения выбора, `r2` — новая ревизия графа.

- Повторное чтение вместо применения изменений закреплено в ADR-0024. Модель подписывается на `GraphCommandCoordinator.completions` так же, как модель каталога. Любое завершение с подтверждённым пакетом новее известной ревизии делает его ревизию обязательной и запускает чтение текущего окна. Виды изменений в пакете модель не разбирает.
- Применить изменение в памяти невозможно. `DailyChoiceChange` описывает один выбор, а состояние дня зависит от всех выборов даты, о которых событие ничего не знает.
- Одновременно выполняется не больше одного чтения. Если за время чтения сменилось окно или появилась новая обязательная ревизия, по завершении читается текущее состояние. Ответ применяется, только если он относится к текущему окну и не старее обязательной ревизии; сравнение ревизий повторяет правила модели каталога.
- Повторное чтение после отброшенного ответа начинается уже после подтверждения ревизии. Чтения и команды проходят одну очередь адаптера, поэтому такое чтение её отражает, и отдельный предел попыток не нужен.
- Между шагами 5 и 8 календарь показывает прежние отметки.

**Альтернатива** — читать только при наличии `DailyChoiceChange` в пакете. Чтений стало бы меньше, но правильность отметок зависела бы от того, помнят ли будущие команды о нужном виде изменения. Цена отказа от фильтра — одно агрегатное чтение на каждую команду пользователя, пока страница каталога существует.

### 5. Передавать календарю готовые состояния и показывать отказ пассивной строкой

- Состояние модели содержит последний успешный результат (`DailyChoiceDayStatuses?`) и признак отказа последнего чтения. Эти две независимые величины не образуют недопустимых сочетаний: отказ без прежнего результата означает дни без отметок и строку отказа. Отдельного видимого состояния загрузки нет.
- Новый вход `DailyChoiceCalendar` — состояние дня по дате (`DailyChoiceDayStatus?`, где `null` — нет отметки) и признак показа строки отказа. Окна, ревизии и хранилище календарь не знает; граница ADR-0017 сохраняется.
- `DailyChoiceCalendarDay` рисует под числом галочку для «все выполнены» и пустой кружок для «есть невыполненный». Цвет берётся из темы, а на выбранном дне с заливкой — контрастный к ней. Место отметки всегда входит в высоту строки, которую рассчитывает `rowHeight`, поэтому строка не меняет высоту, когда отметки появляются. Размер отметки масштабируется вместе с текстом.
- Доступное название дня дополняется локализованным состоянием после даты и отметки «сегодня». У дня без отметки состояние не сообщается.
- Строка отказа стоит под шапкой календаря, оформлена в цвете ошибки, как строка отказа счётчика связей, и не содержит действий. Текст одинаков для всех категорий отказа.

**Альтернативы:**

- Всплывающее сообщение. Общей поверхностью владеют результаты команд (ADR-0012, ADR-0023). Отказ повторялся бы при каждом свайпе, а после исчезновения сообщения календарь снова молча показывал бы пустые дни.
- Кнопка повтора. Повторение и так происходит при следующем перелистывании или изменении, а при повреждении кнопка обещала бы восстановление, которого нет.
- Скрыть отметки при отказе. Это ложный ноль: календарь утверждал бы, что выборов нет.

### 6. Проверять поведение на границах компонентов

- **Адаптер на настоящем SQLite:** три состояния дня, включительные границы диапазона, исключение дат вне диапазона, ревизия снимка, отказ без частичного результата при недопустимой сохранённой дате, проверка запроса.
- **Модель отметок с подменённым репозиторием:**
  - окно по месяцу даты просмотра и отсутствие чтений при свайпе недели внутри месяца и при смене представления;
  - замена результата при успехе; сохранение результата и признак отказа при неудаче;
  - чтение после новой ревизии; отбрасывание ответов прежнего окна и старой ревизии;
  - чтение при любом изменении просмотра после отказа.
- **Компонент календаря:** отметки всех состояний, в том числе на выбранном, сегодняшнем и соседнем по месяцу дне; доступные названия на двух языках; строка отказа; одинаковая высота строки с отметками и без них при увеличенном тексте.
- **Страница каталога:** сценарии дельты — выполнение на странице изменения, перенос даты, отметки соседней недели при частичном перетаскивании и независимость от фильтра выполнения.
- **Диагностика:** кодирование нового события без дат и диапазона.

## Risks / Trade-offs

- [Агрегат на большом личном графе медленнее оценки] → `INDEXED BY` исключает полное сканирование. При реализации длительность чтения окна измеряется по диагностике в profile-сборке на устройстве с большим синтетическим набором выборов. Если измерение покажет, что нужен покрывающий индекс, он вводится отдельным решением с миграцией.
- [Быстрое пролистывание нескольких месяцев обгоняет предзагрузку] → Принято: месяц вне хранимого окна до ответа на текущее окно показывается без отметок. Спецификация гарантирует соседний период только после получения отметок показанного периода.
- [Выдача и отметка выбранного дня ненадолго расходятся] → Обе модели перечитывают данные по одной ревизии независимо и сходятся. Показ прежних отметок до ответа подтверждён владельцем продукта.
- [Чтение после каждой команды, включая не связанные с дневными выборами] → Цена — одно ограниченное агрегатное чтение на действие пользователя. Её платят за то, что отметкам не нужно знать виды изменений.
- [Отказ виден пользователю, но не разработчику] → Диагностика записывается через существующий интерфейс. Постоянный журнал ошибок — отдельное изменение, и события отметок попадут в него без доработок.

Дополнительный аудит сохранённых путей статистикой не обоснован достижимым сценарием по общему контракту локальных данных. Принятых человеком остаточных рисков нет. ## Findings

### F2 · Medium — Опорные намерения теряют явное основание в разбивке после исключения узла

- **Evidence:** [Спецификация, «Раздел статистики намерения»](specs/contribution-statistics/spec.md) относит выбор к активной связи X → Y, если он засчитан Y без прохода через X; явно сохранённое намерение пути получает выбор независимо от достижимости действия. [Дизайн, решение 3](design.md) предлагает для этой разбивки тот же подсчёт по опорным намерениям, но без X. Допустимый пример: выполненный выбор с сохранённым путём Y → X → D и дополнительной активной связью X → Y; все связи активны, D — выбранное действие. Такие циклы разрешены [каноническим контрактом связей](../../specs/long-term-relation-management/spec.md). Y уже находится на сохранённом пути, поэтому разбивка X должна включать X → Y с вкладом 1, наряду с X → D. Единственное опорное намерение по дизайну и [ADR-0026](../../../docs/adr/0026-compute-contribution-through-relations-off-queue.md) — D. После исключения X из обхода Y не достигает D; добавление связи, следующей за X в сохранённом пути, вернёт только X → D.
- **Impact:** Реализация описанного алгоритма пропустит X → Y и занизит точное число элементов разбивки на корректном графе. Доказательство достаточности опорных намерений для полного активного графа не переносится на граф с исключённым X.
- **Required change:** Уточнить алгоритм разбивки в решении 3 так, чтобы исключение X сохраняло засчитывание всем явно сохранённым намерениям пути и одновременно запрещало неявный возврат через X. Ограничить область доказательства в ADR-0026 либо дополнить его для изменённого графа. В проверках дизайна и готовности Phase 3 закрепить сравнение разбивки с нормативным результатом этого примера; задачи Phase 3 оставить последующему планированию. Общий подсчёт Главной этот контрпример не опровергает.

### F3 · Medium — Фикстура «максимум» не покрывает поддерживаемую длину сохранённого пути

- **Evidence:** [Требование «Отзывчивость на максимальных данных»](specs/contribution-statistics/spec.md) ограничивает количество намерений, связей и дневных выборов, но не длину пути. [Дизайн, решение 10](design.md) и [задача 1.5](tasks.md) проверяют только пути из 1–6 шагов. Между тем [черновик пути](../../../lib/src/daily_choice/application/choice_path_draft.dart) ограничивает путь непрерывностью и отсутствием повторов, а не шестью шагами; [тест чтения](../../../test/graph/data/drift_daily_choice_read_test.dart) подтверждает сохранённую цепочку из 405 шагов, и [тест продолжений](../../../test/graph/data/drift_choice_path_continuations_test.dart) проверяет глубину 1100. Полные дубликаты дневных выборов разрешены. При 60 выборах в день за невисокосный год пути из 405 шагов дают 8 869 500 строк шагов вместо 131 400 при шести шагах, оставаясь внутри заявленных размеров графа. Решение 2 пересчитывает промежуточные намерения агрегатом периода для каждой порции в общей очереди.
- **Impact:** Успешный замер коротких путей не подтвердит бюджет чтения и задержку команд для уже допустимых данных. Риск особенно относится к промежуточным намерениям и чтению оснований для вида «Через связи»; ограничение выдачи ста элементами не ограничивает количество обрабатываемых шагов. Фактическое превышение бюджета ещё не измерено.
- **Required change:** Дополнить модель нагрузки и замеры дизайна количеством шагов, включая длинные допустимые пути и их повторное использование выборами периода. Скорректировать проверку задачи 1.5 для Phase 1 и условия готовности Phase 2–3 для зависимых чтений. Проверять время в общей очереди и полный запрос на этой нагрузке; при превышении применять предусмотренную дизайном эскалацию. Ограничение длины пользовательского пути не выводить из тестовой фикстуры без отдельного продуктового решения.

## Review coverage

Проверены граф артефактов схемы `intent-driven` и все существующие артефакты изменения: предложение, четыре дельты спецификаций, дизайн, ADR-манифест, план и задачи. Прочитаны принадлежащие изменению ADR-0026–0028, применимые решения о границе личного графа, SQLite, агрегатах, календаре, навигации и предъявлении результатов, а также предметный глоссарий.

Проверены правила четырёх видов, доли и дубликаты, архивирование и циклы, разбивки, ревизии и продолжения порций, согласование при показе и смене местной даты, отказы, приватность диагностики, локализация и доступность. Решения сопоставлены с реальными схемой и валидатором путей, последовательным исполнителем репозитория, моделями каталога, наблюдателем местного дня, страницей намерения, корневой оболочкой и маршрутизатором. Сценарии изменяемых требований навигации и начального состояния календаря сохраняют существующие обязательства; удаление требования о пустой Главной явно оформлено.

Обязательства прослежены к фазам и проверкам в обоих направлениях, включая поиск избыточной работы. Пакет задач содержит только Phase 1, зависимости предшествуют потребителям в порядке файла. Отсутствие задач Phase 2–4 соответствует поэтапной схеме; их объём проверен по плану. Изменение не вводит внешних сервисов, новых разрешений или миграции; пересмотр схемы при неудачном замере предусмотрен отдельно. Состояния и порядок задач сохранены; исходный код и тесты не изменялись.

Граница проверок целостности сопоставлена с [общим контрактом локальных данных](../../specs/local-data-lifecycle/spec.md#requirement-обработка-обнаруженного-повреждения-данных), [транзакционными командами создания и замены пути](../../../lib/src/graph/data/drift_personal_graph_repository_daily_choice_commands.dart) и [ограничениями схемы](../../../lib/src/data/local/schema/daily_choice_schema.drift). Проверка записи, повторное чтение до подтверждения и защита используемых связей обеспечивают цепочку в поддерживаемых операциях. Тест с посторонним циклом создаёт его прямым SQL в обход этих команд и не доказывает достижимость такого состояния в работе приложения. Обработка сообщённых SQLite повреждений остаётся обязанностью общего механизма отказов.

## Findings

### F1 · Medium — Адрес каталога пакета нельзя непосредственно использовать как запись ресурсов

- **Evidence:** `design.md:53` описывает включение `packages/doable/src/design_system/icons/assets/` в оба манифеста, а задачи 1.2–1.3 ссылаются на это решение без уточнения записей. Физические SVG при этом должны лежать в `lib/src/design_system/icons/assets/`. В закреплённом Flutter 3.47.1 файл `packages/flutter_tools/lib/src/asset.dart`, методы `_parseAssets` и `_parseAssetsFromFolder` (строки 1049 и 1168), обрабатывает запись с завершающим `/` как физический каталог относительно `pubspec.yaml`. Разрешение `packages/<package>/...` через конфигурацию пакетов происходит только на пути отдельного файла в `_resolveAsset` (строка 1389). Существующая регистрация Inter в `widgetbook/pubspec.yaml` указывает конкретный файл и не подтверждает работоспособность пакетного каталога. [Документация Flutter](https://docs.flutter.dev/ui/assets/assets-and-images#asset-images-in-package-dependencies) также иллюстрирует включение ресурсов из `lib/` отдельными пакетными файлами.
- **Impact:** Если перенести приведённый адрес каталога в `assets:`, сборщик будет искать отсутствующий `packages/doable/.../assets/` внутри приложения или Widgetbook и не включит SVG. Проверки загрузки остановят реализацию уже в задачах 1.2–1.3; исполнитель будет вынужден самостоятельно уточнять зафиксированное решение о поставке.
- **Required change:** Уточнить решение 3 и согласовать задачи 1.2–1.3: отделить логический префикс ресурса от поддерживаемых записей манифеста. Для сохранения выбранной адресации можно перечислить конкретные `packages/doable/src/design_system/icons/assets/<имя>.svg`. Результат должен обеспечивать загрузку всех 17 вариантов по одному контракту в приложении и Widgetbook из одних физических файлов, без зависимости от `context`; существующие проверки загрузки сохранить.

### F2 · Medium — Итоговая задача фазы пропускает обязательную проверку проекта

- **Evidence:** Задача 1.9 в `tasks.md:79` завершает единственную фазу, но её проверки ограничены форматированием, анализатором, выбранными каталогами тестов и OpenSpec. `AGENTS.md:43` требует перед завершением фазы выполнить `mise run check`. Эта команда в `mise.toml:13` дополнительно проверяет классификатор CI, разрешает зависимости Widgetbook с `--enforce-lockfile` и запускает весь набор тестов. Задачи 1.2–1.3 изменяют зависимость и lock-файлы обоих пакетов, а задача 1.4 — общий помощник навигационных сценариев.
- **Impact:** Выполнение всех записанных команд задачи 1.9 не подтверждает обязательное условие завершения фазы. В частности, согласованность изменённого lock-файла Widgetbook с манифестом не проверяется в строгом режиме; проверка проекта, требуемая репозиторием и CI, откладывается за пределы завершённой фазы.
- **Required change:** В задаче 1.9 закрепить `mise run check` как обязательную итоговую проверку вместо дублирующего перечня выборочных команд. Сохранить визуальную сверку и строгую валидацию изменения командой `mise exec --no-deps -- openspec validate use-design-source-icons --strict`. Проверки отдельных задач 1.1–1.8 оставить ограниченными их изменениями и непосредственно затронутыми потребителями.

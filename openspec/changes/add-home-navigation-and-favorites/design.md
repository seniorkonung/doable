## Context

Изменение реализует [proposal.md](proposal.md) и три спецификации: [основную навигацию](specs/app-navigation/spec.md), [избранные намерения](specs/favorite-intention-management/spec.md) и [дельту управления намерениями](specs/intention-management/spec.md).

Сейчас приложение — один плоский стек `AppRouter`: начальный маршрут — каталог намерений, каждая страница открывается поверх через `context.router.push` либо `Navigator.of(context).push`. Каталог дневных выборов открывается значком в шапке каталога намерений. Каждая страница владеет собственным `Scaffold`.

Действующие ограничения:

- [ADR-0009](../../../docs/adr/0009-unify-personal-graph-module-and-revision.md): единственная прикладная граница — `PersonalGraphRepository`; команды идут через `GraphCommandCoordinator`, который резервирует типизированные ключи и публикует завершения одним каналом; представления согласуются по `GraphRevision`.
- [ADR-0012](../../../docs/adr/0012-centralize-graph-operation-result-presentation.md): один `GraphOperationPresenter` владеет общей поверхностью `ScaffoldMessenger`; ошибка принадлежит открытой экранной сессии, пока её renderer остаётся в дереве.
- [ADR-0013](../../../docs/adr/0013-load-complete-tag-snapshots.md): небольшие списки читаются полным согласованным снимком; каталог намерений остаётся порционным.
- [ADR-0002](../../../docs/adr/0002-use-drift-sqlite-for-local-graph.md) и решение 5 изменения `remove-relation-tags`: хранилище существует в единственной версии схемы 1.

Факты платформы, проверенные по исходникам закреплённых версий Flutter 3.47.1 и `auto_route` 11.1:

- `context.router` на странице вкладки без вложенного `AutoRouter` возвращает корневой стек, поэтому нынешние переходы открываются поверх оболочки без изменения кода страниц.
- `TabsRouter.maybePop` при заданном `homeIndex` сначала возвращает на домашнюю вкладку и только с неё передаёт «назад» родителю; по умолчанию `homeIndex` равен −1.
- Системное «назад» доходит до framework не всегда. Целевой API приложения — 36, а манифест не задаёт `android:enableOnBackInvokedCallback`, поэтому на Android 16 и новее платформа передаёт «назад» приложению, только пока framework сообщил о готовности его обработать через `SystemNavigator.setFrameworkHandlesBack(true)`. Flutter выводит эту готовность из стека `Navigator` и состояния `PopScope` текущего маршрута. `AutoTabsRouter` не содержит `PopScope` и не отправляет `NavigationNotification`, поэтому один `homeIndex` готовность не объявляет: пока оболочка — единственная страница корневого стека, платформа получает `false`.
- `ScaffoldMessenger` показывает `SnackBar` только в корневом `Scaffold` вложенного набора. `SnackBar` обёрнут в `Hero` с меткой, выведенной из содержимого.
- `IndexedStack` не отключает скрытым потомкам ни тикеры, ни `Hero`: он исключает их только из отрисовки, попаданий и семантики.
- `NavigationBar` рисует подпись обычным текстом без усечения, показывает подсказку по долгому нажатию из `tooltip` либо `label` и объявляет положение пункта экранному диктору. Его высота — заданная `height` плюс нижний безопасный отступ.
- `SliverReorderableList` сам добавляет каждому элементу доступные действия «переместить вверх», «вниз», «в начало» и «в конец» с системной локализацией; для первого и последнего элемента невозможные действия отсутствуют.

Схемы ниже — облегчённые C4-схемы уровня компонентов внутри одного приложения, как в прежних изменениях. Подписи в схемах даны латиницей; соответствие объяснено рядом.

## Goals / Non-Goals

**Goals:**

- Панель с тремя пунктами, существующая по построению на каждой корневой странице и отсутствующая на остальных.
- Прежнее поведение страниц, общих сообщений, основных действий и экранной клавиатуры при появлении оболочки.
- Отметка избранного как отдельные данные намерения с одним подтверждённым состоянием во всех представлениях.
- Единый ручной порядок, однозначный на уровне схемы хранения, и правило перестановки в одном месте.
- Главная, согласованная с подтверждёнными изменениями графа без повторного открытия.

**Non-Goals:**

- Собственные стеки вкладок, восстановление выбранного пункта после перезапуска и визуализация графа.
- Изменение содержимого каталогов, порционного чтения каталога намерений и правил владения сообщениями об ошибках форм.
- Путь обновления хранилища, предел числа избранных и ключи порядка, пригодные для синхронизации.

## Decisions

### 1. Компоненты и их границы

```text
Components inside the Flutter application

+--------------------------------------------------------------+
| Shell (app/navigation)                                       |
|   tabs host + navigation bar + inset layout                  |
+----------+--------------------+--------------------+---------+
           |                    |                    |
           v                    v                    v
   +---------------+   +-----------------+   +------------------+
   | Home          |   | Daily catalog   |   | Intention catalog|
   | (favorite)    |   | (daily_choice)  |   | (intention)      |
   +-------+-------+   +--------+--------+   +---------+--------+
           |                    |                      |
           | view models        |                      |
           v                    v                      v
   +------------------------------------------------------------+
   | Coordinator: keys, completions, presentation claims        |
   +-----------------------------+------------------------------+
                                 | execute / read
                                 v
   +------------------------------------------------------------+
   | Repository (PersonalGraphRepository, Drift / SQLite)       |
   +------------------------------------------------------------+

Pages opened above the shell (intention page, editors, pickers)
use the same Coordinator and Repository and cover the bar.
```

- `Shell` — новая оболочка в `lib/src/app/navigation/`. Она знает три пункта и раскладку, но не знает содержимого страниц.
- `Home` — Главная в новом модуле `lib/src/favorite/` со слоями `domain`, `application` и `presentation`, как у тегов.
- `Daily catalog` и `Intention catalog` — существующие страницы каталогов. Они не получают зависимости от оболочки.
- `Coordinator` и `Repository` — прежние `GraphCommandCoordinator` и `PersonalGraphRepository`; новая граница хранения или второй канал команд не вводятся.

Отметка проходит через модуль намерений (решение 5), порядок и список Главной — через модуль избранного (решения 8–11).

### 2. Корневой маршрут-оболочка с тремя дочерними маршрутами

`AppRouter` получает начальный маршрут оболочки с тремя дочерними: Главная, каталог дневных выборов и каталог намерений. Остальные маршруты остаются корневыми и открываются поверх оболочки. Собственные стеки вкладкам не даются.

Пункты описывает одно закрытое перечисление `AppDestination` со значениями `home`, `dailyChoices` и `intentionGraph`. Из него исчерпывающими `switch` выводятся порядок, дочерний маршрут, значки и название. Индексы вкладок за пределы оболочки не выходят: пустая Главная открывает граф через типизированный маршрут каталога (`navigateTo`).

Оболочка использует `AutoTabsRouter.builder` с `homeIndex`, равным индексу Главной. Он определяет, что делает дошедшее до приложения «назад»: с каталогов — переход на Главную, с Главной — передача родителю, то есть выход из приложения.

Чтобы «назад» дошло до приложения, оболочка сама объявляет платформе готовность его обработать. Она оборачивает своё содержимое в `PopScope`, у которого `canPop` истинно только при выбранном пункте `AppDestination.home`. Значение выводится из того же выбранного пункта, что и панель, и отдельного состояния не имеет:

- выбран каталог дневных выборов или каталог намерений и поверх оболочки нет страниц — маршрут оболочки запрещает закрытие, framework сообщает платформе `true`, и системное «назад» приходит в приложение;
- выбрана Главная и поверх оболочки нет страниц — запрета нет, framework сообщает `false`, и «назад» остаётся платформенным выходом, включая системную анимацию;
- поверх оболочки открыта страница — готовность следует из стека `Navigator`, а `PopScope` оболочки на закрытие верхней страницы не влияет.

`PopScope` служит только объявлением: переход на Главную выполняет один путь — `homeIndex`, и обратный вызов `PopScope` второго перехода не делает. На платформах без системного «назад» объявление ничего не меняет: `setFrameworkHandlesBack` действует только на Android, а маршрут оболочки — первый в стеке, и жеста возврата у него нет.

Вкладки размещает собственный `IndexedStack`:

- вкладка строится при первом выборе и дальше остаётся в дереве, поэтому состояние страницы и её view model живут весь запуск и продолжают получать завершения команд;
- невыбранная вкладка оборачивается `HeroMode(enabled: false)` и `TickerMode(enabled: false)`;
- переключение происходит без анимации перехода.

Обёртки обязательны. Без `HeroMode` общее сообщение, построенное в нескольких `Scaffold` одного маршрута, даёт одинаковые метки `Hero` и отказ утверждения при переходе на другую страницу. Без `TickerMode` свидетельство кадра `PresentationFrameEvidence` могло бы подтвердить сообщение скрытой вкладки.

Альтернативы:

- **Стек на каждую вкладку с панелью на всех страницах.** Отклонено пользователем; дополнительно форма могла бы остаться под другой вкладкой с непредъявленной ошибкой.
- **Штатный режим `AutoTabsRouter` с готовым `IndexedStack`.** Он не позволяет обернуть отдельную вкладку и анимирует переключение затуханием.
- **`android:enableOnBackInvokedCallback="false"` в манифесте вместо объявления оболочки.** Прежняя доставка «назад» возвращается одной строкой, но приложение теряет системные анимации «назад», а сам отказ — временная уступка платформы.

### 3. Оболочка без собственного `Scaffold`

Оболочка — колонка из области вкладок и панели, а не `Scaffold` с `bottomNavigationBar`. Каждая корневая страница сохраняет собственный `Scaffold` и остаётся корневым получателем общих сообщений. Поэтому сообщение появляется над панелью, а основное действие страницы штатно поднимается над ним — как сейчас.

Оболочка заменяет области вкладок только данные `MediaQuery`:

- нижний безопасный отступ обнуляется: его занимает панель;
- нижняя вставка клавиатуры `K` заменяется на `max(0, K − H − P)`, где `H` — заданная высота панели, а `P` — текущий нижний безопасный отступ.

Формула повторяет правило `Scaffold` для тела с нижней панелью: содержимое заканчивается на большем из высоты клавиатуры и высоты панели. Панель остаётся в раскладке и закрывается клавиатурой. Высота панели задаётся оболочкой явно, поэтому измерение после раскладки не требуется.

Альтернативы:

- **`Scaffold` оболочки с вложенными `Scaffold` страниц.** Сообщение показал бы только внешний `Scaffold`, и оно перекрывало бы основное действие вложенной страницы. Это нарушает требование о панели и содержимом корневых страниц.
- **Основные действия и шапки страниц в `Scaffold` оболочки.** Страница перестаёт владеть своим действием и не проверяется отдельно.
- **Панель в `bottomNavigationBar` каждой корневой страницы.** Раскладка остаётся штатной, но панель существует в трёх экземплярах, страницы зависят от оболочки, а новая корневая страница может забыть панель.

### 4. Панель без подписей и один источник названий

Панель — `NavigationBar` с тремя `NavigationDestination` и скрытыми подписями (`alwaysHide`). Название пункта передаётся в `label`: из него панель берёт подсказку по долгому нажатию, а экранный диктор получает название вместе с положением пункта. Каждый пункт имеет контурный и залитый значок, поэтому выбранный пункт отличается не только цветом.

Три названия — отдельные строки локализации, общие для пункта и заголовка его корневой страницы. Заголовок каталога намерений как корневой страницы берёт название пункта «Граф намерений»; прежняя строка заголовка каталога удаляется. Значки: `home`, `calendar_month` и `hub`. Значки `account_tree` и `schema` не используются: они изображают иерархию.

Объявление названия экранным диктором при скрытых подписях закрепляется проверкой семантики, а не предполагается.

### 5. Отметка и её снятие — команды намерения

Вводятся `MarkIntentionFavorite` и `UnmarkIntentionFavorite` как `ExistingIntentionCommand`. Они принимаются существующим `acceptExisting` под ключом `ExistingIntentionKey`. Это без нового механизма даёт три требуемых свойства:

- одну выполняющуюся изменяющую операцию намерения, включая повторное открытие страницы;
- предъявление результата по действующему протоколу: успех — общей поверхности, ошибка — странице;
- завершение принятой операции независимо от экрана.

Успех возвращает `IntentionSaved` с каталожной мутацией `IntentionCatalogUpdated`, краткие снимки которой различаются только отметкой. Каталоги применяют её на месте: принадлежность выдаче, порядок и количество не меняются. Повторная отметка и снятие отсутствующей отметки возвращают `IntentionCatalogUnchanged` без продвижения ревизии. Время изменения намерения команда не трогает.

`IntentionDetailsViewModel` получает два новых вида перехода состояния, поэтому выполнение, ошибка с правом предъявления и повтор при устранимой причине используют существующий путь. Управление отметкой размещается в шапке страницы намерения и показывается только при полученных подробных данных.

Альтернатива — отдельное семейство команд избранного с собственными ключами, как у назначений тегов. Она повторяет ключ намерения, завершение и сообщения ради операции, у которой нет второго участника.

### 6. Отметка в проекциях намерения

Доменный тип `FavoriteMark` — перечисление из двух значений, по образцу `IntentionReadiness`. Сущность `Intention` не меняется: отметка не редактируемое поле. Отметку получают две проекции:

- `IntentionDetails` — для страницы намерения;
- `IntentionSummary` — для четырёх контекстов поиска и для каталожных снимков команд.

Репозиторий читает отметки пакетно для идентификаторов порции в той же транзакции, что счётчики и теги. Снимки до и после любой команды намерения тоже содержат отметку. Это делает каталожную мутацию достаточным сигналом для Главной: переименование, архивирование, восстановление и удаление избранного намерения распознаются по отметке в снимке.

`IntentionSummaryView` получает необязательную подтверждённую отметку по образцу `confirmedTags`: `null` означает представление, которое отметку не показывает. Четыре поиска передают отметку; соседство намерения, участник связи и Главная — нет. Звезда входит в объединённую семантику строки и не становится отдельной целью нажатия.

### 7. Хранение: таблица отметок с целочисленным местом

```text
favorite_intentions
  intention_id  TEXT    PRIMARY KEY  -> intentions(id) ON DELETE CASCADE
  position      INTEGER NOT NULL UNIQUE CHECK (position > 0)
```

Наличие строки и есть отметка, поэтому отметка без места и место без отметки непредставимы. Первичный ключ исключает вторую отметку, внешний ключ — отметку отсутствующего намерения, уникальность — два намерения на одном месте. Каскад удаляет отметку вместе с намерением в той же инструкции. Идентичность строки неизменяема защитным триггером, как у назначений тегов.

`position` — ключ порядка, а не плотный номер:

- отметка получает `max(position) + 1`;
- снятие отметки и удаление намерения оставляют пропуск;
- перестановка переписывает места всех избранных значениями `1..n` в новом порядке.

Перезапись идёт в два шага внутри транзакции команды, потому что SQLite проверяет уникальность построчно. Сначала все места сдвигаются за текущий максимум, затем каждое получает итоговое значение из переданного списка идентификаторов. Промежуточные значения всегда положительны и не совпадают ни с прежними, ни с итоговыми. Число инструкций не зависит от числа избранных.

Схема добавляется новым файлом `favorite_schema.drift` и правится на месте в версии 1: снимок `drift_schemas/drift_schema_v1.json` перегенерируется, шаги обновления не появляются. Основание — подтверждение пользователя, что сборок с данными, требующими переноса, нет. Это исключение ограничено данным изменением и не пересматривает ADR-0002: поэтапные проверяемые миграции остаются обязательными для каждой версии схемы, опубликованной после него.

Альтернативы:

- **Столбец места в `intentions`.** Перестановка писала бы в строки намерений: срабатывал бы триггер поискового индекса, а отметка смешивалась бы с редактируемыми полями.
- **Дробные или строковые ключи между соседями.** Перестановка меняет одну строку, но нужен алгоритм ключей и его проверка. Преимущество проявляется при синхронизации, которой нет.
- **Связный список со ссылкой на предыдущего.** Чтение требует рекурсии, а перестановка — согласованного изменения нескольких ссылок при той же построчной уникальности.

### 8. Список Главной — полный согласованный снимок

`PersonalGraphRepository` реализует новый узкий контракт чтения избранного с одной операцией. Она возвращает на одной транзакции и ревизии:

- активные избранные намерения в порядке мест: идентификатор, название, готовность к действию и число активных связей;
- число архивированных избранных — оно различает два пустых состояния Главной.

Курсоров, размера порции и предела нет, по образцу ADR-0013: ручной порядок и перестановка требуют списка целиком, а избранное мало по смыслу. Отдельный тип строки вместо `IntentionSummary` не тянет за собой теги и временные метки, которых Главная не показывает.

До публикации снимка проверяются все строки, включая архивированные: место без существующего намерения, недопустимый идентификатор или недопустимые поля намерения дают отказ повреждения без частичного списка. Счётчики читаются существующим пакетным агрегатом. Отказы типизированы: недоступность, повреждение и неизвестный отказ.

Альтернатива — порционное чтение с курсором, как у каталога. Перетаскивание через границу порции и перезапись порядка потребовали бы всего списка в любом случае.

### 9. Перестановка: одна чистая функция правила

Команда `MoveFavoriteIntention` несёт перемещаемое намерение и размещение — закрытый тип из двух вариантов: первым во всём порядке либо сразу после названного намерения. Индексы в команду не входят, поэтому запрос по устаревшему списку не может молча поставить намерение не туда.

Правило из спецификации выражено одной чистой функцией в модуле избранного. Она принимает полный порядок с признаком активности каждого намерения, перемещаемое намерение и размещение, а возвращает новый порядок либо отсутствие изменения. Изменения нет, когда ближайшее предшествующее активное намерение уже совпадает с опорным, а для размещения первым — когда активных намерений перед перемещаемым нет. Так перемещение без видимого эффекта не переставляет скрытые архивированные намерения. Функцию используют адаптер Drift и тестовые адаптеры контракта.

Адаптер внутри одной транзакции читает порядок, проверяет предусловия, вычисляет новый порядок и перезаписывает места по решению 7. Отказы:

- перемещаемое или опорное намерение не избранное либо отсутствует — конфликт актуального состояния;
- перемещаемое намерение совпадает с опорным — отказ проверки ввода;
- недоступность, повреждение и неизвестный отказ — как у остальных команд.

Успех несёт одно изменение порядка на новой ревизии. Отсутствие изменения ревизию не продвигает.

### 10. Координатор: ключ порядка и предъявление только отказа

Перестановка принимается координатором под единственным ключом порядка избранных. Он не пересекается с ключами намерений, поэтому даёт одну выполняющуюся перестановку и независимость от операций намерений.

Завершение перестановки получает политику предъявления, которой у координатора ещё нет:

- успех публикуется в канал завершений для согласования, но не образует права предъявления: подтверждением служит новый порядок списка;
- отказ сразу принадлежит общей поверхности, без права инициатора. Главная может быть не выбрана или закрыта другой страницей, и сообщение, привязанное к её renderer, осталось бы непредъявленным.

`GraphOperationPresenter` получает для такого завершения только отказ. Остальные операции сохраняют прежний протокол.

```text
Person      Home page     Home VM      Coordinator    Repository
  |             |            |              |              |
  | 1. drop     |            |              |              |
  |------------>|            |              |              |
  |             | 2. move    |              |              |
  |             |----------->|              |              |
  |             |            | 3. accept    |              |
  |             |            |------------->|              |
  |             |            |              | 4. execute   |
  |             |            |              |------------->|
  |             |            |              | 5. result    |
  |             |            |              |<-------------|
  |             |            | 6. completion|              |
  |             |            |<-------------|              |
  |             |            | 7. read snapshot            |
  |             |            |---------------------------->|
  |             | 8. order   |              |              |
  |             |<-----------|              |              |
  |  on failure: 6 goes to the shared message surface,     |
  |  the list returns to the last confirmed order          |
```

Шаг 3 отклоняется, если перестановка уже выполняется. На шаге 8 список показывает подтверждённый порядок из нового снимка.

### 11. Главная: view model и состояние

Состояние — закрытая иерархия: загрузка; список; пустое состояние с причиной «избранных нет» либо «все избранные архивированы»; недоступность; повреждение; неизвестный отказ. Список и пустое состояние несут актуальность: текущая, обновляется либо не обновлена с причиной. Список дополнительно несёт состояние перестановки.

View model перечитывает полный снимок, когда подтверждённый пакет содержит:

- изменение порядка;
- каталожную мутацию, у которой отметка есть в снимке до или после;
- изменение счётчиков связей намерения из показанного списка.

Перечитывание использует барьер ревизии и поколение запроса по образцу каталога тегов: снимок старше требуемой ревизии не публикуется, чтение повторяется ограниченное число раз. Отказ обновления оставляет прежний список с пометкой и отключает перестановку; следующий подтверждённый пакет повторяет обновление.

Пока перестановка выполняется, список показывает запрошенное положение с признаком сохранения, а ручки перестановки недоступны. После успеха публикуется новый снимок, после отказа — прежний подтверждённый порядок.

Список — `ReorderableListView` с явной ручкой в конце строки. Нажатие строки открывает страницу намерения, ручка начинает перетаскивание; долгое нажатие по строке не используется как менее заметное. Строка переиспользует `IntentionSummaryView` без отметки и тегов.

### 12. Доступность и локализация

Действия перемещения для экранного диктора даёт сам `SliverReorderableList`, включая отсутствие невозможных действий у крайних элементов и системные русские и английские названия. Собственные действия не добавляются. Результат перемещения объявляется живой областью Главной после подтверждения порядка.

Звезда в строке и управление отметкой на странице намерения имеют доступные названия состояния и действия. Все новые строки добавляются в оба файла локализации. Панель, строка со звездой и строка Главной добавляются в Widgetbook, где уже переключаются обе локали.

### 13. Диагностика

Отметка и её снятие — новые значения существующего вида команд намерения. Чтение списка Главной и перестановка получают собственные события с этапом проверки, чтения или записи, длительностью и безопасной категорией отказа, включая конфликт актуального состояния. События не содержат названий, идентификаторов, состава и порядка избранных.

### 14. Проверки и перенос существующих тестов

- **Контракт репозитория.** Отметка, снятие, перестановка, список Главной, целостность и отказы проверяются на адаптере Drift в памяти и на файловом хранилище с повторным открытием; схема — существующим средством сверки со снимком.
- **Правило перестановки.** Чистая функция проверяется отдельно, включая скрытые архивированные намерения и перемещение без изменения.
- **Оболочка.** Вставки клавиатуры и безопасные отступы, «назад», сохранение состояния вкладок, названия и подсказки, сообщение над панелью при доступном основном действии и переход на страницу при видимом сообщении и трёх построенных вкладках.
- **«Назад» на границе с платформой.** Вызов `handlePopRoute()` имитирует «назад», уже дошедшее до framework, и проходит без объявления готовности, поэтому один он требование не подтверждает. Проверка оболочки при целевой платформе Android наблюдает последнее значение, переданное framework в `SystemNavigator.setFrameworkHandlesBack` по платформенному каналу: `true` на каталоге дневных выборов и на каталоге намерений без страниц поверх оболочки, `false` на Главной, в том числе после возврата на неё системным «назад», и `true` при странице, открытой поверх оболочки. Рядом с каждым значением проверяется и результат дошедшего «назад». Прогон на устройстве с Android 16 или новее остаётся дополнительным свидетельством, но обязательным не является.
- **Существующие сценарии.** Около 40 тестовых файлов поднимают приложение или маршрутизатор и начинают с каталога намерений; 17 из них входят в теги и дневные выборы через шапку каталога. Они получают общий вспомогательный шаг выбора пункта панели вместо прежней точки входа.

## Risks / Trade-offs

- **Формула вставок оболочки повторяет правило `Scaffold` вручную** → высота панели задаётся явно; поведение закрепляется проверками с клавиатурой и безопасными отступами. При обновлении Flutter расхождение покажут эти проверки.
- **Обёртки `HeroMode` и `TickerMode` опираются на устройство `IndexedStack` и `SnackBar`** → проверка перехода на другую страницу при видимом сообщении и трёх построенных вкладках ловит возврат одинаковых меток `Hero`.
- **Доставка системного «назад» зависит от объявления готовности, а не только от `homeIndex`** → оболочка объявляет её через `PopScope` из выбранного пункта; проверка наблюдает сигнал framework платформе для обоих каталогов и Главной. Прогон на устройстве с Android 16 или новее не обязателен, поэтому поведение самой платформы подтверждается её документированным контрактом, а не наблюдением.
- **Перестановка переписывает места всех избранных** → две инструкции на перемещение независимо от размера; стоимость линейна по числу избранных и измеряется на большом списке. При потребности в синхронизации представление порядка пересматривается отдельным решением.
- **Полный снимок Главной перечитывается после каждого затрагивающего пакета** → чтение ограничено избранными и их счётчиками; поколение запроса и барьер ревизии исключают возврат прежнего состояния.
- **Успех перестановки без сообщения расширяет протокол предъявления ADR-0012** → политика задаётся типом завершения в координаторе, а не решением экрана; остальные операции не затронуты.
- **Локальное хранилище прежнего состава с тем же маркером версии не распознаётся** → чтение избранного завершится неповторяемым неизвестным отказом без удаления данных; хранилище удаляют вручную перед запуском новой сборки. Подтверждено пользователем: таких данных нет.
- **Смена начального экрана затрагивает много существующих тестов** → перенос выполняется общим вспомогательным шагом входа, а не правкой каждого сценария по месту.

## Migration Plan

1. Добавить `favorite_schema.drift`, включить его в `AppDatabase`, перегенерировать код и снимок схемы версии 1. Версия схемы и стратегия миграции не меняются.
2. Перед первым запуском новой сборки на устройстве разработки очистить данные приложения: хранилище прежнего состава несовместимо.
3. Откат — возврат изменения. Хранилище, созданное новой сборкой, прежняя сборка открывает: лишняя таблица ей не мешает, а каскад удаления отметки продолжает работать.

Долговременные решения записаны в предложенных ADR этого изменения:

- [ADR-0014](../../../docs/adr/0014-host-primary-navigation-in-root-page-shell.md) — решения 2 и 3: оболочка корневых страниц без собственных стеков и без собственного `Scaffold`.
- [ADR-0015](../../../docs/adr/0015-keep-favorite-order-as-explicit-whole-list-places.md) — решения 7–9: отметка строкой отдельной таблицы, целочисленное место, полный снимок и перезапись порядка целиком.
- [ADR-0016](../../../docs/adr/0016-present-only-failure-for-self-evident-success.md) — решение 10: политика предъявления только отказа.

Правка единственной версии схемы на месте отдельным ADR не становится: это исключение данного изменения из практики ADR-0002, описанное в решении 7.

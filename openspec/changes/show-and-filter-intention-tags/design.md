## Context

Изменение реализует поведение из [proposal.md](proposal.md) и трёх delta-спецификаций: [поиск намерений](specs/intention-management/spec.md), [дневные выборы](specs/daily-choice-management/spec.md) и [участники долговременных связей](specs/long-term-relation-management/spec.md). Требования к конкретному интерфейсу фильтра будут определены отдельно.

Четыре контекста уже используют общий `IntentionCatalogViewModel` и `IntentionCatalogQuery`. Назначение поиска задаёт архивный охват и готовность к действию. `DriftPersonalGraphRepository` получает точное количество и первую порцию в одной транзакции, продолжает выдачу курсорами по ключу сортировки и согласовывает изменения через общую ревизию графа. Сейчас запрос содержит только существующие условия охвата, готовности и названия, а `IntentionSummary` не содержит тегов.

Назначения находятся в `tag_assignments`, идентичность тега задаёт `TagId`, а переименование сохраняет этот идентификатор. Удаление тега каскадно удаляет назначения. Подтверждённые команды тегов публикуют `TagChange`, однако каталожное согласование пока не учитывает эти изменения. Общий `IntentionSummaryView` используется также вне поиска; расширение его данных само по себе не должно включать отображение тегов во всех местах использования.

Параллельный PR удаляет назначения тегов долговременным связям. Этот design использует только назначения намерениям и не определяет миграцию того PR. До объединения термин «тег» применяется здесь к собственным назначениям намерению; действующий `CONTEXT.md` пока описывает более широкий круг получателей.

## Goals / Non-Goals

**Goals:**

- Один контракт поиска для каталога, действия дневного выбора, исходного намерения и участника долговременной связи.
- Одновременное применение названия, всех обязательных тегов и отсутствия всех исключённых тегов по полному допустимому каталогу.
- Полные подтверждённые теги каждого результата, точное количество, ограниченные порции и корректное продолжение.
- Немедленное применение изменения условий по тегам и согласование подтверждённых изменений без возврата устаревшей выдачи.
- Сохранение выбранного идентификатора после переименования или удаления самого тега, включая успешную пустую выдачу при удалении обязательного тега.

**Non-Goals:**

- Элементы выбора тегов, расположение, внешний вид и способы переключения условий в интерфейсе.
- Работа с описаниями, конструктор запросов, логика «ИЛИ» и наследование тегов по связям.
- Добавление тегов в дневной путь, отдельные представления соседей и другие представления без поиска.
- Удаление тегов у связей, изменение правил назначения тегов и постоянное сохранение поисковых условий между перезапусками приложения.

## Decisions

### 1. Расширить общий каталог и сохранить назначение поиска как границу допустимости

Все четыре потребителя передают параметры в существующий общий каталог. Контекстные ограничения выводятся из типизированного `IntentionCatalogPurpose` и входят в запрос до подсчёта и получения порций. Для поиска участника добавить в запрос необязательный `excludedIntentionId`: второй участник исключается в репозитории, а не только после получения порции. Это устраняет порции, занятые недопустимым кандидатом, и делает количество согласованным с допустимым результатом.

| Контекст | Архивный охват | Готовность | Исключённое намерение |
| --- | --- | --- | --- |
| Каталог | Выбранный пользователем | Любая | Нет |
| Действие дневного выбора | Активные | Только готовые | Нет |
| Исходное намерение | Активные | Любая | Нет |
| Участник активной связи | Активные | Любая | Второй участник по `IntentionId` |
| Участник архивированной связи | Активные и архивированные | Любая | Второй участник по `IntentionId` |

Компактная схема компонентов показывает зависимости внутри существующего приложения. `Catalog`, `Repository` и `Commands` обозначают общий поиск, единый репозиторий личного графа и координатор подтверждённых команд соответственно.

```text
Components inside Flutter application

+---------------------------+        +---------------------------+
| Catalog / Action / Source | -----> | Catalog                   |
| Relation participant      |        | Query + ViewModel         |
+---------------------------+        +---------------------------+
                                              |          ^
                                              | reads    | changes
                                              v          |
                                    +--------------+  +------------+
                                    | Repository   |  | Commands   |
                                    | Drift / SQL  |  | + revision |
                                    +--------------+  +------------+
                                              ^          |
                                              | writes   |
                                              +----------+
```

- Четыре поиска используют один источник выдачи и сохраняют независимые условия по назначению поиска.
- Репозиторий владеет транзакциями, назначениями, фильтрацией, количеством и курсорами; SQL не выходит в представления.
- Координатор передаёт подтверждённый пакет с одной ревизией. Каталог применяет его целиком и ровно один раз.
- Предположение схемы: сохраняются существующие локальное хранение и единая последовательность команд и чтений. Новые сервисы и внешние зависимости не требуются.

Альтернатива: отдельные реализации фильтра для каждого поиска. Она дублирует правила и создаёт риск разного поведения при удалении тегов, подгрузке и смене охвата.

### 2. Представлять условия двумя неизменяемыми наборами `TagId`

Добавить прикладное значение `IntentionTagFilter` с наборами обязательных и исключённых `TagId`. Пустое значение не ограничивает поиск. `IntentionCatalogQuery` и `IntentionCatalogSelection` содержат это значение целиком; название тега не участвует в предикате. Повторы внутри набора устраняются, а равенство не зависит от порядка добавления условий.

Для собственных назначений `T(i)`, обязательных `R` и исключённых `E` принадлежность определяется так:

```text
eligible(i) AND titleMatches(i) AND R subsetOf T(i) AND E intersection T(i) = empty
```

Если один идентификатор присутствует в обоих наборах, совокупность условий логически невыполнима и даёт успешный пустой результат. Ни одно условие не удаляется автоматически. Это следствие «И», а не дополнительный режим поиска.

Проверка запроса подтверждает тип и допустимость идентификаторов, но не требует существования выбранного тега в текущем каталоге тегов. После физического удаления обязательный идентификатор остаётся в `R` и не встречается в назначениях; исключённый остаётся в `E` и никого не отсекает. Новый одноимённый тег имеет другой идентификатор. Сведения для предъявления выбранного условия хранятся отдельно от предиката: последнее подтверждённое название и подтверждённое удаление не должны терять сам `TagId`. Ошибка чтения каталога тегов не считается подтверждением удаления.

Альтернатива: искать теги по названиям или автоматически оставлять только существующие идентификаторы. Она меняет смысл сохранённого запроса после переименования и удаления. Строковое выражение запроса добавляет ненужный язык и допускает состояния, которые можно выразить точными типами.

### 3. Применять один SQL-предикат до количества, сортировки и ограничения порции

Расширить `_catalogCondition` проверками собственных назначений намерения. Для обязательных условий используется отсутствие выбранного обязательного тега без назначения этому намерению; для исключённых — отсутствие назначения любого выбранного исключённого тега. Условия входят в тот же предикат, что охват, готовность, название и исключённый участник. Первая порция, точное количество, продолжение и восстановление используют одну реализацию этого предиката.

Внешняя выборка остаётся выборкой намерений: назначения проверяются через `EXISTS` / `NOT EXISTS` и не размножают строки. Пустые наборы естественно не ограничивают результат. Существующие правила буквального сопоставления названия и сортировки с дополнительным ключом `IntentionId` сохраняются.

Чтобы число выбранных тегов не упиралось в число параметров одного SQL-выражения, адаптер представляет наборы условий как временные отношения идентификаторов на соединении текущей транзакции. Значения вставляются ограниченными пачками с параметризацией; каждое чтение заново задаёт свой набор. Существующий sequencer исключает смешение запросов. Эти временные данные не входят в долговечную схему и не сохраняют пользовательский запрос. Тот же подход применяется к набору уже загруженных идентификаторов при согласовании массового изменения.

Индексы назначения по `(intention_id, tag_id)` и существующие индексы порядка используются для адресных проверок. План и стоимость сложного фильтра проверяются на больших воспроизводимых данных; ограничение материализации порции не означает постоянного времени подсчёта всего результата.

Альтернатива: отфильтровать полученные 100 намерений или соединить назначения с внешней выборкой и затем устранять повторы. Первый подход пропускает совпадения и даёт неверное количество, второй усложняет точный подсчёт и границы порций. Отдельное SQL-условие с параметром на каждый тег проще для малых наборов, но требует искусственного предела либо отдельного обхода ограничений SQL.

### 4. Получать полные теги кратких данных вместе с порцией

Расширить `IntentionSummary` подтверждённым неизменяемым списком собственных `Tag`. Успех получения порции означает, что состав назначений каждой возвращённой строки известен полностью; пустой список означает проверенное отсутствие назначений. Неизвестный состав не кодируется пустым списком или необязательным полем успешной сводки.

После получения ограниченной порции намерений репозиторий читает назначения только её идентификаторам пакетно, в той же транзакции и на той же ревизии, что строки и количество первой порции. Общий декодер проверяет идентичности, названия и согласованность технического порядка назначений по действующим правилам чтения тегов. Соединение не должно скрывать повреждённую ссылку как отсутствие назначения. Порядок тегов соответствует существующему порядку создания тегов; число назначений одного намерения не ограничивается размером порции намерений.

Ошибка чтения назначений завершает чтение порции явным отказом существующей категории. При отказе обновления сохраняется прежнее подтверждённое содержимое с состоянием неудавшегося обновления. Частично прочитанные теги не выдаются за полную сводку. Методы копирования сводки, в том числе обновление счётчика связей, сохраняют подтверждённый состав тегов.

Краткие снимки до и после команд изменения намерений также содержат собственные теги: иначе изменение названия, готовности или архивного состояния невозможно корректно согласовать при действующих условиях по тегам. Снимок до физического удаления получается до каскадного удаления назначений.

Альтернатива: отдельный watcher или чтение подробностей на каждую строку. Это добавляет запросы на число строк и смешивает ревизии намерения и назначений. Отдельная необязательная загрузка тегов потребовала бы дополнительного протокола частичных состояний, хотя данные уже доступны в общей транзакции.

### 5. Считать весь совместный фильтр единым набором параметров поиска

Изменение любого набора тегов сразу заменяет параметры, отменяет ожидающий debounce названия, инвалидирует старые запросы и начинает первую порцию с текущим введённым названием. Название проходит существующую проверку: недопустимый ввод не подменяется предыдущим корректным значением. При обычном вводе названия сохраняется существующий debounce живого поиска.

Все пути создания запроса, включая продолжение, повтор чтения и восстановление, передают оба набора тегов и контекстные ограничения. Курсор хранит каноническую идентичность всего запроса: охват, готовность, название, обязательные и исключённые идентификаторы, исключённое намерение и порядок. Курсор другого сочетания условий отклоняется. Одного сравнения числа тегов недостаточно.

Поколение запросов в `IntentionCatalogViewModel` защищает первую порцию, продолжение и асинхронное согласование. Ответ старого поколения не публикуется. Смена охвата сохраняет название и оба набора; разные `IntentionCatalogPurpose` не разделяют изменяемое состояние фильтра. Физическое удаление тега меняет данные графа, но не параметры поиска и не снимает условие.

Альтернатива: применять выбранные теги только при следующем вводе названия или общей отправке формы. Она противоречит немедленному применению, подтверждённому пользователем. Независимые состояния трёх частей фильтра увеличивают риск публикации запроса, содержащего смесь старых и новых условий.

### 6. Согласовывать одиночные назначения через снимки, массовое удаление — через недостающую часть выдачи

Расширить обработку подтверждённых пакетов каталога событиями тегов. Ревизия отражает действительно согласованное содержимое; наличие `TagChange` нельзя считать пустым изменением и просто продвинуть ревизию.

| Подтверждённое изменение | Согласование открытого поиска |
| --- | --- |
| Назначение или снятие у одного намерения | До и после операции получить полные краткие снимки этого намерения в транзакции команды и добавить `IntentionCatalogMutation` в тот же подтверждённый пакет. Применить существующие правила соответствия, точного количества и загруженной границы. |
| Переименование | По `TagId` заменить название в подтверждённых тегах загруженных строк и сведениях о выбранных условиях. Состав, порядок и количество не меняются. |
| Удаление обязательного тега | Сохранить условие; согласовать успешный пустой результат, количество ноль и отсутствие продолжения. |
| Удаление только исключённого тега | Удалить тег из сводок, сохранить условие и согласовать появившиеся совпадения и точное количество по описанному ниже протоколу. |
| Удаление тега вне условий | Удалить тег из загруженных сводок; принадлежность, количество и порядок остаются прежними. |
| Создание без назначения или повтор без изменения | Не менять состав намерений и не применять изменения количества. |

Для одиночного назначения компактный `TagAssignmentChangedChange` остаётся фактом изменения пары, а дополнительный снимок каталога относится к той же ревизии. Это не перечисление всех получателей общего тега. Каталог применяет изменение принадлежности только через `IntentionCatalogMutation`, чтобы наличие двух связанных фактов в пакете не изменяло количество дважды. Такой снимок учитывается и для намерения вне загруженной части. Команды тегов не меняют временные метки намерения.

Глобальное удаление исключённого тега может открыть много совпадений до уже загруженной границы. `TagDeletedChange` сохраняет компактный контракт с одним `TagId`; команда удаления не материализует всех получателей. Для этого случая добавить чтение согласования каталога в общий репозиторий со следующим контрактом:

1. Запрос содержит текущий совместный фильтр и типизированную границу: частично загруженный префикс с ключом сортировки либо результат, ранее загруженный до конца. Передаются идентификаторы сохранённых строк. Модель представления связывает запрос со своим поколением поиска. Пустой ранее завершённый результат также обрабатывается как завершённый результат.
2. Репозиторий считает абсолютное количество по полному предикату. Отдельно получает ограниченными порциями соответствующие намерения в согласуемой области, которых нет среди сохранённых строк. Условия области и уже загруженных идентификаторов не ограничивают общий подсчёт. Обычное продолжение после границы остаётся отдельным чтением.
3. Сохранённые строки обновляются по известным фактам удаления и другим подтверждённым пакетам. Недостающие строки добавляются в правильном порядке; предшествующие порции сохранённых строк не перечитываются. Для ранее завершённой выдачи недостающие совпадения читаются до нового конца ограниченными порциями.
4. Количество, недостающие строки и теги каждой порции сопровождаются ревизией. Все порции одного согласования должны отражать одну ревизию. Если между чтениями появились изменения, кандидат остаётся неопубликованным, очередь подтверждённых пакетов применяется к сохранённому содержимому и получение недостающей части повторяется для актуальной ревизии. Продолжение согласования связано также с его границей и набором сохранённых идентификаторов.
5. Публикуется целиком согласованный префикс с абсолютным количеством и ревизией. Для частичного префикса сохраняется обычная граница продолжения. Позиция просмотра привязывается к оставшемуся видимому намерению либо ближайшему соседу по действующему контракту. Изменения до опубликованной ревизии не применяются к количеству повторно.

Во время согласования новые пакеты объединяются и обрабатываются последовательно; запрос прежних параметров или старой ревизии не может вернуть удалённый тег, старое количество либо прежний состав. Отказ обновления сохраняет последнее целиком подтверждённое содержимое и явное состояние отказа. Он не превращается в пустой результат. Состояния чтения согласования различают успешную порцию, необходимость повторить согласование из-за новой ревизии и безопасно классифицированный отказ.

Альтернатива: каждый `TagChange` сбрасывает каталог на первую порцию. Она теряет загруженный префикс и позицию просмотра. Локальное удаление тега только из видимых строк не учитывает новые совпадения и количество. Перечисление всех получателей при глобальном удалении переносит стоимость согласования в предметную команду и нарушает компактность её результата.

### 7. Подключать предъявление тегов явно в четырёх результатах поиска

Расширенные краткие данные передаются четырём страницам поиска. Подключение предъявления тегов должно быть явным на этих местах использования; наличие списка тегов в модели не включает его во всех вызовах общего представления намерения. Дневной путь и самостоятельные представления участников и соседей не становятся потребителями поиска по тегам.

На данном этапе фиксируется контракт данных и поведения: собственные теги доступны вместе с названием без открытия подробностей, а изменение условий вызывает общий поиск и не изменяет граф. Выбор виджетов, способы добавления отрицания, размещение и оформление условий остаются будущими требованиями к интерфейсу. Общая модель не должна связывать эти действия с командами назначения или снятия тегов.

Альтернатива: автоматически показывать новое поле во всех `IntentionSummaryView`. Это распространяет поиск и теги на контексты, которые пользователь явно исключил из объёма.

## Risks / Trade-offs

- **Массовое удаление исключённого тега открывает много новых совпадений** → порции согласования ограничены, сохранённые строки не перечитываются, подтверждённый префикс публикуется согласованно. Время и накопленные данные зависят от числа новых совпадений внутри сохранённой области; для ранее полностью загруженного результата область может быть большой.
- **Много назначений у одной строки или много условий** → пакетное чтение только нужных намерений, временные отношения условий с ограниченными вставками и отсутствие скрытого предела тегов по размеру порции. Проверить запросы и материализацию на больших фикстурах.
- **Количество, сводки и продолжение отражают разные моменты** → единая транзакция каждого чтения, общая ревизия, поколение запроса и повтор неопубликованного согласования при изменении ревизии. Непрерывные изменения могут задерживать завершение; сохранять подтверждённое содержимое с состоянием обновления.
- **Снимок команды содержит неполные или старые теги** → один проверенный путь построения кратких данных для чтений и команд, снимки в транзакции и проверки устаревших ответов. Количество совпадений изменяется только один раз на пакет.
- **Расширение общего представления затрагивает дневной путь** → явное подключение данных тегов только в четырёх поисках и проверки отсутствия нового отображения в исключённых контекстах.
- **Пересечение с параллельным PR** → при объединении согласовать итоговые типы получателей, чтения назначений и общие пакеты изменений. SQL этого изменения использует только назначения намерениям; миграцию удаления тегов связей выполняет соответствующий PR.
- **Диагностика раскрывает запрос или пользовательские данные** → использовать существующие безопасные категории и длительности чтений. Названия, `TagId`, `IntentionId`, наборы условий, назначения и SQL-параметры не записываются в диагностические события.

### Проверка выбранного подхода

Проверить контракт фильтра и курсора; совместный положительный и отрицательный отбор с названием; точное количество и совпадение за пределами прежней первой порции; отсутствие повторов между порциями; полные теги и классификацию отказов. Отдельные проверки покрывают немедленное изменение условий во время debounce, поздние первые порции и продолжения, независимость назначений поиска и их ограничения.

Проверить одиночное назначение вне загруженного префикса, переименование, физическое удаление обязательного и исключённого тегов, одноимённый новый тег, удаление условия из фильтра и массовое согласование при изменениях между его порциями. Нужны случаи частичного, пустого и полностью загруженного результата, сохранение позиции просмотра и отсутствие двойного изменения количества. Проверки производительности фиксируют планы SQL, число чтений и объём материализации на больших локальных данных; они не подменяют поведенческие проверки.

Конкретные проверки виджетов и доступности добавляются после определения интерфейса. Этот документ не утверждает, что реализация или такие проверки уже выполнены.

## Migration Plan

1. Перед реализацией сверить итоговый контракт назначений с параллельным PR. При изменении общих типов и чтений согласовать этот design и последующие задачи с его результатом.
2. Расширить прикладные значения, запросы, краткие данные, идентичность курсора и подтверждённые снимки; затем реализовать единый предикат и пакетное получение тегов в существующем репозитории.
3. Добавить согласование событий тегов, включая чтение недостающей части после массового изменения, и проверить ревизии, количество и загруженную границу.
4. После согласования требований к интерфейсу подключить совместный фильтр и предъявление тегов в четырёх поисках через общий контракт. Выполнить соответствующие проверки поведения, ошибок и доступности.

Новые постоянные поля и таблицы, перенос пользовательских тегов и дополнительная миграция базы этому поиску не требуются. Временные отношения запросов создаются и используются адаптером на рабочих соединениях. Объединение с параллельным PR должно сохранять его миграции и правила удаления назначений связям.

Откат прикладных изменений поиска не требует обратного преобразования пользовательских данных. Миграции параллельного PR не откатываются вместе с поиском. Курсоры и состояния запроса остаются данными текущей сессии и не требуют восстановления после перезапуска процесса.

## Open Questions

Поведенческие вопросы закрыты, включая немедленное применение условий и сохранение обязательного условия после физического удаления тега. Интерфейс фильтра и представления тегов будет определён пользователем позднее; это отдельный незавершённый вход для задач интерфейса, а не повод выбрать его устройство в данном design.

Перед объединением остаётся сверить фактический результат параллельного PR. Новый способ хранения, синхронизация между устройствами и изменение предметного языка тегов этим изменением не вводятся.

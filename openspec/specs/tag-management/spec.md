# Управление тегами Specification

## Purpose

Переиспользуемые теги помогают человеку организовывать личный граф и переходить к помеченным намерениям и долговременным связям «нужно» и «можно». Спецификация определяет жизненный цикл тегов, правила названий, независимые назначения, ограниченный каталог, навигацию по активным и архивированным сущностям и локальное сохранение этих данных.

## Requirements

### Requirement: Идентичность и жизненный цикл тега
Система SHALL позволять пользователю создавать, просматривать, переименовывать и физически удалять переиспользуемые теги своего личного графа. Каждый новый тег MUST получать собственный устойчивый уникальный идентификатор, независимый от названия и назначений. Тег MUST существовать без назначений и оставаться доступным после снятия последнего назначения. Теги SHALL NOT иметь собственного состояния архивирования; архивное состояние относится к помеченной сущности. Создание тега MUST NOT автоматически назначать его намерению или связи. Повторное использование названия после физического удаления тега MUST создавать новую идентичность без восстановления прежних назначений.

#### Scenario: Создание тега без назначений
- **WHEN** пользователь сохраняет новый тег с допустимым свободным названием «Дом»
- **THEN** система создаёт отдельный тег с новым идентификатором и показывает его в каталоге без назначений

#### Scenario: Последнее назначение снято
- **GIVEN** тег назначен только одному намерению
- **WHEN** пользователь снимает это назначение
- **THEN** тег остаётся в каталоге и доступен для нового назначения

#### Scenario: Повторное создание удалённого названия
- **GIVEN** тег «Дом» физически удалён вместе со своими назначениями
- **WHEN** пользователь создаёт тег «Дом» заново
- **THEN** новый тег получает другой идентификатор и не получает назначения удалённого тега

### Requirement: Допустимое название тега
Система MUST проверять переданное название до нормализации, подсчёта длины, сопоставления и записи как корректную последовательность скалярных значений Unicode без `U+0000`. Непарный UTF-16 surrogate или `U+0000` MUST отклоняться без замены либо удаления символов. Перед созданием или переименованием система SHALL удалять окружающие пробельные символы по тем же правилам, что для названия намерения. После этого название MUST содержать от 1 до 255 расширенных графемных кластеров включительно. Внутренние пробелы, регистр и остальные корректные символы MUST сохраняться без дополнительной Unicode-нормализации или грамматического преобразования. Недопустимое значение MUST получать различимую причину отказа на языке интерфейса, оставаться доступным для исправления и MUST NOT изменять сохранённые данные.

#### Scenario: Удаление только окружающих пробелов
- **WHEN** пользователь создаёт тег с названием «  Для  дома  »
- **THEN** сохраняется название «Для  дома» с прежним регистром и двумя внутренними пробелами

#### Scenario: Пустое после нормализации название
- **WHEN** пользователь пытается создать тег из одних пробельных символов
- **THEN** система объясняет необходимость непустого названия, сохраняет ввод для исправления и не создаёт тег

#### Scenario: Граница длины воспринимаемого текста
- **WHEN** пользователь сохраняет свободное название из 255 расширенных графемных кластеров, включая составные emoji
- **THEN** система принимает название без усечения и считает каждый составной emoji по границам графемных кластеров

#### Scenario: Слишком длинное переименование
- **GIVEN** существует тег «Дом»
- **WHEN** пользователь заменяет его названием из 256 расширенных графемных кластеров
- **THEN** система объясняет ограничение, оставляет прежнее название и сохраняет введённый текст для исправления

#### Scenario: Недопустимые скалярные значения
- **WHEN** переданное название содержит `U+0000` или непарный UTF-16 surrogate
- **THEN** система возвращает различимый отказ проверки до кодирования или записи, не заменяет символы и не сохраняет название

### Requirement: Уникальность названия тега
В одном личном графе система MUST запрещать разные теги с совпадающими названиями без учёта регистра и окружающих пробелов. Для проверки совпадения система MUST применять полный Default Case Folding Unicode 17.0.0 без Turkic tailoring к названию после удаления окружающих пробелов и сравнивать полученные последовательности целиком без дополнительной Unicode-нормализации. Правило MUST быть одинаковым при создании и переименовании, независимым от системной локали и языка интерфейса и стабильным между перезапусками и совместимыми обновлениями; обновление поисковых представлений намерений MUST NOT менять идентичность или уникальность тегов. Исходное написание SHALL сохраняться для отображения.

Совпадение с другим тегом MUST отклонять операцию целиком с объяснением занятого названия и возможностью использовать существующий тег; система MUST NOT молча объединять теги, переносить назначения или выдавать существующий тег за вновь созданный. Проверка уникальности MUST выполняться атомарно с записью. Совпадение с собственным названием при переименовании MUST NOT считаться конфликтом. Полностью совпадающее сохранённое название SHALL давать успешный результат без создания новой сущности.

#### Scenario: Регистр и окружающие пробелы не создают новый тег
- **GIVEN** существует тег «Дом»
- **WHEN** пользователь пытается создать тег «  дом  »
- **THEN** система сообщает о занятом названии, оставляет один прежний тег и позволяет использовать его

#### Scenario: Многосимвольное сопоставление регистра
- **GIVEN** существует тег `Straße`
- **WHEN** пользователь создаёт тег `STRASSE`
- **THEN** система отклоняет дубликат независимо от языка интерфейса

#### Scenario: Различимые буквы не объединяются
- **GIVEN** существует тег «Все»
- **WHEN** пользователь создаёт тег «Всё»
- **THEN** система сохраняет два отдельных тега, поскольку сопоставление регистра не приравнивает «е» к «ё»

#### Scenario: Конкурирующее создание одинакового названия
- **WHEN** две операции одновременно пытаются создать теги с совпадающими по этому правилу названиями
- **THEN** подтверждается только одно создание, а другая операция получает конфликт занятого названия без второго тега

### Requirement: Переименование общего тега
Система SHALL позволять переименовать существующий тег с сохранением идентификатора и всех назначений. После подтверждения новое название MUST отображаться во всех представлениях этого тега, включая назначения активным и архивированным сущностям и навигацию по тегу. Переименование MUST NOT изменять помеченные сущности, их архивные состояния, готовность к действию, связи или дневные выборы. Отмена, недопустимое название или конфликт уникальности MUST сохранять прежнее название и все назначения.

#### Scenario: Общее переименование
- **GIVEN** тег «Дом» назначен активному намерению и архивированной долговременной связи
- **WHEN** пользователь переименовывает тег в свободное название «Быт»
- **THEN** оба назначения и открытая навигация по тому же тегу показывают «Быт», сохраняя идентичность тега и состояния сущностей

#### Scenario: Изменение только регистра собственного названия
- **GIVEN** существует тег «дом»
- **WHEN** пользователь сохраняет название «Дом»
- **THEN** тот же тег получает новое написание без конфликта с собой и без изменения назначений

#### Scenario: Переименование в занятое название
- **GIVEN** существуют теги «Дом» и «Работа», каждый со своими назначениями
- **WHEN** пользователь переименовывает «Дом» в «работа»
- **THEN** система отклоняет изменение, сохраняет оба тега и их назначения и оставляет ввод для исправления

### Requirement: Независимые назначения тегов
Система SHALL позволять назначить существующий тег существующему намерению либо долговременной связи «нужно» или «можно», просмотреть назначения и снять каждое отдельно. Каждая сущность SHALL допускать несколько разных тегов, а каждый тег — назначения нескольким сущностям обоих видов. Пара из идентичности тега и идентичности помеченной сущности MUST иметь не более одного назначения. Назначение и снятие MUST быть явными операциями с конкретными идентичностями, не зависеть от названий сущностей и MUST NOT распространяться на участников связи, соседние намерения, другие связи или дневные выборы. Связь «я сегодня» MUST NOT принимать собственные назначения тегов; недопустимый вид получателя MUST отклоняться до записи.

Повторное назначение уже назначенного тега существующей сущности SHALL успешно оставлять одно назначение; повторное снятие уже отсутствующего назначения при существующих теге и сущности SHALL успешно оставлять его отсутствующим. Снятие MUST сохранять сам тег, остальные назначения и помеченную сущность. Назначения MUST быть доступны для активных и архивированных сущностей независимо от готовности намерения и участия долговременной связи в пути выбора.

#### Scenario: Несколько тегов у одной сущности
- **GIVEN** намерению назначен тег «Дом», а тег «Выходные» существует отдельно
- **WHEN** пользователь назначает этому намерению «Выходные»
- **THEN** намерение имеет оба назначения, а другие сущности не изменяются

#### Scenario: Общий тег не распространяется по графу
- **GIVEN** намерения А и Б соединены долговременной связью, а А и Б имеют одинаковые названия
- **WHEN** пользователь назначает тег только связи и намерению А
- **THEN** существуют два независимых назначения, а намерение Б не получает тег

#### Scenario: Повторное назначение
- **GIVEN** тег уже назначен долговременной связи
- **WHEN** поступает повторное назначение того же тега той же связи
- **THEN** операция успешно оставляет ровно одно назначение

#### Scenario: Снятие одного назначения
- **GIVEN** тег «Дом» назначен намерению и двум долговременным связям
- **WHEN** пользователь снимает тег с одной связи
- **THEN** удаляется только это назначение, а тег, намерение, обе связи и два остальных назначения сохраняются

#### Scenario: Дневной выбор не получает собственный тег
- **WHEN** вызывающая сторона пытается назначить тег связи «я сегодня»
- **THEN** система отклоняет недопустимый вид получателя без изменения дневной связи, её участников, пути и назначений тегов

### Requirement: Каталог тегов и выбор для назначения
Система SHALL предоставлять доступный из основного интерфейса каталог всех тегов личного графа, включая неиспользуемые и назначенные только архивным сущностям. Из каталога SHALL быть доступны создание, переименование, отдельное подтверждение удаления и переход к сущностям выбранного тега. Управление назначениями в подробном просмотре намерения или долговременной связи SHALL позволять выбрать существующий тег из этого же каталога и создать отсутствующий. Созданный при таком выборе тег SHALL сначала сохраняться отдельно; назначение MUST требовать явного выбора пользователя и подчиняться правилам проверки существования сущности.

Список назначений MUST показывать актуальные названия тегов, различать назначенные и доступные для назначения теги и позволять перейти к навигации по выбранному тегу. Пустой каталог и отсутствие назначений у сущности MUST объясняться отдельно от загрузки и ошибки.

#### Scenario: Неиспользуемый тег доступен для выбора
- **GIVEN** тег «Дом» существует без назначений
- **WHEN** пользователь открывает выбор тега для архивированного намерения
- **THEN** каталог предлагает «Дом» для назначения без восстановления намерения

#### Scenario: Свободный тег выбран за пределами загруженных порций
- **GIVEN** существующий тег не назначен выбранному намерению или долговременной связи и при прежней порционной загрузке находился за пределами начальной порции
- **WHEN** пользователь выбирает этот тег через редактор
- **THEN** система подтверждает состояние назначения именно этой пары и предлагает явное назначение без загрузки продолжения каталога

#### Scenario: Назначенный тег выбран за пределами загруженных порций
- **GIVEN** существующий тег уже назначен выбранному намерению или долговременной связи и при прежней порционной загрузке находился за пределами начальной порции
- **WHEN** пользователь выбирает этот тег через редактор
- **THEN** система подтверждает состояние назначения именно этой пары и не предлагает повторное назначение

#### Scenario: Отказ проверки назначения выбранного вне порции тега
- **GIVEN** пользователь выбрал существующий тег через редактор для намерения или долговременной связи, а статус назначения этой пары остаётся неизвестным после отказа точечного чтения
- **WHEN** наблюдение выбранного тега позднее успешно подтверждает существование самого тега
- **THEN** каталог сохраняет доступный повтор проверки назначения и не разрешает назначение до подтверждения статуса пары
- **WHEN** пользователь повторяет проверку и она успешно завершается
- **THEN** свободный тег становится доступен для явного назначения, а уже назначенный тег не предлагается назначить повторно

#### Scenario: Создание в процессе назначения
- **GIVEN** пользователь управляет тегами долговременной связи
- **WHEN** он создаёт отсутствующий тег
- **THEN** тег появляется в каталоге, а назначение связи происходит только после явного выбора этого тега

#### Scenario: Отсутствие назначений
- **GIVEN** намерению не назначено ни одного тега, но каталог содержит теги
- **WHEN** система успешно получает назначения намерения
- **THEN** подробный просмотр показывает отсутствие назначений и возможность выбрать тег, не объявляя каталог пустым

Выбор уже загруженного тега MUST немедленно менять выделение без ожидания нового чтения, повторного получения каталога или появления индикатора загрузки. Последовательные и повторные нажатия MUST сохранять строки, геометрию списка, положение прокрутки и постоянную область явного назначения. Без выбора и для уже назначенного тега назначение недоступно. Фоновое наблюдение идентичности MUST сохранять актуальность выбранного тега, не переводя обычное нажатие в загрузку; ответы прежнего выбора MUST NOT менять текущий выбор.

#### Scenario: Последовательный выбор без назначения
- **GIVEN** полный каталог содержит назначенные и свободные теги
- **WHEN** пользователь быстро выбирает разные строки и повторно нажимает выбранную строку, пока наблюдение ещё не ответило
- **THEN** выделение меняется сразу, строки и геометрия списка сохраняются, прокрутка не сбрасывается, каталог не перечитывается и назначения не записываются

#### Scenario: Постоянная область назначения
- **WHEN** пользователь открывает загруженный выбор и чередует свободные и назначенные теги
- **THEN** область назначения сохраняет размеры, а действие доступно только для подтверждённого свободного выбранного тега

### Requirement: Навигация по выбранному тегу
Система SHALL показывать намерения и долговременные связи, непосредственно помеченные выбранным тегом, с переходом к подробному просмотру конкретной сущности. При входе SHALL выбираться активный охват; пользователь SHALL иметь возможность переключаться между активным и архивным охватом. Охват MUST определяться собственным архивным состоянием помеченной сущности: архивная связь с активными участниками принадлежит архивному охвату. Оба вида сущностей MUST быть доступны в каждом охвате и различимы без опоры только на цвет. Намерение SHALL представляться своим названием, а связь — текущей направленной локализованной формулировкой с её типом и участниками; архивное состояние MUST быть явно различимо.

Выдача MUST включать каждую помеченную сущность ровно один раз по её идентичности, не включать непомеченных соседей, шаги пути как отдельные результаты или дневные выборы и не объединять одноимённые намерения. Переход к подробностям MUST сохранять идентичность выбранной сущности. Переименование тега MUST сохранять открытый выбор по его идентификатору. Отсутствие совпадений в выбранном охвате SHALL отличаться от удаления самого тега.

#### Scenario: Тег одновременно на намерении и связи
- **GIVEN** тег «Дом» назначен активному намерению А и активной связи А → Б, но не намерению Б
- **WHEN** пользователь открывает активные результаты тега
- **THEN** выдача содержит отдельно намерение А и направленную формулировку связи А → Б, а намерение Б не появляется

#### Scenario: Архивный охват определяется самой связью
- **GIVEN** помеченная связь архивирована, а оба её участника активны
- **WHEN** пользователь выбирает архивный охват тега
- **THEN** связь доступна как архивированная и открывается в своём подробном просмотре

#### Scenario: Одноимённые намерения не сливаются
- **GIVEN** тег назначен двум разным активным намерениям с одинаковым названием
- **WHEN** пользователь просматривает результаты тега и открывает одно из них
- **THEN** оба результата доступны отдельно, а открывается выбранное намерение по его идентичности

#### Scenario: Пустой активный охват не скрывает тег
- **GIVEN** тег назначен только архивированным сущностям
- **WHEN** пользователь впервые открывает его результаты
- **THEN** система показывает отсутствие активных совпадений и сохраняет возможность перейти к архивному охвату

### Requirement: Ограниченное получение и последовательный просмотр тегов
Каталог тегов, выбор тега для назначения и список назначений сущности MUST получаться целиком одним согласованным снимком без порционного продолжения, усечения или искусственного предела числа тегов. Каталог и список назначений SHALL использовать устойчивый порядок создания тегов. Результаты навигации по тегу MUST получаться ограниченными порциями без обязательной загрузки всех помеченных сущностей; пользователь SHALL иметь последовательный доступ ко всем результатам выбранного охвата. Выдача помеченных сущностей SHALL использовать устойчивый порядок создания назначений. Эти порядки MUST быть полными и однозначными, сохраняться между перезапусками и MUST NOT меняться из-за переименования, языка интерфейса или перевода часов устройства. Снятие и новое назначение SHALL помещать сущность в конец порядка назначений соответствующего тега.

Охват и идентичность выбранного тега MUST применяться до разбиения выдачи помеченных сущностей на порции. При неизменных данных продолжение MUST выдавать все результаты без пропусков и повторов. Несовместимое после подтверждённых изменений продолжение MUST требовать обновления выдачи от начала с сохранением выбранного тега и охвата. Результат прежнего тега, получателя, охвата или запроса MUST NOT подменять текущую выдачу. Повторные запросы одной выполняющейся подгрузки MUST NOT создавать повторные строки. Размер порции выдачи сущностей SHALL оставаться ограничением реализации, а не пределом числа назначений.

#### Scenario: Большой каталог доступен последовательно
- **GIVEN** личный граф содержит больше тегов, чем прежний размер порции
- **WHEN** пользователь открывает каталог, выбор или назначения получателя
- **THEN** соответствующий список получен целиком на одной ревизии, каждый тег доступен ровно один раз и продолжение списка тегов не требуется

#### Scenario: Большая выдача одного тега
- **GIVEN** тег назначен множеству активных и архивных намерений и связей
- **WHEN** пользователь последовательно просматривает архивный охват
- **THEN** система получает ограниченные порции только архивных совпадений обоих видов и позволяет дойти до каждого из них

#### Scenario: Поздний ответ другого охвата
- **GIVEN** выполняется подгрузка активного охвата тега
- **WHEN** пользователь переключается на архивный охват до завершения запроса
- **THEN** поздний активный результат не добавляется в архивный список и не заменяет его состояние

#### Scenario: Изменение назначений между порциями
- **GIVEN** первая порция получена, затем подтверждённое снятие назначения делает прежнее продолжение устаревшим
- **WHEN** пользователь продолжает просмотр
- **THEN** система обновляет выдачу выбранного тега и охвата от начала без смеси прежних и новых порций

### Requirement: Явно подтверждаемое удаление тега
Система SHALL позволять физически удалить любой существующий тег независимо от числа назначений и архивных состояний помеченных сущностей. Перед выполнением система MUST отдельно показать удаляемый тег и объяснить, что необратимо удаляются сам тег и все его назначения активным и архивированным намерениям и долговременным связям, включая назначения вне загруженных порций, а сами сущности и дневные выборы сохраняются. Подтверждение MUST относиться к конкретному идентификатору тега и всем его назначениям на момент выполнения, а не только к ранее показанному списку. Отмена MUST сохранять всё прежнее состояние.

Подтверждённое удаление MUST атомарно удалить тег и все его назначения, сохранив намерения, долговременные связи, другие теги, дневные выборы и шаги их путей. Ошибка MUST сохранять тег и все его назначения. После успеха тег MUST исчезнуть из каталогов и назначений, а открытая навигация по нему SHALL объяснять отсутствие тега без показа старых результатов как актуальных. Удаление MUST NOT перенаправляться на новый тег с тем же названием.

#### Scenario: Подтверждение объясняет полный охват
- **GIVEN** тег назначен активному намерению, архивированной связи и сущностям за пределами загруженной порции
- **WHEN** пользователь начинает удаление тега
- **THEN** система запрашивает отдельное подтверждение удаления тега и всех его назначений в обоих архивных охватах с сохранением помеченных сущностей

#### Scenario: Удаление сохраняет дневной путь
- **GIVEN** тег назначен намерению и долговременной связи, используемой сохранённым дневным путём
- **WHEN** пользователь отдельно подтверждает удаление тега и операция завершается успешно
- **THEN** тег и все его назначения исчезают, а намерение, связь, дневной выбор и его путь сохраняются без изменения

#### Scenario: Отмена удаления тега
- **WHEN** пользователь отменяет подтверждение удаления тега
- **THEN** тег и все назначения сохраняются

#### Scenario: Новое назначение перед выполнением удаления
- **GIVEN** пользователь подтвердил удаление тега со всеми назначениями, затем новое назначение этого же тега успело сохраниться
- **WHEN** выполняется удаление тега
- **THEN** вместе с тегом удаляется и новое назначение без удаления помеченной сущности

#### Scenario: Ошибка в середине удаления
- **GIVEN** тег имеет несколько назначений
- **WHEN** запись удаления завершается ошибкой после начала удаления назначений
- **THEN** система сохраняет весь прежний тег и все назначения и сообщает, что удаление не сохранено

### Requirement: Актуальность идентичностей и атомарность назначений
При изменении тега или назначения система MUST атомарно проверять существование всех затронутых сущностей по их идентификаторам и применимые предметные правила. Удалённый тег или получатель MUST давать различимый результат отсутствия, а не молча создаваться заново, заменяться одноимённой сущностью или считаться успешным новым назначением. Переименование существующего тега MUST NOT делать выбранную идентичность другой. Архивирование получателя MUST NOT блокировать назначение, поскольку оба архивных состояния допустимы.

Одновременное назначение и удаление тега либо получателя MUST оставлять только целостный результат: назначение либо подтверждается раньше и удаляется вместе с удаляемой сущностью, либо отклоняется после её удаления. Система MUST NOT оставлять назначения отсутствующим сущностям или одному тегу более одного раза у одного получателя. Неуспешная операция MUST NOT частично менять назначения или другие данные графа.

#### Scenario: Тег удалён после выбора
- **GIVEN** пользователь выбрал тег, затем тег удалён и создан другой с тем же названием
- **WHEN** выполняется первоначальное назначение
- **THEN** система сообщает об отсутствии выбранного тега и не назначает новый одноимённый тег

#### Scenario: Получатель удалён до назначения
- **GIVEN** пользователь выбрал существующий тег для намерения, которое затем допустимо удалено
- **WHEN** выполняется назначение
- **THEN** система сообщает об отсутствии намерения, сохраняет тег и не создаёт назначения

#### Scenario: Переименование не подменяет выбор
- **GIVEN** пользователь выбрал тег «Дом», который до выполнения назначения переименован в «Быт»
- **WHEN** система сохраняет назначение
- **THEN** сущность получает тот же тег по его идентификатору и показывает актуальное название «Быт»

#### Scenario: Два одновременных назначения
- **WHEN** две операции назначают один и тот же тег одной существующей связи
- **THEN** обе завершаются согласованным результатом с ровно одним сохранённым назначением

### Requirement: Подтверждённые изменения и согласованные представления тегов
Система MUST объявлять изменение тега или назначения успешным только после подтверждения постоянным хранилищем. После успеха каталог, назначения в подробностях сущностей, выбор тегов и результаты навигации MUST отражать актуальное подтверждённое состояние без повторного открытия приложения. Позднее чтение MUST NOT возвращать представления к состоянию до подтверждённой операции. Ошибка обновления представления после успешной записи MUST отличаться от ошибки записи и MUST NOT предлагать повторить уже выполненное создание или удаление.

Одна форма создания или переименования MUST допускать не более одной выполняющейся отправки без постановки повторной отправки в очередь. Изменения одного тега и изменения назначений одной сущности MUST выполняться последовательно; уход и возвращение на экран MUST NOT обходить выполняющуюся операцию. Принятая операция SHALL завершаться независимо от инициировавшего экрана, пока процесс приложения работает. Результат SHALL сообщаться пользователю однократно с соблюдением существующих правил приложения о доступности показа сообщения; результат другой операции MUST NOT вытеснять ещё не показанный результат. В открытой экранной сессии формы ошибка MUST сохранять введённый текст для исправления или допустимой повторной попытки. Явный уход с формы SHALL завершать её экранную сессию без обязанности восстанавливать неподтверждённый ввод при следующем открытии.

#### Scenario: Повторная отправка создания
- **GIVEN** создание тега ещё выполняется
- **WHEN** пользователь повторно отправляет ту же форму
- **THEN** система не принимает вторую отправку и не создаёт ещё один тег

#### Scenario: Запоздалое чтение после переименования
- **GIVEN** переименование тега подтверждено, но прежнее чтение каталога ещё выполняется
- **WHEN** это чтение возвращает старое название
- **THEN** оно не отменяет новое название в каталоге и назначениях

#### Scenario: Наблюдение сообщает об отсутствии выбранного тега раньше пакета изменений
- **GIVEN** выбранный тег ещё присутствует в полном снимке открытого каталога
- **WHEN** наблюдение этого `TagId` подтверждает его отсутствие до получения каталожной страницей пакета изменений
- **THEN** строка отсутствующего тега и действия над ним исчезают без повторного открытия каталога
- **AND** поздний ответ прежней ревизии не возвращает строку и действия

#### Scenario: Подтверждённая запись и ошибка обновления
- **GIVEN** создание тега подтверждено постоянным хранилищем
- **WHEN** последующее обновление каталога завершается ошибкой
- **THEN** система сообщает об успешном создании и отдельной ошибке получения данных, не предлагая повторно создать тот же тег

#### Scenario: Уход с экрана во время назначения
- **GIVEN** назначение принято, а пользователь покинул подробный просмотр до результата
- **WHEN** операция успешно завершается в продолжающем работать процессе приложения
- **THEN** назначение сохраняется один раз, пользователь получает одно сообщение результата, а при возвращении видит подтверждённое назначение

Обновление показанного списка тегов MUST сохранять строки и прокрутку, а выбранную идентичность — до подтверждения её удаления. Ошибка обновления MUST сохранять полученные строки как неактуальные и запрещать действия с неподтверждёнными данными.

#### Scenario: Фоновое обновление сохраняет список
- **GIVEN** пользователь выбрал тег в загруженном каталоге
- **WHEN** подтверждённое изменение требует обновления и новый снимок задерживается или временно недоступен
- **THEN** показанные строки, выбранный идентификатор и прокрутка сохраняются; ошибка обновления отличается от ошибки записи, а действия с неактуальными данными недоступны

### Requirement: Получение данных и безопасные ошибки тегов
Интерфейс MUST различать первоначальную загрузку, успешный пустой результат, подгрузку, отсутствие выбранной сущности и отказ получения данных. Ошибка продолжения MUST сохранять уже полученные данные того же запроса; ошибка нового выбранного тега или охвата MUST NOT показывать прежний список как его результат. Доказанно устранимый отказ SHALL предоставлять явную повторную попытку без потери ввода и без повторов строк. Недопустимый ввод, занятое название, отсутствие сущности и устаревшее продолжение SHALL иметь понятный различимый результат и соответствующее действие: исправление текста, выбор существующего тега, актуализацию выбора либо обновление выдачи.

Повреждённые сохранённые данные и неизвестный отказ MUST отличаться от временной недоступности, пустого списка и отсутствия сущности. Система MUST NOT молча удалять, заменять, объединять или пропускать повреждённые данные ради успешного результата и MUST NOT представлять обычный повтор как способ исправить доказанное повреждение или неизвестную причину. Пользовательские сообщения MUST NOT раскрывать SQL, параметры запросов или необработанные исключения.

Окончание наблюдения выбранного тега после уже установленного типизированного отказа MUST сохранять его причину и предусмотренные для неё действия как до получения первой порции, так и после показа результатов. Завершение наблюдения само по себе MUST NOT заменять временную недоступность или повреждение данных неизвестным отказом. Необъяснённое окончание наблюдения SHALL давать отдельный неизвестный отказ. При временной недоступности явный повтор SHALL восстанавливать чтение и наблюдение того же выбранного тега с сохранением охвата; после успешного восстановления ошибка SHALL исчезать без повторения записей или строк. Пока восстановление не подтверждено, прежние результаты MUST оставаться явно неактуальными и не допускать переходов к получателям.

Независимый отказ наблюдения MUST сохранять свою категорию и предусмотренные действия при любом позднем ответе первоначального чтения или продолжения, начатого до этого отказа. Правило MUST действовать для успешных и неуспешных ответов, независимо от того, завершилось наблюдение или остаётся открытым. Такой ответ MUST NOT снимать отказ наблюдения, объявлять прежние строки актуальными, возвращать пригодное продолжение или разрешать переходы и обычный повтор подгрузки. Восстановление SHALL подтверждаться успешным наблюдением текущей подписки и согласованной новой первой порцией; ответ ранее начатого чтения сам по себе MUST NOT считаться таким подтверждением. Отказ только подгрузки при действующем наблюдении SHALL сохранять обычное поведение продолжения.

#### Scenario: Устранимая ошибка подгрузки
- **GIVEN** первая порция результатов тега уже показана
- **WHEN** получение продолжения завершается доказанно устранимой ошибкой
- **THEN** список сохраняется, доступна явная повторная попытка, а успешный повтор продолжает выдачу без повторных строк

#### Scenario: Повреждённое название тега
- **GIVEN** сохранённое название тега нарушает правила допустимого названия
- **WHEN** система получает тег или его назначение для показа
- **THEN** система возвращает результат повреждения без успешной модели с исправленным либо усечённым названием

#### Scenario: Неизвестный отказ получения
- **WHEN** получение каталога завершается причиной, которую нельзя доказанно классифицировать
- **THEN** система сообщает об отдельном неизвестном отказе, не выдаёт пустой каталог и не представляет обычный повтор как восстановление

#### Scenario: Временный отказ наблюдения до первой порции
- **GIVEN** навигация по выбранному тегу ещё не получила первую порцию и наблюдение сообщило о временной недоступности
- **WHEN** это наблюдение завершается
- **THEN** интерфейс сохраняет причину временной недоступности и доступный явный повтор, не подменяя её неизвестным отказом или пустым результатом

#### Scenario: Временный отказ наблюдения после загрузки
- **GIVEN** результаты выбранного тега уже показаны и наблюдение сообщило о временной недоступности
- **WHEN** это наблюдение завершается
- **THEN** прежние строки остаются явно неактуальными без переходов к получателям, а причина отказа и явный повтор сохраняются

#### Scenario: Завершение наблюдения после повреждения данных
- **GIVEN** наблюдение выбранного тега сообщило о повреждённых сохранённых данных
- **WHEN** это наблюдение завершается
- **THEN** интерфейс сохраняет различимый результат повреждения и не предлагает обычный повтор как восстановление

#### Scenario: Необъяснённое окончание наблюдения
- **GIVEN** наблюдение выбранного тега не сообщало об объясняющем его окончание отказе
- **WHEN** это наблюдение неожиданно завершается в действующей экранной сессии
- **THEN** интерфейс сообщает об неизвестном отказе и не предлагает обычный повтор как восстановление; ранее показанные строки остаются явно неактуальными без переходов

#### Scenario: Явное восстановление завершившегося наблюдения
- **GIVEN** наблюдение выбранного тега завершилось после временной недоступности и причина отказа сохранена
- **WHEN** пользователь выбирает явный повтор и чтение вместе с новым наблюдением успешно восстанавливается
- **THEN** навигация сохраняет выбранные тег и охват, показывает актуальную первую порцию без повторных строк, убирает сообщение об отказе и продолжает наблюдать изменения тега без повторения выполненных записей

#### Scenario: Поздний отказ подгрузки после повреждения в наблюдении
- **GIVEN** подгрузка результатов выбранного тега началась до того, как наблюдение сообщило о повреждении данных и завершилось, а прежние строки уже помечены неактуальными
- **WHEN** это продолжение позднее возвращает временную недоступность
- **THEN** интерфейс сохраняет причину повреждения и неактуальность строк, не возвращает переходы, пригодное продолжение или обычный повтор подгрузки

#### Scenario: Поздняя первая порция после временного отказа наблюдения
- **GIVEN** во время первоначального чтения наблюдение выбранного тега сообщило о временной недоступности и остаётся открытым
- **WHEN** ранее начатое чтение успешно возвращает первую порцию
- **THEN** интерфейс сохраняет отказ наблюдения и возможность явного восстановления, не объявляет полученные строки актуальным результатом и не разрешает переходы

#### Scenario: Поздняя успешная подгрузка после неизвестного отказа наблюдения
- **GIVEN** после начала подгрузки наблюдение выбранного тега сообщило об неизвестном отказе и остаётся открытым
- **WHEN** ранее начатая подгрузка успешно возвращает следующую порцию
- **THEN** прежние строки остаются неактуальными, неизвестная причина сохраняется, а переходы и обычный повтор не представляются доступным восстановлением

#### Scenario: Явное восстановление после отклонённого позднего ответа
- **GIVEN** наблюдение выбранного тега отказало из-за временной недоступности, а поздний ответ прежней подгрузки не снял этот отказ
- **WHEN** пользователь выбирает явный повтор и новое наблюдение вместе с новой первой порцией успешно подтверждают восстановление
- **THEN** навигация сохраняет выбранные тег и охват, убирает отказ и возвращает переходы по актуальным строкам без повторения строк или выполненных записей

### Requirement: Локальное сохранение и миграция тегов
Подтверждённые теги, их идентичности, названия, назначения и устойчивый порядок MUST сохраняться между полными перезапусками и совместимыми обновлениями в пределах одной установки по правилам `local-data-lifecycle`. Обновление существующей установки MUST добавлять возможность тегов без изменения идентичностей, названий, описаний, состояний, порядка и зависимостей существующих намерений, долговременных связей, дневных выборов и шагов их путей. Миграция MUST NOT создавать теги или назначения из существующего пользовательского текста автоматически.

Новая установка и каждый поддерживаемый путь обновления MUST приводить к одинаковому контракту целостности, запрещающему повторные назначения, совпадающие названия тегов и ссылки назначений на отсутствующие сущности. Миграция и каждое изменение данных MUST либо подтверждаться целиком, либо сохранять прежнее целостное состояние. Удаление тега, назначения или получателя MUST NOT отменяться после перезапуска. Ошибка миграции MUST NOT приводить к удалению или пересозданию пользовательского хранилища; готовность и ошибки открытия SHALL подчиняться `local-data-lifecycle`.

#### Scenario: Теги сохраняются после полного перезапуска
- **GIVEN** пользователь создал тег, переименовал его и назначил активному намерению и архивированной связи
- **WHEN** приложение полностью завершается и вновь запускается в той же установке
- **THEN** доступны тот же тег с последним подтверждённым названием, оба назначения и прежний порядок

#### Scenario: Обновление графа без тегов
- **GIVEN** установка содержит намерения, долговременные связи и выполненные дневные выборы с путями
- **WHEN** успешно выполняется обновление с поддержкой тегов
- **THEN** все существующие данные и зависимости сохранены, а каталог тегов изначально пуст

#### Scenario: Прерванная миграция
- **GIVEN** существует целостное хранилище предыдущей поддерживаемой версии
- **WHEN** миграция тегов прерывается до подтверждения
- **THEN** прежние данные и версия остаются целостными, а следующий запуск может повторить миграцию без потери графа

#### Scenario: Удалённые данные не возвращаются
- **GIVEN** удаление тега со всеми назначениями подтверждено
- **WHEN** приложение полностью перезапускается
- **THEN** тег и назначения отсутствуют, а прежние помеченные сущности сохранены

### Requirement: Локализация и доступность управления тегами
Все системные строки управления тегами, проверки ввода, назначения, навигации и подтверждения удаления SHALL поддерживать русский и английский языки по существующим правилам выбора языка приложения. Пользовательские названия тегов MUST NOT переводиться или менять написание при смене языка. Сопоставление названий и идентичности MUST оставаться прежними.

Каталог, формы, назначения, переключение архивного охвата, результаты, ошибки и подтверждение удаления MUST быть доступны экранному диктору и при системном масштабировании текста. Доступные подписи SHALL различать назначение, снятие назначения и удаление самого тега и передавать текущий выбор, вид сущности и архивное состояние без опоры только на цвет. Увеличенный текст MUST NOT скрывать название, причину ошибки или возможность подтвердить либо отменить операцию.

#### Scenario: Смена языка интерфейса
- **GIVEN** существует тег «Дом», назначенный намерению
- **WHEN** язык приложения меняется с русского на английский по системной локали
- **THEN** системные подписи меняют язык, а название «Дом», идентичность, назначения и правила совпадения сохраняются

#### Scenario: Экранный диктор различает операции
- **GIVEN** пользователь управляет назначениями с экранным диктором
- **WHEN** он переходит между действиями снятия назначения и удаления тега
- **THEN** подписи объясняют различный охват действий, а удаление требует отдельного доступного подтверждения

#### Scenario: Увеличенный текст в подтверждении
- **WHEN** пользователь открывает подтверждение удаления при увеличенном системном масштабе текста
- **THEN** название тега, полный смысл удаления, подтверждение и отмена остаются читаемыми и доступными

### Requirement: Диагностика операций тегов без данных личного графа
Система SHALL предоставлять диагностику создания, переименования и удаления тегов, назначения и снятия, получения полных списков тегов, порций помеченных сущностей и миграции через существующую границу диагностики. Диагностика MUST различать вид операции, этап проверки или записи, успех, безопасную категорию отказа и позволять оценивать длительность. События MUST NOT содержать названия тегов или намерений, описания, формулировки связей, идентификаторы предметных сущностей, состав назначений, пути, параметры запросов или необработанные исключения с пользовательскими данными. Отказ диагностики MUST NOT менять предметный результат, повторять запись или откатывать подтверждённую операцию.

#### Scenario: Конфликт занятого названия
- **WHEN** создание тега отклоняется из-за совпадения названия
- **THEN** диагностика различает операцию создания и конфликт уникальности без названия или идентификатора существующего тега

#### Scenario: Ошибка записи удаления
- **WHEN** сохранение удаления тега завершается ошибкой
- **THEN** диагностика содержит безопасную категорию и этап записи без состава назначений, SQL-параметров и исходного исключения с данными

#### Scenario: Диагностика недоступна после успешной записи
- **GIVEN** назначение тега подтверждено хранилищем
- **WHEN** запись диагностического события завершается ошибкой
- **THEN** назначение остаётся подтверждённым и не отправляется повторно

### Requirement: Фильтрация каталога тегов по названию

Система SHALL предоставлять поле «Поиск тегов» над списком общего каталога и в выборе тега для назначения намерению или долговременной связи «нужно» или «можно». В обоих режимах система MUST фильтровать весь каталог личного графа сразу при изменении корректного запроса без отдельной отправки поиска. Последовательный ввод корректных запросов MUST показывать совпадения для текущего запроса, а не прежнего значения поля. Некорректный ввод SHALL обрабатываться по требованию «Обработка некорректного поискового запроса».

Совпадением SHALL считаться буквальное вхождение запроса в любом месте актуального названия тега без учёта регистра. Для игнорирования регистра названия и запрос MUST сопоставляться с применением полного Default Case Folding Unicode 17.0.0 без Turkic tailoring и дополнительной Unicode-нормализации, согласно действующим правилам сопоставления названий тегов. Совпавшие теги MUST сохранять устойчивый порядок создания; фильтрация MUST охватывать и теги за пределами видимой области списка.

Поиск SHALL включать неиспользуемые теги, теги с назначениями только архивированным сущностям и, в режиме выбора, как назначенные получателю, так и доступные для назначения теги. Системные подписи поиска SHALL подчиняться действующим требованиям локализации и доступности управления тегами. Списки уже назначенных тегов в подробностях намерения и долговременной связи SHALL оставаться без поиска.

#### Scenario: Поиск части названия в общем каталоге

- **GIVEN** каталог содержит теги «Работа», «Дом», «Для дома» и «Домашнее» в указанном порядке
- **WHEN** пользователь вводит `дом` в поле поиска общего каталога
- **THEN** список показывает «Дом», «Для дома» и «Домашнее» в прежнем относительном порядке

#### Scenario: Поиск при назначении намерению

- **GIVEN** тег «Дом» уже назначен выбранному намерению, а тег «Для дома» доступен для назначения
- **WHEN** пользователь вводит `дом` в поле выбора тега для этого намерения
- **THEN** список показывает оба тега с прежними признаками назначения и сохраняет возможность явно назначить «Для дома»

#### Scenario: Поиск при назначении долговременной связи

- **GIVEN** пользователь выбирает тег для долговременной связи «нужно» или «можно», а каталог содержит тег «Работа»
- **WHEN** пользователь вводит `работ` в поле поиска
- **THEN** список показывает «Работа» с актуальным признаком назначения выбранной связи

#### Scenario: Поиск за пределами видимой области

- **GIVEN** тег «Для дома» находится за пределами видимой области полного каталога
- **WHEN** пользователь вводит `дом` в поле поиска
- **THEN** «Для дома» входит в отфильтрованный список без предварительной прокрутки к нему

#### Scenario: Последовательный ввод меняет текущий результат

- **GIVEN** каталог содержит теги «Дом» и «Работа», а поле поиска содержит `дом`
- **WHEN** пользователь быстро заменяет запрос на `работ`
- **THEN** поле сохраняет текущий ввод, а список показывает «Работа» вместо совпадений прежнего запроса без отдельной отправки поиска

#### Scenario: Сопоставление регистра следует правилам названий тегов

- **GIVEN** каталог содержит тег `Straße`
- **WHEN** пользователь вводит `STRASS` в поле поиска
- **THEN** список показывает `Straße` независимо от языка интерфейса

#### Scenario: Подробности показывают назначения без поиска

- **GIVEN** намерению или долговременной связи назначены несколько тегов
- **WHEN** пользователь открывает её подробный просмотр
- **THEN** список назначений показывает эти теги без поля поиска

### Requirement: Обработка некорректного поискового запроса

Поисковый запрос MUST проверяться до сопоставления и преобразования регистра как корректная последовательность скалярных значений Unicode без `U+0000`. Ввод с `U+0000` или непарным UTF-16 surrogate MUST отклоняться без молчаливого удаления либо замены символов и MUST NOT использоваться для сопоставления названий.

В общем каталоге и в выборе тега для назначения система MUST сохранять некорректный введённый текст для исправления и показывать понятную локализованную ошибку поля, объясняющую, что этот текст не применён и результаты соответствуют последнему корректному запросу. Последний корректный фильтр MUST оставаться применённым; до первого корректного ввода им SHALL считаться пустой запрос, показывающий полный каталог. Подтверждённые изменения каталога MUST пересчитывать результаты по последнему корректному фильтру с использованием актуальных названий и признаков назначения, сохраняя некорректный ввод и ошибку поля.

После исправления на корректный запрос система MUST сразу применить его и убрать ошибку поля. Очистка некорректного ввода MUST сразу применить пустой запрос, вернуть полный каталог в устойчивом порядке и убрать ошибку поля. Ошибка ввода MUST отличаться от отсутствия совпадений и отказа получения данных; некорректный текст сам по себе MUST NOT вызывать состояние «Теги не найдены».

#### Scenario: Некорректный ввод сохраняет последний корректный фильтр

- **GIVEN** каталог содержит «Работа», «Дом» и «Для дома» в указанном порядке, а корректный запрос `дом` показывает «Дом» и «Для дома»
- **WHEN** пользователь заменяет запрос строкой с `U+0000` или непарным UTF-16 surrogate
- **THEN** поле сохраняет введённую строку для исправления, понятная ошибка объясняет, что она не применена и результаты соответствуют последнему корректному запросу, а список продолжает показывать «Дом» и «Для дома» в прежнем порядке

#### Scenario: Первый некорректный ввод оставляет полный каталог

- **GIVEN** каталог успешно загружен и содержит «Работа» и «Дом», а пользователь ещё не вводил корректный поисковый запрос
- **WHEN** пользователь вводит строку с `U+0000`
- **THEN** поле сохраняет ввод и показывает понятную ошибку, список остаётся полным в прежнем порядке, а некорректный текст не объявляется запросом без совпадений

#### Scenario: Исправление некорректного запроса сразу меняет результаты

- **GIVEN** каталог содержит «Дом» и «Работа», поле содержит некорректный ввод с ошибкой, а последний корректный запрос `дом` оставляет в списке «Дом»
- **WHEN** пользователь исправляет поле на корректный запрос `работ`
- **THEN** поле сохраняет `работ`, ошибка исчезает, а список сразу показывает «Работа» вместо результатов `дом`

#### Scenario: Очистка некорректного запроса возвращает полный каталог

- **GIVEN** каталог содержит «Работа», «Дом» и «Выходные» в указанном порядке, поле содержит некорректный ввод с ошибкой, а последний корректный запрос `дом` показывает только «Дом»
- **WHEN** пользователь очищает поле поиска
- **THEN** поле становится пустым, ошибка исчезает, а список сразу показывает все три тега в прежнем порядке

#### Scenario: Каталог обновляется по последнему корректному фильтру при ошибке ввода

- **GIVEN** каталог содержит «Дом», «Для дома» и «Работа», поле содержит некорректный ввод с ошибкой, а последний корректный запрос `дом` показывает «Дом» и «Для дома»
- **WHEN** подтверждённое переименование меняет название «Дом» на «Спорт» и каталог обновляется
- **THEN** список показывает только «Для дома» по последнему корректному запросу `дом`, а поле сохраняет некорректный ввод и объясняющую ошибку

### Requirement: Очистка поиска и отсутствие совпадений тегов

При пустом поле поиска система SHALL показывать полный каталог в действующем устойчивом порядке. Очистка поля MUST возвращать полный список сразу, сохраняя доступное создание тега. Если применённый корректный непустой запрос не соответствует ни одному тегу, система SHALL показывать «Теги не найдены» на русском языке интерфейса либо соответствующую локализованную подпись и MUST сохранять поле поиска с введённым запросом и действие создания тега. При некорректном вводе наличие и отсутствие совпадений MUST определяться только последним корректным фильтром с сохранением объясняющей ошибки поля. Отсутствие совпадений MUST отличаться от первоначальной загрузки, ошибки получения данных, ошибки поискового ввода и пустого каталога без поискового запроса.

#### Scenario: Очистка поля возвращает весь каталог

- **GIVEN** каталог содержит «Работа», «Дом» и «Выходные» в указанном порядке, а запрос `дом` оставляет в списке только «Дом»
- **WHEN** пользователь очищает поле поиска
- **THEN** список сразу показывает все три тега в прежнем порядке

#### Scenario: Совпадений нет, создание доступно

- **GIVEN** каталог содержит тег «Дом» и не содержит названия с подстрокой `спорт`
- **WHEN** пользователь вводит `спорт` в поле поиска каталога или выбора тега
- **THEN** интерфейс показывает отсутствие совпадений, сохраняет запрос доступным для изменения и позволяет открыть создание тега

#### Scenario: Пустой каталог отличается от отсутствия совпадений

- **GIVEN** в личном графе нет тегов, а поле поиска пусто
- **WHEN** каталог успешно загружается
- **THEN** интерфейс показывает действующее объяснение пустого каталога и доступное создание тега

### Requirement: Поиск сохраняет существующие назначения тегов

Ввод, изменение и очистка поискового запроса MUST сохранять теги и их подтверждённые назначения. Исчезновение тега из отфильтрованного списка MUST NOT снимать его назначения. Сам поиск MUST NOT создавать тег или назначать найденный тег получателю; назначение SHALL сохранять действующее требование отдельного явного выбора пользователя.

#### Scenario: Назначенный тег скрыт фильтром

- **GIVEN** намерению назначен тег «Дом», а каталог содержит также тег «Работа»
- **WHEN** пользователь вводит `работ` в выборе тега для этого намерения
- **THEN** список показывает «Работа», назначение «Дом» сохраняется, а «Работа» не назначается автоматически

#### Scenario: Очистка возвращает прежний признак назначения

- **GIVEN** долговременной связи назначен тег «Дом», скрытый текущим поисковым запросом
- **WHEN** пользователь очищает поле поиска
- **THEN** «Дом» снова появляется в списке как назначенный этой связи тег без повторного назначения

### Requirement: Время жизни поискового запроса в каталоге тегов

Поисковый ввод SHALL принадлежать одному открытию страницы каталога в определённом режиме и, для выбора тега, одному получателю назначения. Обновление каталога, отказ чтения с последующим повтором и переход в редактор с возвращением на ту же страницу MUST сохранять введённый текст и применённый корректный фильтр. При некорректном вводе система MUST также сохранять объясняющую ошибку поля и последний корректный фильтр согласно требованию «Обработка некорректного поискового запроса». Подтверждённые изменения каталога MUST пересчитывать результаты по сохранённому применённому фильтру с актуальными названиями и признаками назначения.

После закрытия страницы новое открытие, а также смена режима каталога или получателя назначения MUST начинать поиск с пустого поля и пустого применённого фильтра без ошибки ввода. Разные одновременно открытые страницы MUST иметь независимый поисковый ввод, в том числе при одинаковых режиме и получателе; изменение или очистка запроса одной страницы MUST NOT менять поиск другой.

#### Scenario: Обновление сохраняет поиск и применяет его к актуальному каталогу

- **GIVEN** каталог содержит «Дом», «Для дома» и «Работа», а запрос `дом` показывает первые два тега
- **WHEN** подтверждённое переименование меняет «Дом» на «Спорт» и каталог обновляется
- **THEN** поле сохраняет `дом`, а список показывает только «Для дома» по тому же фильтру с актуальными названиями

#### Scenario: Возврат из редактора сохраняет запрос на той же странице

- **GIVEN** общий каталог или выбор тега показывает результаты запроса `дом`
- **WHEN** пользователь открывает редактор и возвращается на ту же страницу после сохранения или отмены
- **THEN** поле сохраняет `дом`, а результаты соответствуют этому запросу и подтверждённому состоянию каталога

#### Scenario: Возврат из редактора сохраняет некорректный ввод и последний корректный фильтр

- **GIVEN** последним корректным запросом был `дом`, а поле содержит некорректный ввод с объясняющей ошибкой
- **WHEN** пользователь возвращается из редактора на ту же страницу каталога или выбора тега
- **THEN** поле сохраняет исходный некорректный текст и ошибку, а результаты продолжают соответствовать `дом` с учётом подтверждённых изменений каталога

#### Scenario: Повтор чтения сохраняет запрос

- **GIVEN** на странице каталога или выбора тега введён запрос `дом`, а обновление каталога завершилось устранимым отказом чтения
- **WHEN** пользователь явно повторяет чтение и каталог успешно обновляется
- **THEN** поле сохраняет `дом`, а актуальные результаты снова показываются по этому запросу без повторного ввода

#### Scenario: Новое открытие начинает поиск заново

- **GIVEN** пользователь закрыл страницу каталога или выбора тега с непустым поисковым вводом
- **WHEN** пользователь заново открывает тот же режим каталога для того же получателя, если он есть
- **THEN** поле пусто, ошибка ввода отсутствует, а после успешной загрузки показан полный каталог в устойчивом порядке

#### Scenario: Смена режима начинает поиск заново

- **GIVEN** общий каталог открыт с запросом `дом`
- **WHEN** пользователь переходит к выбору тега для назначения намерению или долговременной связи
- **THEN** поиск в режиме назначения начинается с пустого поля без переноса фильтра общего каталога

#### Scenario: Смена получателя начинает поиск заново

- **GIVEN** пользователь выбирает тег для намерения А с запросом `дом`
- **WHEN** пользователь открывает выбор для другого намерения или долговременной связи «нужно» либо «можно»
- **THEN** поле нового выбора пусто, показан полный каталог с признаками назначения новому получателю, а прежний запрос не переносится

#### Scenario: Две страницы имеют независимый поиск

- **GIVEN** одновременно открыты две страницы каталога с одинаковым режимом и, в режиме назначения, одним получателем, а на второй странице введён `дом`
- **WHEN** пользователь вводит `работ` или очищает поле на первой странице
- **THEN** поиск первой страницы соответствует её вводу, а вторая сохраняет `дом` и свои результаты

### Requirement: Сохранение и явное представление выбранного тега при поиске

Ввод, изменение и очистка запроса MUST сохранять идентичность выбранного существующего тега и MUST NOT автоматически выбирать другую строку или назначать тег. Если выбранный тег не соответствует применённому фильтру, система MUST NOT добавлять его в список совпадений. Когда выбранный тег отсутствует в результатах, в режиме назначения система MUST отдельно от результатов показывать его актуальное подтверждённое название и состояние назначения рядом с областью явного назначения, с доступной подписью текущего выбора. Это правило MUST действовать и при отсутствии совпадений, и для тега, возвращённого редактором до включения в обновлённый полный каталог. Название, состояние выбора и действие MUST оставаться понятными экранному диктору и доступными при увеличенном тексте по действующим требованиям локализации и доступности.

Явное назначение MUST относиться именно к сохранённой выбранной идентичности и текущему получателю, независимо от видимых результатов. Доступность действия MUST сохранять действующие ограничения подтверждения идентичности, состояния назначения, актуальности данных и выполняющихся операций; неизвестное состояние назначения или уже назначенный тег MUST NOT давать доступного назначения. Поисковый ввод MUST NOT подменять идентичность уже принятой команды. Если выбранный существующий тег присутствует в актуальном полном каталоге, очистка поиска MUST возвращать его строку с прежним выделением и актуальным признаком назначения без повторного выбора или назначения.

#### Scenario: Свободный выбранный тег скрыт результатами

- **GIVEN** для назначения намерению выбран свободный тег «Дом», а каталог также содержит «Работа» и действующие условия позволяют назначение
- **WHEN** пользователь вводит `работ`
- **THEN** список совпадений содержит только «Работа», отдельно у действия назначения видны выбранный «Дом» и его доступность для назначения, а выбор и назначения не меняются

#### Scenario: Явное назначение скрытого выбора использует его идентичность

- **GIVEN** выбранный свободный «Дом» показан отдельно, список совпадений содержит «Работа», а назначение выбранному намерению доступно
- **WHEN** пользователь явно назначает выбранный тег
- **THEN** намерение получает назначение именно «Дом», «Работа» не назначается, а отдельное представление «Дом» показывает подтверждённое состояние назначения

#### Scenario: Скрытый уже назначенный выбор не предлагает повторное назначение

- **GIVEN** для долговременной связи «нужно» или «можно» выбран уже назначенный ей тег «Дом»
- **WHEN** запрос `работ` скрывает «Дом» из результатов
- **THEN** название «Дом» и его состояние назначения видны отдельно от совпадений, выбор и назначение сохраняются, а действие назначения недоступно

#### Scenario: Отсутствие совпадений сохраняет понятный выбранный тег

- **GIVEN** выбран свободный «Дом» для назначения намерению или долговременной связи и действующие условия позволяют назначение
- **WHEN** пользователь вводит корректный запрос, которому не соответствует ни один тег
- **THEN** интерфейс сообщает «Теги не найдены», сохраняет поиск и создание тега, отдельно показывает выбранный «Дом» с состоянием назначения и оставляет доступным его явное назначение

#### Scenario: Очистка восстанавливает выделение скрытого выбора

- **GIVEN** выбранный «Дом» присутствует в актуальном полном каталоге и скрыт запросом `работ`
- **WHEN** пользователь очищает поле поиска
- **THEN** полный список возвращается в устойчивом порядке, строка «Дом» выделена с актуальным признаком назначения, а повторный выбор или назначение не требуется

#### Scenario: Выбор из редактора понятен до обновления полного каталога

- **GIVEN** в выборе тега для назначения сохранён запрос `работ`, а полный каталог ещё не содержит создаваемый тег «Дом»
- **WHEN** пользователь возвращается из редактора с сохранённым «Дом» и система подтверждает его идентичность и отсутствие назначения текущему получателю
- **THEN** запрос остаётся `работ`, выбранный «Дом» показан отдельно с актуальным названием и состоянием назначения, не подмешивается в совпадения и доступен для явного назначения без автоматической записи назначения

#### Scenario: Скрытый выбор с неизвестным состоянием назначения остаётся недоступным для назначения

- **GIVEN** выбранный «Дом» скрыт фильтром, его существование подтверждено, но состояние назначения текущему получателю ещё неизвестно
- **WHEN** интерфейс показывает выбранный тег отдельно от совпадений
- **THEN** его название и неподтверждённое состояние выбора понятны пользователю, а действие назначения недоступно до подтверждения состояния пары

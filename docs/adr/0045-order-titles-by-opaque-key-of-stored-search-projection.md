# ADR-0045: Упорядочивать названия намерений непрозрачным ключом сохранённой поисковой проекции

- Status: proposed
- Originating change: add-intention-picker-sorting-and-purpose
- Date: 2026-10-25

## Контекст

Поиски для выбора намерения получают порядок по названию. Каталог читается ограниченными порциями с курсором ([ADR-0009](0009-unify-personal-graph-module-and-revision.md)), а модель каталога сама вставляет подтверждённые правки в загруженную часть, сравнивая краткие сводки в Dart. Поэтому порядок по названию должен совпадать в трёх местах: в `ORDER BY` первой порции, в условии курсора продолжения и в сравнении внутри модели. Любое расхождение даёт пропуски и повторы на стыке порций.

Наивное решение ломают три факта:

- **Сравнение строк.** SQLite сравнивает `TEXT` в `BINARY` побайтно в UTF-8, то есть по кодовым точкам. `String.compareTo` в Dart сравнивает единицы UTF-16. Для символов за пределами BMP против `U+E000`–`U+FFFF` порядки расходятся.
- **Дрейф ключей.** `title_search_key` — хранимая generated column. Данные свёртки регистра могут обновиться между выпусками, а сохранённые ключи при этом не пересчитываются ([ADR-0008](0008-treat-sqlite-schema-functions-as-durable-contract.md)). Ключ, вычисленный в Dart из названия, может отличаться от сохранённого.
- **Граница модуля.** ADR-0009 не выпускает поисковые ключи за границу `PersonalGraphRepository`. Каталожный снимок отвечает о принадлежности фильтру по сохранённой проекции, но не раскрывает её.

Сортировка по правилам языка требует ключей, которые зависят от языка и версии библиотеки: их нельзя хранить и индексировать долговечно. Сортировка всего результата в памяти нарушает ограниченное чтение.

## Решение

- Порядок по названию задаёт сохранённая поисковая проекция названия (`title_search_key`, свёртка регистра Unicode) в порядке кодовых точек, а при равенстве — идентификатор намерения. Отдельной функции или колонки сортировки и пользовательской collation нет.
- Адаптер упорядочивает порции и продолжает их по этой колонке. Курсор — пара «ключ и идентификатор», на каждый охват и направление есть свой индекс.
- Краткая сводка намерения несёт непрозрачный ключ порядка названия. Его строят адаптеры репозитория, production и тестовые, из той же проекции, по которой упорядочивают порции. Наружу ключ даёт только сравнение с другим ключом по кодовым точкам. Его содержимое не раскрывается и не сравнивается как `String`.
- Модель каталога упорядочивает загруженную часть только этим сравнением и не вычисляет ключ из названия.
- Порядок не обещает алфавит конкретного языка.

## Последствия

- SQL, курсор и согласование правок дают один порядок, даже если данные Unicode обновятся: порядок следует сохранённым ключам, как им же следует принадлежность фильтру по ADR-0009.
- Поисковая проекция остаётся внутри модуля графа. Сводка получает только сравнимое значение.
- Пользователь видит компромиссы порядка кодовых точек: латиница идёт перед кириллицей, «ё» — после «я», латинские буквы с диакритикой — после латинских без неё, цифры сравниваются по одной. Спецификация записывает их как принятые.
- Порядок по названию требует индексов на каждый охват и направление, и это увеличивает стоимость записи намерения. Индексы архивного охвата закладываются сразу как основа порядка по названию в каталоге графа намерений, единственном читателе этого охвата; до него их не читает ни один запрос.
- Языковая сортировка потребует нового решения: отдельного хранимого ключа со своей функцией схемы и миграцией по ADR-0008.
- Пересчёт сохранённых ключей при обновлении данных Unicode остаётся отдельным решением. До него порядок может отличаться от текущей свёртки только для символов, чья свёртка изменилась, но SQL и модель по-прежнему согласованы между собой.

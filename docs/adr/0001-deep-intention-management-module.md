# ADR-0001: Сосредоточить управление намерениями в глубоком модуле

- Status: accepted
- Date: 2026-08-28

## Контекст

Жизненный цикл намерения включает нормализацию пользовательского текста, устойчивую идентичность, готовность к действию, архивирование, восстановление, физическое удаление, реактивное чтение и классификацию ошибок. Эти правила будут использоваться несколькими представлениями и станут основанием для следующих change связей и дневного выбора. Размещение правил во ViewModels размножило бы их по UI, а отдельный use case на каждую простую операцию создал бы набор shallow modules с почти одинаковыми interfaces.

## Решение

Управление намерениями сосредотачивается в глубоком module с внешней seam `IntentionRepository`. Его небольшая interface публикует наблюдение каталога, наблюдение одного намерения и выполнение закрытого набора типизированных `IntentionCommand`; результаты возвращаются как неизменяемые предметные модели или типизированные failures. Flutter Views знают только собственные ViewModels, ViewModels зависят от `IntentionRepository`, а классы и строки постоянного хранилища не пересекают эту seam.

Production adapter реализует interface поверх локального хранилища, а fake adapter используется в тестах ViewModels. Предметные инварианты, транзакционные предусловия и преобразование инфраструктурных ошибок остаются внутри module и проверяются через ту же interface, которой пользуется UI.

## Последствия

- Правила намерения получают locality: изменение инварианта выполняется один раз и действует для всех вызывающих сторон.
- UI и тесты не зависят от Drift, SQLite или формы строк базы.
- Закрытый набор commands будет расти вместе с жизненным циклом намерения; его следует разделять только при появлении новой предметной границы, а не ради уменьшения файлов.
- Следующие change могут расширять implementation удаления и архивирования связями, сохраняя существующую внешнюю seam.

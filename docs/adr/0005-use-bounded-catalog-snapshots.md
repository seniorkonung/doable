# ADR-0005: Читать каталог намерений ограниченными снимками

- Status: accepted
- Originating change: manage-intentions
- Date: 2026-08-30
- Supersedes: ADR-0001

## Контекст

ADR-0001 сосредоточил управление намерениями в глубоком модуле с внешней seam `IntentionRepository`, но одновременно закрепил наблюдение всего каталога. Каталог теперь поддерживает несколько охватов, буквальный фильтр, точное количество совпадений, четыре порядка и курсорную подгрузку. Реактивная выдача всех совпадений сделала бы стоимость чтения неограниченной размером пользовательского графа и противоречила бы выбранной модели ограниченных порций.

Граница глубокого модуля, storage-neutral interface и изоляция UI от Drift остаются полезными. Пересматривается не только операция чтения каталога, но и путь изменяющей команды: принятая команда должна продолжаться после освобождения инициировавшей её экранной ViewModel, а уже открытый каталог должен получить её terminal outcome независимо от lifetime дочернего route. Страница каталога и commit команды могут завершиться в одном порядке, а поступить Catalog ViewModel — в другом. Без общего признака порядка поздняя страница способна вернуть прежнее состояние уже подтверждённого изменения, а страница, уже включающая commit, вместе с его completion — повторно изменить membership или точное количество. Поэтому этот ADR полностью supersedes ADR-0001 и заново фиксирует сохраняемую часть прежнего решения вместе с новым контрактом чтения, выполнения и process-local согласования команд.

## Решение

Управление намерениями остаётся в глубоком модуле с единственной storage-neutral seam `IntentionRepository`. Flutter Views знают только собственные ViewModels, а классы и строки постоянного хранилища не пересекают repository seam. Предметные инварианты, транзакционные предусловия, нормализация и классификация инфраструктурных ошибок остаются внутри модуля.

`IntentionRepository` предоставляет три вида операций:

- ограниченный snapshot-запрос `getCatalogPage`, который принимает storage-neutral query с проверяемым конечным размером порции и opaque cursor и не публикует unbounded-вариант чтения каталога;
- реактивное наблюдение подробных данных одного намерения через `watchById`;
- выполнение закрытого набора типизированных `IntentionCommand` с подтверждёнными результатами или failures.

Read/query path остаётся прямым: Catalog ViewModel получает ограниченные страницы через `getCatalogPage`, а provider подробных данных наблюдает одно намерение через `watchById`. Автоматическая реактивная подписка на весь каталог не входит в repository contract.

Command path проходит через feature-specific `IntentionCommandCoordinator`: editor и details ViewModels передают ему типизированные команды, coordinator вызывает `IntentionRepository.execute`, владеет принятым `Future` и gate существующего намерения до terminal outcome и публикует типизированные completions в порядке mutation revisions. Уже открытый Catalog ViewModel потребляет эти completions и согласует подтверждённые результаты с накопленным ограниченным snapshot; route result не является вторым каналом доставки. Coordinator остаётся внутренним application module и не образует вторую storage, transport или sync seam.

Каждый живой экземпляр repository владеет уникальной process-local эпохой и монотонным номером mutation в памяти. Один закрытый асинхронный sequencer упорядочивает полное snapshot-чтение каждой страницы и commit каждой изменяющей команды. Успешная страница возвращает непрозрачную пару `(epoch, sequence)`. Фактически изменившая состояние команда после commit продвигает sequence ровно на единицу и возвращает эту revision; no-op и failure её не меняют. Эпоха и sequence не записываются в SQLite, не сериализуются, не восстанавливаются после перезапуска и не являются временем, версией сущности или sync revision. После пересоздания repository новая первая страница начинает новую эпоху, а старые cursors и результаты считаются непригодными для нового object graph.

Каждый command success дополнительно несёт непрозрачные точные снимки каталожной записи до и после commit: создание не имеет `before`, удаление — `after`, изменение имеет оба, а no-op возвращает одинаковые снимки. Они предоставляют storage-neutral summary и точный ответ о принадлежности текущему scope/filter, включая фактически сохранённую историческую поисковую проекцию, но не раскрывают SQLite, FTS или сырой search key. Поэтому Catalog ViewModel может корректировать membership и count без ошибочного повторного вычисления исторического совпадения из одного title.

Первая страница новой query generation является авторитетной основой на своей revision. Для продолжения Catalog ViewModel отбрасывает страницу старше уже применённой revision и повторяет только её с прежним cursor; страницу той же revision объединяет; страницу новее временно удерживает до поступления предшествующих completions. Mutation, уже включённая в страницу, повторно не применяется. Catalog ViewModel хранит текущую revision, не более одной pending page и конечное число completions выполняющихся операций, а не неограниченный журнал operation tokens.

Production repository adapter реализует interface поверх локального хранилища, а fake adapter используется в тестах application и presentation modules.

`IntentionRepository` не раскрывает расположение данных, transport, состояние синхронизации или классы конкретного adapter. Текущий production adapter использует Drift, но interface допускает внутреннюю композицию локального и будущего удалённого источников без зависимости Flutter Views от способа хранения. Отдельная sync seam, remote port, долговечная revision и sync-метаданные не вводятся до появления их наблюдаемого поведения. Текущий протокол предполагает, что все production-записи проходят через один экземпляр repository/coordinator; другой процесс, isolate, импорт или будущая синхронизация потребуют отдельного решения с долговечной либо предоставляемой источником ревизией.

## Последствия

- Стоимость одного чтения каталога ограничена размером порции и не требует материализации всех совпадений.
- Каталог не получает автоматическую реактивность всего результата; Catalog ViewModel явно управляет query generation, порциями и повторными попытками, а подтверждённые command results получает через coordinator completions.
- Поздние страницы и completions согласуются однозначно: подтверждённое изменение нельзя отменить старым snapshot или применить к membership/count дважды.
- Page reads и изменяющие commits последовательно проходят через один process-local sequencer. Это может задержать запись за уже начатым ограниченным чтением страницы, но не добавляет I/O, schema metadata или долговечное состояние.
- Ревизия исчезает вместе с экземпляром repository. Источником истины после запуска остаётся SQLite, а новая первая страница создаёт основу новой эпохи.
- Состояние согласования ограничено текущей revision, одной pending page и выполняющимися operations; хранить множество всех обработанных operation tokens не требуется.
- Подробный экран сохраняет реактивное чтение одного намерения без расширения подписки до всего каталога.
- Lifetime принятой команды и per-intention gate не зависят от lifetime инициировавшей экранной ViewModel; уход с route не отменяет команду и не переносит её результат через навигацию.
- UI и тесты остаются независимыми от Drift, SQLite и формы строк базы, а будущие adapters могут подключаться за прежней seam.
- Изменение инвариантов и развитие закрытого набора commands остаются локализованы в модуле; новую предметную границу следует выделять только при появлении самостоятельного поведения.

# ADR-0005: Читать каталог намерений ограниченными снимками

- Status: proposed
- Originating change: manage-intentions
- Date: 2026-08-30
- Supersedes: ADR-0001

## Контекст

ADR-0001 сосредоточил управление намерениями в глубоком модуле с внешней seam `IntentionRepository`, но одновременно закрепил наблюдение всего каталога. Каталог теперь поддерживает несколько охватов, буквальный фильтр, точное количество совпадений, четыре порядка и курсорную подгрузку. Реактивная выдача всех совпадений сделала бы стоимость чтения неограниченной размером пользовательского графа и противоречила бы выбранной модели ограниченных порций.

Граница глубокого модуля, storage-neutral interface и изоляция UI от Drift остаются полезными. Пересматривается только операция чтения каталога, поэтому этот ADR полностью supersedes ADR-0001 и заново фиксирует сохраняемую часть прежнего решения вместе с новым контрактом.

## Решение

Управление намерениями остаётся в глубоком модуле с внешней seam `IntentionRepository`. Flutter Views знают только собственные ViewModels, ViewModels зависят от `IntentionRepository`, а классы и строки постоянного хранилища не пересекают эту seam. Предметные инварианты, транзакционные предусловия, нормализация и классификация инфраструктурных ошибок остаются внутри модуля.

`IntentionRepository` предоставляет три вида операций:

- ограниченный snapshot-запрос `getCatalogPage`, который принимает storage-neutral query с проверяемым конечным размером порции и opaque cursor и не публикует unbounded-вариант чтения каталога;
- реактивное наблюдение подробных данных одного намерения через `watchById`;
- выполнение закрытого набора типизированных `IntentionCommand` с подтверждёнными результатами или failures.

Каталог накапливает ограниченные снимки в прикладном состоянии и согласует их с подтверждёнными результатами commands по правилам capability. Автоматическая реактивная подписка на весь каталог не входит в repository contract. Production adapter реализует interface поверх локального хранилища, а fake adapter используется в тестах ViewModels.

`IntentionRepository` не раскрывает расположение данных, transport, состояние синхронизации или классы конкретного adapter. Текущий production adapter использует Drift, но interface допускает внутреннюю композицию локального и будущего удалённого источников без зависимости Flutter Views от способа хранения. Отдельная sync seam, remote port и sync-метаданные не вводятся до появления их наблюдаемого поведения.

## Последствия

- Стоимость одного чтения каталога ограничена размером порции и не требует материализации всех совпадений.
- Каталог не получает автоматическую реактивность всего результата; ViewModel явно управляет query generation, порциями, повторными попытками и согласованием подтверждённых command results.
- Подробный экран сохраняет реактивное чтение одного намерения без расширения подписки до всего каталога.
- UI и тесты остаются независимыми от Drift, SQLite и формы строк базы, а будущие adapters могут подключаться за прежней seam.
- Изменение инвариантов и развитие закрытого набора commands остаются локализованы в модуле; новую предметную границу следует выделять только при появлении самостоятельного поведения.
